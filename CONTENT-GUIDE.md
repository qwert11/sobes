# Как писать вопросы

Правила для всех, кто добавляет контент: людей и агентов. Эталон — первый вопрос в
`src/content/docs/dotnet/types-memory.mdx` и его переводы в `uk/` и `en/`.

## Где что лежит

| Что | Путь |
|---|---|
| Страница темы, русский (основной язык) | `src/content/docs/<категория>/<тема>.mdx` |
| Украинский и английский | `src/content/docs/uk/...`, `src/content/docs/en/...` — те же имена файлов |
| Глоссарий темы | `src/data/glossary/<ru\|uk\|en>/<категория>-<тема>.yaml` |
| Компоненты карточки | `src/components/{Q,A,Ex,Next,Src,T}.astro` |
| Проверка контента | `npm run check:content -- <категория>/<тема>` |

Одна тема — одна страница с 5–8 вопросами. Русская версия пишется первой, украинская и
английская — её переводы с теми же `id`, в том же порядке, с тем же кодом.

Порядок внутри карточки всегда такой: заголовок `##`, три коротких ответа (j, m, s), три
подробных (j, m, s), `<Ex>`, `<Next>`, `<Src>`.

- `id` — `<категория>.<тема>.<слаг>` латиницей, kebab-case, одинаковый во всех языках.
  Он ключ самопроверки в браузере: после публикации его не меняют.
- `level` у `<Q>` — с какого уровня этот вопрос обычно задают: `j`, `m` или `s`.
- Ответы трёх уровней есть у каждого вопроса, даже у «сеньорского»: Junior отвечает на
  него проще, и это тоже полезно уметь.
- `<Ex l="s">` — пример только для одного уровня, если он нужен. Можно несколько `<Ex>`;
  подпись меняется атрибутом `title="..."`.

## Структура как в учебнике

Человек читает линейно и держит в голове 3–5 новых элементов одновременно. Связи, которые
не написаны явно, он не достроит. Поэтому каждый ответ собирается по одной схеме — так
читатель всегда знает, где он и что будет дальше.

### Принципы

1. **От общего к частному.** Сначала что это и зачем, потом как устроено, потом
   исключения и тонкости.
2. **Понятие — до использования.** Новый термин сначала определяется, потом применяется.
   Не ссылаться на то, что объясняется ниже. Если нужен термин из другой темы — `<T>` или
   ссылка на тему.
3. **Одна мысль — один абзац или один пункт списка.** Предложения до 25 слов.
4. **Форма по содержанию.** Шаги и этапы — нумерованный список. Набор равноправных
   пунктов — маркированный. Сравнение двух и более вариантов по двум и более признакам —
   таблица до 3 столбцов (шире не помещается на телефоне). Вложенность списков — не глубже
   двух уровней.
5. **Абстракция — сразу с примером.** После общего утверждения — конкретный случай или
   следствие: «поэтому `list[0].X = 1` не компилируется».
6. **Итог в конце.** Последняя строка подробного ответа — `**Итог:**` и одна фраза,
   которую стоит запомнить.
7. **Без связок-пустышек.** Не начинать с «Важно отметить», «Стоит сказать», «Таким
   образом».

### Короткий ответ

Одна связная мысль из трёх частей, всегда в этом порядке, без списков:

1. Что это — определение в одной фразе.
2. Главное свойство или отличие.
3. Следствие для практики; на Middle и Senior — плюс цена или компромисс.

Длина — то, что кандидат говорит вслух за 20–40 секунд: Junior 1–2 предложения, Middle
2–3, Senior 3–4.

### Подробный ответ

Блоки с жирными метками в фиксированном порядке. Метка — отдельной строкой
(`**Что это**`), под ней текст, список или таблица. Блок, который к вопросу не подходит,
пропускается; своя метка допустима, если стандартная не подходит, но порядок «общее →
детали → итог» сохраняется. Первая и последняя метки обязательны.

| Junior | Middle | Senior |
|---|---|---|
| **Что это** | **Как устроено** | **Под капотом** |
| **Зачем** | **Когда что выбирать** | **Цена** |
| **Как пользоваться** | **Ловушки** | **Компромиссы** |
| **Частая ошибка** | **Правило** | **Как проверить в проде** |
| **Итог:** | **Итог:** | **Итог:** |

- **Junior** отвечает на вопрос «что это и как этим пользоваться?». Определение своими
  словами, зачем оно нужно, базовое использование, одна типичная ошибка.
- **Middle** — «как это работает и когда что выбирать?». Механизм по шагам, сравнение
  альтернатив (часто таблицей), ловушки, практическое правило.
- **Senior** — «почему так устроено и чем это грозит в проде?». Внутренности рантайма,
  цена в памяти, CPU, аллокациях и задержках, компромиссы и дизайн, диагностика
  (dotnet-counters, dotnet-trace, dotnet-dump, PerfView, BenchmarkDotNet), как принять и
  объяснить решение команде.

Каждый уровень самостоятелен: его читают отдельно, переключив уровень. Senior не
пересказывает Middle, но и не ссылается на него («как сказано выше»).

Длина: Junior 60–120 слов, Middle 120–220, Senior 150–280.

Метки на других языках:

|---|---|---|
| Что это | Що це | What it is |
| Зачем | Навіщо | Why |
| Как пользоваться | Як користуватися | How to use |
| Частая ошибка | Типова помилка | Common mistake |

### Пример, уточнения, источники

- **Пример** — код на 5–25 строк, который запускается или очевидно компилируется.
  Комментарии в коде — на языке страницы и показывают результат (`// 1`). Если вывод
  неочевиден — одна-две фразы после кода.
- Пример по возможности самодостаточен и проходит `npm run check:examples -- <тема>`:
  сначала top-level код, потом объявления типов (иначе CS8803). Для ASP.NET Core —
  минимальный `Program.cs` от `WebApplication.CreateBuilder(args)` до `app.Run()`, он
  собирается с Web SDK. Фрагмент без окружения допустим, если иначе пример раздувается.
- Нужен NuGet-пакет — первая строка примера `// NuGet: Имя.Пакета, Другой.Пакет` (версия
  через `@`, по умолчанию последняя стабильная). Читатель видит, что ставить, а
  `check:examples` подключает пакет и собирает пример по-настоящему. Не комментируйте
  вызовы из пакета ради проверки.
- Строки в коде (`Console.WriteLine("...")`, сообщения исключений) — по-английски во всех
  трёх языках, чтобы код был идентичным; переводятся только комментарии.
- **Что спросят дальше** — 3–5 уточняющих вопросов, каждый с подсказкой в одну строку
  через « — ». Это то, чем интервьюер проверяет глубину.
- **Источники** — 1–3 ссылки на официальную документацию. Microsoft Learn — без локали в
  пути (`https://learn.microsoft.com/dotnet/...`), тогда сайт сам откроет язык читателя.

### Страница темы

- Вступление перед первым вопросом: 1–2 предложения о том, что разбирается в теме, и
  строка `**Перед этой темой:**` со ссылками на темы, которые нужно знать заранее (если
  они есть). В `uk/` и `en/` ссылки с префиксом языка: `/sobes/uk/dotnet/...`.
- Вопросы идут от простого к сложному: сначала `level="j"`, потом `m`, потом `s`. Каждый
  следующий вопрос опирается только на предыдущие и на темы из «Перед этой темой».

## Точность

- Сверяйте факты с документацией (Microsoft Learn, спецификация C#, блог .NET). Если не
  уверены — проверьте через поиск или context7, а не пишите по памяти.
- Версии указывайте явно: «с C# 10», «в .NET 8+». Текущие версии на октябрь 2026:
  .NET 10 (LTS, ноябрь 2025) с C# 14; .NET 11 выходит в ноябре 2026.
- Не придумывайте опыт автора сайта. Раздел «из практики» пишется только по его рассказу.
- Мифы, которые часто звучат на собеседованиях («структуры всегда на стеке»), разбирайте
  на уровне Senior, а не повторяйте.

## Стиль

- Короткие предложения, без воды и вступлений «Это очень важный вопрос».
- Термины — как говорят разработчики: «boxing», «state machine», «thread pool» можно
  оставлять по-английски, при первом упоминании дать русский вариант, если он в ходу.
- Английские названия типов, методов, ключевых слов — всегда в `обратных кавычках`.

## Правила MDX (иначе сборка упадёт)

- Всё с угловыми или фигурными скобками в тексте — только в `обратных кавычках`:
  `` `List<T>` ``, `` `Task<int>` ``, `` `{ get; set; }` ``. Голый `List<T>` в тексте MDX
  примет за тег.
- Внутри `<Q>`, `<A>`, `<Ex>`, `<Next>`, `<Src>` — пустая строка после открывающего тега и
  перед закрывающим, иначе Markdown внутри не разберётся.
- Атрибуты — в двойных кавычках: `<A short l="m">`.
- `<T>` не ставится в заголовок `##`.
- Знак `<` перед числом в тексте лучше заменить словами («меньше 16 байт»).

## Термины `<T>` и глоссарий

В тексте: `<T k="boxing">упаковку</T>`. Внутри — любая форма слова, `k` — ключ записи.

- Отмечайте 3–6 ключевых терминов на вопрос, при первом упоминании на странице. Не
  отмечайте каждое слово.
- Перед добавлением ключа поищите его в `src/data/glossary/` — если он уже есть в другой
  теме, используйте его, а не создавайте дубль.
- Ключи — латиница, kebab-case, одинаковые во всех языках.

Формат записи:

```yaml
thread-pool:
  term: Пул потоков (thread pool)
  def: >-
    Набор фоновых потоков, которые CLR переиспользует для коротких задач. Сюда попадают
    продолжения async-методов и Task.Run.
  q: thread pool .NET
  docs: https://learn.microsoft.com/dotnet/standard/threading/the-managed-thread-pool
```

- `def` — 1–3 предложения, всегда блоком `>-`: в обычной строке YAML двоеточие с пробелом
  ломает разбор.
- `q` — запрос для Google, если он лучше названия термина; `docs` — официальная страница;
  `wiki` — точное название статьи Википедии на этом языке (необязательно).

## Переводы

- Украинский — нормальная техническая лексика без суржика: «посилальний тип»,
  «значущий тип», «купа», «збирач сміття», «потік», «виняток».
- Английский — естественный, как говорят на собеседованиях, а не дословный.
- Код тот же, переводятся только комментарии. `id`, ключи терминов, ссылки — те же.

## Проверка

```bash
npm run check:content -- dotnet/async   # одна тема во всех языках
npm run check:content                   # всё
npm run check:examples -- dotnet/async  # компиляция примеров C# (.NET 10 SDK)
npm run build                           # полная сборка
```

`check:examples` собирает каждый пример отдельным проектом. Фрагменты, которым не хватает
окружения (`_repository`, `id`, NuGet-пакет), допустимы; синтаксис, порядок объявлений
(сначала top-level код, потом типы — иначе CS8803) и неверное API — нет. Код во всех трёх
языках одинаковый, поэтому компилируется русская версия.

Проверка ловит синтаксис MDX и YAML, неполный набор ответов, неизвестные термины,
расхождение вопросов между языками и повтор `id`.
