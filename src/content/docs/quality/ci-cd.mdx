Как код попадает из pull request в продакшен: из каких шагов состоит конвейер, какие проверки качества в него встраивают, как управлять пакетами и версиями и как выкладывать, чтобы откат был обычной операцией. На собеседовании это проверяют вопросами про конвейер, с которым кандидат работал сам.

**Перед этой темой:** [Тестирование](/sobes/quality/testing/).

<Q id="quality.ci.pipeline" level="j">

## Что такое CI и CD и из каких шагов состоит конвейер .NET-проекта?

<A short l="j">

<T k="continuous-integration">Непрерывная интеграция</T> (CI) — каждое изменение автоматически собирается и проверяется тестами, а <T k="continuous-delivery">непрерывная поставка</T> (CD) — проверенная сборка автоматически доводится до состояния «можно выкладывать». Поэтому ошибка видна через минуты после push, а не в день релиза.

</A>

<A short l="m">

CI — практика частого слияния в общую ветку, где каждый pull request и коммит проходит <T k="ci-pipeline">конвейер</T>: restore, build, test, анализ кода. CD продолжает его: публикует <T k="build-artifact">артефакт</T> и продвигает его по окружениям; continuous delivery оставляет выкладку в прод за человеком, а <T k="continuous-deployment">continuous deployment</T> выкладывает каждое зелёное изменение сам. Цена — конвейер становится кодом, который надо поддерживать: медленный или нестабильный конвейер команда начинает обходить.

</A>

<A short l="s">

Конвейер — код в репозитории (YAML или `Jenkinsfile`), который превращает коммит в неизменяемый версионированный артефакт и продвигает его по окружениям. Главный принцип — собрать один раз и выкладывать тот же артефакт везде, меняя только конфигурацию, иначе тестировали одно, а выкатили другое. Проверка PR должна укладываться в минуты, поэтому тяжёлые прогоны уходят в ночные или релизные запуски. Выбор между delivery и deployment упирается не в инструмент, а в зрелость тестов, мониторинга и отката.

</A>

<A l="j">

**Что это**

- **CI** — изменения часто сливаются в общую ветку, и каждое автоматически собирается и тестируется.
- **Continuous delivery** — проверенная сборка готова к выкладке в любой момент, в прод — по кнопке.
- **Continuous deployment** — в прод без кнопки уходит каждое изменение, прошедшее проверки.

**Шаги конвейера .NET**

1. `dotnet restore` — скачать NuGet-пакеты.
2. `dotnet build` — собрать решение.
3. `dotnet test` — прогнать тесты.
4. Анализ кода: анализаторы, SonarQube.
5. `dotnet publish` — подготовить файлы приложения.
6. Сохранить результат как артефакт.
7. Выложить его на тестовый стенд, потом в прод.

На pull request обычно идут шаги 1–4, на push в `main` — все.

**Частая ошибка**

Пересобирать проект для каждого окружения. Тогда в прод уходит не та сборка, которую проверяли.

**Итог:** CI проверяет каждое изменение, CD доводит проверенную сборку до выкладки.

</A>

<A l="m">

**Как устроено**

- Конвейер описан кодом в репозитории: `.github/workflows/*.yml` в GitHub Actions, `Jenkinsfile` в Jenkins. Его версионируют и ревьюят, как остальной код.
- Триггеры: `pull_request` проверяет изменение до слияния, `push` в `main` собирает релизного кандидата, ручной запуск — для выкладки и повторов.
- Задачи (jobs) выполняются на агентах: облачных или своих (self-hosted), например на Windows Server рядом с IIS. Разные задачи обмениваются файлами через артефакты.

**Когда что выбирать**

| Признак | Continuous delivery | Continuous deployment |
|---|---|---|
| Выкладка в прод | после ручного подтверждения | автоматически |
| Что нужно | надёжный CI | ещё автотесты, мониторинг, автооткат |

**Ловушки**

- **Долгий конвейер.** Проверка PR на 40 минут — изменения копятся и сливаются пачками. Помогают кеш пакетов, `--no-restore` и `--no-build` в следующих шагах, параллельные задачи.
- **Нестабильные тесты.** «Перезапусти, иногда падает» приучает игнорировать красный конвейер.
- **Секреты в YAML.** Токены хранят в секретах GitHub или в Credentials Jenkins, а не в репозитории.

**Правило**

На PR — быстрые проверки, без зелёного статуса слияние запрещено. На `main` — артефакт собирается один раз и продвигается по окружениям.

**Итог:** конвейер — версионируемый код: на PR он проверяет, на `main` собирает один артефакт для всех окружений.

</A>

<A l="s">

**Под капотом**

- Артефакт неизменяем и помечен версией и commit SHA. По версии из прода находят точный коммит.
- Конфигурация окружения не вшивается в сборку, а приходит при выкладке: переменные окружения, `appsettings.{Environment}.json`, хранилище секретов. Так один артефакт проходит dev, stage и prod.
- Воспроизводимость: `global.json` фиксирует SDK, lock-файлы — пакеты, агенты собираются из одного образа.

**Цена**

- Время обратной связи — главная метрика CI: медленный конвейер тормозит каждое изменение.
- Self-hosted-агенты видят внутреннюю сеть и дешевле на объёме, но их обновляют и защищают сами. Код из PR исполняется на них, поэтому GitHub не советует такие агенты для публичных репозиториев.

**Компромиссы**

- GitHub Actions — YAML рядом с кодом и готовые actions. Jenkins — свой сервер, плагины и Groovy, полный контроль ценой постоянного обновления плагинов.
- Continuous deployment требует отката за минуты и метрик, по которым его запускать. Без них ручное подтверждение честнее.
- Быстрые проверки на PR и тяжёлые по расписанию — компромисс между скоростью и полнотой.

**Как проверить в проде**

- DORA-метрики: частота выкладок, время от коммита до прода, доля неудачных изменений, время восстановления.
- Версия и commit SHA видны в логе старта или в служебном эндпоинте — понятно, что сейчас работает.

**Итог:** ценность конвейера — воспроизводимость: один неизменяемый артефакт, конфигурация снаружи и быстрая обратная связь.

</A>

<Ex>

```yaml
# .github/workflows/ci.yml
name: ci

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          global-json-file: global.json   # версия SDK из репозитория
      - run: dotnet restore
      - run: dotnet build --no-restore -c Release
      - run: dotnet test --no-build -c Release
      - run: dotnet publish src/Shop.Api --no-build -c Release -o out
      # Артефакт сохраняем только из main: его и выкладываем
      - if: github.ref == 'refs/heads/main'
        uses: actions/upload-artifact@v7
        with:
          name: shop-api-${{ github.sha }}
          path: out
```

</Ex>

<Ex title="То же в Jenkinsfile">

```groovy
// Декларативный конвейер на Windows-агенте (multibranch pipeline)
pipeline {
    agent { label 'windows' }
    stages {
        stage('Build') {
            steps {
                bat 'dotnet restore'
                bat 'dotnet build --no-restore -c Release'
            }
        }
        stage('Test') {
            steps { bat 'dotnet test --no-build -c Release' }
        }
        stage('Publish') {
            when { branch 'main' }   // артефакт — только из main
            steps {
                bat 'dotnet publish src/Shop.Api --no-build -c Release -o out'
                archiveArtifacts artifacts: 'out/**'
            }
        }
    }
}
```

</Ex>

- Почему артефакт собирают один раз? — Иначе в прод уходит не та сборка, которую тестировали.
- Что запускать на PR, а что на `main`? — На PR — быстрые проверки для слияния, на `main` — ещё публикацию артефакта и выкладку.
- Как ускорить конвейер? — Кеш пакетов, `--no-restore` и `--no-build`, параллельные задачи, тяжёлые тесты — по расписанию.
- Где хранить секреты конвейера? — В секретах GitHub или Credentials Jenkins, с минимальными правами токена.

<Q id="quality.ci.quality-gates" level="m">

## Как автоматически следить за качеством кода?

<A short l="j">

Качество проверяют на каждом pull request без участия человека: <T k="roslyn-analyzer">анализаторы</T> ищут ошибки при сборке, тесты дают <T k="code-coverage">покрытие</T>, а SonarQube сравнивает результат с <T k="quality-gate">quality gate</T> — набором порогов. Если порог не пройден, PR нельзя слить.

</A>

<A short l="m">

Проверки идут слоями: при сборке — Roslyn-анализаторы и nullable-предупреждения с правилами из <T k="editorconfig">`.editorconfig`</T> и `TreatWarningsAsErrors`, в конвейере — `dotnet format --verify-no-changes` и SonarQube с отчётом покрытия. Quality gate «Sonar way» смотрит только на новый код: ни одного нового замечания, покрытие нового кода от 80%, дублирование до 3%. Статус проверок делают обязательным в <T k="branch-protection">правилах ветки</T> вместе с ревью, а цена — шум ложных срабатываний, поэтому правила включают постепенно.

</A>

<A short l="s">

Автоматическая проверка ценна, когда блокирует слияние: ошибка анализатора в сборке дешевле замечания в дашборде, который никто не открывает. Поэтому строгость задают в коде (`TreatWarningsAsErrors`, `AnalysisLevel`, severity в `.editorconfig`), а SonarQube оставляют то, что видно только на уровне проекта: покрытие, дублирование, <T k="code-smell">code smells</T>, security hotspots. Подход к новому коду позволяет включить строгий gate на легаси-проекте без переписывания старого. Цена — ложные срабатывания и подавления, которые тоже приходится ревьюить.

</A>

<A l="j">

**Что это**

Автоматические проверки качества — правила, которые конвейер применяет к каждому PR.

**Какие бывают**

- **Компилятор и анализаторы.** Предупреждение `CS8602` о возможном `null`, правила `CAxxxx` о надёжности и производительности. Встроены в .NET SDK.
- **Стиль.** `.editorconfig` задаёт отступы, именование и важность правил, `dotnet format` выравнивает код по нему.
- **Покрытие.** Доля кода, которую выполнили тесты.
- **SonarQube.** Собирает всё вместе и выносит вердикт по quality gate.
- **Ревью.** Человек проверяет то, что не видят инструменты: замысел и дизайн.

**Как пользоваться**

Включите `TreatWarningsAsErrors` и сделайте зелёный конвейер обязательным условием слияния в `main`.

**Частая ошибка**

Гнаться за 100% покрытия. Покрытие показывает, какой код выполнялся, а не что его результат проверили.

**Итог:** анализаторы, тесты и quality gate проверяют каждый PR, а ревью — то, что не автоматизируется.

</A>

<A l="m">

**Как устроено**

1. **Сборка.** Анализаторы Roslyn включены по умолчанию с .NET 5. `AnalysisLevel` выбирает набор правил: `latest-recommended` строже умолчания. Правила стиля `IDExxxx` при сборке из командной строки работают только с `EnforceCodeStyleInBuild`.
2. **Строгость.** `TreatWarningsAsErrors` делает ошибкой любое предупреждение. Мягче — `<WarningsAsErrors>Nullable</WarningsAsErrors>`: ошибками становятся только nullable-предупреждения.
3. **Формат.** `dotnet format --verify-no-changes` падает, если код расходится с `.editorconfig`.
4. **SonarQube.** `dotnet sonarscanner begin` до сборки, `dotnet test` с отчётом покрытия, `end` после. Сервер считает quality gate.
5. **Ветка.** Правила ветки требуют зелёных проверок и одобрения ревьюера.

**Ловушки**

- `TreatWarningsAsErrors` на старом проекте даёт сотни ошибок разом. Его включают по проектам или начинают с `WarningsAsErrors`.
- Анализ веток и PR в SonarQube есть с Developer Edition. Бесплатная Community Build анализирует только главную ветку.
- Покрытие SonarQube не считает сам: отчёт делает coverlet, а путь передают свойством `sonar.cs.opencover.reportsPaths`.

**Правило**

Что можно проверить при сборке — проверяйте при сборке. SonarQube держит пороги на новый код, правила ветки делают проверки обязательными.

**Итог:** строгость живёт в сборке, пороги — в SonarQube, обязательность — в правилах ветки.

</A>

<A l="s">

**Под капотом**

- Анализатор Roslyn подписывается на синтаксические и семантические события компилятора. Он видит типы и символы, а результат одинаков в IDE и в CI.
- Важность правила задаётся слоями: `AnalysisLevel` — база, `.editorconfig` или `.globalconfig` — конкретное правило (`dotnet_diagnostic.CA2016.severity`), `#pragma` и `[SuppressMessage]` — конкретное место.
- SonarQube считает метрики относительно периода нового кода: с прошлой версии, за N дней или от ветки. «Sonar way» проверяет только его, а покрытие и дублирование игнорирует, пока новых строк меньше 20.

**Цена**

- Анализаторы удлиняют сборку, `latest-all` на большом решении заметен.
- Подавление без ревью — технический долг без владельца.

**Компромиссы**

- 80% покрытия нового кода — умолчание Sonar, а не закон. Тривиальные DTO исключают через `sonar.coverage.exclusions`, сложную логику — нет.
- Новый SDK приносит новые правила. `AnalysisLevel` с номером (`10.0-recommended`) фиксирует набор, и обновление становится отдельным PR.
- Gate по всему коду на легаси вечно красный, и его перестают замечать. Gate на новый код держит планку для изменений, а старый код чинят, когда трогают.

**Как проверить, что это работает**

- Тренд подавлений (`#pragma warning disable`, `NoWarn`) за квартал.
- Доля PR, слитых в обход правил ветки или с красным gate.

**Итог:** строгость — в сборке и правилах ветки, SonarQube держит планку на новом коде, а подавления ревьюят как код.

</A>

<Ex>

```xml
<!-- Directory.Build.props в корне репозитория: действует на все проекты -->
<Project>
  <PropertyGroup>
    <Nullable>enable</Nullable>
    <!-- Набор правил зафиксирован: новый SDK не включит новые правила сам -->
    <AnalysisLevel>10.0-recommended</AnalysisLevel>
    <!-- Правила стиля IDExxxx проверяются и в dotnet build -->
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
    <!-- Любое предупреждение ломает сборку -->
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>
</Project>
```

```ini

[*.cs]
# CA2016: передавать CancellationToken дальше — ошибка сборки

# IDE0161: file-scoped namespace — предупреждение (формат option:severity, .NET 9+)

```

</Ex>

<Ex title="SonarQube в Jenkinsfile">

```groovy
// Нужны глобальный инструмент dotnet-sonarscanner на агенте
// и webhook SonarQube на <jenkins>/sonarqube-webhook/
stage('Build and analyze') {
    steps {
        // withSonarQubeEnv подставляет SONAR_HOST_URL и SONAR_AUTH_TOKEN
        withSonarQubeEnv('SonarQube') {
            bat '''
              dotnet sonarscanner begin /k:"shop-api" ^
                /d:sonar.host.url=%SONAR_HOST_URL% ^
                /d:sonar.token=%SONAR_AUTH_TOKEN% ^
                /d:sonar.cs.opencover.reportsPaths=**/coverage.opencover.xml
              dotnet build -c Release --no-incremental
              dotnet test -c Release --no-build --collect:"XPlat Code Coverage;Format=opencover"
              dotnet sonarscanner end /d:sonar.token=%SONAR_AUTH_TOKEN%
            '''
        }
    }
}
stage('Quality gate') {
    steps {
        timeout(time: 10, unit: 'MINUTES') {
            waitForQualityGate abortPipeline: true   // красный gate — красная сборка
        }
    }
}
```

</Ex>

<Next>

- Чем `TreatWarningsAsErrors` отличается от `WarningsAsErrors`? — Первый делает ошибками все предупреждения, второй — только перечисленные, например `Nullable`.
- Что проверяет quality gate «Sonar way»? — Новый код: нет новых замечаний, hotspots проверены, покрытие от 80%, дублирование до 3%.
- Почему gate смотрит на новый код, а не на весь? — Иначе легаси-проект вечно красный, а планку нужно держать на изменениях.
- Почему SonarQube показывает нулевое покрытие? — Отчёт не создан в нужном формате или путь в `sonar.cs.opencover.reportsPaths` не совпал.
- Как обновить SDK и не сломать сборку новыми правилами? — Зафиксировать `AnalysisLevel` версией и поднимать её отдельным PR.

</Next>

<Q id="quality.ci.packages-versioning" level="m">

## Как управлять пакетами и версиями?

<A short l="j">

Версию задают по <T k="semver">SemVer</T> — `MAJOR.MINOR.PATCH`: major растёт при ломающих изменениях, minor — при новых возможностях, patch — при исправлениях. Свои библиотеки публикуют в приватный <T k="nuget-feed">NuGet-фид</T>, и проекты подключают их как обычные пакеты, а не копируют `.dll`.

</A>

<A short l="m">

Внутренние библиотеки живут в приватном фиде, версии всех пакетов задаются в одном месте через Central Package Management, а <T k="package-lock-file">lock-файл</T> и `dotnet restore --locked-mode` в CI гарантируют, что restore возьмёт ровно те же версии. <T k="nuget-audit">NuGetAudit</T> при каждом restore предупреждает об уязвимых пакетах. Версию сборки вычисляют из git-тегов (MinVer, GitVersion), а не правят руками; цена — дисциплина тегов и веток.

</A>

<A short l="s">

Зависимости — цепочка поставок: откуда пакет пришёл, какой он версии и можно ли пересобрать то же самое через год. Поэтому фид один и проксирует nuget.org, <T k="package-source-mapping">Package Source Mapping</T> не даёт подменить внутренние имена, lock-файлы делают restore воспроизводимым, а NuGetAudit проверяет и транзитивные пакеты. Версия пакета по SemVer — контракт с потребителями, а <T k="source-link">Source Link</T> ведёт отладчик к точному коммиту. Цена — свежий advisory ломает сборку в неудачный момент, поэтому заранее решают, какие уровни уязвимостей блокируют конвейер.

</A>

<A l="j">

**Что это**

- **SemVer** — версия `MAJOR.MINOR.PATCH`, например `2.4.1`. Ломающее изменение даёт `3.0.0`, новая функция — `2.5.0`, исправление — `2.4.2`. Суффикс `-beta.1` помечает предварительную версию.
- **Приватный фид** — NuGet-сервер компании для внутренних пакетов: общей библиотеки логирования, клиентов к внутренним API.

**Как пользоваться**

1. Конвейер библиотеки выполняет `dotnet pack` и получает `.nupkg`.
2. `dotnet nuget push` публикует пакет в фид.
3. Фид прописан в `nuget.config` в корне репозитория, и пакет ставится как обычный: `dotnet add package Company.Logging`.

**Частая ошибка**

Перезалить изменённый пакет с той же версией. У всех в кеше `~/.nuget/packages` уже лежит старый, и сборки начинают расходиться.

**Итог:** SemVer говорит потребителю, что изменилось, а приватный фид раздаёт внутренние пакеты так же, как nuget.org.

</A>

<A l="m">

**Как устроено**

- **Фид.** Azure Artifacts и GitHub Packages — облачные. BaGetter (продолжение BaGet), Nexus и ProGet — свои серверы. NuGet.Server — старый вариант на .NET Framework. Хороший фид проксирует nuget.org, и все пакеты идут через одну точку.
- **Версии в одном месте.** Central Package Management и `Directory.Packages.props` — см. [Платформу .NET](/sobes/dotnet/platform/).
- **Lock-файл.** `RestorePackagesWithLockFile` создаёт `packages.lock.json` с полным графом. `dotnet restore --locked-mode` в CI падает, если граф изменился, а файл нет.
- **Аудит.** NuGetAudit сверяет граф с базой уязвимостей при restore и выдаёт NU1901–NU1904 — от low до critical.
- **Версия из git.** MinVer берёт версию из последнего тега, GitVersion — из тегов и схемы веток. Ручной `<Version>` в проекте не нужен.

**Когда что выбирать**

| Инструмент | Когда |
|---|---|
| MinVer | версия — последний тег, простой процесс |
| GitVersion | релизные ветки, GitFlow, сложные правила |
| ручной `<Version>` | один пакет, редкие релизы |

**Ловушки**

- Lock-файл библиотеки не помогает её потребителям: граф считает приложение. Его коммитят прежде всего для приложений.
- Floating-версии (`2.*`) без lock-файла делают сборку невоспроизводимой.
- Свежий advisory ломает сборку с `TreatWarningsAsErrors`. Заранее решите, какие коды блокируют.

**Правило**

Один фид, версии в `Directory.Packages.props`, lock-файл и `--locked-mode` для приложений, версия — из тега.

**Итог:** воспроизводимость дают lock-файлы, безопасность — аудит, понятность — SemVer из тегов.

</A>

<A l="s">

**Под капотом**

- NuGet поддерживает SemVer 2.0: предварительная версия ниже релиза (`2.0.0-rc.1` меньше `2.0.0`), метаданные после `+` в сравнении не участвуют.
- Версий у сборки несколько: версия пакета — для NuGet, `AssemblyVersion` — для загрузчика, `FileVersion` — для Windows, `InformationalVersion` — для людей. С .NET 8 SDK дописывает в `InformationalVersion` commit SHA: `2.4.0+a1b2c3d…`.
- Source Link с .NET 8 встроен в SDK для GitHub, Azure Repos, GitLab и Bitbucket. Он записывает в PDB адрес репозитория и коммит, и отладчик скачивает исходник точной версии. `ContinuousIntegrationBuild=true` в CI нормализует пути для детерминированной сборки.

**Цена**

- `.snupkg` не раздувает пакет, но поддерживается не всеми фидами: Azure Artifacts его не принимает. Альтернатива — `DebugType=embedded`, PDB внутри сборки ценой размера.
- Аудит транзитивных пакетов находит больше уязвимостей — и больше шума.

**Компромиссы**

- Dependency confusion: пакет `Company.Logging` с высокой версией на nuget.org может победить внутренний. Защита — Package Source Mapping или один фид с проксированием.
- Блокирующий аудит в отдельном конвейере (рецепт Microsoft с `-p:AuditPipeline=true`) не останавливает срочный фикс из-за свежего advisory.

**Как проверить в проде**

- Версия и SHA из `InformationalVersion` в логе старта ведут к коммиту релиза.
- `dotnet package list --vulnerable --include-transitive` (до .NET 10 — `dotnet list package`) на коммите релиза показывает уязвимости в том, что сейчас работает.
- NuGet Package Explorer показывает, есть ли в пакете Source Link и символы.

**Итог:** пакеты — цепочка поставок: один фид, зафиксированный граф, аудит и версия, по которой находится коммит.

</A>

<Ex>

```xml
<!-- Directory.Build.props: правила для пакетов во всех проектах -->
<Project>
  <PropertyGroup>
    <!-- packages.lock.json с полным графом; в CI: dotnet restore --locked-mode -->
    <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
    <!-- Аудит и транзитивных пакетов (для net10.0 это уже умолчание) -->

    <WarningsAsErrors>$(WarningsAsErrors);NU1903;NU1904</WarningsAsErrors>
  </PropertyGroup>
</Project>
```

- Зачем lock-файл, если версии и так указаны? — Указаны прямые зависимости; транзитивные и floating-версии без него могут измениться.
- Как защититься от dependency confusion? — Package Source Mapping или один фид, который проксирует nuget.org.

<Q id="quality.ci.deployment" level="s">

## Какие бывают стратегии выкладки и как откатываться?

<A short l="j">

Стратегия выкладки определяет, как новая версия заменяет старую: <T k="rolling-deployment">rolling</T> обновляет серверы по одному, <T k="blue-green-deployment">blue-green</T> держит две копии и переключает трафик, <T k="canary-release">canary</T> сначала отдаёт новую версию малой доле пользователей. Откат — возврат на предыдущую версию, и он должен быть таким же отработанным шагом, как выкладка.

</A>

<A short l="m">

Rolling дёшев, но какое-то время работают обе версии; blue-green даёт мгновенное переключение и откат ценой двойных ресурсов; canary ограничивает число пострадавших, но требует метрик для сравнения версий. <T k="feature-toggle">Feature flags</T> отделяют выкладку кода от включения функции, поэтому откат часто сводится к выключению флага. Схему базы при этом меняют по <T k="expand-contract">expand/contract</T>, иначе откат кода упрётся в несовместимую схему.

</A>

<A short l="s">

Безопасный релиз — это малый радиус поражения, решение по метрикам и откат без новой сборки. Все стратегии, кроме остановки с заменой, подразумевают, что две версии работают одновременно, поэтому совместимость схемы, API и сообщений с предыдущей версией — обязательное условие. На IIS без оркестратора нулевой простой дают несколько серверов или два сайта за балансировщиком, а `app_offline.htm` — это короткий плановый простой одного сайта. В контейнерах трафик на новый экземпляр пускает <T k="readiness-probe">readiness-проверка</T>, а откат запускается автоматически по росту ошибок и задержек.

</A>

<A l="j">

**Что это**

Стратегия выкладки — порядок, в котором новая версия попадает на серверы и получает трафик.

| Стратегия | Как работает |
|---|---|
| Остановить и заменить | остановили, заменили файлы, запустили — есть простой |
| Rolling | серверы за балансировщиком обновляются по одному |
| Blue-green | новая копия рядом со старой, трафик переключается разом |
| Canary | новая версия сначала получает 1–5% трафика |

**Как откатываться**

- Хранить предыдущий артефакт и выкладывать его одной командой.
- В blue-green — вернуть трафик на старую копию.
- Функцию под feature flag — выключить флагом, без выкладки.

**Частая ошибка**

Считать откат простым, пока не изменилась база. Если новая версия удалила колонку, старый код с этой базой уже не работает.

**Итог:** стратегию выбирают по цене простоя, а откат проверяют заранее.

</A>

<A l="m">

**Как устроено**

- **Rolling.** Балансировщик выводит сервер из ротации, сервер обновляется, проходит health check и возвращается.
- **Blue-green.** Две полные копии. Новая разворачивается и прогревается без трафика, проходит smoke-тесты, затем балансировщик переключается. Старая остаётся для отката.
- **Canary.** Новая версия получает малую долю трафика, её ошибки и задержки сравнивают со старой, долю увеличивают ступенями.
- **Feature flags.** Код выкладывается выключенным и включается для части пользователей, например через `Microsoft.FeatureManagement`.

**Когда что выбирать**

| Стратегия | Плюс | Минус |
|---|---|---|
| Rolling | без лишних серверов | откат — такой же долгий rolling |
| Blue-green | мгновенный откат | двойные ресурсы |
| Canary | мало пострадавших | нужны метрики и маршрутизация |

**Ловушки**

- **Схема БД.** Миграцию применяют до выкладки, и она обязана работать со старым кодом: добавлять, а не удалять и переименовывать. Подробно — в [изменении схемы без простоя](/sobes/db/design/).
- **Состояние в памяти.** После переключения пользователь попадает на другой экземпляр, поэтому сессии и кеши живут вне процесса.
- **Две версии сразу.** Сообщения в очередях и ответы API должны понимать обе версии.

**Правило**

Каждый релиз совместим с предыдущим по схеме, API и сообщениям. Тогда подходит любая стратегия, и откат кода не требует отката базы.

**Итог:** стратегия — компромисс между ценой ресурсов, скоростью отката и числом пострадавших.

</A>

<A l="s">

**Под капотом: IIS и контейнеры**

- **`app_offline.htm`.** Файл в корне сайта заставляет ASP.NET Core Module корректно остановить приложение и отдавать содержимое файла. DLL освобождаются, файлы заменяют, файл удаляют — следующий запрос запускает новую версию. Это простой: годится для окна обслуживания или как шаг rolling за балансировщиком.
- **Два сайта.** Синий и зелёный сайты со своими пулами и папками за ARR или внешним балансировщиком. Зелёный разворачивают и прогревают, проверяют `/health/ready`, переключают балансировщик, синий держат до конца наблюдения.
- **Контейнеры.** Оркестратор пускает трафик на новый экземпляр только после успешной readiness-проверки. Readiness и liveness — разные проверки: недоступная БД не повод перезапускать процесс.

**Цена**

Любая стратегия без простоя требует совместимости версий N и N−1: expand/contract в базе, необязательные поля в API, версионированные сообщения.

**Компромиссы**

- Откат быстрее, если артефакт и схема совместимы. Исправление вперёд (roll forward) — если миграция данных уже необратима.
- Feature flags отделяют выкладку от релиза, но копят мёртвые ветки кода. У флага должен быть срок жизни.

**Как проверить в проде**

- После переключения конвейер выжидает период наблюдения (bake time), сравнивает долю 5xx, p99 и бизнес-метрики с порогами и при нарушении сам возвращает трафик.
- Выкладка помечена в мониторинге версией, поэтому всплеск ошибок сразу связывается с релизом.
- Откат репетируют: откат, который ни разу не выполняли, не работает.

**Итог:** безопасная выкладка — малые шаги, совместимость N и N−1, решение по метрикам и уже проверенный откат.

</A>

<Ex>

```yaml
# Задача выкладки в ci.yml: blue-green на IIS (для простоты новая копия — зелёная)
jobs:
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: [self-hosted, windows, iis]   # свой агент в сети серверов
    environment: production                # ручное подтверждение в настройках окружения
    defaults:
      run:
        shell: powershell
    steps:
      - uses: actions/checkout@v7          # скрипты выкладки лежат в репозитории
      - uses: actions/download-artifact@v8
        with:
          name: shop-api-${{ github.sha }}
          path: drop
      # 1. Выкладка в копию без трафика
      - run: |
          Import-Module WebAdministration
          Stop-WebAppPool -Name shop-green
          Copy-Item drop\* D:\sites\shop-green -Recurse -Force
          Start-WebAppPool -Name shop-green
      # 2. Прогрев и проверка готовности до переключения
      - run: Invoke-WebRequest http://localhost:8081/health/ready -UseBasicParsing
      # 3. Переключение балансировщика и наблюдение за метриками
      - run: ./deploy/switch-traffic.ps1 -To green
      - run: ./deploy/watch-metrics.ps1 -Minutes 15 -Max5xxPercent 1
      # 4. Сбой на любом шаге — трафик обратно на прежнюю копию
      - if: failure()
        run: ./deploy/switch-traffic.ps1 -To blue
```

`switch-traffic.ps1` и `watch-metrics.ps1` — скрипты проекта: первый меняет правило ARR или пул балансировщика, второй читает метрики из мониторинга. В следующий релиз цвета меняются местами.

</Ex>
