## Что такое нормализация и когда оправдана денормализация?

<A short l="j">

<T k="normalization">Нормализация</T> — разбиение данных на таблицы так, чтобы каждый факт хранился ровно в одном месте. Поэтому смена адреса магазина — одна строка в таблице магазинов, а не тысячи строк продаж; денормализация — сознательное дублирование ради скорости чтения.

</A>

<A short l="m">

Нормальные формы — ступени: 1НФ требует атомарных значений, 2НФ — зависимости неключевых колонок от всего составного ключа, 3НФ — отсутствия зависимостей между неключевыми колонками. Они убирают <T k="update-anomaly">аномалии изменения</T>, которые появляются, когда один факт лежит в нескольких строках. <T k="denormalization">Денормализация</T> ускоряет чтение, но заботу о согласованности копий берёт на себя код, триггер или загрузка.

</A>

<A short l="s">

Нормальные формы определяются через <T k="functional-dependency">функциональные зависимости</T>; BCNF требует, чтобы каждый детерминант был потенциальным ключом, и закрывает редкие случаи, которые пропускает 3НФ. Транзакционную схему держат в 3НФ: запись дешёвая и непротиворечивая, а чтение ускоряют индексы. Денормализуют точечно и с механизмом синхронизации: вычисляемые колонки, <T k="indexed-view">индексированные представления</T>, агрегаты, отчётные таблицы. Цена — дороже запись и риск расхождения, поэтому у каждой копии должен быть один владелец и способ пересчёта.

</A>

<A l="j">

**Что это**

Нормализация — проектирование таблиц так, чтобы один факт хранился в одном месте. Название магазина лежит в таблице `Store`, а продажа ссылается на него по `StoreId`.

**Нормальные формы**

1. **1НФ.** В ячейке одно значение, нет повторяющихся групп: не колонки `Phone1`, `Phone2`, `Phone3`, а отдельная таблица телефонов.
2. **2НФ.** При составном ключе колонка зависит от всего ключа. В строке заказа `(OrderId, ProductId)` название товара зависит только от `ProductId` — ему место в `Product`.
3. **3НФ.** Неключевая колонка не зависит от другой неключевой. Адрес магазина зависит от магазина, а не от продажи.

**Частая ошибка**

Хранить список через запятую в одной колонке: `'A12,B7,C3'`. Такой список не проиндексировать, а поиск превращается в `LIKE '%B7%'`.

**Итог:** нормализация — каждый факт в одном месте, поэтому изменение делается один раз.

</A>

<A l="m">

**Как устроено**

Нормальные формы убирают три аномалии:

- **вставки** — нельзя завести магазин, пока у него нет продаж;
- **обновления** — адрес магазина надо менять в тысячах строк, и часть копий останется старой;
- **удаления** — удалили последнюю продажу и потеряли данные о магазине.

| Форма | Требование |
|---|---|
| 1НФ | атомарные значения, нет повторяющихся групп |
| 2НФ | неключевые колонки зависят от всего составного ключа |
| 3НФ | неключевые колонки не зависят друг от друга |
| BCNF | любой детерминант — потенциальный ключ |

**Когда что выбирать**

- Транзакционная база — 3НФ. Запись дешёвая, данные непротиворечивы, чтение ускоряют индексы.
- Денормализация — когда измерено, что соединения или агрегаты на горячем пути дороги: итог в шапке чека, остаток товара, отчётная таблица.

**Ловушки**

- **История — не дубль.** Цена в строке чека — цена на момент продажи, отдельный факт. Ссылка на текущую цену из справочника исказила бы старые чеки.
- **Копия без владельца.** Денормализованную колонку меняют из нескольких мест, и она расходится с источником.

**Правило**

Сначала 3НФ, денормализация — по измерениям и с явным механизмом синхронизации.

**Итог:** нормальные формы убирают аномалии, а денормализация — осознанный обмен согласованности на скорость чтения.

</A>

<A l="s">

**Под капотом**

- Функциональная зависимость `X → Y`: значение `X` однозначно определяет `Y`. 3НФ допускает зависимость, если `Y` входит в потенциальный ключ; BCNF запрещает и её.
- Расхождение 3НФ и BCNF бывает только при нескольких пересекающихся составных ключах, поэтому на практике таблица в 3НФ почти всегда уже в BCNF.

**Цена денормализации**

| Способ | Кто синхронизирует | Цена |
|---|---|---|
| Вычисляемая колонка `PERSISTED` | движок | только выражения по своей строке |
| Индексированное представление | движок, в той же транзакции | дороже запись в базовые таблицы, много ограничений |
| Колонка-агрегат: итог, остаток | код или триггер | горячая строка, риск расхождения |
| Отчётная таблица | загрузка по расписанию | данные отстают |

**Компромиссы**

- Денормализация переносит стоимость с чтения на запись. Остаток товара в одной строке становится точкой конкуренции: все продажи товара обновляют её.
- Отчётные базы денормализуют намеренно: их пишет одна загрузка, а читают многие запросы.
- Перебор тоже вреден. Модель EAV («сущность — атрибут — значение») ради гибкости теряет типы и ограничения, а каждый атрибут превращается в соединение.

**Как проверить в проде**

- Регулярная сверка: агрегат против пересчёта из исходных строк.
- Горячая строка-агрегат видна по ожиданиям блокировок `LCK_M_U` и `LCK_M_X` на одном ключе.

**Итог:** нормализуют ради дешёвой и непротиворечивой записи; денормализуют точечно, когда ясно, кто и как синхронизирует копию.

</A>

<Ex title="T-SQL">

```sql
-- До: название и адрес магазина повторяются в каждой продаже (нарушение 3НФ)
CREATE TABLE dbo.SaleFlat (
    SaleId       bigint        NOT NULL PRIMARY KEY,
    StoreId      int           NOT NULL,
    StoreName    nvarchar(100) NOT NULL,
    StoreAddress nvarchar(200) NOT NULL,
    Amount       decimal(12,2) NOT NULL
);

-- После: факт о магазине хранится один раз
CREATE TABLE dbo.Store (
    StoreId int           NOT NULL PRIMARY KEY,
    Name    nvarchar(100) NOT NULL,
    Address nvarchar(200) NOT NULL
);

CREATE TABLE dbo.Sale (
    SaleId  bigint        NOT NULL PRIMARY KEY,
    StoreId int           NOT NULL REFERENCES dbo.Store (StoreId),
    SoldAt  datetime2(0)  NOT NULL,
    Amount  decimal(12,2) NOT NULL
);

-- Переезд магазина: одна строка вместо тысяч
UPDATE dbo.Store SET Address = N'New address' WHERE StoreId = 42;
```

</Ex>

- Чем 3НФ отличается от BCNF? — BCNF требует, чтобы любой детерминант был потенциальным ключом; 3НФ допускает зависимость, если зависимая колонка входит в ключ.
- Нарушает ли нормализацию цена в строке чека? — Нет, это цена на момент продажи, отдельный исторический факт.
- Как денормализовать, не теряя согласованности? — Отдать синхронизацию движку (вычисляемая колонка, индексированное представление); иначе — один владелец копии и сверка.
- Что такое EAV и почему его избегают? — «Сущность — атрибут — значение»: гибко, но без типов и ограничений, с соединением на каждый атрибут.
- Почему отчётные базы денормализованы? — Их пишет одна загрузка, а читают многие запросы; меньше соединений — быстрее агрегаты.

</Next>

<Q id="db.design.keys" level="j">

## Какой первичный ключ выбрать: identity, GUID или естественный ключ?

<A short l="j">

<T k="surrogate-key">Суррогатный ключ</T> — искусственный идентификатор без смысла, например число из `IDENTITY` или GUID, а <T k="natural-key">естественный</T> берётся из предметной области: код товара, ИНН. Обычно первичным делают `bigint IDENTITY` — короткий, растущий и неизменный, а естественный ключ защищают ограничением `UNIQUE`.

</A>

<A short l="m">

Первичный ключ в SQL Server по умолчанию становится ключом <T k="clustered-index">кластерного индекса</T> и копируется в каждый некластерный индекс, поэтому важны его размер и порядок вставки. `bigint IDENTITY` — 8 байт и вставка в конец, случайный `NEWID()` — 16 байт и вставка в середину с <T k="page-split">разделением страниц</T>. GUID оправдан, когда идентификатор создаёт приложение или несколько баз без обращения к серверу, и тогда он должен быть последовательным.

</A>

<A short l="s">

Ключ — компромисс между размером, локальностью вставки и тем, кто генерирует значение. `IDENTITY` компактен, но известен только после вставки, а на горячей таблице вставка в последнюю страницу упирается в latch — для этого в SQL Server 2019 есть `OPTIMIZE_FOR_SEQUENTIAL_KEY`. <T k="uuid-v7">UUIDv7</T> из `Guid.CreateVersion7()` (.NET 9+) растёт со временем, но SQL Server сравнивает `uniqueidentifier` начиная с последних 6 байт, и в его индексе v7 ложится почти случайно. Последовательность в порядке SQL Server дают `NEWSEQUENTIALID()` и генератор EF Core, а естественный ключ остаётся уникальным ограничением.

</A>

<A l="j">

**Что это**

| Вид ключа | Пример |
|---|---|
| Суррогатный числовой | `int` или `bigint IDENTITY` |
| Суррогатный GUID | `uniqueidentifier` |
| Естественный | код товара, ИНН, код магазина |

**Как пользоваться**

- По умолчанию — `bigint IDENTITY(1, 1)`: компактный, растёт по порядку, не меняется.
- Естественный ключ остаётся колонкой с ограничением `UNIQUE`: дубли запрещены, но внешние ключи ссылаются на суррогатный.
- GUID — когда идентификатор нужен до вставки: его создаёт приложение или другая база.

**Частая ошибка**

Сделать первичным ключом штрихкод или ИНН. Штрихкоды переиспользуют, ИНН вводят с ошибкой, и менять приходится ключ во всех ссылающихся таблицах.

**Итог:** суррогатный ключ — для связей, естественный — под уникальное ограничение.

</A>

<A l="m">

**Как устроено**

- Первичный ключ по умолчанию создаёт кластерный индекс: строки таблицы хранятся упорядоченными по ключу.
- Ключ кластерного индекса служит указателем на строку в каждом некластерном индексе. GUID на 16 байт вместо `bigint` на 8 увеличивает все индексы таблицы.
- Растущий ключ дописывает строки в последнюю страницу. Случайный `NEWID()` вставляет в середину: страница делится пополам, индекс фрагментируется и заполнен наполовину.

**Когда что выбирать**

| Ключ | Когда |
|---|---|
| `bigint IDENTITY` | по умолчанию, одна база |
| `SEQUENCE` | номер нужен до вставки или общий для нескольких таблиц |
| Последовательный GUID | id создаёт приложение, данные сливаются из нескольких баз |
| `NEWID()` | почти никогда как кластерный ключ |

**Ловушки**

- **Дыры в `IDENTITY`.** Откат транзакции или перезапуск сервера оставляют пропуски. Номер чека без пропусков так не получить.
- **`NEWSEQUENTIALID()`** работает только в `DEFAULT`, а после перезапуска Windows может начать с меньшего значения.
- **UUIDv7.** `Guid.CreateVersion7()` упорядочен по времени для .NET, но не для `uniqueidentifier` в SQL Server.

**Правило**

`bigint IDENTITY` по умолчанию; GUID — когда id создаёт приложение, и тогда последовательный в порядке SQL Server.

**Итог:** ключ входит в каждый индекс, поэтому он должен быть коротким, неизменным и растущим.

</A>

<A l="s">

**Под капотом**

- SQL Server сравнивает `uniqueidentifier` не слева направо: старшими считаются последние 6 байт. В UUIDv7 время лежит в первых 6 байтах, поэтому порядок вставки в индекс почти случайный.
- `NEWSEQUENTIALID()` и `SequentialGuidValueGenerator` (генератор EF Core по умолчанию для SQL Server) переставляют байты под этот порядок.
- UUIDv7 сохраняет порядок в `binary(16)`, записанный в big-endian: `ToByteArray(bigEndian: true)` (.NET 8+). `binary` сравнивается побайтно.

**Цена**

- Растущий ключ на горячей таблице упирается в конкуренцию за последнюю страницу (`PAGELATCH_EX`). `OPTIMIZE_FOR_SEQUENTIAL_KEY` (SQL Server 2019) её сглаживает.
- GUID — 16 байт в каждом индексе и внешнем ключе: на сотнях миллионов строк это гигабайты буферного пула.
- Последовательные id легко угадать: публичный номер заказа отделяют от внутреннего ключа.

**Компромиссы**

- Естественный ключ экономит соединения, но его смена каскадом идёт по всем ссылкам. Исключение — короткие неизменные коды вроде ISO-кода валюты.
- Первичный ключ не обязан быть кластерным: GUID-ключ делают некластерным, а кластеризуют по растущей колонке.
- `IDENTITY` известен только после вставки, поэтому пакетная вставка связанных строк требует `OUTPUT` или `SEQUENCE`.

**Как проверить в проде**

`sys.dm_db_index_physical_stats` показывает фрагментацию и заполненность страниц (`avg_page_space_used_in_percent`), а ожидания `PAGELATCH_EX` на одной странице — конкуренцию за конец индекса.

**Итог:** ключ выбирают по размеру, порядку вставки и месту генерации; «последовательный» GUID должен быть последовательным в порядке сравнения SQL Server.

</A>

<Ex title="T-SQL">

```sql
CREATE TABLE dbo.Product (
    -- Суррогатный ключ: 8 байт, растёт по порядку, не меняется
    ProductId bigint IDENTITY(1, 1) NOT NULL
        CONSTRAINT PK_Product PRIMARY KEY CLUSTERED,
    -- Естественный ключ: уникален, но внешние ключи на него не ссылаются
    Sku       varchar(20)   NOT NULL CONSTRAINT UQ_Product_Sku UNIQUE,
    Name      nvarchar(200) NOT NULL
);

CREATE TABLE dbo.Receipt (
    -- GUID, последовательный в порядке сравнения SQL Server
    ReceiptId uniqueidentifier NOT NULL
        CONSTRAINT DF_Receipt_Id DEFAULT NEWSEQUENTIALID()
        CONSTRAINT PK_Receipt PRIMARY KEY CLUSTERED,
    StoreId   int          NOT NULL,
    CreatedAt datetime2(0) NOT NULL
);

-- Горячая вставка в конец индекса (SQL Server 2019+)
ALTER INDEX PK_Product ON dbo.Product SET (OPTIMIZE_FOR_SEQUENTIAL_KEY = ON);
```

</Ex>

<Ex title="C#">

```csharp
using System.Data.SqlTypes;

var ids = new List<Guid>();
for (var i = 0; i < 5; i++)
{
    ids.Add(Guid.CreateVersion7()); // .NET 9+: время в мс + случайные биты
    Thread.Sleep(2);                // внутри одной мс порядок не гарантирован
}

Console.WriteLine(ids[0].Version);                 // 7
Console.WriteLine(ids.SequenceEqual(ids.Order())); // True: в .NET порядок по времени

// SqlGuid сравнивает как SQL Server: старшие — последние 6 байт, а там случайные биты
var asSqlServer = ids.OrderBy(id => new SqlGuid(id));
Console.WriteLine(ids.SequenceEqual(asSqlServer)); // False (почти всегда)

// binary(16) сравнивается побайтно: big-endian сохраняет порядок по времени
var asBinary = ids.OrderBy(id => Convert.ToHexString(id.ToByteArray(bigEndian: true)), StringComparer.Ordinal);
Console.WriteLine(ids.SequenceEqual(asBinary));    // True
```

`SqlGuid` из `System.Data.SqlTypes` повторяет правила сравнения SQL Server, поэтому показывает, как UUIDv7 ляжет в индекс по `uniqueidentifier`.

</Ex>

<Next>

- Почему случайный GUID плох для кластерного ключа? — Вставка в середину индекса: разделение страниц, фрагментация, полупустые страницы, 16 байт в каждом индексе.
- Почему в `IDENTITY` бывают пропуски? — Значения не возвращаются при откате и теряются из кеша при перезапуске сервера.
- Подходит ли `Guid.CreateVersion7()` для SQL Server? — Для `uniqueidentifier` порядок теряется; нужен `NEWSEQUENTIALID()`, генератор EF Core или хранение в `binary(16)`.
- Обязан ли первичный ключ быть кластерным? — Нет: можно сделать его некластерным, а кластерный индекс построить по другой колонке.
- Когда естественный ключ уместен как первичный? — Когда он короткий и никогда не меняется: ISO-код валюты, код страны.

</Next>

<Q id="db.design.etl-ssis" level="m">

## Как устроен ETL и как строят загрузки в SSIS?

<A short l="j">

<T k="etl">ETL</T> (extract, transform, load) — процесс, который забирает данные из источников, приводит их к нужному виду и загружает в целевую базу, например из баз магазинов в центральную. SSIS — инструмент Microsoft для таких загрузок: пакет собирают в Visual Studio и запускают по расписанию через SQL Server Agent.

</A>

<A short l="m">

Пакет SSIS — это control flow, порядок задач с условиями переходов, и data flow, поток строк от источника через преобразования в приёмник. Загрузку делают инкрементальной: по <T k="watermark">водяному знаку</T> (`rowversion`, дата изменения), через <T k="change-tracking">change tracking</T> или <T k="change-data-capture">CDC</T>. Данные сначала кладут в <T k="staging-table">staging-таблицу</T>, а затем одним set-based запросом переносят в цель, чтобы повторный запуск после сбоя был <T k="idempotency">идемпотентным</T>.

</A>

<A short l="s">

Надёжная загрузка — инкремент плюс идемпотентность: каждый запуск знает, откуда читать, и повтор не создаёт дублей. Водяной знак по `rowversion` ограничивают сверху `MIN_ACTIVE_ROWVERSION()`, иначе строки незавершённых транзакций проскочат. Change tracking дёшев, но отдаёт только ключи изменённых строк, а CDC хранит значения из журнала и не даёт журналу усекаться, пока задание захвата отстаёт. Пакеты живут в каталоге SSISDB, а новые загрузки всё чаще строят в Azure Data Factory или на .NET с `SqlBulkCopy`.

</A>

<A l="j">

**Что это**

ETL — три шага:

1. **Extract** — прочитать данные из источника: базы, файла, API.
2. **Transform** — очистить и привести к формату цели: типы, справочники, дубли.
3. **Load** — записать в целевую базу.

**Как устроен пакет SSIS**

- **Control flow** — задачи и порядок их выполнения: «очистить staging», «загрузить данные», «выполнить процедуру».
- **Data flow** — задача, через которую идут строки: источник → преобразования → приёмник.

**Как пользоваться**

Пакет разрабатывают в Visual Studio, разворачивают на сервер в каталог SSISDB и запускают по расписанию заданием SQL Server Agent.

**Частая ошибка**

Каждый раз перезагружать всю таблицу. Пока данных мало, это работает, а через год загрузка перестаёт помещаться в ночное окно.

**Итог:** ETL — извлечь, преобразовать, загрузить; в SSIS порядок задаёт control flow, а строки идут через data flow.

</A>

<A l="m">

**Как устроено**

Инкрементальная загрузка по шагам:

1. Прочитать из управляющей таблицы последний водяной знак.
2. Data flow забирает строки новее него и быстрой вставкой кладёт в staging.
3. Процедура переносит staging в цель через `MERGE` или `UPDATE` и `INSERT`.
4. В той же транзакции сохранить новый водяной знак.

**Когда что выбирать**

| Способ | Плюс | Минус |
|---|---|---|
| Водяной знак | просто, без настройки источника | не видит удалений |
| Change tracking | дёшево, видит удаления | только ключи, без старых значений |
| CDC | значения до и после из журнала | SQL Server Agent, нагрузка на журнал |

**Ловушки**

- **Построчная обработка.** OLE DB Command и Slowly Changing Dimension выполняют запрос на каждую строку. Большие объёмы обрабатывают в staging одним запросом.
- **Блокирующие преобразования.** Sort и Aggregate ждут весь поток и держат его в памяти. Сортировку отдают источнику (`ORDER BY` и `IsSorted` на выходе).
- **Дата изменения как водяной знак.** Время ставится до коммита, и строки долгой транзакции проскакивают.

**Правило**

Запуск безопасен для повтора: staging очищается в начале, перенос идёт по бизнес-ключу, водяной знак двигается только после успеха.

**Итог:** инкремент находит изменения, staging и set-based перенос делают повтор безопасным.

</A>

<A l="s">

**Под капотом**

- Data flow работает буферами в памяти. Синхронные преобразования (Derived Column, Lookup) меняют строки в том же буфере, асинхронные копируют их в новые.
- OLE DB Destination в режиме fast load вставляет пакетами; `Maximum insert commit size` задаёт размер транзакции.
- Checkpoints перезапускают пакет с упавшей задачи control flow, но не с середины data flow, а циклы Foreach выполняются заново. Идемпотентные шаги надёжнее.

**Компромиссы**

- Change tracking синхронный: каждая запись платит за учёт. Если последняя синхронизация старше `CHANGE_TRACKING_MIN_VALID_VERSION`, нужна полная перезагрузка.
- CDC асинхронный, но журнал не усекается, пока задание захвата его не обработало.
- В SSIS 2025 удалены CDC-компоненты Attunity и Microsoft Connector for Oracle, а 32-битный режим объявлен устаревшим. Для новых загрузок Microsoft предлагает Azure Data Factory и Data Factory в Fabric; готовые пакеты запускают в ADF на Azure-SSIS Integration Runtime.
- Загрузку на .NET (`SqlBulkCopy` в staging, процедура с `MERGE`) проще тестировать и версионировать, но логирование, перезапуск и параллелизм пишутся вручную.

**Как проверить в проде**

- Каталог SSISDB хранит историю запусков: `catalog.executions` и `catalog.event_messages`, а с уровнем логирования Performance — время компонентов в `catalog.execution_component_phases`.
- После загрузки сверяют количество строк и суммы источника и цели.

**Итог:** надёжный ETL — это инкремент без потерь, идемпотентный перенос и наблюдаемость; инструмент вторичен.

</A>

<Ex title="T-SQL">

```sql
SET XACT_ABORT ON;

DECLARE @from binary(8) = (SELECT LastVersion FROM etl.Watermark WHERE TableName = N'Sale');
-- Верхняя граница: строки незавершённых транзакций дождутся следующего запуска
DECLARE @to binary(8) = MIN_ACTIVE_ROWVERSION();

-- Extract: в SSIS это data flow из источника в staging
TRUNCATE TABLE stg.Sale;
INSERT INTO stg.Sale (SaleId, StoreId, Amount)
SELECT SaleId, StoreId, Amount
FROM src.Sale
WHERE RowVer >= @from AND RowVer < @to;

-- Load: повторный запуск не создаст дублей
BEGIN TRAN;

MERGE dw.Sale AS t
USING stg.Sale AS s ON t.SaleId = s.SaleId
WHEN MATCHED THEN UPDATE SET t.StoreId = s.StoreId, t.Amount = s.Amount
WHEN NOT MATCHED THEN INSERT (SaleId, StoreId, Amount) VALUES (s.SaleId, s.StoreId, s.Amount);

-- Водяной знак двигается вместе с данными
UPDATE etl.Watermark SET LastVersion = @to WHERE TableName = N'Sale';

COMMIT;
```

Если `@@DBTS` взять вместо `MIN_ACTIVE_ROWVERSION()`, строка из транзакции, которая закоммитится позже, получит версию ниже сохранённой границы и не загрузится никогда.

</Ex>

<Next>

- Чем change tracking отличается от CDC? — CT синхронно хранит ключи изменённых строк и версию, CDC асинхронно читает журнал и хранит значения до и после.
- Почему `@@DBTS` нельзя брать как водяной знак? — Строки незавершённых транзакций закоммитятся с версией ниже границы и будут пропущены.
- Как перезапустить упавший пакет SSIS? — Checkpoints с упавшей задачи control flow; надёжнее идемпотентные шаги, которые можно просто запустить заново.
- Как задать разные строки подключения для теста и прода? — Параметры проекта и окружения (environments) в каталоге SSISDB.
- Как ускорить data flow? — Убрать построчные и блокирующие преобразования, fast load в staging, сортировку и соединения отдать базе.

</Next>

<Q id="db.design.reporting" level="m">

## Как построить отчётность, чтобы отчёты не положили рабочую базу?

<A short l="j">

<T k="oltp">OLTP</T>-база обслуживает много коротких транзакций — продажи, заказы, а <T k="olap">OLAP</T> — тяжёлые аналитические запросы по большим объёмам. Тяжёлый отчёт по рабочей базе читает миллионы строк и тормозит кассы, поэтому такие отчёты переносят на копию базы или в отдельное хранилище.

</A>

<A short l="m">

Отчёт мешает рабочей базе тремя путями: занимает CPU, память и диск, вытесняет из кеша горячие данные и под READ COMMITTED конфликтует с записью по блокировкам. Решения по нарастанию: RCSI и кеш отчётов SSRS, <T k="readable-secondary">реплика для чтения</T> Always On, отдельная <T k="data-mart">витрина данных</T> со <T k="star-schema">схемой «звезда»</T>, которую наполняет ETL. Цена каждого шага — задержка данных и ещё одна система в поддержке.

</A>

<A short l="s">

Нагрузку делят по допустимой задержке: оперативным отчётам нужны данные «сейчас», аналитике хватает вчерашних. Оперативные читают с реплики Always On (Enterprise, отставание в секунды, snapshot-изоляция) или с <T k="columnstore-index">columnstore-индекса</T> на рабочей таблице, аналитику — из витрины, где схема заточена под агрегаты. Отчётный сервер выбирают с прицелом на будущее: SSRS 2022 — последняя версия, а с SQL Server 2025 его место занял Power BI Report Server, который открывает те же RDL-отчёты.

</A>

<A l="j">

**Что это**

| | OLTP | OLAP |
|---|---|---|
| Запросы | короткие, по ключу | агрегаты по миллионам строк |
| Пример | продажа на кассе | выручка по магазинам за год |
| Схема | нормализованная | денормализованная, «звезда» |

**Зачем разделять**

Тяжёлый отчёт занимает процессор и диск рабочей базы и может блокировать запись. Кассы и сайт начинают ждать.

**Как пользоваться**

- Отчёты строят в SSRS: отчёт описан в файле RDL, сервер отчётов выполняет запрос и отдаёт результат в браузер, Excel или PDF.
- Тяжёлые отчёты подключают не к рабочей базе, а к её копии или к хранилищу данных.

**Частая ошибка**

Лечить блокировки отчётов подсказкой `NOLOCK`. Отчёт начинает читать незакоммиченные данные и может пропустить или дважды посчитать строки.

**Итог:** OLTP — для транзакций, OLAP — для анализа; тяжёлые отчёты уводят с рабочей базы.

</A>

<A l="m">

**Как устроено**

Отчёт мешает рабочей базе тремя путями:

1. **Ресурсы.** Сканы и сортировки занимают CPU, диск и память под запросы.
2. **Кеш.** Прочитанные страницы вытесняют из буферного пула горячие данные.
3. **Блокировки.** Под READ COMMITTED чтение ставит разделяемые блокировки и конфликтует с записью.

**Когда что выбирать**

| Решение | Задержка данных | Когда |
|---|---|---|
| RCSI на рабочей базе | нет | отчёты лёгкие, мешают только блокировки |
| Кеш и снимки SSRS | минуты или сутки | один отчёт открывают многие |
| Реплика Always On | секунды | оперативные отчёты, Enterprise |
| Витрина данных | до следующего ETL | аналитика, история, тяжёлые агрегаты |

**Ловушки**

- **Реплика — та же схема.** Индекс под отчёт создают на первичной базе, и он замедляет запись. Свои индексы возможны только в витрине или в базе-подписчике репликации.
- **Параметры без границ.** Период «за всё время» по умолчанию превращает отчёт в полный скан.
- **Подписки в одно время.** Сотни рассылок в 9:00 — пик нагрузки, который легко размазать.

**Правило**

Сначала найти тяжёлые отчёты, затем уводить их по допустимой задержке: оперативные — на реплику, аналитику — в витрину.

**Итог:** отчёты разводят с транзакциями по ресурсам и блокировкам, а способ выбирают по допустимой задержке данных.

</A>

<A l="s">

**Под капотом**

- Читаемая реплика применяет журнал потоком redo. Все запросы на ней идут под snapshot isolation, подсказки блокировок игнорируются.
- Платит первичная база: при читаемой реплике к изменённым строкам добавляются 14 байт под версии, что может вызвать разделение страниц.
- Долгий отчёт на реплике держит Sch-S и может задержать redo DDL и очистку ghost-записей на первичной.
- Columnstore хранит данные по колонкам со сжатием и обрабатывает пакетами строк. С SQL Server 2016 некластерный columnstore на рабочей таблице обновляемый — это real-time operational analytics.

**Компромиссы**

| Вариант | Цена |
|---|---|
| Реплика Always On | Enterprise; схема и индексы как у первичной; лаг растёт под нагрузкой |
| Columnstore на рабочей таблице | дороже каждая запись, место под индекс |
| Витрина со звездой | ETL, задержка, ещё одна модель данных |

Basic availability group в Standard реплику для чтения не даёт.

**Отчётный сервер в 2025+**

SSRS 2022 — последняя версия, поддержка до 11 января 2033 года. С SQL Server 2025 локальная отчётность — Power BI Report Server: те же RDL-отчёты плюс интерактивные PBIX, право на него входит в лицензии Enterprise и Standard. Облачный путь — Power BI, где RDL работают как paginated reports.

**Как проверить в проде**

- `ExecutionLog3` в базе сервера отчётов показывает по каждому запуску время получения данных, обработки и рендеринга.
- Отставание реплики — `sys.dm_hadr_database_replica_states`: `log_send_queue_size`, `redo_queue_size`.

**Итог:** отчётность разводят с транзакциями по допустимой задержке, а платформу выбирают с учётом конца линейки SSRS.

</A>

<Ex title="T-SQL">

```sql
-- База сервера отчётов: по умолчанию ReportServer, журнал хранится 60 дней
USE ReportServer;

-- Какие отчёты дольше всех ждали базу за неделю
SELECT TOP (10)
    ItemPath,
    COUNT(*)                                       AS Runs,
    SUM(CAST(TimeDataRetrieval AS bigint)) / 1000  AS DataSecTotal,
    AVG(CAST(TimeDataRetrieval AS bigint)) / 1000  AS DataSecAvg,
    MAX([RowCount])                                AS MaxRows
FROM dbo.ExecutionLog3
WHERE TimeStart >= DATEADD(DAY, -7, SYSDATETIME())
GROUP BY ItemPath
ORDER BY DataSecTotal DESC;
```

</Ex>

<Ex title="T-SQL">

```sql
-- Оперативная аналитика прямо по рабочей таблице (SQL Server 2016+):
-- транзакции пишут в обычный индекс, агрегаты читают сжатые колонки
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Sale
    ON dbo.Sale (StoreId, SoldAt, Amount);

SELECT StoreId, SUM(Amount) AS Revenue
FROM dbo.Sale
WHERE SoldAt >= '2026-10-01'
GROUP BY StoreId;
```

</Ex>

- Почему отчёт на реплике не блокирует запись? — На читаемой реплике все запросы идут под snapshot isolation, подсказки блокировок игнорируются.
- Можно ли создать индекс только на реплике Always On? — Нет, схема общая; индекс создают на первичной либо используют витрину или репликацию.
- Что будет с SSRS после SQL Server 2025? — Новых версий нет, SSRS 2022 поддерживается до 2033 года, замена — Power BI Report Server.
- Как найти отчёт, который грузит базу? — `ExecutionLog3` в базе сервера отчётов: время получения данных и число запусков.

<Q id="db.design.partitioning-scaling" level="s">

## Как масштабировать базу: партиционирование, реплики, шардирование и архив?

<A short l="j">

<T k="table-partitioning">Партиционирование</T> делит большую таблицу на секции по диапазону, например по месяцам, реплики для чтения забирают часть запросов, а <T k="sharding">шардирование</T> раскладывает данные по нескольким серверам. Старые данные переносят в архив, чтобы рабочая таблица оставалась небольшой.

</A>

<A short l="m">

Партиционирование в SQL Server — одна логическая таблица из секций по функции секционирования. Оно ускоряет обслуживание и архивацию через <T k="partition-switching">переключение секций</T>, а запросы — только при <T k="partition-elimination">исключении секций</T> по ключу. Чтение масштабируют репликами <T k="availability-group">Always On</T>, запись — шардированием, например по магазину; дальше по списку — выше цена: шарды ломают соединения, транзакции и уникальность.

</A>

<A short l="s">

Сначала выжимают один сервер: индексы, архив истории, columnstore, затем партиционирование ради обслуживания — `SWITCH` переносит месяц в архив как операция метаданных. Чтение выносят на реплики, помня про лаг и версии строк. Шардирование масштабирует запись, но запросы между шардами, распределённые транзакции, глобальные ключи и перебалансировка становятся вашим кодом. Поэтому ключ шардирования выбирают по границе бизнеса — магазин, регион, клиент, — чтобы почти каждая транзакция жила в одном шарде.

</A>

<A l="j">

**Что это**

- **Партиционирование** — таблица хранится секциями по значению колонки, например по месяцу продажи. Для запросов это одна таблица.
- **Реплика для чтения** — копия базы, на которую уводят отчёты.
- **Шардирование** — данные разных магазинов или клиентов лежат в разных базах на разных серверах.
- **Архивирование** — старые данные переносят из рабочей таблицы в архив.

**Зачем**

Большую таблицу дольше обслуживать, копировать и чистить. Удалить прошлый год через `DELETE` — часы блокировок и гигабайты журнала, а с партиционированием это переключение секции.

**Частая ошибка**

Ждать, что партиционирование само ускорит запросы. Если в условии нет колонки секционирования, запрос читает все секции и может стать медленнее.

**Итог:** партиционирование упрощает работу с большой таблицей, реплики разгружают чтение, шардирование делит данные между серверами.

</A>

<A l="m">

**Как устроено партиционирование**

1. **Функция секционирования** задаёт границы: `RANGE RIGHT FOR VALUES ('2026-09-01', '2026-10-01')`.
2. **Схема секционирования** раскладывает секции по файловым группам.
3. Таблицу и индексы создают на схеме. Индекс на той же схеме — <T k="aligned-index">выровненный</T>; `SWITCH` работает только с выровненными индексами.

**Скользящее окно для архива**

1. `SPLIT RANGE` добавляет пустую секцию под следующий месяц.
2. `SWITCH PARTITION` переносит старейший месяц в архивную таблицу той же структуры.
3. `MERGE RANGE` убирает опустевшую границу.

**Когда что выбирать**

| Проблема | Решение |
|---|---|
| Таблицу долго обслуживать и чистить | партиционирование |
| Чтение перегружает сервер | реплики для чтения |
| Запись не помещается в один сервер | шардирование |

**Ловушки**

- Уникальный индекс включает колонку секционирования, иначе он не выровнен. Отсюда составной ключ `(SaleId, SoldOn)`.
- Запрос без ключа секционирования ищет в каждой секции. Microsoft прямо пишет, что в OLTP партиционирование редко ускоряет запросы.
- `SPLIT` и `MERGE` непустой секции перемещают строки и пишут журнал, поэтому крайние секции держат пустыми.

**Итог:** партиционирование — инструмент обслуживания и архивации, а масштаб чтения и записи дают реплики и шарды.

</A>

<A l="s">

**Под капотом**

- `SWITCH` меняет принадлежность страниц, данные не копируются. Условия: одинаковые колонки и индексы, та же файловая группа, цель пуста; при загрузке в секцию источник подтверждает диапазон CHECK-ограничением.
- `SWITCH` нужна монопольная блокировка обеих таблиц. С SQL Server 2014 `WAIT_AT_LOW_PRIORITY` не даёт ей встать в очередь перед всеми запросами.
- `TRUNCATE TABLE ... WITH (PARTITIONS (2))` (SQL Server 2016+) очищает секцию без архива. Партиционирование есть во всех редакциях с SQL Server 2016 SP1.

**Цена**

- До 15 000 секций, но тысячи секций стоят памяти, а запросы без исключения секций замедляются.
- Читаемые реплики — только Enterprise; basic availability group в Standard не даёт читать со вторичной.

**Компромиссы шардирования**

| Что теряем | Чем платим |
|---|---|
| Соединения и агрегаты между шардами | запросы ко всем шардам, отчёты через хранилище |
| Транзакции между шардами | саги, outbox, идемпотентность |
| Глобальная уникальность | GUID или ключ с номером шарда |
| Равномерность | перебалансировка, «горячие» шарды |

Справочники вроде товаров и магазинов копируют в каждый шард.

**Как проверить в проде**

- `sys.dm_db_partition_stats` показывает строки по секциям, а план — `Actual Partition Count`.
- Отставание реплик — `sys.dm_hadr_database_replica_states`.

**Итог:** один сервер выжимают до конца, партиционируют ради обслуживания, а шардируют, только когда запись упёрлась в сервер и есть естественный ключ раздела.

</A>

<Ex title="T-SQL">

```sql
-- RANGE RIGHT: граница — первое число месяца; крайние секции держим пустыми
CREATE PARTITION FUNCTION pfMonth (date)
    AS RANGE RIGHT FOR VALUES ('2026-08-01', '2026-09-01', '2026-10-01', '2026-11-01');
CREATE PARTITION SCHEME psMonth AS PARTITION pfMonth ALL TO ([PRIMARY]);

CREATE TABLE dbo.Sale (
    SaleId bigint        NOT NULL,
    SoldOn date          NOT NULL,
    Amount decimal(12,2) NOT NULL,
    CONSTRAINT PK_Sale PRIMARY KEY (SaleId, SoldOn) -- ключ включает колонку секционирования
) ON psMonth (SoldOn);

-- Архив: та же структура и файловая группа, пустой
CREATE TABLE dbo.SaleArchive (
    SaleId bigint NOT NULL, SoldOn date NOT NULL, Amount decimal(12,2) NOT NULL,
    CONSTRAINT PK_SaleArchive PRIMARY KEY (SaleId, SoldOn)
) ON [PRIMARY];

-- 1. Пустая секция под декабрь, пока данных за ноябрь ещё нет
ALTER PARTITION SCHEME psMonth NEXT USED [PRIMARY];
ALTER PARTITION FUNCTION pfMonth() SPLIT RANGE ('2026-12-01');

-- 2. Август (секция 2) уходит в архив: меняются только метаданные
ALTER TABLE dbo.Sale SWITCH PARTITION 2 TO dbo.SaleArchive
    WITH (WAIT_AT_LOW_PRIORITY (MAX_DURATION = 1 MINUTES, ABORT_AFTER_WAIT = SELF));

-- 3. Убрать границу между двумя пустыми секциями
ALTER PARTITION FUNCTION pfMonth() MERGE RANGE ('2026-08-01');
```

</Ex>

<Next>

- Ускоряет ли партиционирование запросы? — Только при исключении секций по ключу секционирования; иначе часто замедляет.
- Почему `SWITCH` выполняется мгновенно? — Меняются метаданные принадлежности страниц, строки не копируются.
- Зачем держать крайние секции пустыми? — Тогда `SPLIT` и `MERGE` не перемещают строки и не раздувают журнал.
- Чем шардирование отличается от партиционирования? — Секции живут в одной базе на одном сервере, шарды — в разных базах на разных серверах.
- Как выбрать ключ шардирования? — По границе, внутри которой живёт почти каждая транзакция, и с равномерной нагрузкой: магазин, регион, клиент.

</Next>

<Q id="db.design.zero-downtime" level="s">

## Как менять схему базы без простоя?

<A short l="j">

Схему меняют так, чтобы работающая версия приложения не сломалась: сначала только добавляют новое, потом переключают код и лишь в конце удаляют старое. Большие таблицы обновляют небольшими пакетами, чтобы не блокировать пользователей.

</A>

<A short l="m">

Основной приём — <T k="expand-contract">expand/contract</T>: совместимо расширить схему, перевести приложение, заполнить данные пакетами (<T k="backfill">backfill</T>), переключить чтение и только потом удалить старое. Любой `ALTER TABLE` берёт <T k="schema-modification-lock">блокировку Sch-M</T>, поэтому важно, сколько он её держит: изменение метаданных — миллисекунды, перезапись всех строк — простой. Цена — несколько релизов на одно изменение и временный код, который пишет в обе колонки.

</A>

<A short l="s">

Схема в каждый момент совместима с двумя соседними версиями приложения — так работают поэтапный деплой и откат кода без отката базы. Долгие операции заменяют метаданными или онлайн-вариантами (Enterprise), а остальное — новой колонкой и пакетным backfill под контролем журнала и лага реплик. Главный скрытый риск — очередь за Sch-M: DDL, ждущий долгий запрос, блокирует всех, кто пришёл после. Поэтому DDL запускают с `LOCK_TIMEOUT` или `WAIT_AT_LOW_PRIORITY` и повтором.

</A>

<A l="j">

**Что это**

Изменение схемы без простоя — база меняется, пока приложение работает и магазины продолжают продавать.

**Как пользоваться**

Переименование колонки `Phone` в `PhoneNumber` по шагам:

1. Добавить колонку `PhoneNumber`, разрешив `NULL`. Старое приложение её не замечает.
2. Выпустить версию приложения, которая пишет в обе колонки.
3. Скопировать старые данные небольшими пакетами.
4. Выпустить версию, которая читает только `PhoneNumber`.
5. Удалить `Phone`, когда старых версий приложения не осталось.

**Частая ошибка**

Переименовать или удалить колонку в одном релизе с кодом. Пока обновлены не все серверы, старая версия обращается к колонке, которой уже нет, и падает.

**Итог:** сначала добавить, потом переключить, удалить — в самом конце.

</A>

<A l="m">

**Как устроено**

Expand/contract — три фазы:

1. **Expand.** Только совместимые изменения: новая nullable-колонка, таблица, индекс. Старый код работает.
2. **Migrate.** Код пишет в старое и новое, backfill переносит историю, чтение переключается на новое.
3. **Contract.** Когда старого кода нет и окно отката прошло, старое удаляют.

**Сколько держится блокировка**

| Операция | Как выполняется |
|---|---|
| Новая nullable-колонка | метаданные, мгновенно |
| NOT NULL с константным default | метаданные в Enterprise (2012+), иначе перезапись строк |
| Смена типа, например `int` → `bigint` | перезапись всех строк под Sch-M |
| Индекс с `ONLINE = ON` | онлайн, короткие блокировки в начале и конце; Enterprise |

**Ловушки**

- **Очередь за Sch-M.** `ALTER` ждёт долгий отчёт, а все новые запросы к таблице ждут `ALTER`. Перед DDL ставят `SET LOCK_TIMEOUT` и повторяют попытку.
- **Один большой `UPDATE`.** Backfill одной транзакцией раздувает журнал, вызывает <T k="lock-escalation">эскалацию блокировок</T> до таблицы и задерживает реплики. Нужны пакеты по несколько тысяч строк.
- **Переименование в один шаг.** `sp_rename` колонки, которую читает работающая версия, — <T k="breaking-change">ломающее изменение</T>.

**Правило**

Каждая миграция совместима с текущей и предыдущей версией приложения.

**Итог:** expand/contract делает каждый шаг совместимым, а пакеты и онлайн-операции держат блокировки короткими.

</A>

<A l="s">

**Под капотом**

- Sch-M несовместима ни с одной блокировкой, даже со стабильностью схемы у читателей. Важно, сколько DDL её держит и сколько ждёт её получения.
- Эскалация срабатывает примерно на 5 000 блокировках одного оператора на одном объекте. Пакеты меньше этого порога держат построчные блокировки и не останавливают остальных.
- <T k="accelerated-database-recovery">ADR</T> (SQL Server 2019+) делает откат долгой транзакции мгновенным и усекает журнал во время неё; без ADR отмена часового `UPDATE` может длиться столько же.

**Смена типа на большой таблице**

1. Добавить колонку нового типа, nullable.
2. Синхронизировать новые изменения — кодом или триггером.
3. Backfill пакетами по диапазонам ключа.
4. Переключить чтение и запись, затем удалить старую колонку.

`ALTER COLUMN ... WITH (ONLINE = ON)` (SQL Server 2016+, Enterprise) оставляет таблицу доступной, но строки всё равно переписываются.

**Компромиссы**

- State-based развёртывание (dacpac, `sqlpackage`) строит скрипт сравнением схем и при некоторых изменениях пересоздаёт таблицу копированием, поэтому скрипт читают до прода. Миграции (EF Core, DbUp) явны, но порядок шагов на вас.
- После expand откатывают только код: схема совместима со старой версией. Обратные миграции с потерей данных на проде заменяют исправлением вперёд.
- Триггер синхронизации ловит всех писателей, включая ETL, но удорожает каждую запись.

**Как проверить в проде**

- Во время backfill следят за `log_reuse_wait_desc` в `sys.databases` и `redo_queue_size` реплик; пауза между пакетами — регулятор.
- Очередь за DDL видна в `sys.dm_exec_requests`: `wait_type` `LCK_M_SCH_M` и `blocking_session_id`.

**Итог:** без простоя — это совместимость с двумя версиями кода, короткие блокировки и управляемая очередь за Sch-M.

</A>

<Ex title="T-SQL">

```sql
-- DDL ждёт блокировку не дольше 5 секунд и не держит очередь за собой
SET LOCK_TIMEOUT 5000;

-- Expand: новая nullable-колонка шире старой — только метаданные
ALTER TABLE dbo.Receipt ADD TotalAmount decimal(14,2) NULL;

-- Backfill пакетами по диапазону ключа: короткие транзакции без эскалации
DECLARE @batch bigint = 4000, @from bigint = 0, @max bigint;
SELECT @max = MAX(ReceiptId) FROM dbo.Receipt;

WHILE @from < @max
BEGIN
    UPDATE dbo.Receipt
    SET TotalAmount = Total
    WHERE ReceiptId > @from AND ReceiptId <= @from + @batch
      AND TotalAmount IS NULL; -- повторный запуск продолжит с места остановки

    SET @from += @batch;
    WAITFOR DELAY '00:00:00.100'; -- место для рабочей нагрузки и реплик
END;

-- Contract — отдельным релизом, когда код больше не читает старую колонку
-- ALTER TABLE dbo.Receipt DROP COLUMN Total;
```

Пока идёт backfill, новая версия приложения пишет в обе колонки, поэтому новые чеки уже заполнены.

</Ex>

<Next>

- Почему `ALTER TABLE` на миллисекунды может положить систему? — Он ждёт Sch-M за долгим запросом, а все новые запросы встают в очередь за ним.
- Как добавить NOT NULL-колонку в таблицу на миллиард строк? — В Enterprise с константным default это метаданные; иначе nullable-колонка, backfill пакетами, а финальный `NOT NULL` проверит все строки.
- Зачем пакеты по несколько тысяч строк? — Короткие транзакции, нет эскалации до таблицы, журнал усекается, реплики не отстают.
- Как откатить релиз с изменением схемы? — Откатывают код: после expand схема совместима со старой версией; удаление идёт отдельным поздним релизом.
- Чем dacpac отличается от миграций? — Скрипт генерируется сравнением схем и может пересоздать таблицу; миграции явны, но порядок шагов на вас.

</Next>
