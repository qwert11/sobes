## Які вбудовані типи є в Python і чим змінювані відрізняються від незмінних?

<A short l="j">

Основні вбудовані типи — числа (`int`, `float`), `bool`, `str`, `None` і колекції `list`, `tuple`, `dict`, `set`. <T k="py-mutable">Змінювані</T> (`list`, `dict`, `set`) змінюються на місці, а незмінні (`int`, `str`, `tuple`) — ні: будь-яка «правка» створює новий об'єкт, тому ключем `dict` може бути кортеж, але не список.

</A>

<A short l="m">

Змінна в Python — <T k="py-name-binding">ім'я, прив'язане до об'єкта</T>, а не комірка зі значенням: присвоєння копіює посилання, а не об'єкт. Аргументи передаються <T k="py-call-by-sharing">за посиланням на об'єкт</T>: функція може змінити переданий список, але не може переприв'язати ім'я того, хто її викликав. Тому копію роблять явно (`copy.copy`, `copy.deepcopy`), а `is` перевіряє, чи це той самий об'єкт, `==` — чи рівні значення.

</A>

<A short l="s">

Змінюваність — властивість типу, а не змінної: будь-яке значення в Python — об'єкт, і різниця лише в тому, чи має тип операції, що змінюють його на місці. Від неї залежить <T k="py-hashable">хешованість</T>: ключем `dict` і елементом `set` буває лише об'єкт, чий хеш не змінюється за час життя. Звідси типові баги — змінюване значення за замовчуванням, спільний вкладений список після поверхневої копії, `is` замість `==` — і правило: у значеннях за замовчуванням і спільних даних віддавати перевагу незмінним типам. Ціна незмінності — новий об'єкт на кожну зміну.

</A>

<A l="j">

**Що це**

| Тип | Змінюваний | Приклад |
|---|---|---|
| `int`, `float`, `bool` | ні | `42`, `3.14`, `True` |
| `str`, `tuple` | ні | `"text"`, `(1, "a")` |
| `list` | так | `[1, 2]` |
| `dict` | так | `{"id": 1}` |
| `set` | так | `{1, 2}` |

`None` — єдиний об'єкт свого типу, аналог `null`.

**Як користуватися**

- `list` — послідовність, яку змінюватимуть.
- `tuple` — запис фіксованої довжини: координати, пара значень.
- `dict` — пошук за ключем, `set` — унікальні елементи та швидка перевірка `x in s`.
- <T k="py-comprehension">Comprehension</T> збирає колекцію одним виразом: `[x * x for x in items if x > 0]`.

**Типова помилка**

Змінюване значення за замовчуванням: `def add(item, items=[])`. Список створюється один раз і накопичує елементи між викликами. Правильно — `items=None` і всередині `if items is None: items = []`.

**Підсумок:** змінювані типи змінюються на місці, незмінні за кожної «правки» дають новий об'єкт.

</A>

<A l="m">

**Як влаштовано**

- **Імена й об'єкти.** `b = a` прив'язує друге ім'я до того самого об'єкта. Копія не створюється ні для списку, ні для числа.
- **Передача аргументів.** Функція отримує посилання на той самий об'єкт. `items.append(x)` змінить список того, хто викликав, а `items = [x]` переприв'яже лише локальне ім'я.
- **`is` і `==`.** `is` порівнює ідентичність, `==` викликає `__eq__` і порівнює значення. З `None` порівнюють через `is`.
- **Копіювання.** `copy.copy`, `list(a)` і зріз `a[:]` дають <T k="py-shallow-copy">поверхневу копію</T>: новий зовнішній контейнер з тими самими вкладеними об'єктами. `copy.deepcopy` копіює рекурсивно.

**Коли що обирати**

| Задача | Тип |
|---|---|
| Послідовність, яку змінюють | `list` |
| Запис фіксованої довжини, складений ключ | `tuple` |
| Пошук за ключем | `dict` |
| Унікальність, перевірка входження за O(1) | `set`, `frozenset` |

**Пастки**

- **Значення за замовчуванням** обчислюється один раз під час виконання `def`, тому `[]` або `{}` у ньому спільний для всіх викликів.
- **`[[0] * 3] * 3`** — три посилання на один внутрішній список: зміну одного рядка видно в усіх.
- **Кортеж зі змінюваним усередині.** У `t = ([1],)` не можна замінити `t[0]`, але `t[0].append(2)` працює, і такий кортеж нехешований.

**Правило**

Значення за замовчуванням — незмінні або `None`. Якщо функція змінює аргумент, це має бути видно з імені; інакше вона працює з копією.

**Підсумок:** присвоєння й передача у функцію ніколи не копіюють об'єкт — копію роблять явно.

</A>

<A l="s">

**Під капотом**

- Кожне значення — об'єкт у купі з вказівником на свій тип. Змінна зберігає лише посилання, тому значущих типів у сенсі C# немає: навіть `int` — об'єкт.
- Змінюваність задає тип. `int` і `str` незмінні, тому `x += 1` створює новий об'єкт і переприв'язує ім'я. Для `list` той самий `+=` викликає `__iadd__` і змінює список на місці.
- `dict` і `set` — хеш-таблиці. Якби ключ змінювався, його хеш застарів би й елемент «загубився». Тому `list`, `dict` і `set` нехешовані, а `tuple` хешований, лише якщо хешоване все всередині.

**Ціна**

- Кожна «зміна» незмінного об'єкта — нова алокація. Склеювання рядків через `+=` у циклі в гіршому разі квадратичне, `"".join(parts)` — лінійне.
- `list` зберігає посилання на об'єкти, а не самі числа: мільйон різних `int` у списку — мільйон об'єктів. Для числових даних є `array` і NumPy.
- `deepcopy` обходить увесь граф об'єктів і запам'ятовує вже скопійовані — на великих структурах це дорого.

**Компроміси**

- Незмінні об'єкти безпечно ділити між функціями й потоками, але кожна зміна — копія.
- Незмінні аналоги: `tuple`, `frozenset`, `@dataclass(frozen=True)`, `types.MappingProxyType`; із Python 3.15 є вбудований `frozendict`.
- Comprehension швидший за цикл з `append` і не випускає змінну циклу назовні, але три рівні вкладеності читаються гірше за звичайний цикл.

**Як перевірити в продакшені**

Змінювані значення за замовчуванням ловить лінтер: правило B006 у Ruff (з flake8-bugbear). Спільний вкладений об'єкт у налагоджувачі видає однаковий `id()`.

**Підсумок:** змінюваність — властивість типу, і від неї залежать хешованість, безпека спільного доступу та ціна змін.

</A>

<Ex>

```python
import copy

a = [1, 2]
b = a                  # друге ім'я для того самого списку
b.append(3)
print(a)               # [1, 2, 3]

def add(items, x):
    items.append(x)    # змінює об'єкт того, хто викликав
    items = [x]        # переприв'язує лише локальне ім'я

add(a, 4)
print(a)               # [1, 2, 3, 4]

grid = [[0], [0]]
shallow, deep = copy.copy(grid), copy.deepcopy(grid)
grid[0].append(1)
print(shallow[0], deep[0])                 # [0, 1] [0]
print([1, 2] == [1, 2], [1, 2] is [1, 2])  # True False
print([x * x for x in range(5) if x % 2 == 0])  # [0, 4, 16]

def bad(item, bucket=[]):  # список створено один раз, під час def
    bucket.append(item)
    return bucket

print(bad(1), bad(2))  # [1, 2] [1, 2]
```

- Чому `tuple` може бути ключем `dict`, а `list` — ні? — `tuple` незмінний і хешований, якщо хешований його вміст.

## Як влаштовані функції в Python?

<A short l="j">

Функція оголошується через `def` і сама є об'єктом: її можна передати аргументом, повернути або зберегти, як делегат у C#. `*args` збирає зайві позиційні аргументи в кортеж, а `**kwargs` — іменовані в словник.

</A>

<A short l="m">

Функція — об'єкт першого класу, і на цьому побудовані <T k="py-closure">замикання</T> та <T k="py-decorator">декоратори</T>: декоратор приймає функцію й повертає обгортку, а `functools.wraps` зберігає ім'я оригіналу. Параметри до `/` передаються лише за позицією, після `*` — <T k="py-keyword-only">лише за іменем</T>. Функція з `yield` стає <T k="py-generator">генератором</T> і віддає значення ліниво, а `with` з <T k="py-context-manager">контекстним менеджером</T> гарантує звільнення ресурсу, як `using` у C#.

</A>

<A short l="s">

Майже вся «магія» функцій — цукор над об'єктами й протоколами: `@d` — це `f = d(f)`, `with` — виклики `__enter__` і `__exit__`, генератор — об'єкт із замороженим кадром виконання. Замикання зберігає комірки зовнішніх змінних, а не їхні значення, тому лямбди в циклі бачать останнє значення. Ціна гнучкості — дорогі виклики: кожен шар декоратора — ще один виклик Python-функції, що помітно на гарячому шляху. Генератори економлять пам'ять на потоковій обробці, але одноразові: повторний прохід вичерпаним генератором мовчки нічого не дасть.

</A>

<A l="j">

**Що це**

Функція оголошується через `def` і повертає значення через `return`; без нього вона поверне `None`. Функція — звичайний об'єкт: її можна передати в `sorted(users, key=get_age)`.

**Як користуватися**

- Значення за замовчуванням: `def connect(host, port=5432)`.
- Виклик з іменами: `connect(port=6543, host="db")` — порядок не важливий.
- `*args` збирає зайві позиційні аргументи в кортеж, `**kwargs` — іменовані в словник.
- Розпакування під час виклику: `f(*items)` і `f(**options)`.
- `lambda` — анонімна функція з одного виразу: `key=lambda u: u.age`.

**Типова помилка**

Присвоїти значення глобальній змінній усередині функції без `global`. Присвоєння робить ім'я локальним для всієї функції, і читання до нього падає з `UnboundLocalError`.

**Підсумок:** функція — об'єкт, а `*args` і `**kwargs` роблять її сигнатуру гнучкою.

</A>

<A l="m">

**Як влаштовано**

- **Параметри.** У `def f(a, /, b, *, c)` `a` передається лише за позицією, `b` — як завгодно, `c` — лише за іменем. Параметри лише-іменовані рятують від плутанини прапорців: `send(msg, retry=True)`.
- **Області видимості.** Ім'я шукається в локальній, охопній, глобальній і вбудованій області (правило LEGB). `nonlocal` і `global` дозволяють переприв'язати зовнішнє ім'я.
- **Замикання.** Вкладена функція пам'ятає змінні охопної і після її завершення.
- **Декоратор.** `@logged` над `def f` — те саме, що `f = logged(f)`. `functools.wraps` копіює в обгортку `__name__` і `__doc__` та ставить `__wrapped__`.
- **Генератор.** Виклик функції з `yield` не виконує тіло, а повертає ітератор; кожен `next()` іде до наступного `yield`.
- **Контекстний менеджер.** `with` викликає `__enter__`, а наприкінці — `__exit__`, навіть у разі винятку. `@contextlib.contextmanager` будує менеджер із генератора.

**Пастки**

- **Пізнє зв'язування.** Лямбди з `[lambda: i for i in range(3)]` усі повернуть `2`: замикання бачить змінну, а не значення. Лікується параметром `lambda i=i: i`.
- **Вичерпаний генератор.** Другий `for` по ньому не виконається жодного разу.
- **Декоратор без `wraps`.** У логах і трасуваннях усі функції називаються `wrapper`.

**Правило**

Ресурси — через `with`, великі потоки даних — через генератори, наскрізну логіку — через декоратори з `functools.wraps`.

**Підсумок:** декоратори, генератори та `with` — цукор над функціями-об'єктами й протоколами.

</A>

<A l="s">

**Під капотом**

- Об'єкт функції зберігає `__code__` (байт-код), `__defaults__` і `__closure__` — кортеж комірок (cell) захоплених змінних. Комірка спільна для всіх вкладених функцій, тому `nonlocal` в одній видно в іншій.
- Значення за замовчуванням обчислюються один раз під час виконання `def` і лежать у `__defaults__`.
- Генератор зберігає власний кадр з локальними змінними й позицією. `yield` призупиняє кадр, `send()` відновлює його й передає значення всередину — на цьому історично побудували корутини.
- Якщо `__exit__` повертає істину, виняток із блоку `with` пригнічується.

**Ціна**

- Виклик Python-функції набагато дорожчий за виклик методу в C#: інтерпретатор створює кадр і розбирає аргументи, вбудовування (inlining), як у JIT .NET, немає.
- Кожен шар декоратора додає виклик і пакування `*args` і `**kwargs`.
- Генератор тримає в пам'яті один елемент, а не весь список — так обробляють файли й вибірки, які не вміщаються в пам'ять.

**Компроміси**

- Декоратор змінює поведінку непомітно з місця виклику: `@retry` над неідемпотентною операцією може повторити списання.
- Генератори ліниві: помилка джерела спливе там, де генератор читають, а не де створили.
- `contextlib.ExitStack` керує змінною кількістю ресурсів. Асинхронні версії (`async with`, `asynccontextmanager`) — у темі [asyncio і FastAPI](/sobes/uk/python/async-fastapi/).

**Як перевірити в продакшені**

`inspect.signature` і `__wrapped__` показують вихідну функцію за декораторами. Кількість і вартість викликів видно в `cProfile` або в py-spy без перезапуску процесу.

**Підсумок:** гнучкість функцій Python тримається на об'єктах і протоколах, а платою за неї стають дорогі виклики.

</A>

<Ex title="Замикання, декоратор і сигнатура">

```python
import functools

def counter():
    count = 0
    def inc():
        nonlocal count     # переприв'язати змінну зовнішньої функції
        count += 1
        return count
    return inc

c = counter()
c()
print(c())                 # 2

def logged(func):
    @functools.wraps(func)  # зберегти __name__, __doc__, __wrapped__
    def wrapper(*args, **kwargs):
        print(f"call {func.__name__} {args} {kwargs}")
        return func(*args, **kwargs)
    return wrapper

@logged                    # те саме, що scale = logged(scale)
def scale(x, /, *, factor=2):  # x — лише позиційний, factor — лише іменований
    return x * factor

print(scale(3, factor=10))  # call scale (3,) {'factor': 10}, потім 30
print(scale.__name__)       # scale
```

</Ex>

<Ex title="Генератор і контекстний менеджер">

```python
from contextlib import contextmanager

def numbers(n):
    for i in range(n):
        print(f"yield {i}")
        yield i            # пауза до наступного next()

gen = numbers(3)           # тіло ще не виконувалося
print(next(gen))           # yield 0, потім 0
print(sum(gen))            # yield 1, yield 2, потім 3

@contextmanager
def connection(name):
    print(f"open {name}")
    try:
        yield name.upper()  # значення для as
    finally:
        print(f"close {name}")  # виконається і в разі винятку

with connection("db") as conn:
    print(conn)            # open db, DB, close db
```

</Ex>

- Що поверне `[f() for f in [lambda: i for i in range(3)]]`? — `[2, 2, 2]`: замикання бачать змінну, а не значення на момент створення.
- Як написати декоратор з параметрами, наприклад `@retry(times=3)`? — Функція, яка повертає декоратор: три рівні вкладеності.
- Чим `yield from` відрізняється від циклу з `yield`? — Делегує підгенератору, прокидаючи `send()`, `throw()` і значення, що повертається.
- Чим генератор відрізняється від ітератора? — Генератор — ітератор, який Python будує з функції з `yield`.
- Що буде, якщо `__exit__` поверне `True`? — Виняток із блоку `with` буде пригнічено.

</Next>

<Q id="python.lang.oop-typing" level="m">

## Як влаштовані класи й типізація в Python?

<A short l="j">

Клас оголошується через `class`: конструктор — `__init__`, `self` — явне посилання на екземпляр, а <T k="py-dataclass">`@dataclass`</T> сам генерує `__init__`, `__repr__` і `__eq__` для класів-даних. Анотації типів на кшталт `x: int` інтерпретатор не перевіряє — їх читають IDE та <T k="py-type-checker">перевіряльники типів</T> на кшталт mypy.

</A>

<A short l="m">

Поведінку об'єкта задають <T k="py-dunder-method">dunder-методи</T>: `__eq__` — для `==`, `__len__` — для `len()`, `__iter__` — для `for`, тому власний клас вбудовується в мову без інтерфейсів. Python спирається на <T k="py-duck-typing">качину типізацію</T>, а <T k="py-protocol">`typing.Protocol`</T> описує її для перевіряльника: клас підходить, якщо має потрібні методи, без успадкування. Анотації на виконання не впливають, тому їхня цінність — у mypy або pyright у CI, а не в рантаймі.

</A>

<A short l="s">

Об'єктна модель Python динамічна: атрибути лежать у `__dict__`, методи шукаються за кожного звернення за <T k="py-mro">MRO</T>, а множинне успадкування узгоджується C3-лінеаризацією та кооперативним `super()`. Типізація поступова й зовнішня: рантайм анотації не перевіряє, але mypy або pyright у строгому режимі дають гарантії, близькі до C#, з номінальними класами та структурними `Protocol`. Із 3.12 generics пишуться прямо в сигнатурі: `def first[T](items: list[T]) -> T`. Компроміс того ж роду — `@dataclass(slots=True)`: менше пам'яті й швидший доступ, але без динамічних атрибутів.

</A>

<A l="j">

**Що це**

- Клас — шаблон об'єкта, як у C#. Екземпляр створюється викликом класу без `new`: `user = User("Ann")`.
- `__init__` — ініціалізатор, `self` — перший параметр кожного методу екземпляра.
- Модифікаторів доступу немає: `_name` — домовленість «внутрішнє».

**Як користуватися**

- `@property` робить метод обчислюваним атрибутом: `circle.diameter` без дужок, як властивість у C#.
- `@classmethod` отримує клас `cls` — так пишуть альтернативні конструктори: `Rect.square(2)`.
- `@staticmethod` не отримує ні `self`, ні `cls`.
- Анотації: `def total(items: list[float]) -> float`; «може бути `None`» — `str | None` (із 3.10).

**Типова помилка**

Оголосити змінюваний атрибут на рівні класу: `class Cart: items = []`. Такий список спільний для всіх екземплярів; поля екземпляра задають в `__init__`.

**Підсумок:** клас у Python схожий на клас C#, але доступ тримається на домовленостях, а типи — підказки для інструментів.

</A>

<A l="m">

**Як влаштовано**

- **Dunder-методи.** Оператори й вбудовані функції викликають спеціальні методи: `a + b` — `a.__add__(b)`, `len(x)` — `x.__len__()`. Це аналог перевантаження операторів та `IEquatable` у C#.
- **Успадкування.** Дозволене множинне. Порядок пошуку методів — MRO (`Cls.__mro__`), і `super()` викликає наступний клас у ньому, не обов'язково батьківський.
- **Duck typing і Protocol.** Функції важливі методи об'єкта, а не ім'я його типу. `Protocol` описує такий контракт структурно: клас сумісний без успадкування.
- **Анотації.** Зберігаються в `__annotations__`; перевіряють їх mypy і pyright, а не інтерпретатор.

**Коли що обирати**

| Задача | Інструмент |
|---|---|
| Дані з рівністю за значенням | `@dataclass`, незмінні — `frozen=True` |
| Контракт без успадкування | `typing.Protocol` |
| Спільна реалізація, обов'язкові методи | базовий клас, `abc.ABC` |
| Перевірка зовнішніх даних | Pydantic — у темі [asyncio і FastAPI](/sobes/uk/python/async-fastapi/) |

**Пастки**

- **`__eq__` без `__hash__`.** Визначивши `__eq__`, ви робите клас нехешованим: Python ставить `__hash__ = None`. Так само поводиться `@dataclass` без `frozen=True`.
- **`isinstance` з Protocol** працює лише з `@runtime_checkable` і перевіряє тільки наявність методів, не сигнатури.
- **`Optional[X]`** означає «може бути `None`», а не «необов'язковий параметр». Сучасний запис — `X | None`.

**Правило**

Публічні функції анотуйте повністю й запускайте mypy або pyright у CI. Дані — `@dataclass`, контракти — `Protocol`.

**Підсумок:** клас вбудовується в мову через dunder-методи, а типізація — зовнішній шар, який перевіряють інструменти.

</A>

<A l="s">

**Під капотом**

- Атрибути екземпляра лежать у словнику `__dict__`. `__slots__` або `@dataclass(slots=True)` (із 3.10) замінюють його фіксованими слотами: менше пам'яті й швидший доступ, але нові атрибути додати не можна.
- `@property`, `@classmethod` і `@staticmethod` — дескриптори: об'єкти з `__get__`, які перехоплюють доступ до атрибута класу.
- MRO будується C3-лінеаризацією: нащадок раніше за предків, порядок базових класів з оголошення зберігається. Неузгоджувана ієрархія — `TypeError` під час оголошення класу.
- Із 3.14 анотації обчислюються ліниво (PEP 649): посилання на ще не оголошені класи не треба брати в лапки.

**Порівняння з C#**

| C# | Python |
|---|---|
| Номінальні інтерфейси | `Protocol` — структурний, `abc.ABC` — номінальний |
| Generics існують у рантаймі | параметри стираються: `list[int]` у рантаймі — просто `list` |
| `where T : IComparable<T>` | `def f[T: Comparable]` (PEP 695, 3.12+) |
| Помилку типів відхиляє компілятор | помилку знаходить mypy або pyright, рантайм її пропустить |

До 3.12 параметри типу оголошували через `TypeVar` і `Generic[T]`. Синонім типу — `type Pair[T] = tuple[T, T]`, значення за замовчуванням для параметрів типу — із 3.13 (PEP 696).

**Компроміси**

- Слоти економлять пам'ять на кожному об'єкті; на мільйонах дрібних об'єктів це помітно, але виграш варто виміряти (`tracemalloc`).
- Глибокі ієрархії з `super()` за MRO важко читати. Композиція та `Protocol` зазвичай простіші.

**Як перевірити в продакшені**

mypy `--strict` або pyright у режимі `strict` у CI; `reveal_type(x)` показує виведений тип. У рантаймі типи перевіряє лише явна валідація: Pydantic або `isinstance`.

**Підсумок:** Python дає типізацію рівня C# як зовнішній інструмент поверх динамічної моделі об'єктів — гарантії є рівно там, де працює перевіряльник.

</A>

<Ex>

```python
from dataclasses import dataclass
from typing import Protocol

class Shape(Protocol):
    def area(self) -> float: ...

@dataclass(frozen=True, slots=True)
class Rect:
    w: float
    h: float

    def area(self) -> float:
        return self.w * self.h

class Circle:              # не успадковує Shape, але підходить за структурою
    def __init__(self, r: float) -> None:
        self.r = r

    @property
    def diameter(self) -> float:  # обчислюваний атрибут без дужок
        return self.r * 2

    def area(self) -> float:
        return 3.14 * self.r ** 2

def total(shapes: list[Shape]) -> float:
    return sum(s.area() for s in shapes)

print(Rect(2, 3), Rect(2, 3) == Rect(2, 3))  # Rect(w=2, h=3) True
print(Circle(1).diameter)                    # 2
print(total([Rect(2, 3), Circle(1)]))        # 9.14
```

</Ex>

```python
class Base:
    def save(self):
        print("Base")

class Audit(Base):
    def save(self):
        print("Audit")
        super().save()     # наступний клас у MRO, не обов'язково батьківський

class Cache(Base):
    def save(self):
        print("Cache")
        super().save()

class Repo(Audit, Cache):
    pass

Repo().save()                              # Audit, Cache, Base
print([c.__name__ for c in Repo.__mro__])  # ['Repo', 'Audit', 'Cache', 'Base', 'object']
```

<Q id="python.lang.internals" level="s">

## Як Python керує пам'яттю і що таке GIL?

<A short l="j">

Python звільняє пам'ять сам: кожен об'єкт має <T k="py-reference-counting">лічильник посилань</T>, і об'єкт видаляється, щойно посилань не лишилося. <T k="py-gil">GIL</T> — глобальне блокування інтерпретатора CPython: Python-код у кожен момент виконує лише один потік, тому потоки не прискорюють обчислення.

</A>

<A short l="m">

CPython видаляє об'єкт одразу, коли його лічильник посилань падає до нуля, а цикли посилань знаходить окремий <T k="py-cyclic-gc">циклічний збирач</T> з поколіннями. GIL пускає виконувати байт-код лише один потік, тому потоки допомагають під час очікування введення-виведення, яке відпускає GIL, але не під час обчислень. CPU-задачі прискорюють процеси, NumPy або <T k="py-c-extension">C-розширення</T>, які відпускають GIL на час роботи.

</A>

<A short l="s">

Підрахунок посилань дає детерміноване звільнення, але вимагає захисту лічильників від гонок — цю роль і відіграє GIL, одне блокування на весь інтерпретатор. <T k="py-free-threading">Free-threaded збірка</T> (PEP 703) прибирає GIL: у 3.13 вона експериментальна, із 3.14 офіційно підтримується, але й у 3.15 лишається окремою збіркою, а не типовою. Ціна — кілька відсотків на однопотоковому коді й вимога, щоб C-розширення були позначені як сумісні, інакше GIL увімкнеться знову. Тому стандартний шлях для CPU-задач — як і раніше винести гарячий цикл у NumPy, нативне розширення або процеси.

</A>

<A l="j">

**Що це**

- **Керування пам'яттю.** Явно звільняти пам'ять не треба. Кожен об'єкт має лічильник посилань: імена, елементи списків, атрибути. Коли він падає до нуля, об'єкт видаляється одразу.
- **GIL** (Global Interpreter Lock) — блокування в CPython, стандартній реалізації Python. Байт-код у кожен момент виконує лише один потік.

**Навіщо це знати**

- Потоки (`threading`) корисні для очікування: мережа, диск, база. Поки потік чекає, GIL вільний для інших.
- Обчислення на CPU потоки не прискорюють. Для них беруть процеси або бібліотеки на C на кшталт NumPy.

**Типова помилка**

Запускати важкі обчислення в `ThreadPoolExecutor` і чекати прискорення за кількістю ядер. З GIL час лишиться тим самим або навіть зросте.

**Підсумок:** пам'ять звільняє лічильник посилань, а GIL пускає виконувати Python-код лише один потік за раз.

</A>

<A l="m">

**Як влаштовано**

1. Присвоєння, передача у функцію, додавання до списку збільшують лічильник посилань об'єкта, видалення посилання — зменшує.
2. За нуля CPython одразу викликає `__del__`, якщо він є, і звільняє пам'ять.
3. Цикли (`a.peer = b`, `b.peer = a`) лічильник не звільнить. Їх знаходить модуль `gc`: він періодично обходить об'єкти-контейнери за трьома поколіннями й видаляє недосяжні групи.
4. Потік, що тримає GIL, віддає його тим, хто чекає, приблизно раз на 5 мс (`sys.getswitchinterval()`) і завжди — на блокувальному введенні-виведенні.

**Коли що обирати**

| Навантаження | Рішення |
|---|---|
| Очікування: HTTP, база, файли | потоки або asyncio |
| Обчислення на чистому Python | процеси: `ProcessPoolExecutor` |
| Числові масиви | NumPy: цикл іде в C |
| Важке ядро алгоритму | C-розширення, Cython, Rust через PyO3 |

**Пастки**

- **`is` для чисел і рядків.** CPython кешує цілі від −5 до 256 та <T k="py-interning">інтернує</T> частину рядків, тому `is` для них іноді «працює». Це деталь реалізації — значення порівнюють через `==`.
- **GIL не робить код потокобезпечним.** `counter += 1` — кілька інструкцій байт-коду, і потік може перемкнутися між ними. Потрібен `threading.Lock`.
- **Об'єкти в циклі** живуть до проходу збирача, і момент виклику їхнього `__del__` непередбачуваний.

**Правило**

Спершу з'ясуйте, у що впирається задача — в очікування чи в CPU. Докладне порівняння потоків, процесів і asyncio — у темі [asyncio і FastAPI](/sobes/uk/python/async-fastapi/).

**Підсумок:** лічильник посилань звільняє майже все одразу, `gc` дочищає цикли, а GIL обмежує паралельність Python-коду, але не введення-виведення.

</A>

<A l="s">

**Під капотом**

- Із 3.12 (PEP 683) `None`, `True`, малі цілі та інші службові об'єкти безсмертні: їхній лічильник посилань не змінюється.
- GIL захищає лічильники й внутрішні структури інтерпретатора одним блокуванням. Це дешево для однопотокового коду й спрощує C-розширення.
- Free-threaded збірка замінює GIL зміщеним підрахунком посилань (biased reference counting) і блокуваннями на рівні об'єктів. Статус: 3.13 — експериментальна, 3.14 — офіційно підтримується (PEP 779), 3.15 — як і раніше окрема збірка `python3.15t`. Імпорт C-розширення без позначки про підтримку знову вмикає GIL.
- JIT-компілятор (PEP 744) з'явився в 3.13 як експериментальний. Із 3.14 він є в офіційних збірках для Windows і macOS, але вмикається вручну (`PYTHON_JIT=1`) і прискорює код на відсотки, а не в рази.

**Ціна**

- Об'єкт важкий: `sys.getsizeof(1)` — 28 байт, плюс 8 байт на посилання в списку. Масив NumPy зберігає голі значення поспіль.
- Однопотоковий оверхед free-threaded збірки — за документацією від ~1 % до ~8 % залежно від платформи.
- Цикл на чистому Python часто в десятки разів повільніший за аналог на C#.

**Компроміси**

- Процеси обходять GIL, але платять серіалізацією даних (pickle) і пам'яттю на копію інтерпретатора.
- NumPy і багато C-розширень відпускають GIL усередині важких операцій, тому потоки поверх них масштабуються.
- `gc.freeze()` перед `fork` прибирає наявні об'єкти з обходу збирача, і дочірні процеси довше ділять сторінки пам'яті.

**Як перевірити в продакшені**

- py-spy знімає профіль запущеного процесу без перезапуску; прапорець `--gil` лишає тільки потоки, що тримають GIL.
- `tracemalloc` показує, де виділялася пам'ять; `sys._is_gil_enabled()` (3.13+) — чи ввімкнено GIL.

**Підсумок:** CPython платить за простоту підрахунку посилань і GIL повільним однопотоковим кодом; прискорюють його, виносячи гарячий цикл з інтерпретатора, а free-threading і JIT поки змінюють картину лише частково.

</A>

```python
import gc
import sys

data = []
before = sys.getrefcount(data)

class Node:
    def __init__(self):
        self.peer = None

a, b = Node(), Node()
a.peer, b.peer = b, a                # цикл: лічильники не впадуть до нуля
del a, b
print(gc.collect() > 0)              # True: циклічний збирач знайшов цикл

print(int("257") is int("257"))      # False: два різні об'єкти

s1 = "".join(["py", "thon"])
s2 = "".join(["py", "thon"])
print(s1 == s2, s1 is s2)            # True False
```
