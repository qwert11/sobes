## Що таке O-нотація і як оцінити складність коду?

<A short l="j">

<T k="big-o">O-нотація</T> описує, як зростає час роботи або витрата пам'яті алгоритму зі зростанням розміру входу n, без урахування констант. Тому один прохід масивом — O(n), два вкладені цикли по ньому — O(n²), а пошук поділом діапазону навпіл — O(log n).

</A>

<A short l="m">

O-нотація — верхня межа зростання роботи зі зростанням n; час і <T k="space-complexity">пам'ять</T> оцінюють окремо й уточнюють випадок: <T k="worst-case">найгірший</T>, середній чи <T k="amortized-complexity">амортизований</T>. Правила прості: послідовні блоки додаються й лишається старший член, вкладені цикли перемножуються, константи відкидаються. Ціна — O приховує константи, тому на малих n асимптотично гірше рішення буває швидшим.

</A>

<A short l="s">

Формально f(n) = O(g(n)), якщо починаючи з деякого n виконується f(n) ≤ c·g(n); на співбесіді під O зазвичай мають на увазі точну оцінку, тобто Θ. Складність рекурсії виводять із рекурентного співвідношення, наприклад через <T k="master-theorem">основну теорему</T>: T(n) = 2T(n/2) + O(n) дає O(n log n). Окремо шукають приховану складність викликів: `string +=` у циклі, `List<T>.Insert(0, x)`, LINQ усередині циклу. Асимптотика — перший фільтр, а вибір між добрими варіантами вирішує вимірювання.

</A>

<A l="j">

**Що це**

O(f(n)) показує форму зростання, а не секунди: у скільки разів зросте робота, якщо зросте вхід. Збільшили n у 10 разів — O(n) працює в 10 разів довше, O(n²) — у 100 разів.

**Типові класи**

| Складність | Назва | Приклад |
|---|---|---|
| O(1) | константна | елемент масиву за індексом |
| O(log n) | логарифмічна | бінарний пошук |
| O(n) | лінійна | один прохід масивом |
| O(n log n) | лінійно-логарифмічна | сортування `Array.Sort` |
| O(n²) | квадратична | усі пари елементів |
| O(2^n) | експоненційна | перебір усіх підмножин |

**Як оцінити**

1. Цикл по n елементах — n × вартість тіла.
2. Вкладені цикли перемножуються: два по n — O(n²).
3. Послідовні блоки додаються, лишається старший: O(n) + O(n²) = O(n²).
4. Константи відкидаються: два проходи — O(2n) = O(n).
5. Діапазон ділиться навпіл на кожному кроці — O(log n).

**Типова помилка**

Вважати код без вкладених циклів лінійним. `list.Insert(0, x)` або `s += x` у циклі самі коштують O(n), і весь цикл — O(n²).

**Підсумок:** O показує, як зростає робота зі зростанням входу, а не скільки мілісекунд вона триватиме.

</A>

<A l="m">

**Як влаштовано**

Час і пам'ять оцінюють окремо. Пам'ять — додаткова, без самого входу: прохід із `HashSet<T>` коштує O(n) пам'яті, подвійний цикл — O(1).

| Випадок | Що означає | Приклад |
|---|---|---|
| Найгірший | межа для будь-якого входу | quicksort на невдалих опорних — O(n²) |
| Середній | очікування на типовому вході | пошук у хеш-таблиці — O(1) |
| Амортизований | середнє на серії операцій | `List<T>.Add` — O(1) |

Амортизована оцінка — не про ймовірність. Це гарантія для будь-якої серії: рідкісні дорогі операції оплачені багатьма дешевими.

**Пастки**

- **Прихована вартість виклику.** `string +=` копіює рядок, `List<T>.Remove` зсуває елементи — кожен виклик O(n).
- **Два параметри.** Цикл по n замовленнях і вкладений по m товарах — O(n·m), а не O(n²).
- **Рекурсія витрачає пам'ять.** Глибина d займає O(d) стека, навіть без колекцій.
- **Повторний перебір.** `Count()` у лінивого `IEnumerable<T>` усередині циклу щоразу проходить послідовність заново.

**Правило**

Для кожного рішення називайте дві оцінки — час і пам'ять — і уточнюйте, який випадок маєте на увазі.

**Підсумок:** складність — це пара «час і пам'ять» із зазначенням випадку: найгірший, середній чи амортизований.

</A>

<A l="s">

**Під капотом**

- O — верхня межа, Ω — нижня, Θ — точна. Сортування порівняннями в найгіршому випадку не швидше за Ω(n log n).
- Рекурсію оцінюють рекурентним співвідношенням. Бінарний пошук: T(n) = T(n/2) + O(1), це O(log n). Mergesort: T(n) = 2T(n/2) + O(n), це O(n log n).
- Наївна рекурсія Фібоначчі породжує експоненційну кількість викликів: кожна гілка ділиться на дві.

**Ціна**

- O приховує константи: алокації, промахи кешу процесора, виклики делегатів.
- На малих n вирішують константи. Тому `Array.Sort` сортує ділянки до 16 елементів вставками, хоча це O(n²).

**Компроміси**

- **Час проти пам'яті.** `HashSet<T>` перетворює O(n²) на O(n) ціною O(n) пам'яті. Передобчислення — індекс, префіксні суми — переносить роботу в підготовку.
- **Найгірший випадок на чужому вводі.** Зловмисник підбирає вхід під найгірший випадок: колізії хешів, катастрофічний відкат регулярного виразу. Для регулярних виразів із .NET 7 є `RegexOptions.NonBacktracking` з лінійним часом за довжиною входу.

**Як перевірити в продакшені**

<T k="benchmarkdotnet">BenchmarkDotNet</T> з `[Params]` на кількох n показує форму зростання: час зріс у 4 рази при подвоєнні n — квадратичний алгоритм. Гарячий метод знаходять у трасі dotnet-trace або PerfView.

**Підсумок:** асимптотика відсікає погані рішення, а вибір між добрими роблять константи, пам'ять і заміри.

</A>

<Ex>

```csharp
int[] data = [3, 8, 1, 9, 4, 8];

Console.WriteLine(HasDuplicatesPairs(data));  // True
Console.WriteLine(HasDuplicatesHashSet(data)); // True
Console.WriteLine(HasDuplicatesSorted(data));  // True

// Усі пари: час O(n²), пам'ять O(1)
static bool HasDuplicatesPairs(int[] a)
{
    for (int i = 0; i < a.Length; i++)
        for (int j = i + 1; j < a.Length; j++) // n(n-1)/2 порівнянь
            if (a[i] == a[j]) return true;
    return false;
}

// Один прохід: час O(n) у середньому, пам'ять O(n)
static bool HasDuplicatesHashSet(int[] a)
{
    var seen = new HashSet<int>();
    foreach (int x in a)
        if (!seen.Add(x)) return true; // Add поверне false для повтору
    return false;
}

// Сортування копії та сусіди: час O(n log n), пам'ять O(n) на копію
static bool HasDuplicatesSorted(int[] a)
{
    int[] copy = [.. a];
    Array.Sort(copy);
    for (int i = 1; i < copy.Length; i++)
        if (copy[i] == copy[i - 1]) return true;
    return false;
}
```

Три рішення однієї задачі — три різні компроміси між часом і пам'яттю. Якщо сортувати на місці, пам'ять O(1), але зіпсується масив того, хто викликає.

</Ex>

- Чим амортизована складність відрізняється від середньої? — Амортизована гарантована для будь-якої серії операцій, середня залежить від розподілу входів.
- Яка складність двох послідовних циклів по n? — O(n): O(n) + O(n) = O(2n), константа відкидається.
- Яка складність `s += x` у циклі на n ітерацій? — O(n²) за сумарною довжиною копіювань; рішення — `StringBuilder` або `string.Join`.
- Чому O(n) може програти O(n²) на практиці? — Константи й малі n: алокації та промахи кешу важать більше за асимптотику.
- Як оцінити рекурсію? — Записати рекурентне співвідношення й розв'язати його: деревом рекурсії або основною теоремою.

</Next>

<Q id="basics.algo.structures" level="j">

## Які структури даних треба знати і для чого кожна?

<A short l="j">

Структура даних — спосіб організувати дані під потрібні операції: масив дає елемент за індексом, <T k="hash-table">хеш-таблиця</T> — значення за ключем, стек і черга — порядок обробки, дерево — впорядковані ключі, купа — швидкий мінімум, граф — зв'язки між об'єктами. Для більшості в .NET є готовий тип, тому на співбесіді називають і структуру, і клас.

</A>

<A short l="m">

Структури різняться набором швидких операцій: <T k="linked-list">зв'язаний список</T> вставляє за O(1) за відомим вузлом, але шукає за O(n), <T k="binary-search-tree">дерево пошуку</T> тримає ключі впорядкованими з операціями за O(log n), а <T k="binary-heap">купа</T> віддає мінімум за O(log n) — це `PriorityQueue<TElement, TPriority>` із .NET 6. Вибір починається з питання «яка операція найчастіша». Ціна — пам'ять і повільні інші операції.

</A>

<A short l="s">

Структура даних — це гарантії операцій плюс представлення в пам'яті, і в продакшені друге важить не менше: масиви неперервні, а вузлові структури алокують об'єкт на елемент. У BCL немає <T k="graph">графа</T> — його зберігають <T k="adjacency-list">списками суміжності</T> на `Dictionary`. `PriorityQueue` не вміє змінювати пріоритет, а `Remove` (.NET 9) у неї лінійний, тому в алгоритмі Дейкстри кладуть дублікати й пропускають застарілі записи. Для top-k купа розміру k дає O(n log k) замість O(n log n) у повного сортування.

</A>

<A l="j">

**Що це**

- **Стек** — LIFO: останнім поклали, першим узяли. **Черга** — FIFO: першим прийшов, першим пішов.
- **Дерево пошуку** зберігає ключі за порядком, **купа** завжди знає мінімальний елемент.
- **Граф** — вершини й ребра: дороги, залежності, зв'язки між людьми.

**Як користуватися**

| Структура | Тип .NET | Типова задача |
|---|---|---|
| Масив | `T[]`, `List<T>` | дані за індексом |
| Стек | `Stack<T>` | дужки, скасування дій, обхід у глибину |
| Черга | `Queue<T>` | задачі за порядком, обхід у ширину |
| Хеш-таблиця | `Dictionary`, `HashSet<T>` | пошук, підрахунок, дублі |
| Дерево пошуку | `SortedSet<T>`, `SortedDictionary` | порядок, мінімум, діапазони |
| Купа | `PriorityQueue<TElement, TPriority>` | задачі за пріоритетом, top-k |

**Типова помилка**

Писати свою структуру на співбесіді, коли є готова. Інтерв'юер зазвичай чекає `Stack<T>` або `PriorityQueue`, а не саморобний клас, якщо не просить інакше.

**Підсумок:** структуру обирають за операцією, яку треба виконувати швидко.

</A>

<A l="m">

**Як влаштовано**

| Структура | Пошук | Вставка й видалення |
|---|---|---|
| Масив, `List<T>` | за індексом O(1), за значенням O(n) | у кінець O(1) аморт., у середину O(n) |
| `LinkedList<T>` | O(n) | O(1) за відомим вузлом |
| `Stack<T>`, `Queue<T>` | лише вершина або голова, O(1) | O(1) аморт. |
| `Dictionary`, `HashSet<T>` | O(1) у середньому | O(1) у середньому |
| `SortedSet<T>`, `SortedDictionary` | O(log n) | O(log n) |
| `PriorityQueue` | мінімум O(1) | O(log n) |

**Дерево й купа**

- **Дерево пошуку.** Пошук спускається від кореня: менше — ліворуч, більше — праворуч. Вартість дорівнює висоті дерева. Без балансування відсортований ввід витягує дерево в список і дає O(n), тому в .NET використовується збалансоване <T k="red-black-tree">червоно-чорне дерево</T>.
- **Купа.** Дерево в масиві, де батько не більший за нащадків, тому мінімум лежить у корені. Вставка піднімає елемент угору, вилучення опускає новий корінь донизу — O(log n).

**Пастки**

- `PriorityQueue` не зберігає порядок вставки при рівних пріоритетах, а `UnorderedItems` перебирає елементи не за пріоритетом.
- `Stack<T>` перебирається від вершини, а не в порядку додавання.
- Будова `Dictionary` і ціна хешування — у темі [Колекції та LINQ](/sobes/uk/dotnet/collections-linq/).

**Правило**

Назвіть домінантну операцію задачі — структура випливає з неї: пошук за ключем — хеш-таблиця, порядок — дерево, мінімум — купа, порядок обробки — стек або черга.

**Підсумок:** кожна структура пришвидшує свої операції коштом інших, і вибір — це відповідь на питання «що робимо найчастіше».

</A>

<A l="s">

**Під капотом**

- `PriorityQueue<TElement, TPriority>` — 4-арна мін-купа на масиві: дерево нижче за двійкове, а діти одного вузла лежать поруч у пам'яті.
- Операції «змінити пріоритет» немає. `Remove` із .NET 9 шукає елемент лінійно, O(n).
- Граф зберігають списками суміжності, `Dictionary<int, List<int>>`: пам'ять O(V + E). Матриця суміжності `bool[,]` перевіряє ребро за O(1), але займає O(V²) — вона для щільних графів.

**Ціна**

- Вузлові структури (`LinkedList<T>`, `SortedSet<T>`) створюють об'єкт на елемент: алокація, заголовок, посилання, розкид по купі.
- Масивні структури (`List<T>`, `Queue<T>`, `PriorityQueue`) зберігають елементи поспіль і краще влучають у кеш процесора.

**Компроміси**

| Задача | Варіант | Ціна |
|---|---|---|
| top-k з n | `PriorityQueue` розміру k | O(n log k) замість O(n log n) |
| Дейкстра | `PriorityQueue` з дублікатами | зайві записи, пропуск застарілих |
| Дейкстра з видаленням | `SortedSet` пар (відстань, вершина) | O(log n) на видалення, але вузли |
| Рідкісні вставки у впорядковане | відсортований `List<T>` і `BinarySearch` | вставка O(n), зате неперервна пам'ять |

**Як перевірити в продакшені**

Кількість вузлових об'єктів видно в `dotnet-gcdump`. Вибір між двома структурами на реальних обсягах підтверджують BenchmarkDotNet з `[MemoryDiagnoser]`.

**Підсумок:** асимптотика задає вибір структури, а представлення в пам'яті й відсутні операції визначають, як вона поведеться в продакшені.

</A>

<Ex>

```csharp
// Купа: першим виходить найменший пріоритет
var tasks = new PriorityQueue<string, int>();
tasks.Enqueue("deploy", 2);
tasks.Enqueue("hotfix", 1);
tasks.Enqueue("refactor", 3);
Console.WriteLine(tasks.Dequeue()); // hotfix — O(log n)

// Дерево пошуку: порядок, мінімум і діапазони
var prices = new SortedSet<int> { 50, 10, 40, 20, 30 };
Console.WriteLine(prices.Min);                                      // 10
Console.WriteLine(string.Join(",", prices.GetViewBetween(15, 40))); // 20,30,40

// Стек: перевірка дужок — класична задача
Console.WriteLine(IsBalanced("([]{})")); // True
Console.WriteLine(IsBalanced("(]"));     // False

static bool IsBalanced(string s)
{
    var stack = new Stack<char>();
    foreach (char c in s)
    {
        if (c is '(' or '[' or '{') stack.Push(c);
        else if (stack.Count == 0 || stack.Pop() != Opening(c)) return false;
    }
    return stack.Count == 0; // незакриті дужки — теж помилка
}

static char Opening(char close) => close switch { ')' => '(', ']' => '[', _ => '{' };
```

</Ex>

<Next>

- Як влаштована купа і чому мінімум за O(1)? — Батько не більший за нащадків, мінімум завжди в корені; вилучення — O(log n).
- Чому дерево пошуку в .NET збалансоване? — Інакше відсортований ввід перетворює його на список, і операції стають O(n).
- Як зберігати граф у C#? — Списки суміжності `Dictionary<T, List<T>>`; матриця суміжності — для щільних графів.
- Як знайти k найбільших елементів із мільйона? — Купа розміру k: O(n log k) часу й O(k) пам'яті.
- Чи зберігає `PriorityQueue` порядок при рівних пріоритетах? — Ні; потрібен FIFO — додайте до пріоритету порядковий номер.

<Q id="basics.algo.sorting-searching" level="m">

## Які алгоритми сортування й пошуку варто знати?

<A short l="j">

<T k="binary-search">Бінарний пошук</T> знаходить елемент у відсортованому масиві за O(log n), на кожному кроці відкидаючи половину діапазону; лінійний пошук працює на будь-якому масиві, але за O(n). Сортування порівнянням у кращому разі працюють за O(n log n), і в .NET своє не пишуть: `Array.Sort` і `List<T>.Sort` сортують на місці, а `OrderBy` повертає нову послідовність.

</A>

<A short l="m">

Базові сортування — <T k="quicksort">quicksort</T> (у середньому O(n log n), у найгіршому O(n²), на місці), <T k="merge-sort">сортування злиттям</T> (завжди O(n log n), <T k="stable-sort">стабільне</T>, але O(n) пам'яті) і <T k="heapsort">пірамідальне</T> (O(n log n) без додаткової пам'яті, нестабільне). `Array.Sort` і `List<T>.Sort` використовують гібрид <T k="introsort">introsort</T> і нестабільні, а `OrderBy` стабільний. Тому сортування за кількома ключами роблять через `OrderBy(...).ThenBy(...)` або компаратором із додатковим ключем.

</A>

<A short l="s">

Introsort — quicksort, який на ділянках до 16 елементів перемикається на вставки, а за надто глибокого розбиття — на heapsort; так найгірший випадок лишається O(n log n) без додаткового буфера. Ціна — нестабільність, а стабільний `OrderBy` платить пам'яттю: буфер елементів, масив ключів і карта індексів. Бінарний пошук виглядає простим, але помилки на межах і переповнення в `(lo + hi) / 2` роками жили навіть у стандартних бібліотеках. Тому на співбесіді пишуть один перевірений шаблон і проганяють його на крайових випадках.

</A>

<A l="j">

**Що це**

- **Лінійний пошук** перевіряє елементи по черзі: O(n), працює на будь-якому масиві.
- **Бінарний пошук** вимагає відсортованого масиву й ділить діапазон навпіл: O(log n). Мільйон елементів — не більше 20 кроків.

**Як працює бінарний пошук**

1. Межі: `lo = 0`, `hi = n - 1`.
2. Середина: `mid = lo + (hi - lo) / 2`.
3. `a[mid] == target` — знайшли.
4. `a[mid] < target` — шукаємо правіше: `lo = mid + 1`. Інакше лівіше: `hi = mid - 1`.
5. Повторюємо, поки `lo <= hi`. Межі розійшлися — елемента немає.

**Як користуватися**

- Сортування: `Array.Sort(array)`, `list.Sort()`, `items.OrderBy(x => x.Name)`.
- Пошук: `Array.BinarySearch` і `List<T>.BinarySearch`. Якщо елемента немає, вони повертають від'ємне число, а `~result` — індекс, куди його вставити.

**Типова помилка**

Викликати бінарний пошук на невідсортованому масиві. Винятку не буде — просто хибна відповідь.

**Підсумок:** бінарний пошук — O(log n), але лише на відсортованих даних; сортування беруть із бібліотеки.

</A>

<A l="m">

**Як влаштовано**

| Алгоритм | Час | Пам'ять і стабільність |
|---|---|---|
| Вставками | O(n²), майже O(n) на майже відсортованих | O(1), стабільне |
| Quicksort | O(n log n) у середньому, O(n²) у найгіршому | O(log n) стека, нестабільне |
| Злиттям | O(n log n) завжди | O(n), стабільне |
| Пірамідальне | O(n log n) завжди | O(1), нестабільне |

Стабільне сортування зберігає початковий порядок рівних елементів. Це важливо, коли сортують дані, уже впорядковані за іншим полем.

**Що використовує .NET**

| Метод | Алгоритм | Стабільність |
|---|---|---|
| `Array.Sort`, `List<T>.Sort`, `Span<T>.Sort()` | introsort на місці | ні |
| `OrderBy`, `ThenBy` (LINQ) | сортування в буфері | так |

**Пастки**

- **Межі пошуку.** Змішали `lo < hi` з `hi = mid - 1` або `lo <= hi` з `hi = mid` — пропуск елемента або нескінченний цикл.
- **Дублі.** `Array.BinarySearch` повертає індекс одного з рівних, не обов'язково першого. Для першого входження потрібен варіант «нижня межа».
- **Компаратор `a - b`.** Переповнюється на великих числах. Використовуйте `a.CompareTo(b)`.

**Правило**

Своє сортування в робочому коді не пишуть. Потрібна стабільність — `OrderBy` або компаратор із додатковим ключем. Бінарний пошук перевіряють на порожньому масиві, одному елементі та елементах на краях.

**Підсумок:** `Array.Sort` швидкий і нестабільний, `OrderBy` стабільний і дорожчий за пам'яттю, а бінарний пошук ламається на межах.

</A>

<A l="s">

**Під капотом**

Introsort в `Array.Sort`, за документацією:

1. Ділянка до 16 елементів — сортування вставками.
2. Кількість розбиттів перевищила 2·log n — пірамідальне сортування.
3. Інакше — quicksort.

Так quicksort захищений від найгіршого випадку O(n²). .NET Framework 4 і раніші версії використовували чистий quicksort.

**Ціна**

- `Array.Sort` для примітивів без компаратора не викликає делегат на кожне порівняння. З `Comparison<T>` кожне порівняння — непрямий виклик.
- `OrderBy` копіює елементи в буфер, обчислює масив ключів і сортує індекси — O(n) додаткової пам'яті.
- Нижня межа Ω(n log n) діє лише для сортувань порівнянням. Підрахунком або порозрядно цілі числа з малого діапазону сортують за O(n + k).

**Компроміси**

- **Повне сортування чи часткове.** Потрібні k мінімальних — купа за O(n log k) дешевша за сортування за O(n log n).
- **Сортування чи хеш.** Разовий пошук у невідсортованих даних — лінійний прохід. Багато пошуків — сортування плюс бінарний пошук або `HashSet<T>`.
- **Дані не вміщаються в пам'ять.** Зовнішнє сортування злиттям: сортують шматки й зливають. Так сортує й СКБД, коли бракує пам'яті.

**Як перевірити в продакшені**

BenchmarkDotNet з `[MemoryDiagnoser]` на реальних даних порівнює `Array.Sort` і `OrderBy`: різницю в алокаціях видно одразу.

**Підсумок:** introsort дає O(n log n) у найгіршому випадку без буфера ціною стабільності, і вибір методу сортування — це вибір між стабільністю та пам'яттю.

</A>

<Ex>

```csharp
int[] sorted = [1, 3, 5, 7, 9, 11];

Console.WriteLine(BinarySearch(sorted, 7));       // 3
Console.WriteLine(BinarySearch(sorted, 4));       // -1
Console.WriteLine(BinarySearch([], 4));           // -1 — порожній масив
Console.WriteLine(Array.BinarySearch(sorted, 4)); // -3: ~(-3) = 2 — сюди вставити 4

static int BinarySearch(int[] a, int target)
{
    int lo = 0, hi = a.Length - 1;     // шукаємо в [lo, hi] включно
    while (lo <= hi)                   // <=, інакше пропустимо останнього кандидата
    {
        int mid = lo + (hi - lo) / 2;  // не (lo + hi) / 2: переповнення int
        if (a[mid] == target) return mid;
        if (a[mid] < target) lo = mid + 1; // mid уже перевірено
        else hi = mid - 1;
    }
    return -1;
}
```

</Ex>

<Ex title="Стабільність сортування">

```csharp

var byCustomer = orders.OrderBy(o => o.Customer).Select(o => o.Id);
Console.WriteLine(string.Join(" ", byCustomer)); // 2 4 1 3

Array.Sort(copy, (x, y) =>
{

});
Console.WriteLine(string.Join(" ", copy.Select(o => o.Id))); // 2 4 1 3

record Order(int Id, string Customer);
```

На чотирьох елементах `Array.Sort` сортує вставками й випадково збереже порядок, але на великих масивах гарантії немає — тому другий ключ.

- Чому quicksort у найгіршому випадку O(n²)? — Невдалий опорний ділить масив на 0 і n−1 елементів, наприклад на відсортованому вводі з першим елементом як опорним.

- Як знайти перше входження серед дублів? — Нижня межа: при збігу не виходити, а зсувати `hi` і продовжувати.

<Q id="basics.algo.recursion-dp" level="m">

## Рекурсія й динамічне програмування: як розпізнати й розв'язати задачу?

<A short l="j">

<T k="recursion">Рекурсія</T> — функція викликає саму себе для меншої підзадачі й зупиняється на базовому випадку. <T k="dynamic-programming">Динамічне програмування</T> застосовують, коли ті самі підзадачі повторюються: відповідь кожної запам'ятовують, і експоненційний перебір стає швидким, як у чисел Фібоначчі.

</A>

<A short l="m">

Рекурсії потрібні базовий випадок і крок, який до нього наближає; кожен виклик займає кадр <T k="call-stack">стека викликів</T>, тому глибина обмежена. ДП підходить, якщо задача складається з оптимальних відповідей підзадач і ці підзадачі перекриваються. <T k="memoization">Мемоізація</T> кешує рекурсію згори донизу, <T k="tabulation">табуляція</T> заповнює таблицю знизу вгору без рекурсії; ціна обох — пам'ять на відповіді, зате час падає з O(2^n) до O(n) або O(n·m).

</A>

<A short l="s">

ДП розпізнають за формулюванням: «скільки способів», «мінімум або максимум», «чи можна» над префіксами, сумами або парами індексів. Рішення — визначити стан і перехід; складність — кількість станів, помножена на вартість переходу. У .NET глибока рекурсія небезпечна: `StackOverflowException` не перехоплюється й завершує процес, а C# не гарантує <T k="tail-call">оптимізації хвостового виклику</T>. Тому рекурсію за даними користувача замінюють явним стеком або табуляцією, яка ще й дає змогу зберігати лише останні рядки таблиці.

</A>

<A l="j">

**Що це**

Рекурсивна функція складається з двох частин:

1. **Базовий випадок** — відповідь без рекурсії: `Fib(0) = 0`, `Fib(1) = 1`.
2. **Рекурсивний крок** — зведення до меншої задачі: `Fib(n) = Fib(n - 1) + Fib(n - 2)`.

**Навіщо динамічне програмування**

Наївна `Fib(n)` рахує те саме багато разів: `Fib(5)` викликає `Fib(3)` двічі, а `Fib(2)` — тричі. Кількість викликів зростає експоненційно, і `Fib(50)` потребує десятків мільярдів викликів.

**Як користуватися**

Запам'ятовуйте відповідь підзадачі в словнику або масиві й перед обчисленням перевіряйте, чи її немає. Тоді `Fib(50)` — це 50 обчислень.

**Типова помилка**

Забути базовий випадок або зробити крок, який не зменшує задачу. Рекурсія стане нескінченною, і `StackOverflowException` завершить процес — `try`/`catch` його не перехопить.

**Підсумок:** рекурсія — базовий випадок плюс крок до нього, а ДП — рекурсія, яка не рахує те саме двічі.

</A>

<A l="m">

**Як влаштовано**

Кожен виклик кладе в стек кадр з аргументами й локальними змінними. Глибина d — це O(d) пам'яті, а розмір стека обмежений: за документацією .NET типово 1,5 МБ у Windows і macOS та 8 МБ у Linux.

**Як розв'язувати задачу ДП**

1. **Стан.** Що означає `dp[s]`: наприклад, мінімум монет для суми s.
2. **Перехід.** `dp[s] = min(dp[s - c] + 1)` по всіх монетах c.
3. **База.** `dp[0] = 0`.
4. **Порядок і відповідь.** Суми від 0 до amount, відповідь — `dp[amount]`.
5. **Складність.** Стани × перехід: O(amount · k) для k монет.

**Коли що обирати**

| Підхід | Плюс | Мінус |
|---|---|---|
| Мемоізація (згори донизу) | код повторює формулу, рахує лише потрібні стани | рекурсія та її глибина, накладні витрати словника |
| Табуляція (знизу вгору) | без рекурсії, легко стиснути пам'ять | треба знати порядок заповнення |

**Класика**

- **Фібоначчі** — O(n) часу, O(1) пам'яті з табуляцією.
- **Розмін монет** — O(amount · k).
- **Найдовша спільна підпослідовність (LCS)** двох рядків довжиною n і m: якщо символи рівні, `dp[i, j] = dp[i - 1, j - 1] + 1`, інакше `max(dp[i - 1, j], dp[i, j - 1])`. O(n·m).

**Пастки**

Жадібний вибір не завжди оптимальний. Монети 1, 3 і 4, сума 6: жадібно 4 + 1 + 1 — три монети, а оптимально 3 + 3 — дві.

**Підсумок:** задачу ДП розв'язують визначенням стану, переходу й бази, а мемоізація й табуляція — два способи обійти ті самі стани.

</A>

<A l="s">

**Під капотом**

- Кадр стека тримає аргументи, локальні змінні й адресу повернення. `StackOverflowException` не можна перехопити: процес завершується.
- `RuntimeHelpers.EnsureSufficientExecutionStack()` викидає звичайний `InsufficientExecutionStackException`, якщо стека лишилося мало. Так захищають рекурсивні обходи дерев виразів і парсери.
- Компілятор C# не позначає хвостові виклики. JIT іноді оптимізує їх сам, але розраховувати на це не можна.

**Ціна**

- Мемоізація словником — хешування й алокації. Якщо стан — невеликі цілі числа, масив швидший.
- Таблиця LCS займає O(n·m) пам'яті. Якщо потрібна лише довжина, вистачить двох рядків: O(min(n, m)).

**Компроміси**

- **Рекурсія проти явного стека.** Рекурсія читабельніша для дерев і обходу в глибину. Якщо глибина залежить від входу — вкладений JSON, довгий ланцюжок посилань, — потрібні `Stack<T>` і цикл.
- **Мемоізація проти табуляції.** Мемоізацію простіше написати на співбесіді з рекурсивної формули. Табуляція безпечніша й дає змогу стиснути пам'ять.

**Як перевірити в продакшені**

Переповнення стека завершує процес без запису у звичайний лог. Рантайм друкує в stderr `Stack overflow.` і повторювані кадри, а крах-дамп (`DOTNET_DbgEnableMiniDump=1`) відкривають у `dotnet-dump` і дивляться стек.

**Підсумок:** ДП — це стани й переходи, а в .NET рекурсію за чужими даними замінюють циклом, бо переповнення стека не перехоплюється.

</A>

<Ex title="Фібоначчі: мемоізація й табуляція">

```csharp
Console.WriteLine(FibMemo(50, new Dictionary<int, long>())); // 12586269025
Console.WriteLine(FibTable(50));                             // 12586269025

// Згори донизу: рекурсія плюс кеш, O(n) часу та O(n) пам'яті
static long FibMemo(int n, Dictionary<int, long> memo)
{
    if (n < 2) return n;                               // базовий випадок
    if (memo.TryGetValue(n, out long cached)) return cached;
    return memo[n] = FibMemo(n - 1, memo) + FibMemo(n - 2, memo);
}

// Знизу вгору: без рекурсії, O(n) часу та O(1) пам'яті
static long FibTable(int n)
{
    long prev = 0, cur = 1;
    for (int i = 0; i < n; i++)
        (prev, cur) = (cur, prev + cur);
    return prev;
}
```

</Ex>

<Ex title="Розмін монет">

```csharp
Console.WriteLine(MinCoins([1, 5, 10, 25], 63)); // 6: 25 + 25 + 10 + 1 + 1 + 1
Console.WriteLine(MinCoins([1, 3, 4], 6));       // 2: 3 + 3, а жадібно було б 3 монети
Console.WriteLine(MinCoins([2], 3));             // -1: набрати неможливо

// dp[s] — мінімум монет для суми s; O(amount · k) часу, O(amount) пам'яті
static int MinCoins(int[] coins, int amount)
{
    var dp = new int[amount + 1];
    Array.Fill(dp, int.MaxValue);
    dp[0] = 0;                                    // база: сума 0 — нуль монет
    for (int s = 1; s <= amount; s++)
        foreach (int c in coins)
            if (c <= s && dp[s - c] != int.MaxValue)
                dp[s] = Math.Min(dp[s], dp[s - c] + 1);
    return dp[amount] == int.MaxValue ? -1 : dp[amount];
}
```

</Ex>

<Q id="basics.algo.live-coding" level="s">

## Як розв'язувати задачу на live coding і які прийоми трапляються найчастіше?

<A short l="j">

На live coding перевіряють не лише відповідь, а й хід думки: уточнити умову, розібрати приклад, написати просте рішення, покращити його й перевірити на граничних випадках, увесь час міркуючи вголос. Більшість задач розв'язується кількома прийомами: хеш-таблиця, <T k="two-pointers">два вказівники</T>, <T k="sliding-window">ковзне вікно</T>, обхід графа.

</A>

<A short l="m">

Порядок такий: уточнити вхід і обмеження, розібрати приклад, назвати наївне рішення і його складність, оптимізувати, написати код і прогнати тести вголос. Оптимізація зазвичай зводиться до впізнавання прийому: пара із сумою — хеш-таблиця, відсортований масив — два вказівники, підвідрізок — вікно або <T k="prefix-sum">префіксні суми</T>, найкоротший шлях — <T k="bfs">BFS</T>, залежності — <T k="topological-sort">топологічне сортування</T>. Ціна кожного пришвидшення — зазвичай пам'ять, і її називають уголос.

</A>

<A short l="s">

Інтерв'юер оцінює комунікацію, роботу з нечіткою умовою й перевірку свого коду не менше, ніж підсумковий алгоритм. Сильний кандидат сам називає компроміси: O(n) пам'яті заради O(n) часу, сортування на місці псує вхід, рекурсивний <T k="dfs">DFS</T> на глибокому графі переповнить стек. Робоче O(n²) з чесною оцінкою краще за незавершене O(n), тому спершу доводять до кінця просте рішення, а покращення пропонують потім.

</A>

<A l="j">

**Що це**

Live coding — розв'язання задачі при інтерв'юері в редакторі або на дошці. Оцінюють хід міркувань, код і те, як ви його перевіряєте.

**Як користуватися**

1. **Уточніть умову.** Розмір входу, від'ємні числа, дублі, порожній вхід, що повернути, якщо відповіді немає.
2. **Розберіть приклад руками.** Це перевірка, що задачу зрозуміли правильно.
3. **Назвіть наївне рішення** і його складність, навіть якщо воно повільне.
4. **Покращте.** Знайдіть повторювану роботу й приберіть її.
5. **Напишіть код** зі зрозумілими іменами.
6. **Перевірте вголос:** приклад, порожній вхід, один елемент, дублі.

**Типова помилка**

Мовчки писати код одразу після умови. Якщо рішення зайде в глухий кут, інтерв'юерові нічим вам допомогти, а оцінювати йому нічого.

**Підсумок:** на live coding рішення — це процес уголос: умова, приклад, просте рішення, покращення, перевірка.

</A>

<A l="m">

**Коли що обирати**

| Ознака в умові | Прийом | Складність |
|---|---|---|
| Пара, дубль, частоти | хеш-таблиця | O(n), пам'ять O(n) |
| Відсортований масив, пара, паліндром | два вказівники | O(n), пам'ять O(1) |
| Найдовший або найкоротший підвідрізок | ковзне вікно | O(n) |
| Багато запитів суми на відрізку | префіксні суми | O(n) підготовка, O(1) запит |
| Найкоротший шлях без ваг, сітка | BFS | O(V + E) |
| Зв'язність, усі шляхи, перебір | DFS | O(V + E) |
| Порядок із залежностями | топологічне сортування | O(V + E) |
| k найбільших | `PriorityQueue` розміру k | O(n log k) |

**Розбір: дві суми**

Знайти індекси двох чисел із сумою target. Наївно — усі пари, O(n²). Пришвидшення: для кожного x шукати `target - x` серед уже побачених чисел у `Dictionary`. Разом O(n) часу й O(n) пам'яті.

**Розбір: найдовший підрядок без повторів**

Вікно `[left, right]` розширюється праворуч. Якщо символ уже є у вікні, `left` перестрибує за його минулу позицію. Кожен індекс зсувається не більше одного разу — O(n).

**Пастки**

- Переповнення суми: суми великого масиву `int` рахують у `long`.
- BFS і DFS без позначення відвіданих вершин зациклюються на графі з циклом.
- Зміна колекції під час `foreach` дає `InvalidOperationException`.

**Правило**

Спершу впізнайте прийом за ознакою в умові, потім пишіть код.

**Підсумок:** більшість задач зводиться до десятка прийомів, і впізнати прийом за умовою — половина рішення.

</A>

<A l="s">

**Як говорити під час розв'язання**

- Озвучуйте припущення: «вважаю, що вхід уміщається в пам'ять».
- Називайте складність варіанта до того, як писати код.
- Спершу план із двох-трьох фраз, потім код.
- Застрягли — скажіть, що розглядаєте, і спитайте про обмеження.
- Після коду пройдіть приклад по рядках, як налагоджувач.

**Компроміси**

- **Час проти пам'яті.** Хеш-таблиця дає O(n) і O(n) пам'яті. Сортування плюс два вказівники — O(n log n), але O(1) додаткової пам'яті, якщо вхід можна змінювати.
- **Зміна входу.** Сортування на місці псує масив того, хто викликає, — спитайте, чи можна.
- **Рекурсія проти явного стека.** Рекурсивний DFS коротший, а `Stack<T>` витримає глибокий граф.

**Розбір: топологічне сортування**

Алгоритм Кана:

1. Рахуємо вхідний степінь кожної вершини.
2. Вершини без вхідних ребер кладемо в чергу.
3. Знімаємо вершину, додаємо до відповіді, зменшуємо степінь її сусідів. Обнулився — у чергу.
4. Якщо у відповіді не всі вершини — у графі цикл.

Складність — O(V + E). Так впорядковують кроки збирання, міграції й задачі із залежностями.

**Як перевірити рішення**

- Крайові випадки: порожній вхід, один елемент, усі елементи рівні, від'ємні числа, максимальне n.
- Оцінка за обмеженнями: при n = 10^5 рішення O(n²) — це 10^10 операцій, секунди замість мілісекунд.

**Підсумок:** на сеньйорському рівні оцінюють не лише алгоритм, а й те, як ви ведете розв'язання: припущення, компроміси й самоперевірку.

</A>

<Ex title="Хеш-таблиця й ковзне вікно">

```csharp
Console.WriteLine(string.Join(",", TwoSum([2, 7, 11, 15], 9))); // 0,1
Console.WriteLine(LongestUniqueRun("abcabcbb"));                // 3: "abc"
Console.WriteLine(LongestUniqueRun(""));                        // 0 — крайовий випадок

// Для кожного x шукаємо target - x серед побачених: O(n) часу, O(n) пам'яті
static int[] TwoSum(int[] nums, int target)
{
    var indexOf = new Dictionary<int, int>();
    for (int i = 0; i < nums.Length; i++)
    {
        if (indexOf.TryGetValue(target - nums[i], out int j)) return [j, i];
        indexOf[nums[i]] = i;
    }
    return [];
}

// Вікно [left, right] без повторів: O(n), кожен індекс зсувається один раз
static int LongestUniqueRun(string s)
{
    var lastSeen = new Dictionary<char, int>();
    int best = 0, left = 0;
    for (int right = 0; right < s.Length; right++)
    {
        if (lastSeen.TryGetValue(s[right], out int prev) && prev >= left)
            left = prev + 1;                      // перестрибуємо за повтор
        lastSeen[s[right]] = right;
        best = Math.Max(best, right - left + 1);
    }
    return best;
}
```

</Ex>

<Ex title="Два вказівники й префіксні суми">

```csharp
int[] sorted = [1, 2, 4, 7, 11, 15];
Console.WriteLine(PairWithSum(sorted, 15)); // (4, 11)
Console.WriteLine(PairWithSum(sorted, 100) is null); // True — пари немає

int[] sales = [3, 1, 4, 1, 5, 9];
var prefix = new int[sales.Length + 1];      // prefix[i] — сума перших i елементів
for (int i = 0; i < sales.Length; i++)
    prefix[i + 1] = prefix[i] + sales[i];
Console.WriteLine(prefix[5] - prefix[2]);    // 10: sales[2] + sales[3] + sales[4] за O(1)

// Відсортований масив, вказівники з двох кінців: O(n) часу, O(1) пам'яті
static (int, int)? PairWithSum(int[] a, int target)
{
    int left = 0, right = a.Length - 1;
    while (left < right)
    {
        int sum = a[left] + a[right];
        if (sum == target) return (a[left], a[right]);
        if (sum < target) left++;            // потрібна більша сума
        else right--;                        // потрібна менша сума
    }
    return null;
}
```

<Ex title="Топологічне сортування (алгоритм Кана)">

```csharp
// Ребро a → b: крок a має виконатися раніше за b
var graph = new Dictionary<string, string[]>
{
    ["restore"] = ["build"],
    ["build"] = ["test", "pack"],
    ["test"] = ["deploy"],
    ["pack"] = ["deploy"],
    ["deploy"] = [],
};
Console.WriteLine(string.Join(" ", TopoSort(graph))); // restore build test pack deploy

// O(V + E): BFS по вершинах, у яких не лишилося вхідних ребер
static List<string> TopoSort(Dictionary<string, string[]> graph)
{
    var inDegree = graph.Keys.ToDictionary(v => v, _ => 0);
    foreach (var targets in graph.Values)
        foreach (var t in targets) inDegree[t]++;

    var queue = new Queue<string>(inDegree.Where(p => p.Value == 0).Select(p => p.Key));
    var order = new List<string>();
    while (queue.Count > 0)
    {
        var v = queue.Dequeue();
        order.Add(v);
        foreach (var t in graph[v])
            if (--inDegree[t] == 0) queue.Enqueue(t);
    }
    if (order.Count != graph.Count) throw new InvalidOperationException("Cycle detected");
    return order;
}
```
