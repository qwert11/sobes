## Як влаштована верстка в CSS: блокова модель, flexbox і grid?

<A short l="j">

Кожен елемент у CSS — прямокутник із вмісту, внутрішнього відступу, рамки та зовнішнього відступу; це <T k="box-model">блокова модель</T>, а властивість `display` вирішує, як елемент стає серед сусідів. Для розкладки в одну лінію беруть <T k="flexbox">flexbox</T>, для рядків і колонок одразу — <T k="css-grid">grid</T>, а під ширину екрана підлаштовуються <T k="media-query">медіазапитами</T>.

</A>

<A short l="m">

Блокова модель задає розмір елемента, і `box-sizing: border-box` включає padding і border у `width`, тому його ставлять глобально. Flexbox розподіляє місце вздовж однієї осі від вмісту, grid задає сітку рядків і колонок від контейнера, а суперечку стилів вирішує каскад: `!important`, шари, <T k="css-specificity">специфічність</T>, порядок у коді. Адаптивність будують mobile-first на `min-width`, а компоненти, що живуть у колонках різної ширини, підлаштовують <T k="container-query">container queries</T>.

</A>

<A short l="s">

Розкладка — питання про те, хто задає розмір: у flexbox він іде від вмісту, у grid — від контейнера, тому grid беруть для каркаса, а flex — для компонентів. Перегони специфічності з `!important` — головне джерело крихких стилів; `@layer` і `:where()` роблять пріоритети явними. Медіазапит знає лише ширину вікна, а компонент має реагувати на свій контейнер, тому дизайн-системи переходять на container queries і плавні розміри через `clamp()`. Ціна — контейнер із `container-type` більше не бере ширину від вмісту.

</A>

<A l="j">

**Що це**

- **Блокова модель.** Елемент — це content, padding, border і margin. За замовчуванням `width` не включає padding і border.
- **`display`.** `block` займає весь рядок, `inline` тече в тексті, `flex` і `grid` розкладають дітей елемента.
- **Flexbox** ставить дітей у рядок або колонку, **grid** — у сітку рядків і колонок.

**Як користуватися**

1. Для всіх елементів — `box-sizing: border-box`.
2. Каркас сторінки — grid, елементи всередині блока — flex, відстані — `gap`.
3. Стилі за замовчуванням — для телефона, для широких екранів — `@media (min-width: 768px)`. Префікс `md:` у Tailwind працює так само.

**Типова помилка**

Розкладати блоки через `float` і `position: absolute` там, де вистачає flex або grid. Така верстка ламається від першого довгого тексту.

**Підсумок:** блокова модель задає розмір елемента, flex розкладає по одній осі, grid — по двох.

</A>

<A l="m">

**Як влаштовано**

- **Каскад.** Якщо до елемента підходять кілька правил, перемагає те, що вище за списком: `!important`, inline-стиль, правило поза `@layer` або в пізнішому шарі, більша специфічність, пізніше місце в коді.
- **Специфічність** — трійка: id; класи, атрибути й псевдокласи; теги й псевдоелементи. Порівнюється зліва направо, тому `#nav a` (1,0,1) сильніший за `.menu .item a` (0,2,1).
- **Позиціювання.** `relative` зсуває елемент, зберігаючи його місце. `absolute` виймає його з потоку й рахує координати від найближчого позиціонованого предка. `fixed` — від вікна, `sticky` прилипає під час прокручування.

**Коли що обирати**

| | Flexbox | Grid |
|---|---|---|
| Осі | одна: рядок або колонка | дві: рядки й колонки |
| Розмір задає | вміст | контейнер |
| Приклад | меню, кнопки в ряд, картка | каркас сторінки, галерея, форма |

**Пастки**

- **Схлопування margin.** Вертикальні margin сусідніх блоків у звичайному потоці не додаються, береться більший. У flex і grid цього немає.
- **`z-index` «не працює».** Він порівнюється всередині одного контексту накладання, а його створюють, наприклад, `opacity` менше 1 або `transform` у предка.
- **Flex-елемент не стискається.** Мінімальна ширина flex-елемента за замовчуванням — ширина його вмісту; довге слово розпирає колонку, допомагає `min-width: 0`.

**Правило**

Grid — для каркаса, flex — для компонентів, `gap` — замість margin між сусідами, медіазапити — mobile-first.

**Підсумок:** розкладку обирають за кількістю осей, а конфлікти стилів вирішує каскад, а не порядок підключення файлів навмання.

</A>

<A l="s">

**Під капотом**

- Flex-алгоритм спершу бере базовий розмір елементів (`flex-basis`, інакше за вмістом), потім роздає вільне місце за `flex-grow` або забирає за `flex-shrink`. Тому колонки з різним текстом виходять різної ширини.
- Grid спершу будує доріжки з `grid-template-columns`, а `fr` ділить решту місця. `repeat(auto-fit, minmax(12rem, 1fr))` дає адаптивну галерею без медіазапитів.
- `container-type: inline-size` вмикає size containment: ширина контейнера не залежить від вмісту. Інакше виник би цикл «стиль залежить від розміру, розмір — від стилю».

**Компроміси**

- **Медіазапит чи container query.** Медіазапит підходить для каркаса сторінки. Картка, яка стоїть і в сайдбарі, і в основній колонці, має реагувати на свій контейнер. Container queries — Baseline з 2023 року, у Tailwind v4 вони вбудовані (`@container`, `@md:`).
- **Одиниці.** `rem` у шрифтах поважає налаштування розміру шрифту користувача, `px` — ні. `font-size` лише у `vw` не зростає під час масштабування сторінки, тому в `clamp()` додають `rem`. На мобільних `100vh` включає область під панеллю браузера, точніше `100dvh`.
- **Керування каскадом.** `@layer reset, library, app` фіксує порядок шарів, а стилі поза шарами сильніші за будь-який шар. `:where()` обнуляє специфічність базових стилів, і їх легко перевизначити. Утилітарний CSS на кшталт Tailwind і CSS-модулі знімають перегони, бо класи однієї ваги.

**Як перевірити в продакшені**

- DevTools → Elements → Computed показує, яке правило перемогло, а закреслені — ті, що програли. Значки `flex` і `grid` у дереві елементів вмикають оверлей сітки.
- Скриншотні тести Playwright на кількох ширинах ловлять зламану верстку до релізу.

**Підсумок:** grid задає розмір згори, flex — знизу; адаптивність компонента — через його контейнер, а пріоритети стилів — через шари, а не `!important`.

</A>

<Ex>

```css
*, *::before, *::after { box-sizing: border-box; }

/* Каркас: mobile-first — одна колонка */
.page {
  display: grid;
  grid-template-columns: 1fr;
  gap: 1rem;
}
@media (min-width: 768px) {
  .page { grid-template-columns: 16rem 1fr; } /* сайдбар + контент */
}

/* Галерея без медіазапитів: стільки колонок, скільки вміститься */
.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(12rem, 1fr));
  gap: 1rem;
}

/* Картка підлаштовується під свій контейнер, а не під вікно */
.card-slot { container-type: inline-size; }
.card { display: flex; flex-direction: column; gap: 0.5rem; }
@container (min-width: 30rem) {
  .card { flex-direction: row; } /* картинка ліворуч, текст праворуч */
}

/* Від 24px до 40px за кореневого шрифту 16px */
h1 { font-size: clamp(1.5rem, 1rem + 2vw, 2.5rem); }
```

</Ex>

- Чим `display: none` відрізняється від `visibility: hidden`? — Перший прибирає елемент із розкладки, другий ховає, але залишає його місце.
- Що означає `flex: 1`? — `flex-grow: 1`, `flex-shrink: 1`, `flex-basis: 0%`: елементи ділять вільне місце порівну.
- Чим `auto-fit` відрізняється від `auto-fill` у grid? — `auto-fit` схлопує порожні доріжки й розтягує елементи, `auto-fill` залишає порожні доріжки.
- Від чого рахує координати `position: absolute`? — Від найближчого предка з `position` не `static`, інакше від початкового блока-контейнера.
- Яка специфічність у `:is()` і `:where()`? — `:is()` — як у найсильнішого аргументу, `:where()` — завжди нуль.

<Q id="front.web.accessibility" level="m">

## Як зробити інтерфейс доступним?

<A short l="j">

Доступність (accessibility, a11y) — можливість користуватися інтерфейсом без миші, зі <T k="screen-reader">скринрідером</T>, зі слабким зором. Основа — <T k="semantic-html">семантичний HTML</T>: `<button>`, `<label>` і `<nav>` замість `div` уже зрозумілі клавіатурі та скринрідеру, а в картинок є `alt`.

</A>

<A short l="m">

Браузер будує з DOM <T k="accessibility-tree">дерево доступності</T> — роль, ім'я і стан кожного елемента, — і скринрідер читає саме його. Тому спершу нативні елементи, а <T k="wai-aria">ARIA</T> — лише там, де HTML не вистачає: цього прямо вимагає перше правило ARIA. Далі — робота з клавіатури й видимий фокус, контраст тексту 4,5:1, підписи полів і пов'язані з ними помилки; орієнтир — <T k="wcag">WCAG 2.2</T> рівня AA.

</A>

<A short l="s">

Доступність — нефункційна вимога з юридичною вагою: в ЄС з 28 червня 2025 року діє <T k="european-accessibility-act">Європейський акт про доступність</T>, і для інтернет-магазинів і банків це обов'язок. Технічно все зводиться до правильного дерева доступності: нативний елемент дає роль, ім'я, стан і клавіатуру безкоштовно, а саморобний віджет на ARIA мусить повторити все вручну, і поганий ARIA гірший, ніж жодного. Автоматичні перевірки ловлять лише частину проблем, тому в процес входять ручна перевірка з клавіатури й скринрідером і доступні компоненти в дизайн-системі.

</A>

<A l="j">

**Що це**

Доступність — інтерфейсом можуть користуватися люди з порушеннями зору, слуху й моторики: зі скринрідером, лише з клавіатури, зі збільшеним шрифтом.

**Як користуватися**

- Дія — `<button>`, перехід — `<a href>`, а не `div` з обробником кліку: вони фокусуються й натискаються з клавіатури.
- У кожного поля — `<label for="...">`. Плейсхолдер підписом не вважається: він зникає під час введення.
- У картинки — `alt` з її змістом, у декоративної — порожній `alt=""`.
- Заголовки `h1`–`h6` ідуть по порядку, області розмічені `header`, `nav`, `main`.
- Контраст звичайного тексту з тлом — не менше 4,5:1.

**Типова помилка**

Прибрати рамку фокуса через `outline: none`, бо «некрасиво». Користувач клавіатури перестає бачити, де він. Рамку не прибирають, а оформлюють через `:focus-visible`.

**Підсумок:** правильний HTML-елемент дає доступність майже безкоштовно.

</A>

<A l="m">

**Як влаштовано**

1. З DOM і CSS браузер будує дерево доступності: роль (`button`), доступне ім'я («Зберегти») і стан (`disabled`, `expanded`).
2. Скринрідер — NVDA, JAWS, VoiceOver, TalkBack — отримує це дерево через API доступності ОС і озвучує.
3. ARIA змінює лише дерево, але не поведінку: `role="button"` на `div` не дасть ні фокуса, ні реакції на Enter і пробіл.

**Коли що обирати**

| Задача | Рішення |
|---|---|
| Поле без видимого підпису | `aria-label` або `aria-labelledby` |
| Помилка поля | `aria-invalid="true"` і `aria-describedby` на текст помилки |
| Повідомлення після дії | live region: `role="status"` або `role="alert"` |
| Модальне вікно | `<dialog>` і `showModal()`: тло недоступне, Esc закриває |
| Стан віджета | `aria-expanded`, `aria-selected`, `aria-current` |

**Пастки**

- **ARIA поверх нативного.** Перше правило ARIA: якщо є HTML-елемент із потрібною семантикою й поведінкою, беріть його.
- **`tabindex` більше нуля** ламає природний порядок обходу. Використовують лише `0` і `-1`.
- **Зміна маршруту в SPA.** Фокус і озвучення не змінюються самі, їх переводять на заголовок нової сторінки вручну.
- **Лише колір.** Помилку, виділену тільки червоною рамкою, не побачить дальтонік і не озвучить скринрідер — потрібен текст.

**Правило**

Спершу семантичний HTML, потім ARIA для відсутнього; кожен сценарій проходять із клавіатури: Tab, Enter, пробіл, Esc, стрілки.

**Підсумок:** доступність — це правильне дерево доступності й робота з клавіатури, а ARIA лише дописує те, чого немає в HTML.

</A>

<A l="s">

**Стандарти й закон**

- **WCAG 2.2** (W3C, жовтень 2023) — критерії трьох рівнів: A — мінімум, AA — мета законів і контрактів, AAA — для окремих випадків.
- Нове у 2.2 на рівні AA: фокус не перекритий липкими панелями (2.4.11), ціль дотику не менше 24×24 CSS-пікселів (2.5.8), альтернатива перетягуванню (2.5.7), вхід без когнітивного тесту — наприклад, вставлення пароля з менеджера (3.3.8). Критерій 4.1.1 Parsing вилучено.
- **EAA** (директива 2019/882) застосовується з 28 червня 2025 року до продуктів і послуг на ринку ЄС: інтернет-магазини, банки, транспорт, електронні книги. Мікропідприємства, що надають послуги, звільнені. Технічна опора — стандарт EN 301 549, який посилається на WCAG 2.1 AA.

**Компроміси**

- **Свій віджет чи готовий.** Combobox, вкладки або дерево на ARIA — це ролі, стани й клавіатурна модель з ARIA Authoring Practices. Зазвичай дешевше взяти перевірену бібліотеку або Angular CDK `a11y`, ніж писати своє.
- **Автоматика чи руки.** axe-core і Lighthouse знаходять низький контраст, порожні підписи й неправильні ролі. Чи зрозумілий порядок фокуса і чи змістовний `alt`, вони не скажуть.

**Як перевірити в продакшені**

- axe-core в e2e-тестах (`@axe-core/playwright`) і Lighthouse CI в пайплайні ловлять регресії.
- Вручну: основний сценарій проходять лише з клавіатури та зі скринрідером — NVDA на Windows, VoiceOver на macOS.
- DevTools → Elements → Accessibility показує роль, ім'я і стан вузла та все дерево доступності.

**Підсумок:** мета — WCAG 2.2 AA, закріплена в компонентах дизайн-системи та в автотестах, а ручна перевірка закриває те, чого автоматика не бачить.

</A>

<Ex>

```html
<form novalidate>
  <!-- for/id пов'язує підпис із полем: клік по підпису ставить фокус у поле -->
  <label for="email">Email</label>
  <input id="email" type="email" autocomplete="email"
         aria-invalid="true" aria-describedby="email-error">
  <!-- Скринрідер прочитає текст помилки разом із полем -->
  <p id="email-error">Enter a valid email</p>

  <!-- Кнопка-іконка: доступне ім'я через aria-label, іконку ховаємо -->
  <button type="button" aria-label="Close">
    <svg aria-hidden="true" width="16" height="16"><path d="M2 2l12 12M14 2L2 14"/></svg>
  </button>

  <img src="chart.png" alt="Sales grew 20% in Q3">
  <img src="divider.png" alt=""> <!-- декоративна: скринрідер пропустить -->

  <!-- Live region: текст, вставлений сюди, буде озвучено -->
  <div role="status"></div>

  <button type="submit">Save</button>
</form>
```

</Ex>

- Що таке перше правило ARIA? — Якщо нативний HTML-елемент дає потрібну семантику й поведінку, використовуйте його, а не роль на `div`.
- Чим `aria-label` відрізняється від `aria-labelledby`? — Перший задає ім'я рядком, другий посилається на id видимого тексту.
- Чим `role="alert"` відрізняється від `role="status"`? — `alert` озвучується одразу, перериваючи читання, `status` — ввічливо, після поточної фрази.
- Який контраст вимагає WCAG AA? — 4,5:1 для звичайного тексту, 3:1 для великого й для елементів інтерфейсу.
- Що змінив Європейський акт про доступність? — З 28 червня 2025 року доступність обов'язкова для багатьох цифрових послуг в ЄС, орієнтир — EN 301 549 і WCAG.

</Next>

<Q id="front.web.rendering" level="m">

## Як браузер перетворює HTML на пікселі?

<A short l="j">

Браузер розбирає HTML у DOM, CSS — у <T k="cssom">CSSOM</T>, об'єднує їх у дерево відмальовування, рахує розміри й положення елементів (layout), малює пікселі (paint) і збирає шари в кадр (composite). Цей ланцюжок — <T k="critical-rendering-path">критичний шлях відмальовування</T>: поки CSS не завантажено або синхронний скрипт виконується, сторінка не показується.

</A>

<A short l="m">

Критичний шлях — кроки від байтів HTML до першого кадру, і його гальмують <T k="render-blocking-resource">блокувальні ресурси</T>: CSS блокує відмальовування, а звичайний `<script>` зупиняє розбір HTML. Тому скрипти підключають із `defer` або `type="module"`, а критичний CSS тримають маленьким. Зміни після завантаження проходять той самий конвеєр: геометрія запускає <T k="reflow">reflow</T>, колір — лише repaint, а `transform` і `opacity` — лише composite, тому анімують саме їх.

</A>

<A short l="s">

Рендеринг іде в головному потоці разом із JavaScript, тому будь-яке довге завдання затримує і кадр, і відповідь на введення. Найдорожчі помилки — <T k="layout-thrashing">layout thrashing</T>, коли код чергує запис стилів і читання `offsetHeight` та змушує браузер перераховувати layout синхронно, і анімація властивостей геометрії. `transform` і `opacity` на окремому шарі обробляє <T k="compositing">композитор</T> у своєму потоці, і анімація лишається плавною, навіть коли головний потік зайнятий. Ціна — пам'ять GPU під кожен шар, тому `will-change` ставлять точково.

</A>

<A l="j">

**Що це**

Шлях від HTML до пікселів:

1. **DOM.** HTML розбирається в дерево вузлів.
2. **CSSOM.** CSS розбирається в дерево правил.
3. **Дерево відмальовування (render tree).** Лише видимі елементи з підсумковими стилями: `display: none` сюди не потрапляє.
4. **Layout.** Розрахунок розмірів і координат кожного блока.
5. **Paint.** Заливання пікселів: текст, кольори, тіні, картинки.
6. **Composite.** Збирання шарів у підсумковий кадр.

**Як користуватися**

- CSS — у `<head>`, скрипти — з атрибутом `defer`.
- Анімувати `transform` і `opacity`, а не `top`, `left` чи `width`.

**Типова помилка**

Підключити великий скрипт у `<head>` без `defer`. Поки він завантажується й виконується, HTML не розбирається, і екран лишається білим.

**Підсумок:** DOM і CSSOM → дерево відмальовування → layout → paint → composite; усе, що затримує ці кроки, затримує перший кадр.

</A>

<A l="m">

**Як влаштовано**

- **CSS блокує відмальовування.** Без CSSOM браузер не малює, інакше користувач побачив би нестилізовану сторінку. Синхронний скрипт ще й чекає на стилі перед собою: він може їх читати.
- **JS блокує розбір.** Звичайний `<script>` зупиняє парсер до завантаження й виконання. Тим часом preload scanner переглядає HTML далі й заздалегідь починає вантажити картинки та стилі.
- **JS і відмальовування ділять головний потік.** Кадр малюється між завданнями, тому довгий обробник його відкладає. Як влаштований event loop — у темі [JavaScript і TypeScript](/sobes/uk/front/js-ts/).

**Коли що обирати**

| Атрибут `<script>` | Розбір HTML | Виконання |
|---|---|---|
| немає | зупиняється | одразу, по порядку |
| `async` | триває | щойно завантажиться, без порядку |
| `defer` | триває | після розбору, по порядку, до `DOMContentLoaded` |
| `type="module"` | триває | як `defer` за замовчуванням |

**Скільки коштує зміна**

| Зміна | Етапи |
|---|---|
| `width`, `top`, `font-size`, нові вузли | layout, paint, composite (reflow) |
| `color`, `background`, `box-shadow` | paint, composite (repaint) |
| `transform`, `opacity` | лише composite |

**Пастки**

- **Layout thrashing.** Запис стилю, а одразу за ним читання `offsetHeight` чи `getBoundingClientRect()` змушують перерахувати layout негайно; у циклі — на кожній ітерації.
- **`async` для залежних скриптів.** Порядок не гарантований: бібліотека може завантажитися пізніше за код, який її використовує.

**Правило**

Скрипти — `defer` або модулі, читання layout — пачкою до записів, анімації — на `transform` і `opacity`.

**Підсумок:** CSS блокує показ, синхронний JS — розбір, а після завантаження ціна зміни залежить від того, з якого етапу конвеєра її доведеться перераховувати.

</A>

<A l="s">

**Під капотом**

- У Chromium етап paint лише записує команди відмальовування. Растеризацію та збирання кадру виконують потік композитора і GPU, а не головний потік.
- Анімація `transform` і `opacity` на окремому шарі повністю йде в композиторі, тому вона плавна, навіть коли головний потік зайнятий. Шар створюють, наприклад, `will-change: transform`, `<video>` і `<canvas>`.
- Бюджет кадру за 60 Гц — близько 16,7 мс на все: JS, стилі, layout і paint.

**Ціна**

- Forced synchronous layout у циклі по N елементах — N перерахунків layout замість одного.
- Кожен шар — текстура в пам'яті GPU. Сотні шарів на слабкому телефоні гірші за зайвий repaint.
- Великий DOM здорожує кожен перерахунок стилів і layout.

**Компроміси**

- Читання й записи DOM розділяють: спершу всі вимірювання, потім усі зміни, візуальні зміни — у `requestAnimationFrame`.
- `content-visibility: auto` пропускає рендеринг блоків поза екраном, але їм потрібен `contain-intrinsic-size`, інакше стрибає смуга прокручування.
- Критичний CSS, вбудований у `<head>`, пришвидшує перший кадр, але не кешується окремо й збільшує кожну HTML-відповідь.

**Як перевірити в продакшені**

- DevTools → Performance: фіолетові блоки Layout і Recalculate Style всередині довгих завдань, а insight Forced reflow вказує на рядок коду.
- Вкладка Rendering → Paint flashing підсвічує перемальовані області, панель Layers показує шари.
- У полі — Long Animation Frames API (Chromium): у кожного скрипта є `forcedStyleAndLayoutDuration`.

**Підсумок:** головний потік один на JS і рендеринг: не змушуйте його перераховувати layout синхронно й віддавайте анімації композитору.

</A>

<Ex title="Підключення ресурсів">

```html
<head>
  <!-- CSS блокує відмальовування: тримаємо його невеликим і в head -->
  <link rel="stylesheet" href="/app.css">
  <!-- media="print": на екрані показ не блокує -->
  <link rel="stylesheet" href="/print.css" media="print">

  <script src="/legacy.js"></script>             <!-- зупиняє розбір HTML -->
  <script defer src="/app.js"></script>          <!-- після розбору, по порядку -->
  <script async src="/analytics.js"></script>    <!-- щойно завантажиться, без порядку -->
  <script type="module" src="/main.js"></script> <!-- відкладений, як defer -->
</head>
```

</Ex>

<Ex title="Layout thrashing і анімація">

```js
const items = document.querySelectorAll('.item');

// Погано: читання після запису на кожній ітерації — layout перераховується N разів
for (const item of items) {
  item.style.width = item.parentElement.offsetWidth / 2 + 'px';
}

// Добре: спершу всі читання, потім усі записи — один перерахунок
const widths = [...items].map((item) => item.parentElement.offsetWidth);
requestAnimationFrame(() => {
  items.forEach((item, i) => { item.style.width = widths[i] / 2 + 'px'; });
});
```

```css
/* Анімація лише на композиторі: без layout і paint */
.toast { transition: transform 200ms, opacity 200ms; }
.toast.hidden { transform: translateY(100%); opacity: 0; }
```

</Ex>

- Чому `display: none` і `visibility: hidden` по-різному впливають на layout? — Перший прибирає елемент із дерева відмальовування, другий залишає його місце.

<Q id="front.web.performance" level="s">

## Як виміряти й пришвидшити завантаження вебзастосунку?

<A short l="j">

Швидкість сторінки вимірюють метриками <T k="core-web-vitals">Core Web Vitals</T>: <T k="lcp">LCP</T> — коли з'явився головний контент, <T k="inp">INP</T> — як швидко сторінка відповідає на кліки, <T k="cls">CLS</T> — наскільки стрибає верстка. Пришвидшують завантаження, надсилаючи менше коду й картинок, кешуючи статику й завантажуючи зайве ліниво.

</A>

<A short l="m">

Core Web Vitals оцінюють за 75-м перцентилем реальних візитів: LCP до 2,5 с, INP до 200 мс, CLS до 0,1. Lighthouse дає лабораторні цифри для налагодження, а рішення ухвалюють за польовими даними — CrUX або власним <T k="real-user-monitoring">RUM</T>. Головні важелі — <T k="code-splitting">поділ коду</T> за маршрутами, зображення потрібного формату й розміру, пріоритет для LCP-ресурсу й довгий кеш статики; ціна — складніше збирання й більше дрібних запитів.

</A>

<A short l="s">

Продуктивність — це бюджет і моніторинг, а не разова оптимізація: поле за 75-м перцентилем показує, що бачать користувачі на слабких телефонах, а лабораторія пояснює чому. Кожна метрика розкладається на частини, і лагодити треба найдовшу: у LCP це час відповіді сервера, затримка й тривалість завантаження ресурсу та відмальовування. SSR пришвидшує перший показ, але гідратація переносить вартість JavaScript у головний потік і б'є по INP, тому головний важіль — менше JS на клієнті. Бюджети розміру бандла в CI не дають виграшу розповзтися за кілька релізів.

</A>

<A l="j">

**Що це**

| Метрика | Що вимірює | Добре |
|---|---|---|
| LCP | коли відмальовано найбільший елемент першого екрана | до 2,5 с |
| INP | затримку від кліку чи натискання клавіші до наступного кадру | до 200 мс |
| CLS | суму неочікуваних зсувів верстки | до 0,1 |

**Як користуватися**

- Виміряйте: Lighthouse у DevTools або PageSpeed Insights.
- Задайте картинкам `width` і `height`: браузер заздалегідь резервує місце, і верстка не стрибає.
- Картинкам нижче першого екрана — `loading="lazy"`.
- Важкі сторінки завантажуйте під час переходу на них: ліниві маршрути в Angular, `React.lazy` і динамічний `import()`.

**Типова помилка**

Поставити `loading="lazy"` на головну картинку першого екрана. Вона почне завантажуватися пізніше, і LCP зросте.

**Підсумок:** три метрики — швидкість показу, відгук і стабільність; покращують їх, надсилаючи менше й раніше те, що потрібно першому екрану.

</A>

<A l="m">

**Як влаштовано**

| Метрика | Добре | Погано |
|---|---|---|
| LCP | до 2,5 с | більше 4 с |
| INP | до 200 мс | більше 500 мс |
| CLS | до 0,1 | більше 0,25 |

Оцінка — 75-й перцентиль візитів, окремо для мобільних і десктопа. INP замінив FID у березні 2024 року: FID вимірював лише затримку першого введення, INP враховує всі кліки, дотики й натискання клавіш.

**Лабораторія і поле**

| | Лабораторні дані | Польові дані |
|---|---|---|
| Джерело | Lighthouse, DevTools Performance | CrUX, бібліотека `web-vitals`, RUM |
| Умови | один пристрій, задана мережа | реальні пристрої й мережі |
| Для чого | налагодження, регресії в CI | що бачать користувачі |

Lighthouse під час завантаження сторінки INP не вимірює: у лабораторії його замінює Total Blocking Time.

**Пастки**

- Зелений Lighthouse на потужному ноутбуці за поганих польових даних із телефонів.
- `preload` для всього підряд: ресурси конкурують за канал, і важливе вантажиться пізніше.

**Правило**

LCP — картинка в HTML із `fetchpriority="high"`, INP — менше JS і коротші завдання, CLS — розміри в усього, що завантажується пізніше. Проблему шукають у полі, причину — в лабораторії.

**Підсумок:** метрики оцінюють за полем, налагоджують у лабораторії, а кожну лагодять своїм важелем.

</A>

<A l="s">

**Під капотом**

- LCP = час до першого байта + затримка початку завантаження ресурсу + тривалість завантаження + затримка відмальовування. Майже весь час має йти на завантаження HTML і самого ресурсу.
- INP = затримка введення + обробка + затримка до відмальовування. Береться найгірша взаємодія візиту, а за великої їх кількості одна найгірша на кожні 50 відкидається.
- HTTP/2 мультиплексує запити в одному з'єднанні, тому склеювати все в один файл більше не потрібно. HTTP/3 працює поверх QUIC і за втрати пакета не блокує решту потоків.

**Ціна**

- Кілобайт JS дорожчий за кілобайт картинки: його треба розібрати, скомпілювати й виконати в головному потоці.
- Шрифти: WOFF2 і підмножина символів. `font-display: swap` показує текст одразу, але зі зсувом під час підміни шрифту.
- Статика з хешем в імені кешується на рік (`Cache-Control: max-age=31536000, immutable`), HTML — `no-cache`. Серверний бік — у темі [Фонові задачі й кешування](/sobes/uk/aspnet/background-caching/), CDN — у [System design](/sobes/uk/arch/system-design/).

**Компроміси**

- **SSR і гідратація.** Сервер віддає готовий HTML, і LCP настає раніше. Але клієнт однаково завантажує JS і навішує обробники, і до кінця гідратації сторінка видима, але не відповідає. Детально — у темі [React і Next.js](/sobes/uk/front/react-next/).
- **Код-сплітинг.** Стартовий бандл менший, але перехід на лінивий маршрут чекає на завантаження чанка. Допомагає попереднє завантаження в простої або під час наведення.
- **`preconnect` і `preload`.** Перший заздалегідь відкриває з'єднання з іншим доменом, другий вантажить ресурс, який браузер знаходить пізно. Зайві підказки забирають канал у важливого.

**Як перевірити в продакшені**

- RUM: бібліотека `web-vitals` надсилає LCP, INP і CLS з атрибуцією у вашу аналітику; CrUX і Search Console показують підсумок за 28 днів.
- Бюджети в CI: `budgets` в `angular.json`, Lighthouse CI з порогами, аналіз бандла через `source-map-explorer`.

**Підсумок:** вимірюйте в полі, розбирайте метрику на частини й лагодьте найдовшу, а головний довгостроковий важіль — менше JavaScript на клієнті.

</A>

<Ex>

```html
<head>
  <!-- Заздалегідь відкрити з'єднання з CDN картинок: DNS, TCP, TLS -->
  <link rel="preconnect" href="https://img.example.com">
  <!-- Шрифт потрібен одразу, а в CSS браузер знайде його пізно -->
  <link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin>
  <style>
    @font-face {
      font-family: Inter;
      src: url(/fonts/inter.woff2) format("woff2");
      font-display: swap; /* текст одразу, резервним шрифтом */
    }
  </style>
```
