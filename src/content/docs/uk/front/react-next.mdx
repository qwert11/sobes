## Як влаштований React: компоненти, props, state і хуки?

<A short l="j">

React-застосунок складається з компонентів — функцій, які приймають <T k="props">props</T> і повертають розмітку на <T k="jsx">JSX</T>. Коли змінюється <T k="react-state">стан</T> з `useState`, React знову викликає компонент і оновлює в DOM лише те, що змінилося.

</A>

<A short l="m">

Компонент — чиста функція від props і state: дані йдуть згори вниз, а нагору повертаються через колбеки. <T k="react-hooks">Хуки</T> (`useState`, `useEffect` та інші) зберігають дані компонента між рендерами й прив'язані до порядку виклику, тому їх не викликають в умовах і циклах. Ціна моделі — зміна стану за замовчуванням перемальовує компонент разом з усіма нащадками, тому стан тримають якомога нижче в дереві.

</A>

<A short l="s">

React описує UI як функцію від стану: рендер будує нове дерево елементів, а <T k="react-reconciliation">узгодження</T> (reconciliation) порівнює його з попереднім і вносить у DOM мінімум змін. Ідентичність компонента задають місце в дереві та `key`, тому неправильний `key` губить або плутає стан. State — знімок на один рендер: `setState` планує новий рендер, а не змінює змінну, і оновлення пакетуються. Чистота рендера — контракт, на якому тримаються StrictMode, конкурентний рендеринг і React Compiler.

</A>

<A l="j">

**Що це**

- **Компонент** — функція, яка повертає JSX: розмітку, схожу на HTML, просто в JavaScript.
- **Props** — вхідні параметри від батька, лише для читання.
- **State** — дані, які компонент пам'ятає між рендерами.

**Як користуватися**

1. `const [count, setCount] = useState(0)` — значення й функція його зміни.
2. Виклик `setCount(count + 1)` запускає новий рендер з новим значенням.
3. Список рендерять через `map`, кожному елементу дають `key` — стабільний id.
4. Поле введення роблять <T k="controlled-component">контрольованим</T>: `value` береться зі state, `onChange` змінює state.

**Типова помилка**

Змінювати state напряму: `todos.push(x)`. Посилання на масив те саме, і React не побачить змін. Потрібен новий масив: `setTodos([...todos, x])`.

**Підсумок:** компонент — функція від props і state, а новий стан через `setState` — це новий рендер.

</A>

<A l="m">

**Як влаштовано**

1. **Рендер.** React викликає функцію компонента й отримує дерево елементів.
2. **Commit.** Порівнює його з попереднім деревом і точково змінює DOM.
3. **Повтор.** Новий state або рендер батька знову запускає компонент і за замовчуванням усіх його дітей.

**Правила хуків**

- Лише на верхньому рівні компонента або свого хука: не в умовах, циклах і після раннього `return`. React знаходить стан хуків за порядком виклику.
- Лише з компонентів і хуків, чиє ім'я починається з `use`.
- Порушення ловить `eslint-plugin-react-hooks`.

**Пастки**

- **State — знімок.** Після `setCount(count + 1)` змінна `count` до наступного рендера та сама. Три такі виклики поспіль дадуть +1, а `setCount(c => c + 1)` — +3.
- **Індекс як `key`.** Під час вставки на початок або сортування введення й фокус рядків переїдуть до чужих елементів.
- **Односпрямований потік.** Дитина не змінює props, а викликає колбек батька: `onChange`, `onSelect`.

**Правило**

Зберігайте в state мінімум, решту обчислюйте в рендері. Спільний стан кладіть у найближчого спільного батька.

**Підсумок:** рендер — чиста функція від props і state, а хуки працюють, поки порядок їх виклику не змінюється.

</A>

<A l="s">

**Під капотом**

- Кожному екземпляру компонента відповідає вузол fiber. У ньому лежить список хуків у порядку виклику, тому умовний хук зсуває список і ламає стан.
- Узгодження евристичне й лінійне: елемент іншого типу не порівнюється вглиб, а створюється заново разом з піддеревом. Діти списку зіставляються за `key`.
- З React 18 оновлення пакетуються всюди (automatic batching): кілька `setState` в обробнику, промісі чи таймері дають один рендер.

**Ціна**

- Рендер дешевший за commit, але не безкоштовний: перемальовування великого піддерева на кожне натискання клавіші помітне. Стан, що часто змінюється, тримають у листових компонентах.
- Зміна `key` або типу елемента скидає стан усього піддерева. Це й інструмент: `key={userId}` скидає форму під час зміни користувача.

**Компроміси**

- Контрольоване поле дає валідацію на кожне введення ціною рендера на кожен символ. Неконтрольовані поля з `FormData` дешевші, якщо значення потрібне лише під час надсилання.
- StrictMode у розробці викликає компонент двічі, щоб спіймати побічні ефекти в рендері. На тій самій чистоті побудовані конкурентний рендеринг і React Compiler.

**Як перевірити в продакшені**

- Profiler у React DevTools з опцією «Record why each component rendered while profiling» показує причину кожного рендера.
- Опція «Highlight updates when components render» підсвічує перемальовані компоненти.

**Підсумок:** ідентичність компонента — його позиція та `key`, а чистий рендер — умова, на якій тримаються всі оптимізації React.

</A>

<Ex>

```tsx
import { useState } from 'react';

type Todo = { id: number; title: string };

export function TodoList({ initial }: { initial: Todo[] }) {
  const [todos, setTodos] = useState(initial); // стан компонента
  const [title, setTitle] = useState('');      // контрольоване поле

  function add() {
    // Новий масив, а не push: React порівнює посилання
    setTodos([...todos, { id: Date.now(), title }]);
    setTitle('');
  }

  return (
    <>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      <button onClick={add} disabled={!title}>Add</button>
      <ul>
        {todos.map((t) => <li key={t.id}>{t.title}</li>)} {/* key — стабільний id, не індекс */}
      </ul>
    </>
  );
}
```

</Ex>

## Як правильно використовувати useEffect і де він не потрібен?

<A short l="j">

<T k="react-effect">Ефект</T> (`useEffect`) — код, який React запускає після відмальовування, щоб синхронізувати компонент із зовнішньою системою: підпискою, з'єднанням, стороннім віджетом. Другий аргумент — <T k="dependency-array">масив залежностей</T>: ефект перезапускається, лише коли вони змінюються.

</A>

<A short l="m">

Ефект синхронізує компонент із зовнішньою системою: після commit React виконує setup, а перед перезапуском і під час демонтування — <T k="effect-cleanup">очищення</T>, яке setup повернув. У залежностях — усі реактивні значення, прочитані всередині, інакше ефект працює із <T k="stale-closure">застарілим замиканням</T>. Якщо значення можна порахувати в рендері або дію виконати в обробнику події, ефект не потрібен: він додає зайвий рендер і місце для помилок.

</A>

<A short l="s">

Ефект — механізм синхронізації, а не «життєвий цикл»: setup і cleanup симетричні, і <T k="strict-mode">StrictMode</T> у розробці навмисно запускає зайвий цикл setup → cleanup → setup, щоб це перевірити. Об'єкт або функція в залежностях перезапускають ефект на кожен рендер, а нереактивну логіку виносять у <T k="use-effect-event">`useEffectEvent`</T> (React 19.2). Завантаження даних в ефекті дає водоспади запитів і гонки та не має кешу, тому його віддають TanStack Query або серверним компонентам.

</A>

<A l="j">

**Що це**

`useEffect(setup, deps)` виконує `setup` після того, як React оновив екран. Функція, яку повернув `setup`, — очищення.

**Як користуватися**

1. Усередині — робота із зовнішнім світом: `addEventListener`, `setInterval`, WebSocket.
2. У масив залежностей — усе, що ефект читає з props і state.
3. Поверніть очищення: `removeEventListener`, `clearInterval`, закриття з'єднання.

| Залежності | Коли запускається |
|---|---|
| масиву немає | після кожного рендера |
| `[]` | один раз після появи на екрані |
| `[userId]` | під час появи та зміни `userId` |

**Типова помилка**

Синхронізувати ефектом похідні дані: `useEffect(() => setFullName(first + ' ' + last), [first, last])`. Це зайвий рендер; досить `const fullName = first + ' ' + last` просто в компоненті.

**Підсумок:** ефект — для зв'язку із зовнішньою системою, а обчислення робляться в рендері.

</A>

<A l="m">

**Як влаштовано**

1. Рендер → commit у DOM → браузер малює → React запускає ефекти.
2. На наступному рендері React порівнює залежності через `Object.is`. Якщо щось змінилося — cleanup попереднього ефекту, потім новий setup.
3. Під час демонтування виконується останній cleanup.

**Пастки**

- **Застаріле замикання.** Ефект бачить props і state свого рендера. `setInterval(() => setCount(count + 1))` з `[]` застрягне на 1; потрібно `setCount(c => c + 1)`.
- **Об'єкт або функція в залежностях.** Вони створюються заново в кожному рендері, і ефект перезапускається завжди. Створіть їх усередині ефекту або залежте від примітивів.
- **Гонка відповідей.** Під час швидкої зміни `query` стара відповідь може прийти останньою. Прапорець `ignore` або `AbortController` у cleanup відкидає її.
- **Подвійний запуск у розробці.** Якщо через нього ламається логіка, в ефекту немає коректного очищення.

**Коли ефект не потрібен**

| Задача | Замість ефекту |
|---|---|
| похідне значення | обчислити в рендері, дороге — `useMemo` |
| реакція на клік або надсилання | обробник події |
| скидання state під час зміни prop | `key` у компонента |
| завантаження даних | TanStack Query, серверний компонент |

**Правило**

Ефект потрібен, коли код виконується тому, що компонент показано, а не тому, що користувач щось зробив.

**Підсумок:** у залежностях — усе прочитане, очищення — дзеркало setup, решта — у рендер і обробники.

</A>

<A l="s">

**Під капотом**

- `useEffect` виконується після відмальовування й не блокує його. `useLayoutEffect` виконується до відмальовування, для вимірювання DOM, і затримує кадр.
- Під час серверного рендерингу ефекти не виконуються — лише в браузері.
- StrictMode у розробці додає кожному ефекту цикл setup → cleanup → setup. У продакшені його немає, але він моделює реальні сценарії: перехід зі сторінки й повернення, Fast Refresh.

**Ціна**

Завантаження даних в ефекті стартує лише після завантаження JS і рендера. Вкладені компоненти з власними ефектами утворюють водоспад: запит дитини чекає відповіді батька. Кешу, дедуплікації та повторів у разі помилки немає.

**Компроміси**

- Прочитати свіже значення без перезапуску, наприклад тему всередині обробника з'єднання, — `useEffectEvent` (стабільний з React 19.2). Вимикати правило `exhaustive-deps` — ховати баг.
- Підписка на зовнішнє сховище — `useSyncExternalStore`, а не ефект із `setState`: він коректний під час конкурентного рендерингу.
- Дані — серверний компонент або TanStack Query: кеш, скасування й гонки розв'язані там.

**Як перевірити в продакшені**

- `eslint-plugin-react-hooks` з `exhaustive-deps` і `set-state-in-effect` — помилкою в CI.
- У Profiler React DevTools ланцюжок «ефект → `setState` → рендер» видно як зайві коміти поспіль.

**Підсумок:** ефект — інструмент синхронізації із зовнішнім світом; що менше ефектів, то менше водоспадів, гонок і зайвих рендерів.

</A>

<Ex>

```tsx
import { useEffect, useState } from 'react';

type Item = { name: string; active: boolean };

export function Search({ query, onlyActive }: { query: string; onlyActive: boolean }) {
  const [items, setItems] = useState<Item[]>([]);

  // Ефект: синхронізація із зовнішньою системою (сервером) під час зміни query
  useEffect(() => {
    let ignore = false; // відповідь на застарілий query не перезапише нову
    fetch(`/api/items?q=${encodeURIComponent(query)}`)
      .then((r) => r.json())
      .then((data: Item[]) => { if (!ignore) setItems(data); });
    return () => { ignore = true; }; // очищення: перед перезапуском і під час демонтування
  }, [query]);

  // Не ефект: похідне значення рахується просто в рендері
  const visible = onlyActive ? items.filter((i) => i.active) : items;

  return <ul>{visible.map((i) => <li key={i.name}>{i.name}</li>)}</ul>;
}
```

</Ex>

<Ex title="Застаріле замикання">

```tsx
import { useEffect, useState } from 'react';

export function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    // Помилка: setCount(count + 1) бачить count = 0 з першого рендера — застрягне на 1
    const id = setInterval(() => setCount((c) => c + 1), 1000); // апдейтер бере актуальне значення
    return () => clearInterval(id);
  }, []);

  return <p>{count}</p>; // 1, 2, 3...
}
```

</Ex>

- Чому ефект у розробці спрацьовує двічі? — StrictMode перевіряє, що очищення скасовує setup; у продакшені повторного запуску немає.
- Як не перезапускати ефект, якщо потрібно лише прочитати свіже значення? — Винести читання в `useEffectEvent` (React 19.2+).
- Як скасувати запит під час зміни параметрів? — `AbortController` і `abort()` у cleanup або прапорець `ignore`.
- Чи можна зробити функцію ефекту `async`? — Ні: вона має повернути cleanup, а не проміс; async-функцію оголошують усередині й викликають.

<Q id="front.react.state" level="m">

## Як керувати станом у React-застосунку?

<A short l="j">

Стан спочатку тримають локально в компоненті через `useState`. Якщо він потрібен двом сусідам, його <T k="lifting-state-up">піднімають</T> у спільного батька й передають через props, а дані із сервера зберігають у бібліотеці на кшталт <T k="tanstack-query">TanStack Query</T>, яка кешує відповіді.

</A>

<A short l="m">

Стан ділять за власником: клієнтський (UI, форми) живе в `useState`, у спільного батька або в сторі на кшталт <T k="zustand">Zustand</T>, а <T k="server-state">серверний</T> — копія даних сервера — у TanStack Query з кешем та інвалідацією. <T k="react-context">Context</T> прибирає <T k="prop-drilling">prop drilling</T>, але під час зміни значення перемальовує всіх споживачів. Фільтри, сторінка й вкладка — в URL, щоб посиланням можна було поділитися.

</A>

<A short l="s">

Головна помилка — змішувати серверний і клієнтський стан в одному сторі: тоді кеш, застарівання, повторні запити й інвалідацію пишуть вручну. Серверний — у TanStack Query або серверних компонентах, навігаційний — в URL, а глобальний стор із селекторами — для рідкісного справді спільного клієнтського стану. Context — спосіб передати значення, а не стор: підписки на частину значення в нього немає, тому дані, що часто змінюються, у ньому дорогі. У Next.js стор на рівні модуля спільний для всіх запитів сервера, тому його створюють на запит.

</A>

<A l="j">

**Що це**

Стан — дані, від яких залежить екран: чи відкритий діалог, текст у полі, список замовлень.

**Як користуватися**

1. Почніть з `useState` у компоненті, якому він потрібен.
2. Потрібен двом компонентам — підніміть state у найближчого спільного батька й передайте вниз значення та функцію зміни.
3. Значення потрібне глибоко й у багатьох місцях (тема, поточний користувач) — Context.
4. Дані із сервера — `useQuery` з TanStack Query: він завантажить, закешує й оновить їх.

**Типова помилка**

Копіювати props у state: `useState(props.user.name)`. Початкове значення береться один раз, і під час зміни props state залишиться старим.

**Підсумок:** state тримають якомога ближче до місця використання й піднімають, лише коли він потрібен кільком компонентам.

</A>

<A l="m">

**Як влаштовано**

- **Підняття стану.** State переїжджає в спільного батька, діти отримують значення й колбек. Ціна — props проходять через компоненти, яким вони не потрібні.
- **Context.** `createContext`, провайдер `<ThemeContext value={theme}>` (React 19) і `useContext` або `use`. Під час зміни значення перемальовуються всі споживачі.
- **Стор.** Zustand і Redux Toolkit зберігають стан поза деревом React. Компонент підписується селектором і перемальовується, лише коли змінюється вибрана частина.
- **Серверний стан.** TanStack Query зберігає відповіді в кеші за `queryKey`. Після мутації `invalidateQueries` позначає дані застарілими й перезапитує активні.

**Коли що обирати**

| Стан | Де зберігати |
|---|---|
| діалог відкритий, введення в полі | `useState` у компоненті |
| потрібен сусідам | спільний батько |
| тема, мова, користувач | Context |
| кошик, складний спільний UI | Zustand або Redux Toolkit |
| дані з API | TanStack Query, серверний компонент |
| фільтри, сторінка, вкладка | URL (`searchParams`) |

**Пастки**

- Новий об'єкт у `value` провайдера на кожному рендері перемальовує всіх споживачів. Розділяйте контексти або мемоізуйте `value`.
- Селектор Zustand, що повертає новий об'єкт або масив, перемальовує на кожну зміну стору — обгорніть його в `useShallow`.

**Правило**

Спершу вирішіть, чиї це дані: сервера, URL чи інтерфейсу. Від цього залежить місце зберігання.

**Підсумок:** серверний стан — у кеші запитів, навігаційний — в URL, клієнтський — якомога локальніше.

</A>

<A l="s">

**Під капотом**

- Context порівнює `value` через `Object.is` і перемальовує всіх споживачів нижче провайдера; `memo` їх не зупиняє.
- Zustand побудований на `useSyncExternalStore`: компонент перемальовується, лише якщо результат селектора змінився за `Object.is`.
- TanStack Query (v5) за замовчуванням вважає дані одразу застарілими (`staleTime: 0`) і перезапитує їх під час монтування, фокусу вікна та відновлення мережі. Невикористаний кеш живе 5 хвилин (`gcTime`).

**Ціна**

- Без `staleTime` кожне монтування й повернення на вкладку — мережевий запит. Для довідників ставлять хвилини.
- `queryKey` — контракт: неточний ключ дає застарілий екран після мутації або зайві запити.

**Компроміси**

- Zustand — мінімум коду й хук без провайдера. Redux Toolkit — сувора структура, історія дій у DevTools і RTK Query; виправданий у великій команді.
- У Next.js App Router дані читають у серверних компонентах. TanStack Query залишається для інтерактивного клієнта: нескінченні списки, опитування, оптимістичні оновлення.
- Стор на рівні модуля на сервері Next.js спільний для всіх запитів, і дані одного користувача витечуть до іншого. Документація Zustand радить створювати стор на запит і передавати через Context.

**Як перевірити в продакшені**

- TanStack Query Devtools показує ключі, свіжість і кількість підписників запиту.
- Profiler React DevTools показує, скільки компонентів перемалювала зміна значення Context.

**Підсумок:** вибір сховища — вибір власника даних, а швидкість залежить від гранулярності підписок.

</A>

```tsx
import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';

type Order = { id: number; status: string };

export function Orders() {
  const queryClient = useQueryClient();

  const { data, isPending } = useQuery({
    queryKey: ['orders'], // ключ кешу
    queryFn: (): Promise<Order[]> => fetch('/api/orders').then((r) => r.json()),
    staleTime: 30_000, // 30 секунд дані свіжі: без повторних запитів
  });

  const close = useMutation({
    mutationFn: (id: number) => fetch(`/api/orders/${id}/close`, { method: 'POST' }),
    // Інвалідація: кеш застарів, активні запити перезапитаються
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['orders'] }),
  });

  if (isPending) return <p>Loading…</p>;
  return (
    <ul>
      {data?.map((o) => (
        <li key={o.id}>
          #{o.id} {o.status} <button onClick={() => close.mutate(o.id)}>Close</button>
        </li>
      ))}
    </ul>
  );
}
```

<Q id="front.react.nextjs" level="m">

## Як влаштований Next.js і App Router?

<A short l="j">

Next.js — фреймворк поверх React з маршрутизацією за папками й рендерингом на сервері. В <T k="app-router">App Router</T> папка всередині `app/` — сегмент URL, `page.tsx` — сторінка, `layout.tsx` — спільний каркас. Компоненти за замовчуванням <T k="react-server-components">серверні</T>, а інтерактивні позначають директивою `'use client'`.

</A>

<A short l="m">

App Router будує маршрути з папок `app/` і вкладає layout один в одного, зберігаючи їхній стан під час навігації. Серверні компоненти виконуються лише на сервері й можуть читати базу напряму, а <T k="client-component">клієнтські</T> (`'use client'`) отримують JS у браузері для state і подій. HTML готується під час збирання або на кожен запит (<T k="ssr">SSR</T>), а дані змінюють через <T k="server-action">Server Actions</T>; з Next.js 16 кешування вмикається явно через `'use cache'`.

</A>

<A short l="s">

Next.js 16 змінив модель кешування: з Cache Components увесь код за замовчуванням виконується на запит, а кешується лише позначене <T k="use-cache">`'use cache'`</T> з `cacheLife` і `cacheTag`. Статичне й закешоване потрапляє в статичну оболонку, а динамічне стрімиться з-під `Suspense` — це <T k="partial-prerendering">Partial Prerendering</T>, і сторінка більше не обирає між SSG і SSR цілком. З 16.4 нові проєкти отримують Cache Components за замовчуванням, а в Next.js 17 модель стане спільною. Ціна — дисципліна: кожне звернення до даних запиту кешують або обгортають у `Suspense`, інакше dev-оверлей і збирання вкажуть на помилку.

</A>

<A l="j">

**Що це**

Next.js додає до React маршрутизацію, рендеринг на сервері, збирання й серверний код. App Router — маршрутизатор на основі папки `app/`.

**Як користуватися**

- `app/page.tsx` — це `/`, `app/blog/[slug]/page.tsx` — `/blog/hello`. Квадратні дужки — динамічний сегмент.
- `layout.tsx` обгортає всі сторінки під собою: шапка, меню.
- `loading.tsx` і `error.tsx` — екрани завантаження й помилки для сегмента.
- Серверний компонент може бути `async` і отримувати дані через `await`.
- Потрібні `useState` або `onClick` — перший рядок файлу `'use client'`.

**Типова помилка**

Ставити `'use client'` на всю сторінку заради однієї кнопки. Тоді весь код сторінки йде в браузер; у клієнтський компонент виносять лише кнопку.

**Підсумок:** папки — це URL, компоненти за замовчуванням серверні, а `'use client'` — лише для інтерактивних частин.

</A>

<A l="m">

**Як влаштовано**

1. Запит проходить `proxy.ts` (до Next.js 16 — `middleware.ts`), якщо він є: редиректи, перезапис URL, заголовки.
2. Серверні компоненти рендеряться в RSC Payload — серіалізоване дерево з місцями для клієнтських компонентів.
3. З нього будується HTML першого завантаження, а браузер завантажує JS клієнтських компонентів.
4. Під час переходу за `<Link>` сервер віддає лише сегменти, що змінилися; спільні layout не перемальовуються.

**Коли що обирати**

| Режим | Коли готовий HTML |
|---|---|
| SSG | під час збирання; однаковий для всіх |
| ISR | під час збирання, оновлюється у фоні за часом або тегом |
| SSR | на кожен запит; дані користувача |

**Серверний код**

- **Server Actions** (`'use server'`) — функції для зміни даних з форм і обробників. Викликаються POST-запитом.
- **Route Handlers** (`app/api/.../route.ts` з `export async function GET`) — HTTP API для вебхуків і зовнішніх клієнтів, наприклад мобільного застосунку.

**Пастки**

- З Next.js 15 `params`, `searchParams`, `cookies()` і `headers()` асинхронні, у 16 синхронний доступ вилучено.
- З Next.js 15 `fetch` і GET Route Handlers за замовчуванням не кешуються.
- Server Action — публічний ендпоінт: авторизацію перевіряють усередині кожного.

**Правило**

Читають дані в серверних компонентах, змінюють — у Server Actions, Route Handler — для зовнішніх споживачів.

**Підсумок:** App Router — серверні компоненти за замовчуванням, вкладені layout і явний серверний код для читання та зміни даних.

</A>

<A l="s">

**Під капотом**

- З `cacheComponents: true` усе динамічне виконується на запит. `'use cache'` у функції, компонента або файлу кешує результат; ключ — аргументи й захоплені значення, тому вони серіалізовні.
- Під час збирання статичне й закешоване потрапляє в статичну оболонку, а замість даних запиту під `Suspense` — fallback. Оболонку роздає CDN, решта стрімиться в тій самій відповіді.
- `cookies()` і `headers()` усередині `'use cache'` недоступні: значення читають ззовні й передають аргументом або використовують `'use cache: private'`.

**Інвалідація**

| API | Семантика |
|---|---|
| `updateTag(tag)` | лише в Server Action; автор одразу бачить свої зміни |
| `revalidateTag(tag, 'max')` | stale-while-revalidate: віддається старе, нове будується у фоні |
| `refresh()` | оновити некешовані дані, кеш не чіпає |

**Компроміси**

- Без Cache Components діє попередня модель: маршрут статичний, поки не читає даних запиту, а `export const revalidate` задає ISR. Одне читання `cookies()` робить динамічною всю сторінку.
- За замовчуванням кеш `'use cache'` живе в пам'яті екземпляра. Спільний для кількох екземплярів — `'use cache: remote'` з обробником кешу.
- `proxy.ts` працює на Node.js; `middleware.ts` для Edge застарів. Proxy — для швидких редиректів і заголовків, не для повної авторизації.
- Розгортання: Vercel, `next start` або `output: 'standalone'` у Docker, адаптери платформ (стабільні з 16.2). `output: 'export'` — статика без серверних можливостей.

**Як перевірити в продакшені**

- `next build` друкує тип кожного маршруту, dev-оверлей показує звернення до даних запиту поза `Suspense`.
- `export const ensureStatic = 'navigation'` (16.4) валить збирання, якщо в статичний маршрут потрапив динамічний компонент.

**Підсумок:** у Next.js 16 кеш явний і гранулярний: статична оболонка з CDN, динаміка стрімиться, інвалідація — за тегами.

</A>

```tsx
// app/products/[id]/page.tsx — серверний компонент за замовчуванням

import { cacheLife, cacheTag } from 'next/cache';
import { AddToCart } from './add-to-cart'; // файл з 'use client'

type Props = { params: Promise<{ id: string }> }; // з Next.js 15 params — проміс

export default function Page({ params }: Props) {
  return (
    <Suspense fallback={<p>Loading…</p>}> {/* fallback потрапляє в статичну оболонку */}
      <Product params={params} />
    </Suspense>
  );
}

async function Product({ params }: Props) {
  const { id } = await params;
  const product = await getProduct(id);
  return (
    <main>
      <h1>{product.name}</h1>
      <AddToCart id={id} /> {/* у браузер іде JS лише цього компонента */}
    </main>
  );
}

async function getProduct(id: string) {
  'use cache'; // Cache Components: результат кешується за аргументами
  cacheLife('hours');
  cacheTag(`product-${id}`); // скинути після зміни: updateTag у Server Action
  const res = await fetch(`https://api.example.com/products/${id}`);
  return (await res.json()) as { name: string };
}
```

<Q id="front.react.rendering" level="s">

## Що нового в React 19 і як досягти швидкого рендерингу?

<A short l="j">

React 19 додав <T k="react-action">Actions</T> — асинхронні функції для форм і мутацій, у яких React сам відстежує очікування, помилки й оптимістичні оновлення через `useActionState` і `useOptimistic`. <T k="react-compiler">React Compiler</T> сам мемоізує компоненти, тому `useMemo` і `useCallback` пишуть рідше.

</A>

<A short l="m">

Action — асинхронна функція, запущена в <T k="transition">переході</T> (transition): `useActionState` дає результат і прапорець очікування, `useOptimistic` показує зміну до відповіді сервера, а `use` читає проміс або контекст. Швидкий перший показ дає серверний рендер зі <T k="streaming-ssr">стрімінгом</T>: HTML іде частинами, які відділяють межі <T k="suspense">`Suspense`</T>, і повільні дані не блокують сторінку. З React Compiler ручна мемоізація потрібна рідко, але компілятор вимагає дотримуватися правил React.

</A>

<A short l="s">

У React 19 сервер став частиною моделі: серверні компоненти не надсилають свій код у браузер, а межа `'use client'` — межа серіалізації, крізь яку проходять лише серіалізовні props. Actions і переходи роблять мутації й очікування декларативними, а `Suspense` зі стрімінгом і вибірковою <T k="hydration">гідратацією</T> розбиває завантаження на незалежні частини. React Compiler 1.0 автоматично мемоізує те, що раніше робили `memo`, `useMemo` і `useCallback`. Ціна — чистий рендер, однаковий HTML на сервері й клієнті та вимірювання в Profiler замість мемоізації навмання.

</A>

<A l="j">

**Що це**

- **Action** — функція, передана в `<form action={...}>`: отримує `FormData`, а React сам знає, чи триває надсилання.
- **`useActionState`** — результат останньої дії та прапорець `isPending`.
- **`useOptimistic`** — тимчасове значення, яке видно, поки дія виконується.
- **React Compiler** — плагін збирання, який сам кешує обчислення й пропускає зайві рендери.

**Як користуватися**

1. `const [error, formAction, isPending] = useActionState(save, null)`.
2. `<form action={formAction}>` і кнопка з `disabled={isPending}`.
3. Компілятор у Next.js 16 вмикають опцією `reactCompiler: true`; в Expo SDK 54+ він увімкнений за замовчуванням.

**Типова помилка**

Обгортати кожну функцію в `useCallback` «для швидкості». Без вимірювань це шум, а з компілятором — зайвий код.

**Підсумок:** Actions прибирають ручні прапорці завантаження, а компілятор — більшу частину ручної мемоізації.

</A>

<A l="m">

**Як влаштовано**

- **Перехід.** `startTransition` позначає оновлення нетерміновим: введення лишається чутливим, а старий UI видно, поки готується новий. Action — асинхронна функція всередині переходу.
- **`useOptimistic`.** Сетер викликають усередині Action. Коли дія завершилася, оптимістичне значення змінюється реальним, у разі помилки — зникає.
- **`use`.** Читає проміс, призупиняючи компонент до результату, або контекст. Його, на відміну від інших хуків, можна викликати в умовах.
- **Suspense і стрімінг.** Найближчий `Suspense` показує fallback, поки компонент чекає дані. Сервер одразу надсилає оболонку, а готові частини дописує в ту саму відповідь.
- **Гідратація.** React прив'язує обробники до HTML, що прийшов із сервера. Межі `Suspense` гідратуються незалежно, першою — та, з якою взаємодіє користувач.

**Пастки**

- **Помилка гідратації** — HTML сервера не збігся з першим клієнтським рендером: `Date.now()`, `typeof window`, локаль, `<div>` усередині `<p>`. React перемалює ділянку на клієнті — це повільніше.
- **Проміс, створений у рендері клієнтського компонента**, для `use` створюється заново на кожен рендер. Його передають із серверного компонента або беруть із кешувальної бібліотеки.

**Правило**

Спершу виміряйте в Profiler, потім оптимізуйте: опустіть стан нижче, розбийте сторінку на `Suspense`, увімкніть компілятор.

**Підсумок:** React 19 робить очікування й мутації декларативними, а перше завантаження пришвидшують стрімінг і вибіркова гідратація.

</A>

<A l="s">

**Під капотом**

- Серверні компоненти виконуються на сервері й серіалізуються в RSC Payload; їхній код і залежності не потрапляють у бандл.
- Межа `'use client'` — межа серіалізації. Props крізь неї: примітиви, прості об'єкти, масиви, `Date`, `Map`, `Set`, проміси, JSX і Server Functions. Звичайні функції та екземпляри класів передати не можна.
- React Compiler 1.0 (жовтень 2025) під час збирання аналізує потік даних і мемоізує значення, JSX і колбеки, зокрема після раннього `return`, де `useMemo` неможливий. Компонент, що порушує правила React, він пропускає.

**Компроміси**

- `useMemo` і `useCallback` лишаються для точного контролю, наприклад стабільної залежності ефекту. Наявну мемоізацію прибирають лише з тестами: це змінює результат компіляції.
- У Next.js 16 компілятор не ввімкнений за замовчуванням і працює через Babel, збирання повільніше; Rust-версія експериментальна з 16.3.
- Стрімінг пришвидшує перший байт, але кожна межа `Suspense` — окремий стан завантаження. Надто дрібні межі дають розсип спінерів.
- Компонент лише для браузера (`localStorage`, часовий пояс) — `use(browser())` з React 19.3 замість прапорця `mounted` в ефекті.

**Як перевірити в продакшені**

- Profiler у React DevTools: flamegraph комітів і причини рендерів. Компоненти, оптимізовані компілятором, позначені бейджем «Memo ✨».
- Performance Tracks у Chrome DevTools (React 19.2) показують роботу планувальника й компонентів на одній шкалі з мережею.
- Помилки гідратації видно в консолі з діфом сервер/клієнт, а в продакшені — через `onRecoverableError`.

**Підсумок:** швидкий React — менше JS на клієнті завдяки серверним компонентам, стрімінг, розбитий межами `Suspense`, і автоматична мемоізація замість ручної.

</A>

<Ex>

```tsx
'use client';
import { useActionState, useOptimistic } from 'react';
import { addComment } from './actions'; // Server Function: (prev, formData) => Promise<string | null>

type Comment = { id: string; text: string };

export function Comments({ comments }: { comments: Comment[] }) {
  const [optimistic, addOptimistic] = useOptimistic(
    comments,
    (list, c: Comment) => [...list, c],
  );
  const [error, formAction, isPending] = useActionState(
    async (prev: string | null, formData: FormData) => {
      // Видно одразу, до відповіді сервера; у разі помилки рядок зникне
      addOptimistic({ id: crypto.randomUUID(), text: String(formData.get('text')) });
      return addComment(prev, formData); // текст помилки або null
    },
    null,
  );

  return (
    <form action={formAction}>
      <ul>{optimistic.map((c) => <li key={c.id}>{c.text}</li>)}</ul>
      <input name="text" />
      <button disabled={isPending}>Send</button>
      {error && <p role="alert">{error}</p>}
    </form>
  );
}
```

</Ex>

<Ex title="Проміс крізь межу серіалізації">

```tsx
// app/orders/page.tsx — серверний компонент
import { Suspense } from 'react';
import { OrderList } from './order-list';

export default function Page() {
  const orders = getOrders(); // без await: запит стартує одразу
  return (
    <Suspense fallback={<p>Loading…</p>}> {/* fallback іде в HTML першим */}
      <OrderList orders={orders} /> {/* проміс серіалізовний — його можна передати */}
    </Suspense>
  );
}

// app/orders/order-list.tsx
'use client';
import { use } from 'react';

export function OrderList({ orders }: { orders: Promise<{ id: number }[]> }) {
  const list = use(orders); // призупиняє компонент до відповіді
  return <ul>{list.map((o) => <li key={o.id}>#{o.id}</li>)}</ul>;
}
```

<Next>

- Що можна передати із серверного компонента в клієнтський? — Серіалізовне: примітиви, прості об'єкти, масиви, `Date`, `Map`, `Set`, проміси, JSX, Server Functions; не звичайні функції й класи.
- Чим `useActionState` відрізняється від `useFormStatus`? — Перший зберігає результат і очікування конкретної дії; `useFormStatus` з `react-dom` читає статус батьківської форми в дочірньому компоненті.
- Чи потрібні `useMemo` і `useCallback` з React Compiler? — Рідко: для точного контролю, наприклад стабільної залежності ефекту; стару мемоізацію прибирають лише з тестами.
- Як виправити помилку гідратації? — Прибрати відмінність сервер/клієнт: браузерне — в ефект або `use(browser())`; `suppressHydrationWarning` — лише для тексту на кшталт дати.
- Чим `useTransition` відрізняється від `useDeferredValue`? — Перший позначає нетерміновим своє оновлення, другий відкладає значення, оновлення якого ви не контролюєте.
