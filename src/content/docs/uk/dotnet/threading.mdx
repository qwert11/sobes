<Q id="dotnet.threading.thread-vs-task" level="j">

## Чим `Thread` відрізняється від `Task` і що таке пул потоків?

<A short l="j">

`Thread` — це потік операційної системи, який ви створюєте й запускаєте самі, а <T k="task">`Task`</T> — задача, тобто опис роботи з майбутнім результатом. Задача виконується на готовому потоці з <T k="thread-pool">пулу потоків</T>, який CLR перевикористовує, тому для фонової роботи беруть `Task.Run`, а не `new Thread`.

</A>

<A short l="m">

`Thread` — ресурс ОС зі своїм стеком, а `Task` — об'єкт, який описує роботу й ставиться в чергу пулу потоків. Головна відмінність: задача дає результат, винятки, скасування, продовження та `await`, а потік для неї пул бере готовий. Ціна свободи `Thread` — ручне керування й дороге створення, тому власний потік потрібен лише для довгої блокувальної роботи, особливого пріоритету, STA або <T k="background-thread">основного (foreground) потоку</T>.

</A>

<A short l="s">

`Task` — promise-подібна абстракція, і не кожна задача взагалі займає потік: задача від асинхронного I/O або `TaskCompletionSource` просто чекає сигналу. Пул один на процес: у нього глобальна FIFO-черга, локальні черги робочих потоків і <T k="work-stealing">work stealing</T>, а кількість потоків він підбирає сам за пропускною здатністю. Тому блокувати потоки пулу дорого: понад мінімум нові потоки з'являються поступово, і під навантаженням робота накопичується в черзі.

</A>

<A l="j">

**Що це**

- **`Thread`** — потік ОС. Його створюють через `new Thread(...)`, запускають `Start()` і чекають `Join()`.
- **Пул потоків** — набір фонових потоків, які CLR створює за потреби й перевикористовує.
- **`Task`** — одиниця роботи з результатом. `Task.Run(...)` ставить делегат у чергу пулу й повертає `Task` або `Task<T>`.

**Навіщо**

Створювати потік дорого: кожен резервує свій стек — за замовчуванням 1,5 МБ на Windows і 8 МБ на Linux. Пул прибирає цю ціну: після задачі потік повертається в пул.

**Як користуватися**

1. Запустити роботу: `var task = Task.Run(() => Compute());`.
2. Дочекатися результату: `int result = await task;`.

**Типова помилка**

Вважати, що `Task` — це потік. Задача може взагалі не займати потік, поки чекає відповіді від мережі чи диска.

**Підсумок:** для фонової роботи беріть `Task`, а власний `Thread` — лише коли без нього не обійтися.

</A>

<A l="m">

**Як влаштовано**

- `Task` зберігає стан, результат (`Task<T>`) і виняток. Під час `await` виняток прокидається як є, під час `.Wait()` і `.Result` — загорнутим в `AggregateException`.
- Потоки пулу фонові: процес не чекає на них під час завершення.
- `new Thread` за замовчуванням основний (`IsBackground = false`) і тримає процес живим, доки не закінчить роботу.
- `TaskCreationOptions.LongRunning` — підказка планувальнику виділити задачі окремий потік поза пулом.

**Коли що обирати**

| Задача | Що взяти |
|---|---|
| Коротка CPU-робота у фоні | `Task.Run` |
| Очікування мережі чи диска | асинхронний API і `await`, без `Task.Run` |
| Довга блокувальна робота | `LongRunning` або власний `Thread` |
| STA (COM, UI), особливий пріоритет | власний `Thread` |

**Пастки**

- `Task.Run(() => File.ReadAllText(path))` займає потік пулу очікуванням диска. Краще `await File.ReadAllTextAsync(path)`.
- `Thread.Abort` у .NET 5+ кидає `PlatformNotSupportedException`. Потік зупиняють кооперативно, через `CancellationToken`.

**Правило**

`Task.Run` — для CPU-роботи, `await` — для I/O, `Thread` — лише коли потрібен контроль над самим потоком.

**Підсумок:** `Task` описує роботу, а пул вирішує, на якому потоці її виконати.

</A>

<A l="s">

**Під капотом**

- Кожна задача для пулу — це work item, елемент його черги.
- Work item, поставлений із коду на потоці пулу, потрапляє в локальну чергу цього потоку. Її читають у порядку LIFO — заради кеш-локальності.
- Решта роботи йде в глобальну FIFO-чергу.
- Вільний потік шукає роботу по черзі:
  1. у своїй локальній черзі;
  2. у глобальній;
  3. з хвоста чужої локальної черги — це і є work stealing.
- До мінімуму потоків (`ThreadPool.GetMinThreads`, за замовчуванням — кількість процесорів) пул створює їх одразу. Вище вирішує алгоритм, який змінює кількість потоків і стежить за пропускною здатністю.

**Ціна**

- Кожен зайвий потік — це пам'ять під стек, перемикання контексту й зайва робота GC під час обходу стеків.
- Заблокований потік пулу випадає з роботи, а заміна йому понад мінімум з'являється не одразу.

**Компроміси**

- `LongRunning` з async-делегатом безглуздий: виділений потік живе лише до першого `await`, далі продовження йде в пул.
- З .NET 8 на Windows можна перейти на пул Windows (`UseWindowsThreadPool`); у Native AOT на Windows він увімкнений за замовчуванням. Виграш залежить від навантаження й перевіряється замірами.

**Як перевірити в продакшені**

`dotnet-counters monitor` показує кількість потоків пулу, довжину його черги й кількість завершених work items. Потоків більше приблизно трьох на ядро — ознака того, що код блокує потоки пулу.

**Підсумок:** пул розрахований на короткі неблокувальні work items, і все, що тримає його потоки, б'є по пропускній здатності.

</A>

<Ex>

```csharp
// Власний потік: створюємо й чекаємо вручну, за замовчуванням він основний (foreground)
var thread = new Thread(() => Console.WriteLine("running on a dedicated thread"));
thread.Start();
thread.Join();

// Задача на пулі потоків: є результат
Task<int> task = Task.Run(() => 6 * 7);
Console.WriteLine(await task); // 42

// Потоки пулу — фонові
await Task.Run(() => Console.WriteLine(Thread.CurrentThread.IsBackground)); // True

// Довга блокувальна робота — окремий потік поза пулом
await Task.Factory.StartNew(() => Thread.Sleep(1000), TaskCreationOptions.LongRunning);
```

</Ex>

<Next>

- Що станеться з процесом, якщо `Main` завершився, а `new Thread` ще працює? — Процес дочекається потоку: за замовчуванням він основний (foreground).
- Чим `Task.Run` відрізняється від `Task.Factory.StartNew`? — У `Task.Run` безпечні значення за замовчуванням (`DenyChildAttach`, типовий планувальник), і він розгортає async-лямбди.
- Чи займає потік задача, яка чекає відповіді від БД? — Ні: асинхронний I/O не тримає потік, потік потрібен лише продовженню.
- Скільки потоків у пулі? — Мінімум за замовчуванням дорівнює кількості процесорів, далі пул підбирає кількість сам.
- Навіщо `TaskCreationOptions.LongRunning`? — Щоб довга блокувальна робота отримала окремий потік і не займала пул.

</Next>

<Q id="dotnet.threading.race-condition" level="j">

## Що таке race condition і deadlock і як їх уникнути?

<A short l="j">

<T k="race-condition">Race condition</T> (стан гонитви) — помилка, коли результат залежить від порядку звертань потоків до спільних даних, а <T k="deadlock">deadlock</T> (взаємоблокування) — вічне очікування потоків один на одного. Гонка тихо псує дані, а дедлок вішає програму, тому від гонки захищаються синхронізацією, а від дедлоку — єдиним порядком захоплення блокувань.

</A>

<A short l="m">

Гонка — це несинхронізована складена операція над спільними даними, а дедлок — цикл очікування між потоками, які тримають блокування. Гонка виникає, бо «прочитати — змінити — записати» не атомарне, а дедлок — бо потоки беруть ті самі блокування в різному порядку. Захист коштує продуктивності, тому <T k="critical-section">критичні секції</T> тримають короткими й без чужого коду всередині, а де можна відступити — беруть блокування з тайм-аутом.

</A>

<A short l="s">

Race condition — логічна помилка порядку подій, а data race — її низькорівневий різновид: одночасний доступ до пам'яті без синхронізації, де хоча б один потік пише. Data race небезпечніший, ніж здається: JIT і процесор мають право переставляти й кешувати такі звертання, і потік може взагалі не побачити чужий запис. Дедлок потребує чотирьох умов Коффмана, і найдешевше розірвати циклічне очікування глобальним порядком блокувань. У продакшені його знаходять за дампом, де видно, хто тримає блокування і хто на нього чекає.

</A>

<A l="j">

**Що це**

- **Race condition** — результат залежить від того, який потік встиг першим.
- **Deadlock** — потік 1 тримає ресурс A і чекає B, потік 2 тримає B і чекає A. Обидва стоять вічно.

**Навіщо**

Це дві головні помилки багатопотокового коду. Обидві залежать від таймінгу й погано ловляться тестами.

**Як уникнути**

- Не ділити змінювані дані між потоками, якщо можна.
- Спільні дані захищати `lock` — він пускає в блок лише один потік.
- Прості лічильники змінювати через `Interlocked.Increment` — однією неподільною операцією.
- Брати блокування завжди в одному порядку й тримати їх якомога менше.

**Типова помилка**

Вважати `count++` однією операцією. Це три кроки — прочитати, додати, записати, — і у двох потоків одне збільшення може загубитися.

**Підсумок:** гонка псує дані, дедлок вішає програму; від обох захищає дисципліна роботи зі спільним станом.

</A>

<A l="m">

**Як влаштовано**

- <T k="atomic-operation">Атомарна операція</T> виконується повністю: інший потік не побачить проміжного стану.
- Читання й запис вирівняного `int` або посилання атомарні. Складені операції — ні: `x++`, «перевірити, потім додати».
- Дедлок виникає, коли кожен потік тримає блокування й чекає на те, яке тримає інший.

**Коли що обирати**

| Ситуація | Інструмент |
|---|---|
| Одна змінна: лічильник, прапорець | `Interlocked` |
| Інваріант із кількох полів | `lock` |
| Спільний словник або черга | конкурентні колекції |
| Дані можна не ділити | ізоляція за потоками, незмінні об'єкти |

**Пастки**

- `if (!dict.ContainsKey(k)) dict[k] = v;` — гонка навіть на `ConcurrentDictionary`: між перевіркою й записом вклиниться інший потік. Потрібен один виклик `TryAdd`.
- Виклик подій, колбеків або віртуальних методів усередині `lock`: чужий код може взяти інше блокування й замкнути цикл.
- Синхронне очікування асинхронного коду (`.Result`) під однопотоковим `SynchronizationContext` — дедлок без жодного `lock`.

**Правило**

Усі беруть блокування в одному порядку. Де можна відступити — `Monitor.TryEnter` або `Lock.TryEnter` з тайм-аутом.

**Підсумок:** гонку прибирає атомарність, дедлок — порядок захоплення й короткі критичні секції.

</A>

<A l="s">

**Під капотом**

- Data race — одночасний доступ до однієї комірки пам'яті без синхронізації, де хоча б один доступ — запис.
- JIT може прочитати поле один раз і тримати значення в регістрі. Цикл `while (!_stop)` без `volatile` може так і не побачити `_stop = true`.
- Дедлок потребує чотирьох умов Коффмана:
  1. взаємне виключення;
  2. утримання ресурсу з очікуванням іншого;
  3. відсутність витіснення;
  4. циклічне очікування.

**Ціна**

Дедлок — це зависання без навантаження на CPU, яке часто проявляється лише під навантаженням. Процес живий, але запити, яким потрібне блокування, не завершуються.

**Компроміси**

- Порядок блокувань (ієрархія рівнів) розриває цикл, але потребує дисципліни в усій кодовій базі.
- `TryEnter` з тайм-аутом прибирає нескінченне очікування, але додає гілку відмови, яку треба продумати.
- Livelock: потоки активні, але без прогресу — наприклад, нескінченно повторюють `CompareExchange`. Лікується паузами між спробами (`SpinWait`).
- Найкраща синхронізація — її відсутність: незмінні знімки, передача повідомлень через черги, розбиття даних за потоками.

**Як перевірити в продакшені**

1. Зняти дамп: `dotnet-dump collect -p PID`.
2. У `dotnet-dump analyze` виконати `clrstack -all` або `parallelstacks` і знайти потоки, що стоять у `Monitor.Enter`.
3. Команда `syncblk` покаже, який потік володіє `Monitor` і скільки потоків на нього чекають.
4. Для async-ланцюжків — `dumpasync`.

**Підсумок:** дедлок — це цикл очікування; його запобігають порядком блокувань і знаходять за дампом.

</A>

<Ex>

```csharp
int unsafeCount = 0;
int safeCount = 0;

Parallel.For(0, 100_000, _ =>
{
    unsafeCount++;                        // гонка: читання, додавання й запис не атомарні
    Interlocked.Increment(ref safeCount); // атомарно
});

Console.WriteLine(unsafeCount); // зазвичай менше 100000
Console.WriteLine(safeCount);   // 100000

// Дедлок: два потоки беруть блокування a і b у різному порядку
var a = new object();
var b = new object();
var t1 = Task.Run(() => { lock (a) { Thread.Sleep(50); lock (b) { } } });
var t2 = Task.Run(() => { lock (b) { Thread.Sleep(50); lock (a) { } } });
// await Task.WhenAll(t1, t2) не завершиться ніколи.
// Виправлення: обидва потоки беруть спершу a, потім b.
```

Перше число змінюється від запуску до запуску — це і є гонка.

</Ex>

- Чи атомарний запис `long`? — На 64-бітній платформі — так, якщо значення вирівняне; на 32-бітній — ні, потрібні `Interlocked.Read` або `Volatile`.
- Чому `ContainsKey`, а потім запис — помилка навіть для `ConcurrentDictionary`? — Між двома викликами вклиниться інший потік; потрібна одна операція `TryAdd` або `GetOrAdd`.
- Як знайти дедлок у продакшені? — Зняти дамп і подивитися `clrstack -all` і `syncblk` у `dotnet-dump analyze` або Parallel Stacks у Visual Studio.
- Що таке livelock? — Потоки не заблоковані, але через постійні повтори не роблять корисної роботи.
- Чи може потік влаштувати дедлок сам із собою? — З `lock` ні, він реентерабельний; із `SemaphoreSlim(1, 1)` так: повторний `Wait` чекає сам на себе.

</Next>

<Q id="dotnet.threading.lock" level="m">

## Як працює `lock` і що дає тип `System.Threading.Lock` (.NET 9)?

<A short l="j">

`lock (obj) { ... }` пускає в блок лише один потік за раз, а решта чекають, доки він вийде. Блокування знімається навіть під час винятку, а з .NET 9 і C# 13 блокуються на окремому полі типу `System.Threading.Lock`.

</A>

<A short l="m">

`lock` — синтаксичний цукор: для звичайного об'єкта він розгортається в <T k="monitor">`Monitor.Enter`</T> і `Monitor.Exit` у `try/finally`, а для виразу типу <T k="lock-type">`System.Threading.Lock`</T> — у `using (x.EnterScope())`. Обидва варіанти <T k="reentrant-lock">реентерабельні</T> й прив'язані до потоку: звільнити блокування має той самий потік, що його взяв. Тому всередині `lock` не можна `await` (помилка компіляції), а I/O і виклики чужого коду там перетворюють блокування на вузьке місце або на дедлок.

</A>

<A short l="s">

`Monitor` зберігає стан блокування в заголовку об'єкта й за конкуренції переходить на <T k="sync-block">sync block</T>, тому заблокуватися можна на будь-якому об'єкті — зокрема на чужому. `Lock` — виділений тип із власним станом, і Microsoft рекомендує його заради продуктивності та ясності наміру. Ціна — сувора типізація: якщо статичний тип виразу не `Lock`, наприклад після приведення до `object`, компілятор згенерує `Monitor` і видасть попередження CS9216.

</A>

<A l="j">

**Що це**

`lock` гарантує, що код усередині блоку в кожен момент виконує лише один потік. Решта потоків, які дійшли до `lock` з тим самим об'єктом, чекають.

**Навіщо**

Щоб кілька потоків не змінювали спільні дані одночасно. Наприклад, щоб два списання з одного рахунку не вивели баланс у мінус.

**Як користуватися**

1. Завести приватне поле: `private readonly Lock _sync = new();` (до .NET 9 — `new object()`).
2. Обгорнути роботу зі спільними даними: `lock (_sync) { _balance -= amount; }`.
3. Тримати всередині лише цю роботу — без I/O і довгих обчислень.

**Типова помилка**

Блокуватися на `this`, `typeof(...)` або рядку. Їх може заблокувати й чужий код — вийде зайва конкуренція або дедлок.

**Підсумок:** `lock` — на приватному полі, коротко й лише навколо спільних даних.

</A>

<A l="m">

**Як влаштовано**

- Для посилального типу `lock` компілюється в `Monitor.Enter(obj, ref lockTaken)` у `try` і `Monitor.Exit(obj)` у `finally`.
- Для `Lock` — у `using (x.EnterScope())`. `Lock.Scope` — це `ref struct` з методом `Dispose`.
- Потік, який уже володіє блокуванням, може ввійти повторно. Вийти потрібно стільки ж разів.
- Звільнити блокування може лише потік-власник, інакше `SynchronizationLockException`.

**Коли що обирати**

| Ситуація | Що взяти |
|---|---|
| .NET 9+, синхронний код | поле `Lock` і `lock` |
| .NET 8 і раніше | поле `object` і `lock` |
| Потрібен `await` усередині | семафор на один слот: `SemaphoreSlim(1, 1)` і `WaitAsync` |
| Потрібен тайм-аут | `Lock.TryEnter` або `Monitor.TryEnter` |

**Пастки**

- `await` усередині `lock` — помилка CS1996: продовження може виконатися на іншому потоці, а вийти має власник.
- `object o = _sync; lock (o)` — це вже `Monitor`, а не `Lock` (попередження CS9216).
- Виклик подій, колбеків і віртуальних методів усередині `lock`: чужий код може взяти інше блокування й влаштувати дедлок.
- `lock` за значущим типом не компілюється: кожне пакування давало б новий об'єкт.

**Правило**

Одне блокування — на один ресурс, усередині — лише робота з його даними.

**Підсумок:** `lock` — це `Monitor` або `Lock` у `try/finally`, прив'язаний до потоку, тому без `await` усередині.

</A>

<A l="s">

**Під капотом**

- Будь-який об'єкт може слугувати монітором. Поки конкуренції немає, стан блокування лежить у заголовку об'єкта (thin lock).
- За конкуренції або очікування рантайм «роздуває» блокування до sync block — запису у внутрішній таблиці.
- `Lock` зберігає стан у власному полі й не чіпає заголовок об'єкта. Швидкий шлях без конкуренції — атомарна операція над цим полем.
- Вхід у блокування не дає наступним читанням виконатися раніше за нього, а вихід не дає попереднім записам затриматися після нього. Тому полям, доступним лише під `lock`, `volatile` не потрібен.

**Ціна**

- Неконкурентний `lock` дешевий. Дорогий — конкурентний: потоки крутяться в спіні, потім ідуть в очікування, і зростає затримка.
- Довга черга на одне блокування (lock convoy) зводить паралельний код до послідовного.

**Компроміси**

- `Lock` прибирає зайвий `object` і показує намір типом, але в нього немає `Wait` і `Pulse`. Код на `Monitor.Wait` під час міграції доведеться переписати на інший примітив.
- Проти конкуренції: звузити секцію, розбити дані на шарди з окремими блокуваннями або перейти на структури без блокувань.

**Як перевірити в продакшені**

- У `dotnet-counters` — `dotnet.monitor.lock_contentions` (до .NET 9 — Monitor Lock Contention Count): скільки разів потік чекав на зайнятий `Monitor`.
- У дампі команда `syncblk` показує власників `Monitor` і кількість потоків, що чекають.
- З .NET 9 `dotnet-trace` пише подію WaitHandleWait зі стеком, зокрема для очікувань у `lock`.

**Підсумок:** `Lock` — вибір за замовчуванням у .NET 9+, а вузьке місце шукають за лічильником конкуренції та стеками очікувань.

</A>

<Ex>

```csharp
public sealed class Account
{
    private readonly Lock _sync = new(); // C# 13 / .NET 9+, раніше — new object()
    private decimal _balance;

    public bool TryDebit(decimal amount)
    {
        lock (_sync) // компілятор генерує using (_sync.EnterScope())
        {
            if (_balance < amount) return false;
            _balance -= amount;
            return true;
        }
    }

    public void Credit(decimal amount)
    {
        lock (_sync) { _balance += amount; }
    }

    // object o = _sync; lock (o) { }       — попередження CS9216: це вже Monitor
    // lock (_sync) { await SaveAsync(); }  — помилка CS1996: await усередині lock заборонений
}
```

</Ex>

<Next>

- Чому не можна `lock (this)`? — Зовнішній код може заблокуватися на тому самому об'єкті: зайва конкуренція або дедлок.
- Що буде, якщо всередині `lock` вилетить виняток? — Блокування зніметься у `finally`, але дані можуть залишитися в неузгодженому стані.
- Як зробити взаємне виключення в async-коді? — `SemaphoreSlim(1, 1)`: `await WaitAsync()`, а `Release()` — у `finally`.
- Чи реентерабельний `lock`? — Так, і з `Monitor`, і з `Lock`: той самий потік може ввійти повторно.
- Що зміниться, якщо поле з `new Lock()` оголосити як `object`? — `lock` перейде на `Monitor`, а компілятор видасть CS9216.

</Next>

<Q id="dotnet.threading.sync-primitives" level="m">

## Які примітиви синхронізації є в .NET і чим вони відрізняються?

<A short l="j">

Примітиви синхронізації — типи, які координують потоки: одні пускають у секцію один потік (`lock`, <T k="mutex">`Mutex`</T>), інші — до N потоків (<T k="semaphore-slim">`SemaphoreSlim`</T>), треті передають сигнал «можна» (`ManualResetEventSlim`). Тому обирають за задачею: виключити одночасний доступ, обмежити паралелізм або дочекатися події.

</A>

<A short l="m">

Примітиви діляться на обгортки над об'єктами ядра ОС (`Mutex`, `Semaphore`, `EventWaitHandle`) і легкі керовані типи (`SemaphoreSlim`, `ManualResetEventSlim`, <T k="reader-writer-lock">`ReaderWriterLockSlim`</T>, `Barrier`). Перші повільніші, зате вміють працювати між процесами, другі швидші, але живуть усередині одного процесу. Ще одна відмінність — <T k="thread-affinity">прив'язка до потоку</T>: `Mutex` і `ReaderWriterLockSlim` звільняє лише власник, тому з `await` із них працює лише `SemaphoreSlim.WaitAsync`.

</A>

<A short l="s">

Вибір зводиться до трьох питань: чи потрібна міжпроцесна синхронізація, чи є в примітива власник і яке співвідношення читань і записів. Kernel-об'єкти платять системним викликом навіть без конкуренції, примітиви з власником забороняють `await`, а `ReaderWriterLockSlim` окупається лише за довгих читань. Асинхронних RW-блокувань і подій у BCL немає, тому їх будують на `SemaphoreSlim` і `TaskCompletionSource` або беруть із Microsoft.VisualStudio.Threading.

</A>

<A l="j">

**Що це**

Примітив синхронізації — тип, який змушує потоки чекати один на одного за певним правилом.

**Навіщо**

`lock` розв'язує одну задачу: один потік у секції. Для обмеження паралелізму, розділення читання й запису та сигналів потрібні інші інструменти.

**Як користуватися**

| Примітив | Що робить |
|---|---|
| `Mutex` | як `lock`, але може працювати між процесами |
| `SemaphoreSlim` | пускає одночасно не більше N потоків |
| `ReaderWriterLockSlim` | читати можуть багато потоків одразу, писати — один |
| `ManualResetEventSlim` | потоки чекають у `Wait()`, доки хтось не викличе `Set()` |
| `Barrier` | потоки чекають один на одного наприкінці кожної фази |

**Типова помилка**

Не звільнити примітив під час винятку. `Release()`, `ExitReadLock()` і `ReleaseMutex()` завжди викликають у `finally`.

**Підсумок:** `lock` — для взаємного виключення, семафор — для обмеження паралелізму, події — для сигналів.

</A>

<A l="m">

**Як влаштовано**

- `Mutex`, `Semaphore`, `AutoResetEvent` і `ManualResetEvent` успадковують `WaitHandle` й обгортають об'єкт ядра ОС.
- Іменований `Mutex` видно іншим процесам на всіх ОС, іменовані `Semaphore` і `EventWaitHandle` — лише на Windows.
- Типи із суфіксом `Slim` обходяться без об'єктів ядра, доки це можливо, і працюють лише всередині процесу.
- У семафорів немає власника: `Wait` в одному потоці й `Release` в іншому — нормальний сценарій.

**Коли що обирати**

| Задача | Примітив |
|---|---|
| Один екземпляр застосунку | іменований `Mutex` |
| Не більше N операцій, є `await` | `SemaphoreSlim` і `WaitAsync` |
| Читають часто й довго, пишуть рідко | `ReaderWriterLockSlim` |
| Один потік відчиняє «ворота» багатьом | `ManualResetEventSlim` |
| Дочекатися N сигналів | `CountdownEvent` |
| Фази обчислень у N потоках | `Barrier` |

**Пастки**

- Потік завершився, не звільнивши `Mutex`, — наступний власник отримає `AbandonedMutexException`.
- Зайвий `Release` у семафора проходить мовчки, а `SemaphoreFullException` згодом отримає інший потік зі своїм законним `Release`.
- `ReaderWriterLockSlim` за замовчуванням без рекурсії. Із читання в запис переходять лише через upgradeable-режим, а в ньому одночасно може бути один потік.

**Правило**

З `await` із цього списку працює лише `SemaphoreSlim`; решта — для синхронного коду.

**Підсумок:** примітив обирають за задачею і за тим, чи є в коді `await`.

</A>

<A l="s">

**Під капотом**

- `Monitor` і `Slim`-типи спершу крутяться в циклі (`SpinWait`), розраховуючи, що власник скоро звільнить ресурс. Лише потім потік іде в очікування ядра.
- Kernel-об'єкти роблять системний виклик на кожну операцію, навіть без конкуренції.
- `SpinLock` — структура, яка лише крутиться. Копія `SpinLock` — незалежне блокування, тому його не можна передавати за значенням.

**Ціна**

- Спін палить CPU і вигідний лише для дуже коротких очікувань.
- У `ReaderWriterLockSlim` вхід і вихід дорожчі, ніж у `lock`. На коротких секціях і частих записах звичайний `lock` буває швидшим.

**Компроміси**

- Для даних, які майже лише читають, замість RW-блокування — незмінний знімок і атомарна заміна посилання. Читачі тоді не синхронізуються взагалі.
- Асинхронні RW-блокування й події беруть із Microsoft.VisualStudio.Threading (`AsyncReaderWriterLock`, `AsyncManualResetEvent`) або будують на `TaskCompletionSource`.
- `SemaphoreSlim` без власника не реентерабельний: повторний `WaitAsync` у тому самому ланцюжку викликів чекає сам на себе.
- Покинутий `Mutex` — сигнал, що захищений стан може бути пошкоджений.

**Як перевірити в продакшені**

- З .NET 9 `dotnet-trace` пише подію WaitHandleWait, коли потік блокується в `lock`, `ManualResetEventSlim.Wait` або `SemaphoreSlim.Wait`. Стеки цих подій показують, хто й де чекає.
- У дампі `parallelstacks` групує потоки, що стоять в одному й тому самому очікуванні.

**Підсумок:** найдешевший примітив — той, без якого вдалося обійтися; далі обирають за власником, міжпроцесністю й профілем навантаження.

</A>

<Ex>

```csharp
// SemaphoreSlim: не більше 3 одночасних операцій, працює з await
using var gate = new SemaphoreSlim(3);
await Task.WhenAll(Enumerable.Range(1, 10).Select(async i =>
{
    await gate.WaitAsync();
    try { await Task.Delay(100); }
    finally { gate.Release(); } // власника немає: звільнити може будь-який потік
}));

// Barrier: три потоки синхронно проходять фази обчислень
using var barrier = new Barrier(3, b => Console.WriteLine($"phase {b.CurrentPhaseNumber} done"));
var threads = Enumerable.Range(0, 3).Select(_ => new Thread(() =>
{
    for (int phase = 0; phase < 2; phase++)
    {
        Thread.Sleep(Random.Shared.Next(50)); // рахуємо свою частину
        barrier.SignalAndWait();             // чекаємо на решту
    }
})).ToList();
threads.ForEach(t => t.Start());
threads.ForEach(t => t.Join());
// phase 0 done
// phase 1 done
```

</Ex>

<Next>

- Чим `Mutex` відрізняється від `lock`? — Це об'єкт ядра: повільніший, зате працює між процесами за іменем; покинутий дає `AbandonedMutexException`.
- Чому `SemaphoreSlim(1, 1)` — не повна заміна `lock`? — У нього немає власника й реентерабельності: повторний вхід у тому самому ланцюжку викликів зависне.
- Коли `ReaderWriterLockSlim` гірший за звичайний `lock`? — За коротких секцій і частих записів: вхід і вихід у нього дорожчі.
- Чим `CountdownEvent` відрізняється від `Barrier`? — У `CountdownEvent` чекають N сигналів, у `Barrier` N учасників чекають один на одного, фаза за фазою.
- Як асинхронно дочекатися сигналу? — Через `TaskCompletionSource` замість `ManualResetEvent`.

</Next>

<Q id="dotnet.threading.concurrent-collections" level="m">

## Як влаштовані конкурентні колекції і коли вони потрібні?

<A short l="j">

<T k="concurrent-collections">Конкурентні колекції</T> з `System.Collections.Concurrent` — `ConcurrentDictionary`, `ConcurrentQueue`, `ConcurrentStack`, `ConcurrentBag` — можна змінювати з кількох потоків без власного `lock`. Звичайні `List<T>` і `Dictionary<TKey,TValue>` за одночасного запису псуються, тому спільну змінювану колекцію беруть конкурентну.

</A>

<A short l="m">

Конкурентні колекції синхронізують себе самі: `ConcurrentDictionary` пише під <T k="fine-grained-locking">дрібнозернистими блокуваннями</T> й читає без блокувань, а `ConcurrentQueue` і `ConcurrentStack` узагалі <T k="lock-free">lock-free</T>. Головна тонкість — усі методи потокобезпечні, але не всі атомарні: фабрика в `GetOrAdd` виконується поза блокуванням і може відпрацювати кілька разів. Тому дорогі фабрики або фабрики з побічними ефектами обгортають у `Lazy<T>`, а складені операції роблять одним викликом.

</A>

<A short l="s">

Конкурентна колекція захищає свою структуру, але не ваші інваріанти: «перевірити й змінити» двома викликами лишається гонкою. Тому API побудований на атомарних `TryAdd`, `TryRemove`, `TryUpdate` і `GetOrAdd`. Платять за це пам'яттю й глобальними операціями: `Count`, `Keys`, `Values` і `ToArray` у `ConcurrentDictionary` беруть усі внутрішні блокування. Для даних, які майже лише читають, вигідніші незмінні колекції або `FrozenDictionary` з атомарною заміною посилання.

</A>

<A l="j">

**Що це**

Колекції з `System.Collections.Concurrent`, які безпечно змінювати з кількох потоків одночасно.

**Навіщо**

Звичайний `Dictionary<TKey,TValue>` за одночасного запису може зіпсувати свою внутрішню структуру. Конкурентні колекції синхронізують себе самі.

**Як користуватися**

| Колекція | Порядок | Основні методи |
|---|---|---|
| `ConcurrentDictionary` | за ключем | `TryAdd`, `GetOrAdd`, `AddOrUpdate`, `TryRemove` |
| `ConcurrentQueue` | FIFO | `Enqueue`, `TryDequeue` |
| `ConcurrentStack` | LIFO | `Push`, `TryPop` |
| `ConcurrentBag` | без порядку | `Add`, `TryTake` |

Методи з `Try` повертають `false`, якщо не вийшло: інший потік міг устигнути першим.

**Типова помилка**

`if (!dict.ContainsKey(key)) dict[key] = value;` — два виклики, між якими вклиниться інший потік. Правильно — один виклик `dict.TryAdd(key, value)`.

**Підсумок:** спільну колекцію в багатопотоковому коді беруть із `System.Collections.Concurrent` і змінюють одним викликом.

</A>

<A l="m">

**Як влаштовано**

- `ConcurrentDictionary` — таблиця бакетів і масив блокувань, кожне з яких захищає частину бакетів. Запис бере одне блокування, читання йде без блокувань.
- Перелічування безпечне, але це не знімок: обхід може побачити зміни, зроблені після його початку.
- `ConcurrentQueue` і `ConcurrentStack` побудовані на `Interlocked`, без блокувань.
- `ConcurrentBag` зберігає елементи в списках, прив'язаних до потоків. `TryTake` спершу дивиться свій список, потім забирає з чужих.

**Коли що обирати**

| Задача | Колекція |
|---|---|
| Спільний кеш або індекс за ключем | `ConcurrentDictionary` |
| Робота в порядку надходження | `ConcurrentQueue` |
| Потік сам кладе й сам забирає (пул об'єктів) | `ConcurrentBag` |

**Пастки**

- **`GetOrAdd` з фабрикою.** Делегат викликається поза блокуванням. Два потоки можуть одночасно не знайти ключ і обидва викликати фабрику, а збережеться одне значення.
- **`AddOrUpdate`** за конфлікту може викликати делегат оновлення повторно. Тому він має бути чистою функцією.
- **`ConcurrentQueue` не вміє чекати елемент.** Цикл `TryDequeue` без паузи палить CPU.

**Правило**

Складену операцію робіть одним атомарним методом, а фабрику з побічними ефектами — через `Lazy<T>`: `dict.GetOrAdd(key, k => new Lazy<T>(() => Create(k))).Value`. `Lazy<T>` за замовчуванням потокобезпечний і викличе `Create` один раз.

**Підсумок:** конкурентна колекція потокобезпечна, але атомарний лише кожен окремий виклик.

</A>

<A l="s">

**Під капотом**

- `Count`, `Keys`, `Values`, `ToArray`, `Clear` і зростання таблиці в `ConcurrentDictionary` захоплюють усі блокування.
- Кількість блокувань за замовчуванням залежить від кількості процесорів; її задає параметр конструктора `concurrencyLevel`.
- `ConcurrentQueue` побудована на сегментах — кільцевих буферах — і в усталеному режимі майже не алокує.
- `ConcurrentStack` створює вузол на кожен `Push`, `ConcurrentDictionary` — вузол на кожен запис.

**Ціна**

- Частий `Count` на гарячому шляху серіалізує писачів. Потрібен лічильник — ведіть його окремо через `Interlocked`.
- `ConcurrentBag` як черга між різними виробниками й споживачами програє: споживачі весь час забирають із чужих списків.

**Компроміси**

- Довідники й конфігурацію, які майже лише читають, вигідніше тримати у `FrozenDictionary` (.NET 8+) або `ImmutableDictionary` і атомарно замінювати посилання цілком. Читання тоді йдуть узагалі без синхронізації.
- Дві пов'язані колекції не стануть узгодженими самі: такий інваріант потребує зовнішнього `lock`.
- Одночасне читання звичайного `Dictionary` без записів безпечне — конкурентна колекція там не потрібна.

**Як перевірити в продакшені**

- У профілі CPU (dotnet-trace, PerfView) видно час у внутрішніх блокуваннях `ConcurrentDictionary`, наприклад в `AcquireAllLocks`.
- У дампі `dotnet-dump analyze` показує вміст командами `dumpconcurrentdictionary` і `dumpconcurrentqueue`.

**Підсумок:** конкурентні колекції добрі для частих записів із багатьох потоків; для рідких записів і частих читань дешевші незмінні знімки.

</A>

<Ex>

```csharp
using System.Collections.Concurrent;

var cache = new ConcurrentDictionary<string, Lazy<Client>>();
int created = 0;

Client Get(string key) =>
    cache.GetOrAdd(key, k => new Lazy<Client>(() =>
    {
        Interlocked.Increment(ref created); // усередині Lazy фабрика виконається один раз
        return new Client(k);
    })).Value;

Parallel.For(0, 1000, _ => Get("billing"));
Console.WriteLine(created); // 1

var counts = new ConcurrentDictionary<string, int>();
Parallel.ForEach(new[] { "a", "b", "a" }, word =>
    counts.AddOrUpdate(word, 1, (_, old) => old + 1)); // чиста функція: може викликатися повторно
Console.WriteLine(counts["a"]); // 2

record Client(string Name);
```

Без `Lazy` за одночасних викликів фабрика могла б відпрацювати кілька разів, хоча в словнику однаково лишилося б одне значення.

</Ex>

<Next>

- Чому `GetOrAdd` може викликати фабрику двічі? — Делегат виконується поза блокуванням, щоб не тримати його на чужому коді; зберігається лише одне значення.
- Чи дорого викликати `Count` у `ConcurrentDictionary`? — Так: беруться всі внутрішні блокування; на гарячому шляху краще окремий лічильник.
- Коли `ConcurrentBag` — поганий вибір? — Коли виробники й споживачі — різні потоки: споживачі постійно забирають із чужих списків.
- Чи дає перелічування `ConcurrentDictionary` знімок? — Ні: обхід безпечний, але бачить зміни; знімок дає `ToArray()`.
- Чи потрібні конкурентні колекції, якщо дані лише читаються? — Ні: одночасне читання звичайних колекцій без записів безпечне.

</Next>

<Q id="dotnet.threading.interlocked-volatile" level="s">

## Що таке `Interlocked`, `volatile` і модель пам'яті .NET?

<A short l="j">

<T k="interlocked">`Interlocked`</T> виконує прості операції над змінною атомарно, а <T k="volatile">`volatile`</T> лише гарантує, що читання поля не закешується й не переставиться. Тому спільний лічильник збільшують через `Interlocked.Increment(ref count)`, а `volatile` годиться хіба що для прапорця зупинки.

</A>

<A short l="m">

`Interlocked` — атомарні операції процесора (`Increment`, `Add`, `Exchange`, <T k="compare-and-swap">`CompareExchange`</T>), кожна з яких ще й <T k="memory-barrier">повний бар'єр пам'яті</T>, а `volatile` дає лише порядок звертань без атомарності. Volatile-читання не пускає наступні звертання раніше за себе, volatile-запис не пускає попередні пізніше за себе. Тому `volatile` підходить для прапорців і публікації готового об'єкта, а для `x++` і «перевірити й записати» потрібен `Interlocked` або `lock`.

</A>

<A short l="s">

<T k="memory-model">Модель пам'яті .NET</T> дозволяє JIT і процесору переставляти звичайні звертання, якщо всередині потоку це непомітно, а атомарні лише вирівняні значення до розміру вказівника. Volatile-операції дають порядок <T k="acquire-release">acquire/release</T>, а `Interlocked` і `Thread.MemoryBarrier` — повний бар'єр; acquire/release не забороняє перестановку запису з наступним читанням іншої змінної. На x64 процесор переставляє лише такі пари, тому багато помилок спливають тільки на ARM64. Звідси правило: `lock` за замовчуванням, `Interlocked` для поодиноких змінних, `Volatile` — лише коли точно зрозуміло, що він гарантує.

</A>

<A l="j">

**Що це**

- **`Interlocked`** — статичний клас з атомарними операціями: `Increment`, `Decrement`, `Add`, `Exchange`, `CompareExchange`.
- **`volatile`** — модифікатор поля, яке змінюють інші потоки.

**Навіщо**

- `count++` — це читання, додавання й запис. Інший потік може вклинитися між ними, і збільшення загубиться.
- Без `volatile` JIT може прочитати поле один раз і тримати значення в регістрі. Цикл `while (!_stop)` тоді не побачить `_stop = true`.

**Як користуватися**

- Лічильник: `Interlocked.Increment(ref _count);`.
- Прапорець зупинки: `private volatile bool _stop;`.

**Типова помилка**

Думати, що `volatile` робить `x++` безпечним. Він не об'єднує читання й запис в одну операцію. До того ж його не можна застосувати до `long` і `double`.

**Підсумок:** `Interlocked` — для атомарних змін, `volatile` — лише для видимості прапорця.

</A>

<A l="m">

**Як влаштовано**

- Усі методи `Interlocked` атомарні й працюють як повний бар'єр: звертання до пам'яті не переносяться через них у жоден бік.
- Volatile-читання (acquire) не дає наступним звертанням виконатися раніше за нього.
- Volatile-запис (release) не дає попереднім звертанням затриматися після нього.
- Ключове слово `volatile` робить такими всі звертання до поля. Клас `Volatile` (`Volatile.Read`, `Volatile.Write`) — окремі звертання, зокрема до `long`, `double` і елементів масивів.

**Коли що обирати**

| Задача | Інструмент |
|---|---|
| Лічильник, сума | `Interlocked.Increment`, `Interlocked.Add` |
| Прапорець «зупинитися» | `volatile` або `Volatile.Read` і `Volatile.Write` |
| Власна атомарна операція (максимум) | CAS-цикл на `CompareExchange` |
| Інваріант із кількох полів | `lock` |

**Пастки**

- Volatile не дає «свіжості»: читання не зобов'язане повернути останнє значення, записане іншим процесором.
- Немає єдиного порядку volatile-записів, однакового для всіх потоків.
- `long` і `double` на 32-бітній платформі читаються неатомарно. Використовуйте `Interlocked.Read` або `Volatile.Read`.

**Правило**

CAS-цикл будується так:

1. Прочитати поточне значення.
2. Обчислити нове.
3. Викликати `CompareExchange`; якщо значення встигли змінити — повернутися до кроку 1.

**Підсумок:** `Interlocked` дає атомарність і повний бар'єр, `volatile` — лише порядок.

</A>

<A l="s">

**Під капотом**

Модель пам'яті .NET описана в специфікації `Memory-model.md` у репозиторії dotnet/runtime і суворіша за ECMA-335:

- звичайні звертання переставляються, лише якщо цього не видно всередині потоку;
- JIT не додає нових читань, але може склеїти сусідні читання одного поля — звідси завислий `while (!_flag)`;
- спекулятивні записи заборонені;
- запис посилання на об'єкт у спільну пам'ять — release для його полів, тому опублікований об'єкт видно повністю сконструйованим;
- читання через посилання не випереджають читання самого посилання.

**Ціна**

- На x64 volatile-читання й запис — звичайні інструкції: процесор (модель TSO) переставляє лише запис із наступним читанням.
- На ARM64 модель слабша, і volatile-операціям потрібні інструкції з бар'єрною семантикою.
- `Interlocked` на спільній кеш-лінії дорогий: лінія переходить між ядрами, і гарячий спільний лічильник погано масштабується.

**Компроміси**

- Схеми «записав свій прапорець — перевірив чужий» потребують `Interlocked` або `Interlocked.MemoryBarrier`: acquire/release таку перестановку не забороняє.
- Гарячий лічильник краще шардувати: свій на потік або ядро, сума — під час читання.
- False sharing: незалежні гарячі поля в одній кеш-лінії заважають одне одному.
- Double-checked locking у .NET коректний, але `Lazy<T>` і `LazyInitializer` читаються простіше.

**Як перевірити в продакшені**

- Код, стабільний на x64, ганяють стрес-тестами на ARM64 (Graviton, Apple Silicon).
- Масштабованість лічильників міряють у BenchmarkDotNet з різною кількістю потоків.

**Підсумок:** коректний код спирається на гарантії моделі пам'яті, а не на поведінку x64.

</A>

<Ex>

```csharp
public sealed class Stats
{
    private long _requests;          // лічильник: лише через Interlocked
    private int _maxLatencyMs;       // максимум: CAS-цикл
    private volatile bool _stopped;  // прапорець: volatile достатньо

    public void Record(int latencyMs)
    {
        Interlocked.Increment(ref _requests);

        int current = Volatile.Read(ref _maxLatencyMs);
        while (latencyMs > current)
        {
            // записуємо, лише якщо з моменту читання ніхто не змінив значення
            int seen = Interlocked.CompareExchange(ref _maxLatencyMs, latencyMs, current);
            if (seen == current) break;
            current = seen; // нас випередили — пробуємо знову
        }
    }

    public long Requests => Interlocked.Read(ref _requests); // атомарно й на 32-бітній платформі
    public void Stop() => _stopped = true;
    public bool IsStopped => _stopped;
}
```

</Ex>

<Next>

- Чому `volatile` не робить `x++` безпечним? — Це три операції; volatile упорядковує кожну, але не об'єднує їх в атомарну.
- Чи потрібен `volatile` полю, до якого звертаються лише під `lock`? — Ні: вхід і вихід із блокування вже впорядковують звертання.
- Що таке ABA-проблема? — CAS бачить попереднє значення, хоча між читанням і записом його змінили й повернули; для лічильників та індексів вона реальна.
- Чому код, що працював на x64, ламається на ARM64? — В ARM слабша модель пам'яті: видно перестановки, яких x64 не робить.
- Що таке false sharing? — Незалежні гарячі поля в одній кеш-лінії: ядра постійно відбирають її одне в одного.

</Next>

<Q id="dotnet.threading.channels" level="s">

## Як побудувати producer-consumer: `BlockingCollection` чи `System.Threading.Channels`?

<A short l="j">

<T k="producer-consumer">Producer-consumer</T> — схема, де одні потоки кладуть роботу в чергу, а інші забирають і обробляють. У .NET для неї є <T k="blocking-collection">`BlockingCollection<T>`</T>, що блокує потік в очікуванні, і <T k="channels">канали</T> `Channel<T>`, що чекають через `await`, тому в новому коді беруть канали.

</A>

<A short l="m">

`BlockingCollection<T>` — синхронна черга з обмеженням місткості, а `Channel<T>` — її асинхронний аналог. `Add` і `Take` блокують потік, коли черга повна або порожня, а `WriteAsync` і `ReadAllAsync` у тих самих ситуаціях відпускають потік до появи місця чи даних. Обмежений канал (`CreateBounded`) дає <T k="backpressure">backpressure</T>: швидкий виробник чекає, а не роздуває пам'ять.

</A>

<A short l="s">

Producer-consumer — це передусім рішення про межу черги: необмежена черга за повільного споживача перетворює затримку на зростання пам'яті. Обмежений канал переносить тиск на виробника — чекати (`Wait`) або скидати елементи (`DropOldest`, `DropNewest`, `DropWrite`), а його async-методи повертають `ValueTask` і не тримають потоки. `BlockingCollection` тримає заблокованими потоки пулу й погано поєднується з async-кодом, тому лишається для виділених потоків у синхронному коді.

</A>

<A l="j">

**Що це**

- **Producer** (виробник) створює роботу.
- **Consumer** (споживач) її обробляє.
- Між ними — потокобезпечна черга.

**Навіщо**

Щоб розділити швидке приймання й повільну обробку. Наприклад, приймати повідомлення одразу, а записувати їх у базу у своєму темпі.

**Як користуватися**

1. Створити канал: `var channel = Channel.CreateBounded<int>(100);` — не більше 100 елементів.
2. Виробник пише `await channel.Writer.WriteAsync(item)`, а наприкінці викликає `channel.Writer.Complete()`.
3. Споживач читає `await foreach (var item in channel.Reader.ReadAllAsync())`.

**Типова помилка**

Забути `Complete()`. Споживач тоді чекає нових елементів вічно.

**Підсумок:** канали — стандартна асинхронна черга між виробниками й споживачами.

</A>

<A l="m">

**Як влаштовано**

- `CreateUnbounded` — запис завжди завершується одразу, пам'ять не обмежена.
- `CreateBounded` — під час заповнення спрацьовує режим `FullMode` з `BoundedChannelOptions`.
- Канали підтримують кількох виробників і споживачів. Споживачі з `ReadAllAsync` ділять елементи між собою.
- `BlockingCollection<T>` — синхронна обгортка над `ConcurrentQueue<T>` (за замовчуванням): `Add`, `Take`, `CompleteAdding`, `GetConsumingEnumerable`.

**Коли що обирати**

| `FullMode` | Що відбувається під час заповнення |
|---|---|
| `Wait` (за замовчуванням) | `WriteAsync` чекає місця, `TryWrite` повертає `false` |
| `DropOldest` | із черги викидається найстаріший елемент |
| `DropNewest` | із черги викидається найновіший елемент |
| `DropWrite` | викидається елемент, який намагаються записати |

**Пастки**

- За кількох виробників `Complete()` викликають, коли закінчили всі.
- `ReadAsync` на завершеному каналі кидає `ChannelClosedException`, а `ReadAllAsync` просто закінчує перелічування.
- Помилку не можна губити: `Writer.TryComplete(ex)` зупинить запис і передасть виняток у `Reader.Completion`.

**Правило**

Канал за замовчуванням — обмежений; необмежений — лише якщо джерело обмежене саме.

**Підсумок:** канал — це асинхронна черга з явною межею й протоколом завершення.

</A>

<A l="s">

**Під капотом**

- Async-методи каналів повертають `ValueTask`: якщо операція завершилася синхронно, алокації немає.
- `SingleReader = true` і `SingleWriter = true` — обіцянка каналу, яка дозволяє йому обрати швидшу реалізацію.
- `AllowSynchronousContinuations = true` дозволяє продовженню читача виконатися просто всередині `WriteAsync` писача.

**Ціна**

- Споживач каналу, що чекає, не займає потік. Кожен `BlockingCollection.Take` в очікуванні тримає потік, і на пулі це швидко з'їдає вільні потоки.
- Необмежений канал за повільного споживача перетворює затримку на зростання пам'яті, а потім на `OutOfMemoryException`.

**Компроміси**

- `Wait` прокидає уповільнення назад по конвеєру — до джерела, яке перестає читати сокет або брокер.
- `DropOldest` підходить для телеметрії та «останнього значення». Для режимів зі скиданням є колбек `itemDropped`.
- Синхронні продовження зменшують перемикання, але писач неочікувано виконує код читача й чекає на нього.
- Для графів із розгалуженням і вбудованим обмеженням паралелізму є TPL Dataflow; канали — низькорівневіший будівельний блок.

**Як перевірити в продакшені**

- Довжина черги — головний сигнал: `Reader.Count`, якщо `Reader.CanCount` дорівнює `true`.
- Зростання часу `WriteAsync` означає, що система впирається в споживача.
- Завершення `Reader.Completion` з винятком у логах показує, що конвеєр зупинився з помилкою.

**Підсумок:** головне рішення в producer-consumer — межа черги й поведінка під час її досягнення.

</A>

<Ex>

```csharp
using System.Threading.Channels;

// Не більше 100 елементів; під час заповнення виробник чекає (backpressure)
var channel = Channel.CreateBounded<int>(
    new BoundedChannelOptions(100) { FullMode = BoundedChannelFullMode.Wait });

var producer = Task.Run(async () =>
{
    try
    {
        for (int i = 0; i < 1_000; i++)
            await channel.Writer.WriteAsync(i); // чекає, якщо черга повна
        channel.Writer.Complete();
    }
    catch (Exception ex) { channel.Writer.TryComplete(ex); } // помилка дійде до споживачів
});

// Три споживачі ділять елементи між собою
var consumers = Enumerable.Range(0, 3).Select(_ => Task.Run(async () =>
{
    await foreach (int item in channel.Reader.ReadAllAsync())
        await Task.Delay(1); // повільна обробка
})).ToArray();

await Task.WhenAll(consumers.Append(producer));
```

</Ex>

<Next>

- Що буде з необмеженим каналом, якщо споживач повільніший за виробника? — Черга росте без меж: пам'ять, затримка й зрештою OOM.
- Чим `DropOldest` відрізняється від `DropWrite`? — Перший викидає найстаріший елемент із черги, другий — той, який намагаються записати.
- Як зупинити конвеєр у разі помилки? — `Writer.TryComplete(ex)`: запис припиниться, а `Reader.Completion` завершиться з цим винятком.
- Коли `BlockingCollection` ще доречна? — У синхронному коді з виділеними потоками-споживачами, де блокування потоку не заважає.
- Що дає `SingleReader = true`? — Обіцянку, що читач один: канал може обрати швидшу реалізацію.

</Next>

<Q id="dotnet.threading.thread-pool-starvation" level="s">

## Що таке голодування пулу потоків і як його діагностувати?

<A short l="j">

<T k="thread-pool-starvation">Голодування пулу потоків</T> — ситуація, коли всі потоки пулу зайняті (зазвичай просто чекають), і новій роботі ні на чому виконуватися. Застосунок відповідає дедалі повільніше, хоча процесор майже вільний, і найчастіше винен <T k="sync-over-async">sync-over-async</T> — `.Result` або `.Wait()` на асинхронній операції.

</A>

<A short l="m">

Голодування — це брак вільних потоків пулу за зростання черги роботи. Пул понад мінімум (за замовчуванням — кількість процесорів) додає потоки поступово, тому під навантаженням черга росте швидше, ніж він устигає. Ознаки — повільне зростання кількості потоків, довга черга й низьке завантаження CPU, а лікують це переведенням блокувального коду на `await`, а не збільшенням кількості потоків.

</A>

<A short l="s">

Голодування пулу — це коли робота стоїть у черзі не через брак CPU, а через заблоковані потоки. Пул нарощує потоки повільно: <T k="hill-climbing">hill climbing</T> підбирає їхню кількість за пропускною здатністю, а з .NET 6 блокування на `Task.Wait` компенсується швидше. Компенсація коштує сотень потоків, тому `SetMinThreads` — лише латка, а лікують прибиранням sync-over-async. Діагностика: `dotnet-counters` дає картину, `dotnet-stack` або дамп — постійну причину, `dotnet-trace` з подією WaitHandleWait (.NET 9+) — плаваючу.

</A>

<A l="j">

**Що це**

Усі потоки пулу зайняті очікуванням, а нові запити стоять у черзі.

**Як це виглядає**

Сервіс під навантаженням відповідає за секунди замість мілісекунд. Процесор при цьому завантажений слабко.

**Чому виникає**

1. Запит виконується на потоці пулу.
2. Код викликає `httpClient.GetStringAsync(url).Result` — потік стоїть і чекає відповіді.
3. Під навантаженням так стають усі потоки пулу.
4. Нові запити чекають у черзі, поки пул повільно додає потоки.

**Типова помилка**

Лікувати симптом: підняти мінімум потоків замість того, щоб прибрати блокування.

**Підсумок:** у коді на пулі потоків — `await` до самого верху, без `.Result` і `.Wait()`.

</A>

<A l="m">

**Як влаштовано**

1. До мінімуму (`ThreadPool.GetMinThreads`, за замовчуванням — кількість процесорів) пул створює потоки одразу.
2. Вище — із затримкою. У прикладі Microsoft кількість потоків швидко доходить до 2–3 на ядро, а далі додається по 1–2 на секунду.
3. Поки потоків бракує, зростає черга й затримка кожного запиту.

**Коли що обирати**

| Причина | Рішення |
|---|---|
| `.Result`, `.Wait()` на async-коді | `await` по всьому ланцюжку |
| Синхронний I/O | асинхронні API (`ReadAsync`, `SaveChangesAsync`) |
| Сторонній блокувальний API | окремий потік або `LongRunning` з обмеженням паралелізму |
| Пережити сплеск до виправлення | тимчасово `SetMinThreads` |

**Пастки**

- Кількість потоків стабілізувалася високо — більше приблизно трьох на ядро. Отже, код блокує потоки, а пул компенсує; під час сплеску чи рестарту голодування повернеться.
- `Thread.Sleep` і довгий `lock` у коді на пулі теж з'їдають потоки.

**Правило**

Ознаки голодування в `dotnet-counters`: кількість потоків пулу повільно росте, черга довга, завершеної роботи мало, CPU помітно нижче 100%.

**Підсумок:** голодування лікують прибиранням блокувань, а не додаванням потоків.

</A>

<A l="s">

**Під капотом**

- Hill climbing періодично змінює кількість активних потоків і дивиться, чи зросла пропускна здатність — кількість завершених work items за секунду.
- Окремий механізм додає потік, коли черга є, а прогресу немає. Обидва видно в подіях `ThreadPoolWorkerThreadAdjustment` з причинами на кшталт Climbing move і Starvation.
- З .NET 6 пул одразу додає потоки, коли потік пулу блокується в очікуванні задачі. Без затримки — до `ThreadsToAddWithoutDelay_ProcCountFactor`, помноженого на кількість процесорів, далі зі зростаючою затримкою.
- Цей механізм працює лише для очікування задач (`Task.Wait`, `.Result`), а не для `lock`, синхронного I/O чи `Thread.Sleep`.

**Ціна**

- Компенсація — це сотні потоків: пам'ять під стеки, перемикання контексту, довший обхід стеків під час збирання сміття.
- Великий `SetMinThreads` платить ті самі витрати постійно, а не лише під час сплеску.

**Компроміси**

Налаштування `System.Threading.ThreadPool.Blocking.*` і `MinThreads` купують час до виправлення коду. Справжнє рішення — асинхронність по всьому стеку й виділені потоки для неминучого блокування.

**Як перевірити в продакшені**

1. `dotnet-counters monitor -n MyApp`. У .NET 9+ це метрики `dotnet.thread_pool.thread.count`, `dotnet.thread_pool.queue.length` і `dotnet.thread_pool.work_item.count`; раніше — ThreadPool Thread Count, ThreadPool Queue Length і ThreadPool Completed Work Item Count.
2. Постійна проблема: `dotnet-stack report -n MyApp` або дамп із `parallelstacks`. Шукайте потоки з `WorkerThread` унизу стека й `Task.Wait` або `GetResult` нагорі.
3. Плаваюча проблема: `dotnet-trace collect -n MyApp --clrevents waithandle --clreventlevel verbose` (.NET 9+), потім стеки WaitHandleWait у PerfView.

**Підсумок:** голодування видно за лічильниками, а причину показують стеки заблокованих потоків пулу.

</A>

<Ex>

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddHttpClient();
var app = builder.Build();

// Погано: sync-over-async — потік пулу стоїть увесь час запиту
app.MapGet("/bad", (IHttpClientFactory f) =>
    f.CreateClient().GetStringAsync("https://example.com").Result.Length);

// Добре: на час очікування потік повертається в пул
app.MapGet("/good", async (IHttpClientFactory f) =>
    (await f.CreateClient().GetStringAsync("https://example.com")).Length);

app.Run();
```

Під навантаженням `/bad` тримає по потоку на кожен запит, і кількість потоків пулу росте; `/good` обходиться кількома потоками.

</Ex>

<Next>

- Чому CPU завантажений слабко, а запити гальмують? — Потоки не рахують, а чекають; робота стоїть у черзі пулу.
- Чи допоможе `ThreadPool.SetMinThreads(500, 500)`? — Зніме симптом під час сплесків, але додасть пам'яті й перемикань; блокувальний код залишиться.
- Що змінилося в .NET 6? — Пул швидше додає потоки, коли потік блокується на `Task.Wait` або `.Result`; голодування коротше, але не зникає.
- Як відрізнити голодування від дедлоку? — За голодування кількість потоків росте й робота йде повільно; за дедлоку потоки стоять на тих самих блокуваннях, і прогресу немає зовсім.
- Чим допомагає `TaskCreationOptions.LongRunning`? — Довга блокувальна робота отримує окремий потік і не займає пул.

</Next>
