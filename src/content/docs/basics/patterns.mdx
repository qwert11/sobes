<Q id="basics.pattern.what" level="j">

## Что такое паттерны проектирования и как они классифицируются?

<A short l="j">

<T k="design-pattern">Паттерн проектирования</T> — типовое решение часто встречающейся задачи проектирования, описанное ролями классов и связями между ними, а не готовый код. Каталог <T k="gang-of-four">«банды четырёх»</T> (GoF) делит 23 паттерна на порождающие, структурные и поведенческие, и многие уже встроены в .NET: например, `IEnumerable<T>` — это паттерн <T k="iterator">«итератор»</T>.

</A>

<A short l="m">

Паттерн — именованная пара «проблема и решение» с известными последствиями, и его главная ценность — общий словарь: фраза «здесь декоратор» объясняет устройство кода без схемы классов. GoF группирует паттерны по назначению: <T k="creational-pattern">порождающие</T> создают объекты, <T k="structural-pattern">структурные</T> собирают из них структуры, <T k="behavioral-pattern">поведенческие</T> распределяют обязанности. Цена любого паттерна — лишняя косвенность, поэтому его вводят, когда проблема уже есть, а не на будущее.

</A>

<A short l="s">

Каталог GoF (1994) писался для C++ и Smalltalk, и в современном C# часть паттернов растворилась в языке: стратегия и команда — это делегаты, итератор — `yield return`, наблюдатель — `event`. Кроме назначения, GoF делит паттерны по уровню: уровня классов (связь через наследование, фиксируется при компиляции) и уровня объектов (через композицию, меняется во время выполнения). Сквозные принципы книги — «программируйте на уровне интерфейса» и «предпочитайте композицию наследованию». На ревью название паттерна — повод обсудить последствия, а не оправдание сложности.

</A>

<A l="j">

**Что это**

Паттерн проектирования — описание решения типовой задачи: какая проблема, какие классы участвуют, как они связаны и к чему это приводит. Это не библиотека и не код для копирования: паттерн каждый раз реализуют под свою задачу.

**Зачем**

- Общий словарь: «оберни в декоратор» короче, чем объяснять схему классов.
- Проверенные решения: не нужно заново придумывать, как добавить поведение, не меняя класс.

**Как классифицируются**

Книга «Design Patterns» (1994) Гаммы, Хелма, Джонсона и Влиссидеса — «банды четырёх», GoF — описывает 23 паттерна в трёх группах:

| Группа | Что решает | Примеры |
|---|---|---|
| Порождающие (5) | как создавать объекты | Singleton, Factory Method, Builder |
| Структурные (7) | как собирать объекты в структуры | Adapter, Decorator, Facade |
| Поведенческие (11) | как объекты взаимодействуют | Strategy, Observer, Iterator |

**Частая ошибка**

Учить паттерны как шаблоны кода и вставлять их везде. Паттерн нужен там, где есть проблема, которую он решает.

**Итог:** паттерн — именованное решение типовой задачи; главное в нём — общий словарь, а не код.

</A>

<A l="m">

**Как устроено**

Каждый паттерн GoF описан по одной схеме: назначение, мотивация, применимость, участники, последствия, реализация. Важнее всего назначение и последствия: что паттерн решает и чем за это платят.

**Где встретить в .NET**

| Паттерн | Где в .NET |
|---|---|
| Builder | `StringBuilder`, `WebApplicationBuilder` |
| Abstract Factory | `DbProviderFactory`: `CreateConnection`, `CreateCommand` |
| Prototype | выражение `with` у `record` |
| Decorator | `BufferedStream`, `GZipStream` поверх `Stream` |
| Iterator | `IEnumerable<T>`, `yield return` |
| Observer | `event`, `IObservable<T>` |
| Strategy | `IComparer<T>` в `List<T>.Sort` |

**Ловушки**

- **Похожие схемы.** Адаптер, декоратор и прокси выглядят одинаково — обёртка над объектом. Различаются они намерением, а не кодом.
- **Название — не паттерн.** Статический метод `Create` — просто фабричный метод-конструктор, а не Factory Method из GoF: тот предполагает, что класс создаваемого объекта выбирает подкласс.

**Правило**

Сначала проблема, потом паттерн. Если не получается назвать проблему, которую паттерн решает в этом месте, он лишний.

**Итог:** паттерны GoF уже окружают вас в BCL; узнавать их важнее, чем писать с нуля.

</A>

<A l="s">

**Под капотом**

- GoF классифицирует паттерны по двум осям: назначение (порождающие, структурные, поведенческие) и уровень (класса или объекта).
- Паттерны уровня класса — Factory Method, Template Method, Interpreter, адаптер класса — строятся на наследовании и фиксируются при компиляции. Остальные строятся на композиции и меняются во время выполнения.

**Паттерны и язык**

Питер Норвиг ещё в 1996 году показал, что в динамических языках 16 из 23 паттернов становятся проще или исчезают. В C# то же сделали возможности языка: стратегия и команда — `Func<T>` и `Action`, итератор — `yield return`, наблюдатель — `event`, прототип — `with`, ленивый singleton — `Lazy<T>`.

**Компромиссы**

- Каждый паттерн добавляет типы и косвенность: навигация по коду сложнее, стек вызовов длиннее. Взамен появляется точка расширения.
- Точка расширения окупается, только если ею пользуются: вторая реализация, подмена в тесте, частые изменения в прошлом.
- GoF — не единственный каталог: есть паттерны корпоративных приложений Фаулера (Repository, Unit of Work), интеграционные паттерны, облачные паттерны Microsoft (Retry, Circuit Breaker).

**Как обсуждать в команде**

Название паттерна на ревью — сокращение для разговора о последствиях: «тут декоратор, значит, порядок регистрации важен». Если паттерн нужно знать, чтобы понять класс, а сам он ничего не даёт, — это «паттерн ради паттерна».

**Итог:** паттерн — словарь для обсуждения дизайна; в C# многие паттерны GoF стали возможностями языка, а выбирать их стоит по последствиям, а не по каталогу.

</A>

<Ex>

```csharp
using System.IO.Compression;

// Итератор: yield return генерирует IEnumerator<T>
foreach (var n in Evens(6)) Console.Write($"{n} "); // 0 2 4
Console.WriteLine();

// Стратегия: алгоритм сравнения передаётся снаружи
var words = new List<string> { "ccc", "a", "bb" };
words.Sort(Comparer<string>.Create((x, y) => x.Length.CompareTo(y.Length)));
Console.WriteLine(string.Join(",", words)); // a,bb,ccc

// Декоратор: GZipStream добавляет сжатие к любому Stream
using var buffer = new MemoryStream();
using (var gzip = new GZipStream(buffer, CompressionLevel.Optimal, leaveOpen: true))
    gzip.Write(new byte[1000]);
Console.WriteLine(buffer.Length < 1000); // True

static IEnumerable<int> Evens(int max)
{
    for (var i = 0; i < max; i += 2) yield return i;
}
```

</Ex>

## Singleton, фабрика и строитель: когда что и почему Singleton часто называют антипаттерном?

<A short l="j">

<T k="singleton-pattern">Singleton</T> гарантирует один экземпляр класса, <T k="factory-method">фабрика</T> прячет выбор и создание нужного класса за методом, а <T k="builder-pattern">строитель</T> собирает сложный объект по шагам, как `StringBuilder` или `WebApplicationBuilder`. Singleton со статическим свойством `Instance` называют антипаттерном, потому что это глобальное состояние, которое трудно подменить в тестах.

</A>

<A short l="m">

Порождающие паттерны отделяют код, которому нужен объект, от решения, какой объект создать и как. Классический Singleton совмещает «один экземпляр» и «глобальный доступ», и вредит второе: зависимость не видна в конструкторе, а состояние общее для всех тестов, поэтому в .NET «один экземпляр» поручают контейнеру через `AddSingleton`. Factory Method переносит выбор класса в подкласс, <T k="abstract-factory">Abstract Factory</T> создаёт семейства согласованных объектов, Builder — пошаговую сборку; цена каждого — ещё один тип и косвенность.

</A>

<A short l="s">

«Один экземпляр» — решение о времени жизни, а не свойство класса, поэтому его выносят в <T k="composition-root">composition root</T>, и класс снова тестируется. Потокобезопасная ленивая инициализация в C# — поле `static readonly` или <T k="lazy-initialization">`Lazy<T>`</T> в режиме по умолчанию `ExecutionAndPublication`, но `Lazy<T>` кеширует исключение фабрики, и упавшая инициализация не повторится. Фабрики в DI — делегат регистрации, `IHttpClientFactory`, `IDbContextFactory<T>` — нужны, когда объект создаётся с параметрами времени выполнения или живёт меньше потребителя. Builder оправдан при множестве необязательных частей и проверке в `Build()`, а для пяти полей хватит `record` с `required`.

</A>

<A l="j">

**Что это**

| Паттерн | Что делает | Пример в .NET |
|---|---|---|
| Singleton | один экземпляр на приложение | `AddSingleton` в DI |
| Фабрика | создаёт объект и выбирает класс | `IHttpClientFactory.CreateClient()` |
| Строитель | собирает объект по шагам | `StringBuilder`, `WebApplicationBuilder` |

**Зачем**

Коду, которому нужен объект, незачем знать, как его собрать: какой класс выбрать, какие параметры передать, в каком порядке настроить.

**Как пользоваться**

- Нужен один общий объект — зарегистрируйте его в DI как singleton, а не пишите статическое свойство `Instance`.
- Класс выбирается по условию — фабрика.
- Много необязательных настроек — строитель с цепочкой вызовов.

**Частая ошибка**

Писать singleton со `static Instance` для сервиса с зависимостями. Его нельзя подменить в тесте, и все тесты делят одно состояние.

**Итог:** singleton — один экземпляр, фабрика — выбор класса, строитель — пошаговая сборка.

</A>

<A l="m">

**Как устроено**

- **Singleton.** Приватный конструктор и статическое свойство. Потокобезопасно и лениво — через `Lazy<T>`: по умолчанию его фабрика выполняется ровно один раз даже при гонке потоков.
- **Factory Method.** Базовый класс объявляет виртуальный метод создания, а подкласс решает, какой объект вернуть.
- **Abstract Factory.** Интерфейс с несколькими методами создания для семейства согласованных объектов: `DbProviderFactory` создаёт соединение, команду и параметр одного провайдера.
- **Builder.** Объект собирается вызовами методов, а `Build()` проверяет данные и отдаёт результат.

**Когда что выбирать**

| Задача | Решение |
|---|---|
| Один экземпляр на приложение | `AddSingleton` в DI |
| Объект с параметрами времени выполнения | фабрика-делегат или интерфейс фабрики |
| Семейство согласованных объектов | Abstract Factory |
| Много необязательных частей и проверка | Builder |

**Ловушки**

- **Почему Singleton — антипаттерн.** Глобальная точка доступа прячет зависимость, состояние переживает тесты, а класс сам управляет своим временем жизни — это лишняя обязанность.
- **Fluent API — не всегда Builder.** Цепочка методов — стиль интерфейса. Builder — когда есть отдельный объект-сборщик и итоговый `Build()`.

**Правило**

Время жизни решает контейнер, создание с параметрами — фабрика, сложную сборку — строитель.

**Итог:** порождающие паттерны отделяют «что нужно» от «как создать», а «один экземпляр» в .NET — это регистрация, а не статика.

</A>

<A l="s">

**Под капотом**

- Поле `static readonly` инициализирует конструктор типа, и CLR гарантирует, что он выполнится один раз. Но без явного статического конструктора момент инициализации выбирает рантайм, поэтому для настоящей ленивости берут `Lazy<T>`.
- `Lazy<T>` по умолчанию работает в режиме `ExecutionAndPublication`: фабрика выполняется под блокировкой одним потоком. Исключение фабрики кешируется — каждый следующий `Value` выбросит его же. `PublicationOnly` исключения не кеширует, но при гонке может создать лишние экземпляры.
- `IHttpClientFactory` — фабрика с пулом: `HttpClient` создаётся каждый раз, а `HttpMessageHandler` переиспользуется и пересоздаётся по таймеру, по умолчанию раз в две минуты.

**Компромиссы**

- **Статика против DI.** Статический singleton доступен отовсюду, DI делает зависимость видимой и заменяемой. Статика оправдана для неизменяемых значений без зависимостей: `Comparer<T>.Default`, `Array.Empty<T>()`.
- **Своя фабрика.** Контейнер уже фабрика, и интерфейс фабрики на каждый сервис — лишний слой. Своя фабрика нужна, если объект зависит от данных запроса или должен жить меньше долгоживущего потребителя.
- **Builder против `record`.** Builder даёт пошаговую проверку и неизменяемый результат, но удваивает число типов.

**Как проверить в проде**

- Singleton с изменяемым состоянием выдаёт себя гонками под нагрузкой. На ревью ищут `static`-поля с изменяемыми коллекциями и свойства `Instance`.
- Упавшая инициализация `Lazy<T>` видна как одно и то же исключение на каждом запросе до перезапуска процесса.

**Итог:** «один экземпляр» — решение composition root, фабрика — для создания во время выполнения, строитель — для сложной сборки, и за каждым стоит цена косвенности.

</A>

<Ex>

```csharp
// Singleton через Lazy<T>: фабрика выполнится один раз, даже из нескольких потоков
Parallel.For(0, 8, i => { var config = Config.Instance; });
Console.WriteLine(Config.Created); // 1

// Строитель: пошаговая сборка, проверка в Build()
var mail = new EmailBuilder().To("ann@example.com").Subject("Hi").Build();
Console.WriteLine(mail); // Email { To = ann@example.com, Subject = Hi }

public sealed class Config
{
    private static readonly Lazy<Config> instance = new(() => new Config());
    public static int Created;
    public static Config Instance => instance.Value;
    private Config() => Interlocked.Increment(ref Created);
}

public record Email(string To, string Subject);

public class EmailBuilder
{
    private string? to, subject;
    public EmailBuilder To(string value) { to = value; return this; }
    public EmailBuilder Subject(string value) { subject = value; return this; }
    public Email Build() => new(to ?? throw new InvalidOperationException("To is required"), subject ?? "");
}
```

</Ex>

// Базовый класс задаёт порядок работы, а подкласс выбирает, какой объект создать
public abstract class Exporter

public class CsvExporter : Exporter

    protected override IFormatter CreateFormatter() => new CsvFormatter();

<Q id="basics.pattern.structural" level="m">

## Adapter, Decorator, Facade и Proxy: чем отличаются?

<A short l="j">

Все четыре оборачивают другой объект, а отличаются целью: <T k="adapter-pattern">адаптер</T> приводит чужой интерфейс к нужному, <T k="decorator-pattern">декоратор</T> добавляет поведение и сохраняет интерфейс, <T k="facade-pattern">фасад</T> даёт простой вход в сложную подсистему, а <T k="proxy-pattern">прокси</T> управляет доступом к объекту. Например, `BufferedStream` — декоратор над `Stream`, а `StreamReader` — адаптер от потока байтов к чтению текста.

</A>

<A short l="m">

По устройству эти паттерны похожи — объект держит ссылку на другой и делегирует ему вызовы, — поэтому различают их по намерению. Адаптер согласует несовместимые интерфейсы, декоратор добавляет обязанность с тем же интерфейсом и допускает цепочки, как <T k="delegating-handler">`DelegatingHandler`</T> в `HttpClient`, фасад упрощает работу с несколькими объектами подсистемы. Прокси с тем же интерфейсом решает, когда и как обращаться к реальному объекту: лениво, удалённо, с проверкой прав. Цена — лишний уровень вызова и риск спрятать за обёрткой важное поведение, например запрос в базу.

</A>

<A short l="s">

Намерение определяет и контракт: декоратор и прокси обязаны сохранять семантику интерфейса, а адаптер и фасад вводят новый. Прокси в .NET чаще генерируются во время выполнения: <T k="dynamic-proxy">Castle DynamicProxy</T> в Moq и ленивой загрузке EF Core, `DispatchProxy` из BCL; им нужны `virtual`-члены или интерфейсы, и они меняют поведение незаметно для вызывающего. Декораторы удобны для сквозной функциональности, но порядок в цепочке — часть поведения: логирование снаружи повторов и внутри них пишет разное. Фасад полезен на границе модуля, но если через него идёт всё, он превращается в класс, который знает обо всём.

</A>

<A l="j">

**Что это**

Все четыре паттерна оборачивают другой объект. Различие — в том, зачем.

| Паттерн | Зачем обёртка | Пример в .NET |
|---|---|---|
| Адаптер | привести чужой интерфейс к нужному | `StreamReader` поверх `Stream` |
| Декоратор | добавить поведение, интерфейс тот же | `BufferedStream`, `GZipStream` |
| Фасад | простой вход в сложную подсистему | `DbContext` |
| Прокси | управлять доступом, интерфейс тот же | ленивая загрузка в EF Core |

**Как пользоваться**

- Подключаете библиотеку с неудобным API — напишите адаптер под свой интерфейс.
- Нужны логирование или кеш без правки класса — декоратор.

**Частая ошибка**

Называть любую обёртку декоратором. Если интерфейс меняется — это адаптер. Если обёртка не добавляет поведение, а решает, вызывать ли объект, — прокси.

**Итог:** адаптер меняет интерфейс, декоратор добавляет поведение, фасад упрощает, прокси контролирует доступ.

</A>

<A l="m">

**Как устроено**

- **Адаптер.** Реализует интерфейс клиента и переводит вызовы в API адаптируемого объекта. В своём коде это обычно обёртка над SDK внешнего сервиса.
- **Декоратор.** Реализует тот же интерфейс и получает его в конструкторе, поэтому декораторы вкладываются друг в друга. `DelegatingHandler` — декоратор для `HttpMessageHandler`: он может что-то сделать до и после `base.SendAsync`.
- **Фасад.** Свой интерфейс, за которым несколько объектов. `DbContext` скрывает соединение, отслеживание изменений и генерацию SQL, а свойство `Database` возвращает объект `DatabaseFacade` для операций с самой базой.
- **Прокси.** Тот же интерфейс, но решает, вызывать ли реальный объект и когда: ленивое создание, удалённый вызов, проверка прав.

**Когда что выбирать**

| Задача | Паттерн |
|---|---|
| Чужой API не совпадает с вашим интерфейсом | Адаптер |
| Добавить логирование, повторы, кеш | Декоратор |
| Скрыть пять вызовов за одним | Фасад |
| Отложить загрузку или вызвать удалённо | Прокси |

**Ловушки**

- **Прокси прячет стоимость.** Обращение к навигационному свойству с ленивой загрузкой — запрос в базу, и в цикле получается N+1.
- **Порядок декораторов.** Логирование снаружи повторов пишет одну запись, внутри — запись на каждую попытку.

Как зарегистрировать декоратор во встроенном контейнере, разобрано в теме [Внедрение зависимостей](/sobes/aspnet/di/).

**Правило**

Сформулируйте, что меняет обёртка: интерфейс, поведение, сложность или доступ, — от этого и название.

**Итог:** устройство у четырёх паттернов похоже, различают их по намерению.

</A>

<A l="s">

**Под капотом**

- Динамический прокси — тип, сгенерированный во время выполнения через `System.Reflection.Emit`. Castle DynamicProxy создаёт подкласс с переопределёнными `virtual`-членами или реализацию интерфейса. Так работают моки Moq и прокси ленивой загрузки из `Microsoft.EntityFrameworkCore.Proxies`.
- `DispatchProxy` из BCL создаёт тип, реализующий интерфейс, и направляет все вызовы в `Invoke(MethodInfo, object[])`.
- Генерация кода во время выполнения недоступна в Native AOT, поэтому такие прокси там не работают.

**Цена**

- Каждый слой — лишний вызов через интерфейс или виртуальный метод. На фоне ввода-вывода это незаметно, в горячем цикле — заметно.
- `DispatchProxy` на каждый вызов создаёт массив аргументов и упаковывает значимые типы.

**Компромиссы**

- Ручной декоратор явный и проверяется компилятором, но его пишут под каждый интерфейс. Прокси-перехватчик один на все интерфейсы, но его поведение не видно в коде.
- Source generators — третий путь: обёртка генерируется при сборке, видна в отладчике и совместима с AOT.
- Фасад на границе модуля снижает связанность, но толстый фасад со временем собирает всю логику.

**Как проверить в проде**

- Ленивая загрузка видна как поток мелких одинаковых запросов в логе EF Core на одну операцию.
- Типы вида `Castle.Proxies.OrderProxy` в стеке исключения или в дампе показывают, что вызов шёл через перехватчик.

**Итог:** обёртки различаются намерением и контрактом; динамический прокси мощнее ручного декоратора, но прячет поведение и несовместим с AOT.

</A>

<Ex>

```csharp
INotifier notifier = new LoggingNotifier(new SmsAdapter(new LegacySmsClient()));
notifier.Send("Order shipped");
// log: Order shipped
// SMS: ORDER SHIPPED

public interface INotifier { void Send(string message); }

// Чужой класс с неудобным API: менять его нельзя
public class LegacySmsClient
{
    public void Transmit(string upperText) => Console.WriteLine($"SMS: {upperText}");
}

// Адаптер: интерфейс INotifier поверх чужого API
public class SmsAdapter(LegacySmsClient client) : INotifier
{
    public void Send(string message) => client.Transmit(message.ToUpperInvariant());
}

// Декоратор: тот же интерфейс плюс логирование
public class LoggingNotifier(INotifier inner) : INotifier
{
    public void Send(string message)
    {
        Console.WriteLine($"log: {message}");
        inner.Send(message);
    }
}
```

</Ex>

<Ex title="Динамический прокси через DispatchProxy">

```csharp
using System.Reflection;

var greeter = DispatchProxy.Create<IGreeter, LoggingProxy>();
((LoggingProxy)(object)greeter).Target = new Greeter();
Console.WriteLine(greeter.Greet("Ann"));
// call Greet
// Hello, Ann

public interface IGreeter { string Greet(string name); }

public class Greeter : IGreeter
{
    public string Greet(string name) => $"Hello, {name}";
}

// Тип прокси генерируется во время выполнения, все вызовы приходят в Invoke
public class LoggingProxy : DispatchProxy
{
    public IGreeter? Target { get; set; }

    protected override object? Invoke(MethodInfo? method, object?[]? args)
    {
        Console.WriteLine($"call {method!.Name}");
        return method.Invoke(Target, args);
    }
}
```

</Ex>

- Чем декоратор отличается от прокси, если интерфейс одинаковый? — Декоратор добавляет поведение, прокси управляет доступом: вызывать ли объект и когда.
- Почему для ленивой загрузки EF Core свойства должны быть `virtual`? — Прокси — сгенерированный подкласс, он переопределяет навигационные свойства.
- Где декораторы в `HttpClient`? — `DelegatingHandler` в цепочке обработчиков: каждый вызывает следующий через `base.SendAsync`.
- Чем фасад отличается от адаптера? — Адаптер подгоняет один интерфейс под ожидаемый, фасад вводит новый упрощённый интерфейс к нескольким объектам.
- Почему динамические прокси не работают в Native AOT? — Они генерируют типы во время выполнения, а AOT компилирует всё заранее.

<Q id="basics.pattern.behavioral" level="m">

## Strategy, Observer, Command, Chain of Responsibility и Template Method: где они в повседневном коде?

<A short l="j">

<T k="strategy-pattern">Стратегия</T> подменяет алгоритм (`IComparer<T>` в `Sort`), <T k="observer-pattern">наблюдатель</T> оповещает подписчиков (`event`), <T k="command-pattern">команда</T> упаковывает запрос в объект, <T k="chain-of-responsibility">цепочка обязанностей</T> передаёт запрос по звеньям, как <T k="middleware">middleware</T> ASP.NET Core, а <T k="template-method">шаблонный метод</T> фиксирует шаги алгоритма и отдаёт часть из них подклассу. Почти каждый из них вы используете ежедневно, просто не называя.

</A>

<A short l="m">

Все пять отвечают на вопрос «кто решает, что делать»: у стратегии — подставленный объект или делегат `Func<T>`, у наблюдателя — подписчики (`event`, `IObservable<T>`), у команды — обработчик объекта-запроса, которого можно поставить в очередь и залогировать, как в CQRS. Цепочка обязанностей — конвейер middleware и `DelegatingHandler`, шаблонный метод — базовый класс с хуками вроде `BackgroundService.ExecuteAsync`. Цена — поток управления перестаёт читаться сверху вниз: чтобы понять, что произойдёт, нужно знать, что подставлено и кто подписан.

</A>

<A short l="s">

В C# три из пяти паттернов сжались до возможностей языка: стратегия — `Func<T>`, наблюдатель — `event`, команда без отмены — `Action`; классы остаются там, где нужны состояние, несколько методов или сериализация. Подписка на `event` держит подписчика сильной ссылкой, и забытая отписка от долгоживущего издателя — классическая утечка памяти. Шаблонный метод связывает через наследование и проигрывает стратегии в гибкости, зато базовый класс гарантирует порядок шагов. Middleware — вариант цепочки, где звено может и обработать запрос, и передать его дальше, поэтому порядок регистрации определяет поведение.

</A>

<A l="j">

**Что это**

Поведенческие паттерны описывают, как объекты делят обязанности и общаются.

| Паттерн | Идея | Где в .NET |
|---|---|---|
| Стратегия | алгоритм передаётся снаружи | `IComparer<T>`, лямбды в LINQ |
| Наблюдатель | объект оповещает подписчиков | `event`, `IObservable<T>` |
| Команда | запрос — это объект | `ICommand` в WPF, обработчики команд |
| Цепочка обязанностей | запрос проходит звенья по очереди | middleware ASP.NET Core |
| Шаблонный метод | скелет алгоритма в базовом классе | `BackgroundService.ExecuteAsync` |

**Как пользоваться**

- `list.Sort(comparer)` — вы передаёте стратегию сравнения.
- `button.Click += OnClick` — подписываетесь как наблюдатель.
- Наследуете `BackgroundService` и пишете `ExecuteAsync` — заполняете шаг шаблонного метода.

**Частая ошибка**

Подписаться на событие долгоживущего объекта и не отписаться. Издатель держит ссылку на подписчика, и сборщик мусора его не освободит.

**Итог:** стратегия — подменяемый алгоритм, наблюдатель — оповещение, команда — запрос-объект, цепочка — конвейер, шаблонный метод — скелет с хуками.

</A>

<A l="m">

**Как устроено**

- **Стратегия.** Интерфейс или делегат с одним методом; контекст вызывает его, не зная реализацию.
- **Наблюдатель.** `event` — список делегатов. `IObservable<T>` добавляет сигналы завершения и ошибки и отписку через `IDisposable`.
- **Команда.** Запрос с данными — отдельный объект, исполняет его обработчик. На этом строятся очереди и CQRS-обработчики, подробнее — в теме [Архитектурные стили](/sobes/arch/styles/).
- **Цепочка обязанностей.** Звено получает запрос и ссылку на следующее и решает: обработать, передать дальше или оборвать цепочку. Так устроены middleware, подробнее — в теме [Хостинг и конвейер](/sobes/aspnet/hosting/).
- **Шаблонный метод.** Невиртуальный метод вызывает виртуальные шаги. `BackgroundService` реализует запуск и остановку и вызывает ваш `ExecuteAsync`.

**Когда что выбирать**

| Задача | Паттерн |
|---|---|
| Алгоритм меняется по настройке | Стратегия |
| Несколько реакций на одно событие | Наблюдатель |
| Запрос надо отложить, повторить, залогировать | Команда |
| Последовательные проверки и обработчики | Цепочка |
| Общий порядок шагов, разные детали | Шаблонный метод |

**Ловушки**

- Исключение в одном обработчике `event` прерывает вызов остальных.
- Шаблонный метод с десятком хуков делает базовый класс хрупким: изменение порядка шагов ломает наследников.

**Правило**

Одна операция — делегат, несколько операций или состояние — интерфейс, общий скелет — шаблонный метод, если композиции не хватает.

**Итог:** поведенческие паттерны решают, кто принимает решение, и в C# многие из них выражаются делегатами.

</A>

<A l="s">

**Под капотом**

- Событие-поле компилируется в приватный делегат и методы `add` и `remove`. Они атомарно заменяют неизменяемый многоадресный делегат через `Interlocked.CompareExchange`, а вызов идёт по снимку списка, поэтому отписка во время оповещения безопасна.
- Лямбда-стратегия, захватившая переменные, — это аллокация замыкания. Лямбду без захвата компилятор кеширует.
- Конвейер middleware собирается один раз при старте: каждое звено оборачивает следующее, и запрос идёт по готовой цепочке делегатов.

**Цена**

- Подписка держит подписчика сильной ссылкой: объект, подписанный на событие singleton, живёт, пока живёт singleton.
- Команда-объект и диспетчер добавляют аллокацию и косвенный вызов, а поиск обработчиков через рефлексию — ещё и время старта.

**Компромиссы**

- **Шаблонный метод против стратегии.** Наследование гарантирует порядок шагов, композиция позволяет менять и тестировать шаги независимо.
- **`event` против `IObservable<T>` и каналов.** Событие синхронно и без обратного давления; для асинхронных потоков данных есть Rx и `System.Threading.Channels`.
- **Свой диспетчер против MediatR.** Библиотека даёт общий конвейер обработчиков, но прячет связь «команда — обработчик» от навигации по коду. С версии 13 у неё коммерческая лицензия.

**Как проверить в проде**

- Утечку через события видно в `dotnet-gcdump`: путь удержания подписчика идёт через делегат в поле издателя.
- Порядок middleware фиксируют интеграционным тестом на `WebApplicationFactory`.

**Итог:** поведенческие паттерны в .NET — это в основном делегаты и конвейеры; их цена — неявный поток управления и сильные ссылки подписок.

</A>

<Ex>

```csharp
// Стратегия: правило скидки передаётся делегатом
var checkout = new Checkout(price => price * 90 / 100);

// Наблюдатель: подписчики узнают об оплате и не знают друг о друге
checkout.Paid += total => Console.WriteLine($"email: paid {total}");
checkout.Paid += total => Console.WriteLine($"audit: {total}");

checkout.Pay(200);
// email: paid 180
// audit: 180

// Шаблонный метод: порядок шагов задан в базовом классе
new CsvReport().Print(); // header | csv rows | footer

public class Checkout(Func<int, int> discount)
{
    public event Action<int>? Paid;
    public void Pay(int price) => Paid?.Invoke(discount(price));
}

public abstract class Report
{
    public void Print() => Console.WriteLine($"header | {Body()} | footer");
    protected abstract string Body(); // шаг, который задаёт подкласс
}

public class CsvReport : Report
{
    protected override string Body() => "csv rows";
}
```

</Ex>

<Next>

- Чем стратегия отличается от шаблонного метода? — Стратегия меняет алгоритм композицией во время выполнения, шаблонный метод — наследованием при компиляции.
- Почему событие может вызвать утечку памяти? — Издатель держит подписчика через делегат; без отписки тот живёт столько же, сколько издатель.
- Чем `IObservable<T>` богаче `event`? — Есть завершение, ошибка, отписка через `IDisposable` и операторы Rx.
- Middleware — это Chain of Responsibility? — Да, вариант: звено может обработать запрос, передать его дальше или оборвать цепочку.
- MediatR — это реализация CQRS? — Нет, это паттерн Mediator для доставки сообщений обработчикам; CQRS — про раздельные модели чтения и записи.

</Next>

<Q id="basics.pattern.anti-patterns" level="s">

## Какие антипаттерны встречаются чаще всего и как от них уходить?

<A short l="j">

<T k="anti-pattern">Антипаттерн</T> — часто повторяемое решение, которое выглядит разумным, но приносит больше вреда, чем пользы. Типичные примеры — <T k="god-object">God object</T>, класс, который знает и делает всё, магические числа в коде и Service Locator вместо явных зависимостей; уходят от них маленькими шагами рефакторинга под защитой тестов.

</A>

<A short l="m">

Антипаттерн отличается от просто плохого кода тем, что он повторяется и у него есть известная замена. Самые частые — God object, <T k="primitive-obsession">примитивная одержимость</T> (`string` и `decimal` вместо типов предметной области), <T k="shotgun-surgery">Shotgun Surgery</T>, когда одно изменение требует правок во многих классах, Service Locator и «паттерн ради паттерна». Их находят по <T k="code-smell">запахам кода</T> из каталога Фаулера и устраняют рефакторингом малыми шагами; исправление дорожает со временем, поэтому ловить их дешевле на ревью.

</A>

<A short l="s">

Антипаттерн — повторяющаяся проблема дизайна, а запах кода — локальный симптом, по которому её замечают: Large Class указывает на God object, Speculative Generality — на «паттерн ради паттерна». Часть ярлыков спорна: анемичная модель — антипаттерн для Фаулера, но нормальный выбор для CRUD-сервиса без сложных правил. Крайняя стадия — <T k="big-ball-of-mud">Big Ball of Mud</T>, система без различимой структуры, которую Foote и Yoder называют фактическим стандартом архитектуры. Лечение — не переписывание, а постепенный рефакторинг с тестами и правила, которые не дают проблеме вернуться: анализаторы, архитектурные тесты, ревью.

</A>

<A l="j">

**Что это**

Антипаттерн — решение, которое часто встречается и кажется удобным, но со временем делает код дороже в изменении. У него есть известная замена.

**Самые частые**

- **God object.** Один `OrderManager` на 3000 строк делает всё: проверки, расчёт, SQL, отправку писем.
- **Магические числа.** `if (status == 3)` — что такое 3, знает только автор.
- **Копипаста.** Одна и та же логика в пяти местах, а исправили её в четырёх.
- **Service Locator.** `provider.GetService<T>()` внутри методов вместо параметров конструктора.

**Как уходить**

1. Покрыть код тестами, чтобы рефакторинг ничего не сломал.
2. Менять малыми шагами: вынести константу, вынести метод, вынести класс.

**Частая ошибка**

Переписать всё с нуля. Старый код хранит знания о крайних случаях, которые новый потеряет.

**Итог:** антипаттерн — привычное плохое решение; его исправляют маленькими шагами под защитой тестов.

</A>

<A l="m">

**Как устроено**

Запах кода — видимый симптом: длинный метод, большой класс, длинный список параметров. Антипаттерн — диагноз, который за ним стоит. Каталог запахов и рефакторингов против них собрал Мартин Фаулер в книге «Refactoring», второе издание вышло в 2018 году.

| Антипаттерн | Симптом | Рефакторинг |
|---|---|---|
| God object | Large Class, десятки зависимостей | Extract Class |
| Магические числа | литералы в условиях | Replace Magic Literal |
| Примитивная одержимость | `string` для email, `decimal` для денег | Replace Primitive with Object |
| Shotgun Surgery | одна правка — много файлов | Move Function, Combine Functions into Class |
| Паттерн ради паттерна | Speculative Generality | Inline Class, Collapse Hierarchy |
| Service Locator | `GetService` в бизнес-коде | параметр конструктора |

**Ловушки**

- **Анемичная модель — спорный ярлык.** Для CRUD без правил это нормально. Проблемой она становится, когда одни и те же проверки дублируются по сервисам; подробнее — в теме [Архитектурные стили](/sobes/arch/styles/).
- **Лечение порождает новую болезнь.** Если раздробить God object на мелкие классы без смысла, получится Shotgun Surgery.

**Правило**

Рефакторинг — отдельный коммит без изменения поведения: малые шаги и зелёные тесты после каждого.

**Итог:** запах — симптом, антипаттерн — диагноз, рефакторинг из каталога Фаулера — лечение.

</A>

<A l="s">

**Как возникают**

- Антипаттерны редко пишут намеренно. God object растёт, потому что добавить метод в существующий класс дешевле, чем придумать новый: каждое решение локально разумно, а сумма — нет.
- Big Ball of Mud (Foote и Yoder, 1997) — результат давления сроков, смены людей и роста без рефакторинга.

**Цена**

- God object и Shotgun Surgery дорожают с каждым изменением: больше конфликтов слияния, регрессий и времени на ревью.
- Примитивная одержимость переносит проверки в рантайм: email проверяют в десяти местах или ни в одном.

**Компромиссы**

- Не каждый ярлык — приговор. Анемичная модель приемлема для CRUD, а `TimeSpan.FromSeconds(30)` читается и без константы.
- «Паттерн ради паттерна» и YAGNI тянут в одну сторону, DRY и расширяемость — в другую. Абстракцию вводят на втором-третьем случае, а не на первом.
- Большой рефакторинг — это проект: его режут на шаги, каждый из которых можно выпустить, например через Strangler Fig.

**Как проверить в проде**

- Анализаторы Roslyn и SonarQube ловят часть запахов: сложность методов, дублирование, магические числа.
- Частота изменений файлов в истории git показывает горячие точки: большой файл, который меняется почти в каждом коммите, — кандидат в God object.
- Архитектурные тесты (NetArchTest, ArchUnitNET) фиксируют границы слоёв, чтобы Big Ball of Mud не вернулся.

**Итог:** антипаттерны вырастают из локально разумных решений; их ловят метриками и ревью, а лечат постепенным рефакторингом, а не переписыванием.

</A>

<Ex>

```csharp
// До: if (status == 3 && email.Contains('@')) — магическое число и строка вместо типа
// После: именованное состояние и тип с проверкой при создании
var email = Email.Parse("ann@example.com");
Console.WriteLine(CanShip(email, OrderStatus.Paid)); // True

try { Email.Parse("not-an-email"); }
catch (ArgumentException e) { Console.WriteLine(e.Message); } // Invalid email

static bool CanShip(Email email, OrderStatus status) => status == OrderStatus.Paid;

public enum OrderStatus { New = 1, Reserved = 2, Paid = 3 }

// Replace Primitive with Object: неверный email не создать
public sealed record Email
{
    public string Value { get; }
    private Email(string value) => Value = value;

    public static Email Parse(string value) =>
        value.Contains('@') ? new Email(value) : throw new ArgumentException("Invalid email");
}
```

- Чем антипаттерн отличается от запаха кода? — Запах — локальный симптом, антипаттерн — повторяющееся неудачное решение за ним.
- Почему Service Locator — антипаттерн? — Прячет зависимости и переносит ошибки в рантайм; подробно — в теме «Внедрение зависимостей».
- Как разбить God object? — Найти группы полей и методов, которые меняются вместе, и вынести их в отдельные классы (Extract Class) малыми шагами.
- Анемичная модель — всегда плохо? — Нет: для CRUD без инвариантов это нормально; плохо, когда правила дублируются по сервисам.
- Когда переписать с нуля лучше рефакторинга? — Редко; чаще старую систему заменяют по частям через Strangler Fig.
