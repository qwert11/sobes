## Как устроен React: компоненты, props, state и хуки?

<A short l="j">

React-приложение собирается из компонентов — функций, которые принимают <T k="props">props</T> и возвращают разметку на <T k="jsx">JSX</T>. Когда меняется <T k="react-state">состояние</T> из `useState`, React снова вызывает компонент и обновляет в DOM только то, что изменилось.

</A>

<A short l="m">

Компонент — чистая функция от props и state: данные идут сверху вниз, а наверх возвращаются через колбэки. <T k="react-hooks">Хуки</T> (`useState`, `useEffect` и другие) хранят данные компонента между рендерами и привязаны к порядку вызова, поэтому их не вызывают в условиях и циклах. Цена модели — изменение состояния по умолчанию перерисовывает компонент вместе со всеми потомками, поэтому состояние держат как можно ниже по дереву.

</A>

<A short l="s">

React описывает UI как функцию от состояния: рендер строит новое дерево элементов, а <T k="react-reconciliation">согласование</T> (reconciliation) сравнивает его с прошлым и вносит в DOM минимум изменений. Идентичность компонента задают место в дереве и `key`, поэтому неверный `key` теряет или путает состояние. State — снимок на один рендер: `setState` планирует новый рендер, а не меняет переменную, и обновления пакетируются. Чистота рендера — контракт, на котором держатся StrictMode, конкурентный рендеринг и React Compiler.

</A>

<A l="j">

**Что это**

- **Компонент** — функция, которая возвращает JSX: разметку, похожую на HTML, прямо в JavaScript.
- **Props** — входные параметры от родителя, только для чтения.
- **State** — данные, которые компонент помнит между рендерами.

**Как пользоваться**

1. `const [count, setCount] = useState(0)` — значение и функция его изменения.
2. Вызов `setCount(count + 1)` запускает новый рендер с новым значением.
3. Список рендерят через `map`, каждому элементу дают `key` — стабильный id.
4. Поле ввода делают <T k="controlled-component">контролируемым</T>: `value` берётся из state, `onChange` меняет state.

**Частая ошибка**

Менять state напрямую: `todos.push(x)`. Ссылка на массив прежняя, и React не увидит изменения. Нужен новый массив: `setTodos([...todos, x])`.

**Итог:** компонент — функция от props и state, а новое состояние через `setState` — это новый рендер.

</A>

<A l="m">

**Как устроено**

1. **Рендер.** React вызывает функцию компонента и получает дерево элементов.
2. **Commit.** Сравнивает его с прошлым деревом и точечно меняет DOM.
3. **Повтор.** Новый state или рендер родителя снова запускает компонент и по умолчанию всех его детей.

**Правила хуков**

- Только на верхнем уровне компонента или своего хука: не в условиях, циклах и после раннего `return`. React находит состояние хуков по порядку вызова.
- Только из компонентов и хуков, чьё имя начинается с `use`.
- Нарушения ловит `eslint-plugin-react-hooks`.

**Ловушки**

- **State — снимок.** После `setCount(count + 1)` переменная `count` до следующего рендера прежняя. Три таких вызова подряд дадут +1, а `setCount(c => c + 1)` — +3.
- **Индекс как `key`.** При вставке в начало или сортировке ввод и фокус строк переедут к чужим элементам.
- **Однонаправленный поток.** Ребёнок не меняет props, а вызывает колбэк родителя: `onChange`, `onSelect`.

**Правило**

Храните в state минимум, остальное вычисляйте в рендере. Общее состояние кладите в ближайшего общего родителя.

**Итог:** рендер — чистая функция от props и state, а хуки работают, пока порядок их вызова не меняется.

</A>

<A l="s">

**Под капотом**

- Каждому экземпляру компонента соответствует узел fiber. В нём лежит список хуков в порядке вызова, поэтому условный хук сдвигает список и ломает состояние.
- Согласование эвристическое и линейное: элемент другого типа не сравнивается вглубь, а пересоздаётся вместе с поддеревом. Дети списка сопоставляются по `key`.
- С React 18 обновления пакетируются везде (automatic batching): несколько `setState` в обработчике, промисе или таймере дают один рендер.

**Цена**

- Рендер дешевле commit, но не бесплатен: перерисовка большого поддерева на каждое нажатие клавиши заметна. Часто меняющееся состояние держат в листовых компонентах.
- Смена `key` или типа элемента сбрасывает состояние всего поддерева. Это и инструмент: `key={userId}` сбрасывает форму при смене пользователя.

**Компромиссы**

- Контролируемое поле даёт валидацию на каждый ввод ценой рендера на каждый символ. Неконтролируемые поля с `FormData` дешевле, если значение нужно только при отправке.
- StrictMode в разработке вызывает компонент дважды, чтобы поймать побочные эффекты в рендере. На той же чистоте построены конкурентный рендеринг и React Compiler.

**Как проверить в проде**

- Profiler в React DevTools с опцией «Record why each component rendered while profiling» показывает причину каждого рендера.
- Опция «Highlight updates when components render» подсвечивает перерисованные компоненты.

**Итог:** идентичность компонента — его позиция и `key`, а чистый рендер — условие, на котором держатся все оптимизации React.

</A>

<Ex>

```tsx
import { useState } from 'react';

type Todo = { id: number; title: string };

export function TodoList({ initial }: { initial: Todo[] }) {
  const [todos, setTodos] = useState(initial); // состояние компонента
  const [title, setTitle] = useState('');      // контролируемое поле

  function add() {
    // Новый массив, а не push: React сравнивает ссылки
    setTodos([...todos, { id: Date.now(), title }]);
    setTitle('');
  }

  return (
    <>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      <button onClick={add} disabled={!title}>Add</button>
      <ul>
        {todos.map((t) => <li key={t.id}>{t.title}</li>)} {/* key — стабильный id, не индекс */}
      </ul>
    </>
  );
}
```

</Ex>

- Почему индекс — плохой `key`? — При вставке и сортировке состояние строк достаётся чужим элементам.

## Как правильно использовать useEffect и где он не нужен?

<A short l="j">

<T k="react-effect">Эффект</T> (`useEffect`) — код, который React запускает после отрисовки, чтобы синхронизировать компонент с внешней системой: подпиской, соединением, сторонним виджетом. Второй аргумент — <T k="dependency-array">массив зависимостей</T>: эффект перезапускается, только когда они меняются.

</A>

<A short l="m">

Эффект синхронизирует компонент с внешней системой: после commit React выполняет setup, а перед перезапуском и при размонтировании — <T k="effect-cleanup">очистку</T>, которую setup вернул. В зависимостях — все реактивные значения, прочитанные внутри, иначе эффект работает с <T k="stale-closure">устаревшим замыканием</T>. Если значение можно посчитать в рендере или действие выполнить в обработчике события, эффект не нужен: он добавляет лишний рендер и место для ошибок.

</A>

<A short l="s">

Эффект — механизм синхронизации, а не «жизненный цикл»: setup и cleanup симметричны, и <T k="strict-mode">StrictMode</T> в разработке нарочно запускает лишний цикл setup → cleanup → setup, чтобы это проверить. Объект или функция в зависимостях перезапускают эффект на каждый рендер, а нереактивную логику выносят в <T k="use-effect-event">`useEffectEvent`</T> (React 19.2). Загрузка данных в эффекте даёт водопады запросов и гонки и не имеет кеша, поэтому её отдают TanStack Query или серверным компонентам.

</A>

<A l="j">

**Что это**

`useEffect(setup, deps)` выполняет `setup` после того, как React обновил экран. Функция, которую вернул `setup`, — очистка.

**Как пользоваться**

1. Внутри — работа с внешним миром: `addEventListener`, `setInterval`, WebSocket.
2. В массив зависимостей — всё, что эффект читает из props и state.
3. Верните очистку: `removeEventListener`, `clearInterval`, закрытие соединения.

| Зависимости | Когда запускается |
|---|---|
| массива нет | после каждого рендера |
| `[]` | один раз после появления на экране |
| `[userId]` | при появлении и при смене `userId` |

**Частая ошибка**

Синхронизировать эффектом производные данные: `useEffect(() => setFullName(first + ' ' + last), [first, last])`. Это лишний рендер; достаточно `const fullName = first + ' ' + last` прямо в компоненте.

**Итог:** эффект — для связи с внешней системой, а вычисления делаются в рендере.

</A>

<A l="m">

**Как устроено**

1. Рендер → commit в DOM → браузер рисует → React запускает эффекты.
2. На следующем рендере React сравнивает зависимости через `Object.is`. Если что-то изменилось — cleanup прошлого эффекта, затем новый setup.
3. При размонтировании выполняется последний cleanup.

**Ловушки**

- **Устаревшее замыкание.** Эффект видит props и state своего рендера. `setInterval(() => setCount(count + 1))` с `[]` застрянет на 1; нужно `setCount(c => c + 1)`.
- **Объект или функция в зависимостях.** Они создаются заново в каждом рендере, и эффект перезапускается всегда. Создайте их внутри эффекта или зависьте от примитивов.
- **Гонка ответов.** При быстрой смене `query` старый ответ может прийти последним. Флаг `ignore` или `AbortController` в cleanup отбрасывает его.
- **Двойной запуск в разработке.** Если из-за него ломается логика, у эффекта нет корректной очистки.

**Когда эффект не нужен**

| Задача | Вместо эффекта |
|---|---|
| производное значение | вычислить в рендере, дорогое — `useMemo` |
| реакция на клик или отправку | обработчик события |
| сброс state при смене prop | `key` у компонента |
| загрузка данных | TanStack Query, серверный компонент |

**Правило**

Эффект нужен, когда код выполняется потому, что компонент показан, а не потому, что пользователь что-то сделал.

**Итог:** в зависимостях — всё прочитанное, очистка — зеркало setup, остальное — в рендер и обработчики.

</A>

<A l="s">

**Под капотом**

- `useEffect` выполняется после отрисовки и не блокирует её. `useLayoutEffect` выполняется до отрисовки, для измерения DOM, и задерживает кадр.
- При серверном рендеринге эффекты не выполняются — только в браузере.
- StrictMode в разработке добавляет каждому эффекту цикл setup → cleanup → setup. В проде его нет, но он моделирует реальные сценарии: уход со страницы и возврат, Fast Refresh.

**Цена**

Загрузка данных в эффекте стартует только после загрузки JS и рендера. Вложенные компоненты со своими эффектами образуют водопад: запрос ребёнка ждёт ответа родителя. Кеша, дедупликации и повторов при ошибке нет.

**Компромиссы**

- Прочитать свежее значение без перезапуска, например тему внутри обработчика соединения, — `useEffectEvent` (стабилен с React 19.2). Отключать правило `exhaustive-deps` — прятать баг.
- Подписка на внешнее хранилище — `useSyncExternalStore`, а не эффект с `setState`: он корректен при конкурентном рендеринге.
- Данные — серверный компонент или TanStack Query: кеш, отмена и гонки решены там.

**Как проверить в проде**

- `eslint-plugin-react-hooks` с `exhaustive-deps` и `set-state-in-effect` — ошибкой в CI.
- В Profiler React DevTools цепочка «эффект → `setState` → рендер» видна как лишние коммиты подряд.

**Итог:** эффект — инструмент синхронизации с внешним миром; чем меньше эффектов, тем меньше водопадов, гонок и лишних рендеров.

</A>

<Ex>

```tsx
import { useEffect, useState } from 'react';

type Item = { name: string; active: boolean };

export function Search({ query, onlyActive }: { query: string; onlyActive: boolean }) {
  const [items, setItems] = useState<Item[]>([]);

  // Эффект: синхронизация с внешней системой (сервером) при смене query
  useEffect(() => {
    let ignore = false; // ответ на устаревший query не перезапишет новый
    fetch(`/api/items?q=${encodeURIComponent(query)}`)
      .then((r) => r.json())
      .then((data: Item[]) => { if (!ignore) setItems(data); });
    return () => { ignore = true; }; // очистка: перед перезапуском и при размонтировании
  }, [query]);

  // Не эффект: производное значение считается прямо в рендере
  const visible = onlyActive ? items.filter((i) => i.active) : items;

  return <ul>{visible.map((i) => <li key={i.name}>{i.name}</li>)}</ul>;
}
```

</Ex>

<Ex title="Устаревшее замыкание">

```tsx
import { useEffect, useState } from 'react';

export function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    // Ошибка: setCount(count + 1) видит count = 0 из первого рендера — застрянет на 1
    const id = setInterval(() => setCount((c) => c + 1), 1000); // апдейтер берёт актуальное значение
    return () => clearInterval(id);
  }, []);

  return <p>{count}</p>; // 1, 2, 3...
}
```

<Next>

- Чем `useEffect` отличается от `useLayoutEffect`? — Layout-эффект выполняется до отрисовки, для измерения DOM; обычный — после.
- Почему эффект в разработке срабатывает дважды? — StrictMode проверяет, что очистка отменяет setup; в проде повторного запуска нет.
- Как не перезапускать эффект, если нужно только прочитать свежее значение? — Вынести чтение в `useEffectEvent` (React 19.2+).
- Как отменить запрос при смене параметров? — `AbortController` и `abort()` в cleanup или флаг `ignore`.
- Можно ли сделать функцию эффекта `async`? — Нет: она должна вернуть cleanup, а не промис; async-функцию объявляют внутри и вызывают.

</Next>

<Q id="front.react.state" level="m">

## Как управлять состоянием в React-приложении?

<A short l="j">

Состояние сначала держат локально в компоненте через `useState`. Если оно нужно двум соседям, его <T k="lifting-state-up">поднимают</T> в общего родителя и передают через props, а данные с сервера хранят в библиотеке вроде <T k="tanstack-query">TanStack Query</T>, которая кеширует ответы.

</A>

<A short l="m">

Состояние делят по владельцу: клиентское (UI, формы) живёт в `useState`, у общего родителя или в сторе вроде <T k="zustand">Zustand</T>, а <T k="server-state">серверное</T> — копия данных сервера — в TanStack Query с кешем и инвалидацией. <T k="react-context">Context</T> убирает <T k="prop-drilling">prop drilling</T>, но при смене значения перерисовывает всех потребителей. Фильтры, страница и вкладка — в URL, чтобы ссылкой можно было поделиться.

</A>

<A short l="s">

Главная ошибка — смешивать серверное и клиентское состояние в одном сторе: тогда кеш, устаревание, повторные запросы и инвалидацию пишут руками. Серверное — в TanStack Query или серверных компонентах, навигационное — в URL, а глобальный стор с селекторами — для редкого по-настоящему общего клиентского состояния. Context — способ передать значение, а не стор: подписки на часть значения у него нет, поэтому часто меняющиеся данные в нём дороги. В Next.js стор на уровне модуля общий для всех запросов сервера, поэтому его создают на запрос.

</A>

<A l="j">

**Что это**

Состояние — данные, от которых зависит экран: открыт ли диалог, текст в поле, список заказов.

**Как пользоваться**

1. Начните с `useState` в компоненте, которому оно нужно.
2. Нужно двум компонентам — поднимите state в ближайшего общего родителя и передайте вниз значение и функцию изменения.
3. Значение нужно глубоко и во многих местах (тема, текущий пользователь) — Context.
4. Данные с сервера — `useQuery` из TanStack Query: он загрузит, закеширует и обновит их.

**Частая ошибка**

Копировать props в state: `useState(props.user.name)`. Начальное значение берётся один раз, и при смене props state останется старым.

**Итог:** state держат как можно ближе к месту использования и поднимают, только когда он нужен нескольким компонентам.

</A>

<A l="m">

**Как устроено**

- **Подъём состояния.** State переезжает в общего родителя, дети получают значение и колбэк. Цена — props проходят через компоненты, которым они не нужны.
- **Context.** `createContext`, провайдер `<ThemeContext value={theme}>` (React 19) и `useContext` или `use`. При смене значения перерисовываются все потребители.
- **Стор.** Zustand и Redux Toolkit хранят состояние вне дерева React. Компонент подписывается селектором и перерисовывается, только когда меняется выбранная часть.
- **Серверное состояние.** TanStack Query хранит ответы в кеше по `queryKey`. После мутации `invalidateQueries` помечает данные устаревшими и перезапрашивает активные.

**Когда что выбирать**

| Состояние | Где хранить |
|---|---|
| диалог открыт, ввод в поле | `useState` в компоненте |
| нужно соседям | общий родитель |
| тема, язык, пользователь | Context |
| корзина, сложный общий UI | Zustand или Redux Toolkit |
| данные с API | TanStack Query, серверный компонент |
| фильтры, страница, вкладка | URL (`searchParams`) |

**Ловушки**

- Новый объект в `value` провайдера на каждом рендере перерисовывает всех потребителей. Разделяйте контексты или мемоизируйте `value`.
- Селектор Zustand, возвращающий новый объект или массив, перерисовывает на каждое изменение стора — оберните его в `useShallow`.

**Правило**

Сначала решите, чьи это данные: сервера, URL или интерфейса. От этого зависит место хранения.

**Итог:** серверное состояние — в кеше запросов, навигационное — в URL, клиентское — как можно локальнее.

</A>

<A l="s">

**Под капотом**

- Context сравнивает `value` через `Object.is` и перерисовывает всех потребителей ниже провайдера; `memo` их не останавливает.
- Zustand построен на `useSyncExternalStore`: компонент перерисовывается, только если результат селектора изменился по `Object.is`.
- TanStack Query (v5) по умолчанию считает данные сразу устаревшими (`staleTime: 0`) и перезапрашивает их при монтировании, фокусе окна и восстановлении сети. Неиспользуемый кеш живёт 5 минут (`gcTime`).

**Цена**

- Без `staleTime` каждое монтирование и возврат на вкладку — сетевой запрос. Для справочников ставят минуты.
- `queryKey` — контракт: неточный ключ даёт устаревший экран после мутации или лишние запросы.

**Компромиссы**

- Zustand — минимум кода и хук без провайдера. Redux Toolkit — строгая структура, история действий в DevTools и RTK Query; оправдан в большой команде.
- В Next.js App Router данные читают в серверных компонентах. TanStack Query остаётся для интерактивного клиента: бесконечные списки, опрос, оптимистичные обновления.
- Стор на уровне модуля на сервере Next.js общий для всех запросов, и данные одного пользователя утекут другому. Документация Zustand советует создавать стор на запрос и передавать через Context.

**Как проверить в проде**

- TanStack Query Devtools показывает ключи, свежесть и число подписчиков запроса.
- Profiler React DevTools показывает, сколько компонентов перерисовала смена значения Context.

**Итог:** выбор хранилища — выбор владельца данных, а скорость зависит от гранулярности подписок.

</A>

```tsx
import { useMutation, useQuery, useQueryClient } from '@tanstack/react-query';

type Order = { id: number; status: string };

export function Orders() {
  const queryClient = useQueryClient();

  const { data, isPending } = useQuery({
    queryKey: ['orders'], // ключ кеша
    queryFn: (): Promise<Order[]> => fetch('/api/orders').then((r) => r.json()),
    staleTime: 30_000, // 30 секунд данные свежие: без повторных запросов
  });

  const close = useMutation({
    mutationFn: (id: number) => fetch(`/api/orders/${id}/close`, { method: 'POST' }),
    // Инвалидация: кеш устарел, активные запросы перезапросятся
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['orders'] }),
  });

  if (isPending) return <p>Loading…</p>;
  return (
    <ul>
      {data?.map((o) => (
        <li key={o.id}>
          #{o.id} {o.status} <button onClick={() => close.mutate(o.id)}>Close</button>
        </li>
      ))}
    </ul>
  );
}
```

## Как устроен Next.js и App Router?

<A short l="j">

Next.js — фреймворк поверх React с маршрутизацией по папкам и рендерингом на сервере. В <T k="app-router">App Router</T> папка внутри `app/` — сегмент URL, `page.tsx` — страница, `layout.tsx` — общий каркас. Компоненты по умолчанию <T k="react-server-components">серверные</T>, а интерактивные помечают директивой `'use client'`.

</A>

<A short l="m">

App Router строит маршруты из папок `app/` и вкладывает layout друг в друга, сохраняя их состояние при навигации. Серверные компоненты выполняются только на сервере и могут читать базу напрямую, а <T k="client-component">клиентские</T> (`'use client'`) получают JS в браузере для state и событий. HTML готовится при сборке или на каждый запрос (<T k="ssr">SSR</T>), а данные меняют через <T k="server-action">Server Actions</T>; с Next.js 16 кеширование включается явно через `'use cache'`.

</A>

<A short l="s">

Next.js 16 сменил модель кеширования: с Cache Components весь код по умолчанию выполняется на запрос, а кешируется только помеченное <T k="use-cache">`'use cache'`</T> с `cacheLife` и `cacheTag`. Статическое и кешированное попадает в статическую оболочку, а динамическое стримится из-под `Suspense` — это <T k="partial-prerendering">Partial Prerendering</T>, и страница больше не выбирает между SSG и SSR целиком. С 16.4 новые проекты получают Cache Components по умолчанию, а в Next.js 17 модель станет общей. Цена — дисциплина: каждое обращение к данным запроса кешируют или оборачивают в `Suspense`, иначе dev-оверлей и сборка укажут на ошибку.

</A>

<A l="j">

**Что это**

Next.js добавляет к React маршрутизацию, рендеринг на сервере, сборку и серверный код. App Router — маршрутизатор на основе папки `app/`.

**Как пользоваться**

- `app/page.tsx` — это `/`, `app/blog/[slug]/page.tsx` — `/blog/hello`. Квадратные скобки — динамический сегмент.
- `layout.tsx` оборачивает все страницы ниже себя: шапка, меню.
- `loading.tsx` и `error.tsx` — экраны загрузки и ошибки для сегмента.
- Серверный компонент может быть `async` и получать данные через `await`.
- Нужны `useState` или `onClick` — первая строка файла `'use client'`.

**Частая ошибка**

Ставить `'use client'` на всю страницу ради одной кнопки. Тогда весь код страницы уходит в браузер; в клиентский компонент выносят только кнопку.

**Итог:** папки — это URL, компоненты по умолчанию серверные, а `'use client'` — только для интерактивных частей.

</A>

<A l="m">

**Как устроено**

1. Запрос проходит `proxy.ts` (до Next.js 16 — `middleware.ts`), если он есть: редиректы, перезапись URL, заголовки.
2. Серверные компоненты рендерятся в RSC Payload — сериализованное дерево с местами для клиентских компонентов.
3. Из него строится HTML первой загрузки, а браузер загружает JS клиентских компонентов.
4. При переходе по `<Link>` сервер отдаёт только изменившиеся сегменты; общие layout не перерисовываются.

**Когда что выбирать**

| Режим | Когда готов HTML |
|---|---|
| SSG | при сборке; одинаков для всех |
| ISR | при сборке, обновляется в фоне по времени или тегу |
| SSR | на каждый запрос; данные пользователя |

**Серверный код**

- **Server Actions** (`'use server'`) — функции для изменения данных из форм и обработчиков. Вызываются POST-запросом.
- **Route Handlers** (`app/api/.../route.ts` с `export async function GET`) — HTTP API для вебхуков и внешних клиентов, например мобильного приложения.

**Ловушки**

- С Next.js 15 `params`, `searchParams`, `cookies()` и `headers()` асинхронные, в 16 синхронный доступ удалён.
- С Next.js 15 `fetch` и GET Route Handlers по умолчанию не кешируются.
- Server Action — публичный эндпоинт: авторизацию проверяют внутри каждого.

**Правило**

Читают данные в серверных компонентах, меняют — в Server Actions, Route Handler — для внешних потребителей.

**Итог:** App Router — серверные компоненты по умолчанию, вложенные layout и явный серверный код для чтения и изменения данных.

</A>

<A l="s">

**Под капотом**

- С `cacheComponents: true` всё динамическое выполняется на запрос. `'use cache'` у функции, компонента или файла кеширует результат; ключ — аргументы и захваченные значения, поэтому они сериализуемые.
- При сборке статическое и кешированное попадает в статическую оболочку, а вместо данных запроса под `Suspense` — fallback. Оболочку раздаёт CDN, остальное стримится в том же ответе.
- `cookies()` и `headers()` внутри `'use cache'` недоступны: значение читают снаружи и передают аргументом или используют `'use cache: private'`.

**Инвалидация**

| API | Семантика |
|---|---|
| `updateTag(tag)` | только в Server Action; автор сразу видит свои изменения |
| `revalidateTag(tag, 'max')` | stale-while-revalidate: отдаётся старое, новое строится в фоне |
| `refresh()` | обновить некешированные данные, кеш не трогает |

**Компромиссы**

- Без Cache Components действует прежняя модель: маршрут статический, пока не читает данные запроса, а `export const revalidate` задаёт ISR. Одно чтение `cookies()` делает динамической всю страницу.
- По умолчанию кеш `'use cache'` живёт в памяти экземпляра. Общий для нескольких экземпляров — `'use cache: remote'` с обработчиком кеша.
- `proxy.ts` работает на Node.js; `middleware.ts` для Edge устарел. Proxy — для быстрых редиректов и заголовков, не для полной авторизации.
- Развёртывание: Vercel, `next start` или `output: 'standalone'` в Docker, адаптеры платформ (стабильны с 16.2). `output: 'export'` — статика без серверных возможностей.

**Как проверить в проде**

- `next build` печатает тип каждого маршрута, dev-оверлей показывает обращения к данным запроса вне `Suspense`.
- `export const ensureStatic = 'navigation'` (16.4) роняет сборку, если в статический маршрут попал динамический компонент.

**Итог:** в Next.js 16 кеш явный и гранулярный: статическая оболочка с CDN, динамика стримится, инвалидация — по тегам.

</A>

<Ex>

```tsx
// app/products/[id]/page.tsx — серверный компонент по умолчанию
import { Suspense } from 'react';
import { cacheLife, cacheTag } from 'next/cache';
import { AddToCart } from './add-to-cart'; // файл с 'use client'

type Props = { params: Promise<{ id: string }> }; // с Next.js 15 params — промис

export default function Page({ params }: Props) {
  return (
    <Suspense fallback={<p>Loading…</p>}> {/* fallback попадает в статическую оболочку */}
      <Product params={params} />
    </Suspense>
  );
}

async function Product({ params }: Props) {
  const { id } = await params;
  const product = await getProduct(id);
  return (
    <main>
      <h1>{product.name}</h1>
      <AddToCart id={id} /> {/* в браузер уходит JS только этого компонента */}
    </main>
  );
}

async function getProduct(id: string) {
  'use cache'; // Cache Components: результат кешируется по аргументам
  cacheLife('hours');
  cacheTag(`product-${id}`); // сбросить после изменения: updateTag в Server Action
  const res = await fetch(`https://api.example.com/products/${id}`);
  return (await res.json()) as { name: string };
}
```

## Что нового в React 19 и как добиться быстрого рендеринга?

<A short l="j">

React 19 добавил <T k="react-action">Actions</T> — асинхронные функции для форм и мутаций, у которых React сам отслеживает ожидание, ошибки и оптимистичные обновления через `useActionState` и `useOptimistic`. <T k="react-compiler">React Compiler</T> сам мемоизирует компоненты, поэтому `useMemo` и `useCallback` пишут реже.

</A>

<A short l="m">

Action — асинхронная функция, запущенная в <T k="transition">переходе</T> (transition): `useActionState` даёт результат и флаг ожидания, `useOptimistic` показывает изменение до ответа сервера, а `use` читает промис или контекст. Быстрый первый показ даёт серверный рендер со <T k="streaming-ssr">стримингом</T>: HTML уходит частями по границам <T k="suspense">`Suspense`</T>, и медленные данные не блокируют страницу. С React Compiler ручная мемоизация нужна редко, но компилятор требует соблюдать правила React.

</A>

<A short l="s">

В React 19 сервер стал частью модели: серверные компоненты не отправляют свой код в браузер, а граница `'use client'` — граница сериализации, через которую проходят только сериализуемые props. Actions и переходы делают мутации и ожидание декларативными, а `Suspense` со стримингом и выборочной <T k="hydration">гидратацией</T> разбивает загрузку на независимые части. React Compiler 1.0 автоматически мемоизирует то, что раньше делали `memo`, `useMemo` и `useCallback`. Цена — чистый рендер, одинаковый HTML на сервере и клиенте и измерения в Profiler вместо мемоизации наугад.

</A>

<A l="j">

**Что это**

- **Action** — функция, переданная в `<form action={...}>`: получает `FormData`, а React сам знает, идёт ли отправка.
- **`useActionState`** — результат последнего действия и флаг `isPending`.
- **`useOptimistic`** — временное значение, которое видно, пока действие выполняется.
- **React Compiler** — плагин сборки, который сам кеширует вычисления и пропускает лишние рендеры.

**Как пользоваться**

1. `const [error, formAction, isPending] = useActionState(save, null)`.
2. `<form action={formAction}>` и кнопка с `disabled={isPending}`.
3. Компилятор в Next.js 16 включают опцией `reactCompiler: true`; в Expo SDK 54+ он включён по умолчанию.

**Частая ошибка**

Оборачивать каждую функцию в `useCallback` «для скорости». Без измерений это шум, а с компилятором — лишний код.

**Итог:** Actions убирают ручные флаги загрузки, а компилятор — большую часть ручной мемоизации.

</A>

<A l="m">

**Как устроено**

- **Переход.** `startTransition` помечает обновление несрочным: ввод остаётся отзывчивым, а старый UI виден, пока готовится новый. Action — асинхронная функция внутри перехода.
- **`useOptimistic`.** Сеттер вызывают внутри Action. Когда действие завершилось, оптимистичное значение сменяется реальным, при ошибке — исчезает.
- **`use`.** Читает промис, приостанавливая компонент до результата, или контекст. Его, в отличие от других хуков, можно вызывать в условиях.
- **Suspense и стриминг.** Ближайший `Suspense` показывает fallback, пока компонент ждёт данные. Сервер сразу отправляет оболочку, а готовые части дописывает в тот же ответ.
- **Гидратация.** React привязывает обработчики к HTML, пришедшему с сервера. Границы `Suspense` гидратируются независимо, первой — та, с которой взаимодействует пользователь.

**Ловушки**

- **Ошибка гидратации** — HTML сервера не совпал с первым клиентским рендером: `Date.now()`, `typeof window`, локаль, `<div>` внутри `<p>`. React перерисует участок на клиенте — это медленнее.
- **Промис, созданный в рендере клиентского компонента**, для `use` пересоздаётся на каждый рендер. Его передают из серверного компонента или берут из кеширующей библиотеки.

**Правило**

Сначала измерьте в Profiler, потом оптимизируйте: опустите состояние ниже, разбейте страницу на `Suspense`, включите компилятор.

**Итог:** React 19 делает ожидание и мутации декларативными, а первую загрузку ускоряют стриминг и выборочная гидратация.

</A>

<A l="s">

**Под капотом**

- Серверные компоненты выполняются на сервере и сериализуются в RSC Payload; их код и зависимости не попадают в бандл.
- Граница `'use client'` — граница сериализации. Props через неё: примитивы, простые объекты, массивы, `Date`, `Map`, `Set`, промисы, JSX и Server Functions. Обычные функции и экземпляры классов передать нельзя.
- React Compiler 1.0 (октябрь 2025) при сборке анализирует поток данных и мемоизирует значения, JSX и колбэки, в том числе после раннего `return`, где `useMemo` невозможен. Компонент, нарушающий правила React, он пропускает.

**Компромиссы**

- `useMemo` и `useCallback` остаются для точного контроля, например стабильной зависимости эффекта. Существующую мемоизацию убирают только с тестами: это меняет результат компиляции.
- В Next.js 16 компилятор не включён по умолчанию и работает через Babel, сборка медленнее; Rust-версия экспериментальна с 16.3.
- Стриминг ускоряет первый байт, но каждая граница `Suspense` — отдельное состояние загрузки. Слишком мелкие границы дают россыпь спиннеров.
- Компонент только для браузера (`localStorage`, часовой пояс) — `use(browser())` из React 19.3 вместо флага `mounted` в эффекте.

**Как проверить в проде**

- Profiler в React DevTools: flamegraph коммитов и причины рендеров. Компоненты, оптимизированные компилятором, помечены бейджем «Memo ✨».
- Performance Tracks в Chrome DevTools (React 19.2) показывают работу планировщика и компонентов на одной шкале с сетью.
- Ошибки гидратации видны в консоли с диффом сервер/клиент, а в проде — через `onRecoverableError`.

**Итог:** быстрый React — меньше JS на клиенте благодаря серверным компонентам, стриминг по границам `Suspense` и автоматическая мемоизация вместо ручной.

</A>

<Ex>

```tsx
'use client';
import { useActionState, useOptimistic } from 'react';
import { addComment } from './actions'; // Server Function: (prev, formData) => Promise<string | null>

type Comment = { id: string; text: string };

export function Comments({ comments }: { comments: Comment[] }) {
  const [optimistic, addOptimistic] = useOptimistic(
    comments,
    (list, c: Comment) => [...list, c],
  );
  const [error, formAction, isPending] = useActionState(
    async (prev: string | null, formData: FormData) => {
      // Видно сразу, до ответа сервера; при ошибке строка исчезнет
      addOptimistic({ id: crypto.randomUUID(), text: String(formData.get('text')) });
      return addComment(prev, formData); // текст ошибки или null
    },
    null,
  );

  return (
    <form action={formAction}>
      <ul>{optimistic.map((c) => <li key={c.id}>{c.text}</li>)}</ul>
      <input name="text" />
      <button disabled={isPending}>Send</button>
      {error && <p role="alert">{error}</p>}
    </form>
  );
}
```

<Ex title="Промис через границу сериализации">

```tsx
// app/orders/page.tsx — серверный компонент
import { Suspense } from 'react';
import { OrderList } from './order-list';

export default function Page() {
  const orders = getOrders(); // без await: запрос стартует сразу
  return (
    <Suspense fallback={<p>Loading…</p>}> {/* fallback уходит в HTML первым */}
      <OrderList orders={orders} /> {/* промис сериализуемый — его можно передать */}
    </Suspense>
  );
}

// app/orders/order-list.tsx
'use client';
import { use } from 'react';

export function OrderList({ orders }: { orders: Promise<{ id: number }[]> }) {
  const list = use(orders); // приостанавливает компонент до ответа
  return <ul>{list.map((o) => <li key={o.id}>#{o.id}</li>)}</ul>;
}
```

<Next>

- Что можно передать из серверного компонента в клиентский? — Сериализуемое: примитивы, простые объекты, массивы, `Date`, `Map`, `Set`, промисы, JSX, Server Functions; не обычные функции и классы.
- Чем `useActionState` отличается от `useFormStatus`? — Первый хранит результат и ожидание конкретного действия; `useFormStatus` из `react-dom` читает статус родительской формы в дочернем компоненте.
- Нужны ли `useMemo` и `useCallback` с React Compiler? — Редко: для точного контроля, например стабильной зависимости эффекта; старую мемоизацию убирают только с тестами.
- Как исправить ошибку гидратации? — Убрать различие сервер/клиент: браузерное — в эффект или `use(browser())`; `suppressHydrationWarning` — только для текста вроде даты.
- Чем `useTransition` отличается от `useDeferredValue`? — Первый помечает несрочным своё обновление, второй откладывает значение, обновление которого вы не контролируете.
