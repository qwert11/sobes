## Какие встроенные типы есть в Python и чем изменяемые отличаются от неизменяемых?

<A short l="j">

Основные встроенные типы — числа (`int`, `float`), `bool`, `str`, `None` и коллекции `list`, `tuple`, `dict`, `set`. <T k="py-mutable">Изменяемые</T> (`list`, `dict`, `set`) меняются на месте, а неизменяемые (`int`, `str`, `tuple`) — нет: любая «правка» создаёт новый объект, поэтому ключом `dict` может быть кортеж, но не список.

</A>

<A short l="m">

Переменная в Python — <T k="py-name-binding">имя, привязанное к объекту</T>, а не ячейка со значением: присваивание копирует ссылку, а не объект. Аргументы передаются <T k="py-call-by-sharing">по ссылке на объект</T>: функция может изменить переданный список, но не может перепривязать имя вызывающего. Поэтому копию делают явно (`copy.copy`, `copy.deepcopy`), а `is` проверяет, тот ли это объект, `==` — равны ли значения.

</A>

<A short l="s">

Изменяемость — свойство типа, а не переменной: любое значение в Python — объект, и разница лишь в том, есть ли у типа операции, меняющие его на месте. От неё зависит <T k="py-hashable">хешируемость</T>: ключом `dict` и элементом `set` бывает только объект, чей хеш не меняется за время жизни. Отсюда типовые баги — изменяемое значение по умолчанию, общий вложенный список после поверхностной копии, `is` вместо `==` — и правило: в значениях по умолчанию и общих данных предпочитать неизменяемые типы. Цена неизменяемости — новый объект на каждое изменение.

</A>

<A l="j">

**Что это**

| Тип | Изменяемый | Пример |
|---|---|---|
| `int`, `float`, `bool` | нет | `42`, `3.14`, `True` |
| `str`, `tuple` | нет | `"text"`, `(1, "a")` |
| `list` | да | `[1, 2]` |
| `dict` | да | `{"id": 1}` |
| `set` | да | `{1, 2}` |

`None` — единственный объект своего типа, аналог `null`.

**Как пользоваться**

- `list` — последовательность, которую будут менять.
- `tuple` — запись фиксированной длины: координаты, пара значений.
- `dict` — поиск по ключу, `set` — уникальные элементы и быстрая проверка `x in s`.
- <T k="py-comprehension">Comprehension</T> собирает коллекцию одним выражением: `[x * x for x in items if x > 0]`.

**Частая ошибка**

Изменяемое значение по умолчанию: `def add(item, items=[])`. Список создаётся один раз и копит элементы между вызовами. Правильно — `items=None` и внутри `if items is None: items = []`.

**Итог:** изменяемые типы меняются на месте, неизменяемые при каждой «правке» дают новый объект.

</A>

<A l="m">

**Как устроено**

- **Имена и объекты.** `b = a` привязывает второе имя к тому же объекту. Копии не создаётся ни для списка, ни для числа.
- **Передача аргументов.** Функция получает ссылку на тот же объект. `items.append(x)` изменит список вызывающего, а `items = [x]` перепривяжет только локальное имя.
- **`is` и `==`.** `is` сравнивает идентичность, `==` вызывает `__eq__` и сравнивает значения. С `None` сравнивают через `is`.
- **Копирование.** `copy.copy`, `list(a)` и срез `a[:]` дают <T k="py-shallow-copy">поверхностную копию</T>: новый внешний контейнер с теми же вложенными объектами. `copy.deepcopy` копирует рекурсивно.

**Когда что выбирать**

| Задача | Тип |
|---|---|
| Последовательность, которую меняют | `list` |
| Запись фиксированной длины, составной ключ | `tuple` |
| Поиск по ключу | `dict` |
| Уникальность, проверка вхождения за O(1) | `set`, `frozenset` |

**Ловушки**

- **Значение по умолчанию** вычисляется один раз при выполнении `def`, поэтому `[]` или `{}` в нём общий для всех вызовов.
- **`[[0] * 3] * 3`** — три ссылки на один внутренний список: изменение одной строки видно во всех.
- **Кортеж с изменяемым внутри.** В `t = ([1],)` нельзя заменить `t[0]`, но `t[0].append(2)` работает, и такой кортеж нехешируемый.

**Правило**

Значения по умолчанию — неизменяемые или `None`. Если функция меняет аргумент, это должно быть видно из имени; иначе она работает с копией.

**Итог:** присваивание и передача в функцию никогда не копируют объект — копию делают явно.

</A>

<A l="s">

**Под капотом**

- Каждое значение — объект в куче с указателем на свой тип. Переменная хранит только ссылку, поэтому значимых типов в смысле C# нет: даже `int` — объект.
- Изменяемость задаёт тип. `int` и `str` неизменяемы, поэтому `x += 1` создаёт новый объект и перепривязывает имя. Для `list` тот же `+=` вызывает `__iadd__` и меняет список на месте.
- `dict` и `set` — хеш-таблицы. Если бы ключ менялся, его хеш устарел бы и элемент «потерялся». Поэтому `list`, `dict` и `set` нехешируемы, а `tuple` хешируем, только если хешируемо всё внутри.

**Цена**

- Каждое «изменение» неизменяемого объекта — новая аллокация. Склейка строк через `+=` в цикле в худшем случае квадратична, `"".join(parts)` — линейна.
- `list` хранит ссылки на объекты, а не сами числа: миллион разных `int` в списке — миллион объектов. Для числовых данных есть `array` и NumPy.
- `deepcopy` обходит весь граф объектов и запоминает уже скопированные — на больших структурах это дорого.

**Компромиссы**

- Неизменяемые объекты безопасно делить между функциями и потоками, но каждое изменение — копия.
- Неизменяемые аналоги: `tuple`, `frozenset`, `@dataclass(frozen=True)`, `types.MappingProxyType`; с Python 3.15 есть встроенный `frozendict`.
- Comprehension быстрее цикла с `append` и не выпускает переменную цикла наружу, но три уровня вложенности читаются хуже обычного цикла.

**Как проверить в проде**

Изменяемые значения по умолчанию ловит линтер: правило B006 в Ruff (из flake8-bugbear). Общий вложенный объект в отладчике выдаёт одинаковый `id()`.

**Итог:** изменяемость — свойство типа, и от неё зависят хешируемость, безопасность разделения и цена изменений.

</A>

<Ex>

```python
import copy

a = [1, 2]
b = a                  # второе имя для того же списка
b.append(3)
print(a)               # [1, 2, 3]

def add(items, x):
    items.append(x)    # меняет объект вызывающего
    items = [x]        # перепривязывает только локальное имя

add(a, 4)
print(a)               # [1, 2, 3, 4]

grid = [[0], [0]]
shallow, deep = copy.copy(grid), copy.deepcopy(grid)
grid[0].append(1)
print(shallow[0], deep[0])                 # [0, 1] [0]
print([1, 2] == [1, 2], [1, 2] is [1, 2])  # True False
print([x * x for x in range(5) if x % 2 == 0])  # [0, 4, 16]

def bad(item, bucket=[]):  # список создан один раз, при def
    bucket.append(item)
    return bucket

print(bad(1), bad(2))  # [1, 2] [1, 2]
```

</Ex>

## Как устроены функции в Python?

<A short l="j">

Функция объявляется через `def` и сама является объектом: её можно передать аргументом, вернуть или сохранить, как делегат в C#. `*args` собирает лишние позиционные аргументы в кортеж, а `**kwargs` — именованные в словарь.

</A>

<A short l="m">

Функция — объект первого класса, и на этом построены <T k="py-closure">замыкания</T> и <T k="py-decorator">декораторы</T>: декоратор принимает функцию и возвращает обёртку, а `functools.wraps` сохраняет имя оригинала. Параметры до `/` передаются только по позиции, после `*` — <T k="py-keyword-only">только по имени</T>. Функция с `yield` становится <T k="py-generator">генератором</T> и отдаёт значения лениво, а `with` с <T k="py-context-manager">контекстным менеджером</T> гарантирует освобождение ресурса, как `using` в C#.

</A>

<A short l="s">

Почти вся «магия» функций — сахар над объектами и протоколами: `@d` — это `f = d(f)`, `with` — вызовы `__enter__` и `__exit__`, генератор — объект с замороженным кадром выполнения. Замыкание хранит ячейки внешних переменных, а не их значения, поэтому лямбды в цикле видят последнее значение. Цена гибкости — дорогие вызовы: каждый слой декоратора — ещё один вызов Python-функции, что заметно на горячем пути. Генераторы экономят память на потоковой обработке, но одноразовые: повторный проход по исчерпанному генератору молча ничего не даст.

</A>

<A l="j">

**Что это**

Функция объявляется через `def` и возвращает значение через `return`; без него она вернёт `None`. Функция — обычный объект: её можно передать в `sorted(users, key=get_age)`.

**Как пользоваться**

- Значение по умолчанию: `def connect(host, port=5432)`.
- Вызов с именами: `connect(port=6543, host="db")` — порядок не важен.
- `*args` собирает лишние позиционные аргументы в кортеж, `**kwargs` — именованные в словарь.
- Распаковка при вызове: `f(*items)` и `f(**options)`.
- `lambda` — анонимная функция из одного выражения: `key=lambda u: u.age`.

**Частая ошибка**

Присвоить глобальной переменной внутри функции без `global`. Присваивание делает имя локальным для всей функции, и чтение до него падает с `UnboundLocalError`.

**Итог:** функция — объект, а `*args` и `**kwargs` делают её сигнатуру гибкой.

</A>

<A l="m">

**Как устроено**

- **Параметры.** В `def f(a, /, b, *, c)` `a` передаётся только по позиции, `b` — как угодно, `c` — только по имени. Именованные-только параметры спасают от путаницы флагов: `send(msg, retry=True)`.
- **Области видимости.** Имя ищется в локальной, объемлющей, глобальной и встроенной области (правило LEGB). `nonlocal` и `global` разрешают перепривязать внешнее имя.
- **Замыкание.** Вложенная функция помнит переменные объемлющей и после её завершения.
- **Декоратор.** `@logged` над `def f` — то же, что `f = logged(f)`. `functools.wraps` копирует в обёртку `__name__` и `__doc__` и ставит `__wrapped__`.
- **Генератор.** Вызов функции с `yield` не выполняет тело, а возвращает итератор; каждый `next()` идёт до следующего `yield`.
- **Контекстный менеджер.** `with` вызывает `__enter__`, а в конце — `__exit__`, даже при исключении. `@contextlib.contextmanager` строит менеджер из генератора.

**Ловушки**

- **Позднее связывание.** Лямбды из `[lambda: i for i in range(3)]` все вернут `2`: замыкание видит переменную, а не значение. Лечится параметром `lambda i=i: i`.
- **Исчерпанный генератор.** Второй `for` по нему не выполнится ни разу.
- **Декоратор без `wraps`.** В логах и трассировках все функции называются `wrapper`.

**Правило**

Ресурсы — через `with`, большие потоки данных — через генераторы, сквозную логику — через декораторы с `functools.wraps`.

**Итог:** декораторы, генераторы и `with` — сахар над функциями-объектами и протоколами.

</A>

<A l="s">

**Под капотом**

- Объект функции хранит `__code__` (байт-код), `__defaults__` и `__closure__` — кортеж ячеек (cell) захваченных переменных. Ячейка общая для всех вложенных функций, поэтому `nonlocal` в одной видно в другой.
- Значения по умолчанию вычисляются один раз при выполнении `def` и лежат в `__defaults__`.
- Генератор хранит собственный кадр с локальными переменными и позицией. `yield` приостанавливает кадр, `send()` возобновляет его и передаёт значение внутрь — на этом исторически построили корутины.
- Если `__exit__` возвращает истину, исключение из блока `with` подавляется.

**Цена**

- Вызов Python-функции намного дороже вызова метода в C#: интерпретатор создаёт кадр и разбирает аргументы, встраивания (inlining), как у JIT .NET, нет.
- Каждый слой декоратора добавляет вызов и упаковку `*args` и `**kwargs`.
- Генератор держит в памяти один элемент, а не весь список — так обрабатывают файлы и выборки, которые не помещаются в память.

**Компромиссы**

- Декоратор меняет поведение незаметно из места вызова: `@retry` над неидемпотентной операцией может повторить списание.
- Генераторы ленивы: ошибка источника всплывёт там, где генератор читают, а не где создали.
- `contextlib.ExitStack` управляет переменным числом ресурсов. Асинхронные версии (`async with`, `asynccontextmanager`) — в теме [asyncio и FastAPI](/sobes/python/async-fastapi/).

**Как проверить в проде**

`inspect.signature` и `__wrapped__` показывают исходную функцию за декораторами. Число и стоимость вызовов видны в `cProfile` или в py-spy без перезапуска процесса.

**Итог:** гибкость функций Python держится на объектах и протоколах, а платой за неё становятся дорогие вызовы.

</A>

<Ex title="Замыкание, декоратор и сигнатура">

```python
import functools

def counter():
    count = 0
    def inc():
        nonlocal count     # перепривязать переменную внешней функции
        count += 1
        return count
    return inc

c = counter()
c()
print(c())                 # 2

def logged(func):
    @functools.wraps(func)  # сохранить __name__, __doc__, __wrapped__
    def wrapper(*args, **kwargs):
        print(f"call {func.__name__} {args} {kwargs}")
        return func(*args, **kwargs)
    return wrapper

@logged                    # то же, что scale = logged(scale)
def scale(x, /, *, factor=2):  # x — только позиционный, factor — только именованный
    return x * factor

print(scale(3, factor=10))  # call scale (3,) {'factor': 10}, затем 30
print(scale.__name__)       # scale
```

</Ex>

<Ex title="Генератор и контекстный менеджер">

```python
from contextlib import contextmanager

def numbers(n):
    for i in range(n):
        print(f"yield {i}")
        yield i            # пауза до следующего next()

gen = numbers(3)           # тело ещё не выполнялось
print(next(gen))           # yield 0, затем 0
print(sum(gen))            # yield 1, yield 2, затем 3

@contextmanager
def connection(name):
    print(f"open {name}")
    try:
        yield name.upper()  # значение для as
    finally:
        print(f"close {name}")  # выполнится и при исключении

with connection("db") as conn:
    print(conn)            # open db, DB, close db
```

</Ex>

- Как написать декоратор с параметрами, например `@retry(times=3)`? — Функция, которая возвращает декоратор: три уровня вложенности.

<Q id="python.lang.oop-typing" level="m">

## Как устроены классы и типизация в Python?

<A short l="j">

Класс объявляется через `class`: конструктор — `__init__`, `self` — явная ссылка на экземпляр, а <T k="py-dataclass">`@dataclass`</T> сам генерирует `__init__`, `__repr__` и `__eq__` для классов-данных. Аннотации типов вроде `x: int` интерпретатор не проверяет — их читают IDE и <T k="py-type-checker">проверщики типов</T> вроде mypy.

</A>

<A short l="m">

Поведение объекта задают <T k="py-dunder-method">dunder-методы</T>: `__eq__` — для `==`, `__len__` — для `len()`, `__iter__` — для `for`, поэтому свой класс встраивается в язык без интерфейсов. Python опирается на <T k="py-duck-typing">утиную типизацию</T>, а <T k="py-protocol">`typing.Protocol`</T> описывает её для проверщика: класс подходит, если у него есть нужные методы, без наследования. Аннотации на выполнение не влияют, поэтому их ценность — в mypy или pyright в CI, а не в рантайме.

</A>

<A short l="s">

Объектная модель Python динамическая: атрибуты лежат в `__dict__`, методы ищутся при каждом обращении по <T k="py-mro">MRO</T>, а множественное наследование согласуется C3-линеаризацией и кооперативным `super()`. Типизация постепенная и внешняя: рантайм аннотации не проверяет, но mypy или pyright в строгом режиме дают гарантии, близкие к C#, с номинальными классами и структурными `Protocol`. С 3.12 generics пишутся прямо в сигнатуре: `def first[T](items: list[T]) -> T`. Компромисс того же рода — `@dataclass(slots=True)`: меньше памяти и быстрее доступ, но без динамических атрибутов.

</A>

<A l="j">

**Что это**

- Класс — шаблон объекта, как в C#. Экземпляр создаётся вызовом класса без `new`: `user = User("Ann")`.
- `__init__` — инициализатор, `self` — первый параметр каждого метода экземпляра.
- Модификаторов доступа нет: `_name` — договорённость «внутреннее».

**Как пользоваться**

- `@property` делает метод вычисляемым атрибутом: `circle.diameter` без скобок, как свойство в C#.
- `@classmethod` получает класс `cls` — так пишут альтернативные конструкторы: `Rect.square(2)`.
- `@staticmethod` не получает ни `self`, ни `cls`.
- Аннотации: `def total(items: list[float]) -> float`; «может быть `None`» — `str | None` (с 3.10).

**Частая ошибка**

Объявить изменяемый атрибут на уровне класса: `class Cart: items = []`. Такой список общий для всех экземпляров; поля экземпляра задают в `__init__`.

**Итог:** класс в Python похож на класс C#, но доступ держится на договорённостях, а типы — подсказки для инструментов.

</A>

<A l="m">

**Как устроено**

- **Dunder-методы.** Операторы и встроенные функции вызывают специальные методы: `a + b` — `a.__add__(b)`, `len(x)` — `x.__len__()`. Это аналог перегрузки операторов и `IEquatable` в C#.
- **Наследование.** Разрешено множественное. Порядок поиска методов — MRO (`Cls.__mro__`), и `super()` вызывает следующий класс в нём, не обязательно родителя.
- **Duck typing и Protocol.** Функции важны методы объекта, а не имя его типа. `Protocol` описывает такой контракт структурно: класс совместим без наследования.
- **Аннотации.** Хранятся в `__annotations__`; проверяют их mypy и pyright, а не интерпретатор.

**Когда что выбирать**

| Задача | Инструмент |
|---|---|
| Данные с равенством по значению | `@dataclass`, неизменяемые — `frozen=True` |
| Контракт без наследования | `typing.Protocol` |
| Общая реализация, обязательные методы | базовый класс, `abc.ABC` |
| Проверка внешних данных | Pydantic — в теме [asyncio и FastAPI](/sobes/python/async-fastapi/) |

**Ловушки**

- **`__eq__` без `__hash__`.** Определив `__eq__`, вы делаете класс нехешируемым: Python ставит `__hash__ = None`. Так же ведёт себя `@dataclass` без `frozen=True`.
- **`isinstance` с Protocol** работает только с `@runtime_checkable` и проверяет лишь наличие методов, не сигнатуры.
- **`Optional[X]`** значит «может быть `None`», а не «необязательный параметр». Современная запись — `X | None`.

**Правило**

Публичные функции аннотируйте полностью и запускайте mypy или pyright в CI. Данные — `@dataclass`, контракты — `Protocol`.

**Итог:** класс встраивается в язык через dunder-методы, а типизация — внешний слой, который проверяют инструменты.

</A>

<A l="s">

**Под капотом**

- Атрибуты экземпляра лежат в словаре `__dict__`. `__slots__` или `@dataclass(slots=True)` (с 3.10) заменяют его фиксированными слотами: меньше памяти и быстрее доступ, но новые атрибуты добавить нельзя.
- `@property`, `@classmethod` и `@staticmethod` — дескрипторы: объекты с `__get__`, которые перехватывают доступ к атрибуту класса.
- MRO строится C3-линеаризацией: потомок раньше предков, порядок базовых классов из объявления сохраняется. Несогласуемая иерархия — `TypeError` при объявлении класса.
- С 3.14 аннотации вычисляются лениво (PEP 649): ссылки на ещё не объявленные классы не нужно брать в кавычки.

**Сравнение с C#**

| C# | Python |
|---|---|
| Номинальные интерфейсы | `Protocol` — структурный, `abc.ABC` — номинальный |
| Generics существуют в рантайме | параметры стираются: `list[int]` в рантайме — просто `list` |
| `where T : IComparable<T>` | `def f[T: Comparable]` (PEP 695, 3.12+) |
| Ошибку типов отклоняет компилятор | ошибку находит mypy или pyright, рантайм её пропустит |

До 3.12 параметры типа объявляли через `TypeVar` и `Generic[T]`. Синоним типа — `type Pair[T] = tuple[T, T]`, значения по умолчанию для параметров типа — с 3.13 (PEP 696).

**Компромиссы**

- Слоты экономят память на каждом объекте; на миллионах мелких объектов это заметно, но выигрыш стоит измерить (`tracemalloc`).
- Глубокие иерархии с `super()` по MRO трудно читать. Композиция и `Protocol` обычно проще.

**Как проверить в проде**

mypy `--strict` или pyright в режиме `strict` в CI; `reveal_type(x)` показывает выведенный тип. В рантайме типы проверяет только явная валидация: Pydantic или `isinstance`.

**Итог:** Python даёт типизацию уровня C# как внешний инструмент поверх динамической модели объектов — гарантии есть ровно там, где работает проверщик.

</A>

<Ex>

```python
from dataclasses import dataclass
from typing import Protocol

class Shape(Protocol):
    def area(self) -> float: ...

@dataclass(frozen=True, slots=True)
class Rect:
    w: float
    h: float

    def area(self) -> float:
        return self.w * self.h

class Circle:              # не наследует Shape, но подходит по структуре
    def __init__(self, r: float) -> None:
        self.r = r

    @property
    def diameter(self) -> float:  # вычисляемый атрибут без скобок
        return self.r * 2

    def area(self) -> float:
        return 3.14 * self.r ** 2

def total(shapes: list[Shape]) -> float:
    return sum(s.area() for s in shapes)

print(Rect(2, 3), Rect(2, 3) == Rect(2, 3))  # Rect(w=2, h=3) True
print(Circle(1).diameter)                    # 2
print(total([Rect(2, 3), Circle(1)]))        # 9.14
```

</Ex>

class Base:
    def save(self):
        print("Base")

class Audit(Base):
    def save(self):
        print("Audit")
        super().save()     # следующий класс в MRO, не обязательно родитель

class Cache(Base):

        print("Cache")
        super().save()

class Repo(Audit, Cache):
    pass

Repo().save()                              # Audit, Cache, Base

<Q id="python.lang.internals" level="s">

## Как Python управляет памятью и что такое GIL?

<A short l="j">

Python освобождает память сам: у каждого объекта есть <T k="py-reference-counting">счётчик ссылок</T>, и объект удаляется, как только ссылок не осталось. <T k="py-gil">GIL</T> — глобальная блокировка интерпретатора CPython: Python-код в каждый момент выполняет только один поток, поэтому потоки не ускоряют вычисления.

</A>

<A short l="m">

CPython удаляет объект сразу, когда его счётчик ссылок падает до нуля, а циклы ссылок находит отдельный <T k="py-cyclic-gc">циклический сборщик</T> с поколениями. GIL пускает исполнять байт-код только один поток, поэтому потоки помогают при ожидании ввода-вывода, который отпускает GIL, но не при вычислениях. CPU-задачи ускоряют процессы, NumPy или <T k="py-c-extension">C-расширения</T>, которые отпускают GIL на время работы.

</A>

<A short l="s">

Подсчёт ссылок даёт детерминированное освобождение, но требует защиты счётчиков от гонок — эту роль и играет GIL, одна блокировка на весь интерпретатор. <T k="py-free-threading">Free-threaded сборка</T> (PEP 703) убирает GIL: в 3.13 она экспериментальная, с 3.14 официально поддерживается, но и в 3.15 остаётся отдельной сборкой, а не умолчанием. Цена — несколько процентов на однопоточном коде и требование, чтобы C-расширения были помечены как совместимые, иначе GIL включится снова. Поэтому стандартный путь для CPU-задач — по-прежнему вынести горячий цикл в NumPy, нативное расширение или процессы.

</A>

<A l="j">

**Что это**

- **Управление памятью.** Явно освобождать память не нужно. У каждого объекта есть счётчик ссылок: имена, элементы списков, атрибуты. Когда он падает до нуля, объект удаляется сразу.
- **GIL** (Global Interpreter Lock) — блокировка в CPython, стандартной реализации Python. Байт-код в каждый момент выполняет только один поток.

**Зачем это знать**

- Потоки (`threading`) полезны для ожидания: сеть, диск, база. Пока поток ждёт, GIL свободен для других.
- Вычисления на CPU потоки не ускоряют. Для них берут процессы или библиотеки на C вроде NumPy.

**Частая ошибка**

Запускать тяжёлые вычисления в `ThreadPoolExecutor` и ждать ускорения по числу ядер. С GIL время останется прежним или даже вырастет.

**Итог:** память освобождает счётчик ссылок, а GIL пускает выполнять Python-код только один поток за раз.

</A>

<A l="m">

**Как устроено**

1. Присваивание, передача в функцию, добавление в список увеличивают счётчик ссылок объекта, удаление ссылки — уменьшает.
2. При нуле CPython сразу вызывает `__del__`, если он есть, и освобождает память.
3. Циклы (`a.peer = b`, `b.peer = a`) счётчик не освободит. Их находит модуль `gc`: он периодически обходит объекты-контейнеры по трём поколениям и удаляет недостижимые группы.
4. Поток, держащий GIL, отдаёт его ожидающим примерно раз в 5 мс (`sys.getswitchinterval()`) и всегда — на блокирующем вводе-выводе.

**Когда что выбирать**

| Нагрузка | Решение |
|---|---|
| Ожидание: HTTP, база, файлы | потоки или asyncio |
| Вычисления на чистом Python | процессы: `ProcessPoolExecutor` |
| Числовые массивы | NumPy: цикл идёт в C |
| Тяжёлое ядро алгоритма | C-расширение, Cython, Rust через PyO3 |

**Ловушки**

- **`is` для чисел и строк.** CPython кеширует целые от −5 до 256 и <T k="py-interning">интернирует</T> часть строк, поэтому `is` для них иногда «работает». Это деталь реализации — значения сравнивают через `==`.
- **GIL не делает код потокобезопасным.** `counter += 1` — несколько инструкций байт-кода, и поток может переключиться между ними. Нужен `threading.Lock`.
- **Объекты в цикле** живут до прохода сборщика, и момент вызова их `__del__` непредсказуем.

**Правило**

Сначала выясните, во что упирается задача — в ожидание или в CPU. Подробное сравнение потоков, процессов и asyncio — в теме [asyncio и FastAPI](/sobes/python/async-fastapi/).

**Итог:** счётчик ссылок освобождает почти всё сразу, `gc` дочищает циклы, а GIL ограничивает параллельность Python-кода, но не ввода-вывода.

</A>

<A l="s">

**Под капотом**

- С 3.12 (PEP 683) `None`, `True`, малые целые и другие служебные объекты бессмертны: их счётчик ссылок не меняется.
- GIL защищает счётчики и внутренние структуры интерпретатора одной блокировкой. Это дёшево для однопоточного кода и упрощает C-расширения.
- Free-threaded сборка заменяет GIL смещённым подсчётом ссылок (biased reference counting) и блокировками на уровне объектов. Статус: 3.13 — экспериментальная, 3.14 — официально поддерживается (PEP 779), 3.15 — по-прежнему отдельная сборка `python3.15t`. Импорт C-расширения без пометки о поддержке снова включает GIL.
- JIT-компилятор (PEP 744) появился в 3.13 как экспериментальный. С 3.14 он есть в официальных сборках для Windows и macOS, но включается вручную (`PYTHON_JIT=1`) и ускоряет код на проценты, а не в разы.

**Цена**

- Объект тяжёлый: `sys.getsizeof(1)` — 28 байт, плюс 8 байт на ссылку в списке. Массив NumPy хранит голые значения подряд.
- Однопоточный оверхед free-threaded сборки — по документации от ~1 % до ~8 % в зависимости от платформы.
- Цикл на чистом Python часто в десятки раз медленнее аналога на C#.

**Компромиссы**

- Процессы обходят GIL, но платят сериализацией данных (pickle) и памятью на копию интерпретатора.
- NumPy и многие C-расширения отпускают GIL внутри тяжёлых операций, поэтому потоки поверх них масштабируются.
- `gc.freeze()` перед `fork` убирает существующие объекты из обхода сборщика, и дочерние процессы дольше делят страницы памяти.

**Как проверить в проде**

- py-spy снимает профиль работающего процесса без перезапуска; флаг `--gil` оставляет только потоки, держащие GIL.
- `tracemalloc` показывает, где выделялась память; `sys._is_gil_enabled()` (3.13+) — включён ли GIL.

**Итог:** CPython платит за простоту подсчёта ссылок и GIL медленным однопоточным кодом; ускоряют его, вынося горячий цикл из интерпретатора, а free-threading и JIT пока меняют картину лишь частично.

</A>

<Ex>

```python
import gc
import sys

data = []
before = sys.getrefcount(data)
alias = data                         # ещё одна ссылка на тот же объект
print(sys.getrefcount(data) - before)  # 1

class Node:
    def __init__(self):
        self.peer = None

a, b = Node(), Node()
a.peer, b.peer = b, a                # цикл: счётчики не упадут до нуля
del a, b
print(gc.collect() > 0)              # True: циклический сборщик нашёл цикл

print(int("256") is int("256"))      # True: кеш малых int от -5 до 256
print(int("257") is int("257"))      # False: два разных объекта

s1 = "".join(["py", "thon"])
s2 = "".join(["py", "thon"])
print(s1 == s2, s1 is s2)            # True False
print(sys.intern(s1) is sys.intern(s2))  # True
```

</Ex>
