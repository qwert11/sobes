## Чем `Thread` отличается от `Task` и что такое пул потоков?

<A short l="j">

`Thread` — это поток операционной системы, который вы создаёте и запускаете сами, а <T k="task">`Task`</T> — задача, то есть описание работы с будущим результатом. Задача выполняется на готовом потоке из <T k="thread-pool">пула потоков</T>, который CLR переиспользует, поэтому для фоновой работы берут `Task.Run`, а не `new Thread`.

</A>

<A short l="m">

`Thread` — ресурс ОС со своим стеком, а `Task` — объект, который описывает работу и ставится в очередь пула потоков. Главное отличие: задача даёт результат, исключения, отмену, продолжения и `await`, а поток для неё пул берёт готовый. Цена свободы `Thread` — ручное управление и дорогое создание, поэтому свой поток нужен только для долгой блокирующей работы, особого приоритета, STA или <T k="background-thread">основного (foreground) потока</T>.

</A>

<A short l="s">

`Task` — promise-подобная абстракция, и не каждая задача вообще занимает поток: задача от асинхронного I/O или `TaskCompletionSource` просто ждёт сигнала. Пул один на процесс: у него глобальная FIFO-очередь, локальные очереди рабочих потоков и <T k="work-stealing">work stealing</T>, а число потоков он подбирает сам по пропускной способности. Поэтому блокировать потоки пула дорого: сверх минимума новые потоки появляются постепенно, и под нагрузкой работа копится в очереди.

</A>

<A l="j">

**Что это**

- **`Thread`** — поток ОС. Его создают через `new Thread(...)`, запускают `Start()` и ждут `Join()`.
- **Пул потоков** — набор фоновых потоков, которые CLR создаёт по мере нужды и переиспользует.
- **`Task`** — единица работы с результатом. `Task.Run(...)` ставит делегат в очередь пула и возвращает `Task` или `Task<T>`.

**Зачем**

Создавать поток дорого: каждый резервирует свой стек — по умолчанию 1,5 МБ на Windows и 8 МБ на Linux. Пул снимает эту цену: после задачи поток возвращается в пул.

**Как пользоваться**

1. Запустить работу: `var task = Task.Run(() => Compute());`.
2. Дождаться результата: `int result = await task;`.

**Частая ошибка**

Считать, что `Task` — это поток. Задача может вообще не занимать поток, пока ждёт ответа от сети или диска.

**Итог:** для фоновой работы берите `Task`, а свой `Thread` — только когда без него нельзя.

</A>

<A l="m">

**Как устроено**

- `Task` хранит состояние, результат (`Task<T>`) и исключение. При `await` исключение пробрасывается как есть, при `.Wait()` и `.Result` — завёрнутым в `AggregateException`.
- Потоки пула — фоновые: процесс не ждёт их при завершении.
- `new Thread` по умолчанию основной (`IsBackground = false`) и держит процесс живым, пока не закончит работу.
- `TaskCreationOptions.LongRunning` — подсказка планировщику выделить задаче отдельный поток вне пула.

**Когда что выбирать**

| Задача | Что взять |
|---|---|
| Короткая CPU-работа в фоне | `Task.Run` |
| Ожидание сети или диска | асинхронный API и `await`, без `Task.Run` |
| Долгая блокирующая работа | `LongRunning` или свой `Thread` |
| STA (COM, UI), особый приоритет | свой `Thread` |

**Ловушки**

- `Task.Run(() => File.ReadAllText(path))` занимает поток пула ожиданием диска. Лучше `await File.ReadAllTextAsync(path)`.
- `Thread.Abort` в .NET 5+ бросает `PlatformNotSupportedException`. Поток останавливают кооперативно, через `CancellationToken`.

**Правило**

`Task.Run` — для CPU-работы, `await` — для I/O, `Thread` — только когда нужен контроль над самим потоком.

**Итог:** `Task` описывает работу, а пул решает, на каком потоке её выполнить.

</A>

<A l="s">

**Под капотом**

- Каждая задача для пула — это work item, элемент его очереди.
- Work item, поставленный из кода на потоке пула, попадает в локальную очередь этого потока. Её читают в порядке LIFO — ради кеш-локальности.
- Остальная работа идёт в глобальную FIFO-очередь.
- Свободный поток ищет работу по порядку:
  1. в своей локальной очереди;
  2. в глобальной;
  3. с хвоста чужой локальной очереди — это и есть work stealing.
- До минимума потоков (`ThreadPool.GetMinThreads`, по умолчанию — число процессоров) пул создаёт их сразу. Выше решает алгоритм, который меняет число потоков и следит за пропускной способностью.

**Цена**

- Каждый лишний поток — это память под стек, переключения контекста и лишняя работа GC при обходе стеков.
- Заблокированный поток пула выпадает из работы, а замена ему сверх минимума появляется не сразу.

**Компромиссы**

- `LongRunning` с async-делегатом бессмыслен: выделенный поток живёт только до первого `await`, дальше продолжение уходит в пул.
- С .NET 8 на Windows можно переключиться на пул Windows (`UseWindowsThreadPool`); у Native AOT на Windows он включён по умолчанию. Выигрыш зависит от нагрузки и проверяется замерами.

**Как проверить в проде**

`dotnet-counters monitor` показывает число потоков пула, длину его очереди и число завершённых work items. Потоков больше примерно трёх на ядро — признак того, что код блокирует потоки пула.

**Итог:** пул рассчитан на короткие неблокирующие work items, и всё, что держит его потоки, бьёт по пропускной способности.

</A>

<Ex>

```csharp
// Свой поток: создаём и ждём вручную, по умолчанию он основной (foreground)
var thread = new Thread(() => Console.WriteLine("running on a dedicated thread"));
thread.Start();
thread.Join();

// Задача на пуле потоков: есть результат
Task<int> task = Task.Run(() => 6 * 7);
Console.WriteLine(await task); // 42

// Потоки пула — фоновые
await Task.Run(() => Console.WriteLine(Thread.CurrentThread.IsBackground)); // True

// Долгая блокирующая работа — отдельный поток вне пула
await Task.Factory.StartNew(() => Thread.Sleep(1000), TaskCreationOptions.LongRunning);
```

</Ex>

<Next>

- Что будет с процессом, если `Main` завершился, а `new Thread` ещё работает? — Процесс дождётся потока: по умолчанию он основной (foreground).
- Чем `Task.Run` отличается от `Task.Factory.StartNew`? — У `Task.Run` безопасные умолчания (`DenyChildAttach`, планировщик по умолчанию), и он разворачивает async-лямбды.
- Занимает ли поток задача, которая ждёт ответа от БД? — Нет: асинхронный I/O не держит поток, поток нужен только продолжению.
- Сколько потоков в пуле? — Минимум по умолчанию равен числу процессоров, дальше пул подбирает число сам.
- Зачем `TaskCreationOptions.LongRunning`? — Чтобы долгая блокирующая работа получила отдельный поток и не занимала пул.

</Next>

## Что такое race condition и deadlock и как их избежать?

<A short l="j">

<T k="race-condition">Race condition</T> (состояние гонки) — ошибка, когда результат зависит от порядка обращений потоков к общим данным, а <T k="deadlock">deadlock</T> (взаимоблокировка) — вечное ожидание потоков друг друга. Гонка тихо портит данные, а дедлок вешает программу, поэтому от гонки защищаются синхронизацией, а от дедлока — единым порядком захвата блокировок.

</A>

<A short l="m">

Гонка — это несинхронизированная составная операция над общими данными, а дедлок — цикл ожидания между потоками, которые держат блокировки. Гонка возникает, потому что «прочитать — изменить — записать» не атомарно, а дедлок — потому что потоки берут одни и те же блокировки в разном порядке. Защита стоит производительности, поэтому <T k="critical-section">критические секции</T> держат короткими и без чужого кода внутри, а где можно отступить — берут блокировку с таймаутом.

</A>

<A short l="s">

Race condition — логическая ошибка порядка событий, а data race — её низкоуровневый вид: одновременный доступ к памяти без синхронизации, где хотя бы один поток пишет. Data race опаснее, чем кажется: JIT и процессор вправе переставлять и кешировать такие обращения, и поток может вообще не увидеть чужую запись. Дедлок требует четырёх условий Коффмана, и дешевле всего разорвать циклическое ожидание глобальным порядком блокировок. В проде его находят по дампу, где видно, кто держит блокировку и кто её ждёт.

</A>

<A l="j">

**Что это**

- **Race condition** — результат зависит от того, какой поток успел первым.
- **Deadlock** — поток 1 держит ресурс A и ждёт B, поток 2 держит B и ждёт A. Оба стоят вечно.

**Зачем**

Это две главные ошибки многопоточного кода. Обе зависят от тайминга и плохо ловятся тестами.

**Как избежать**

- Не делить изменяемые данные между потоками, если можно.
- Общие данные защищать `lock` — он пускает в блок только один поток.
- Простые счётчики менять через `Interlocked.Increment` — одной неделимой операцией.
- Брать блокировки всегда в одном порядке и держать их как можно меньше.

**Частая ошибка**

Считать `count++` одной операцией. Это три шага — прочитать, прибавить, записать, — и у двух потоков одно увеличение может потеряться.

**Итог:** гонка портит данные, дедлок вешает программу; от обоих защищает дисциплина работы с общим состоянием.

</A>

<A l="m">

**Как устроено**

- <T k="atomic-operation">Атомарная операция</T> выполняется целиком: другой поток не увидит промежуточного состояния.
- Чтение и запись выровненного `int` или ссылки атомарны. Составные операции — нет: `x++`, «проверить, потом добавить».
- Дедлок возникает, когда каждый поток держит блокировку и ждёт ту, что держит другой.

**Когда что выбирать**

| Ситуация | Инструмент |
|---|---|
| Одна переменная: счётчик, флаг | `Interlocked` |
| Инвариант из нескольких полей | `lock` |
| Общий словарь или очередь | конкурентные коллекции |
| Данные можно не делить | изоляция по потокам, неизменяемые объекты |

**Ловушки**

- `if (!dict.ContainsKey(k)) dict[k] = v;` — гонка даже на `ConcurrentDictionary`: между проверкой и записью вклинится другой поток. Нужен один вызов `TryAdd`.
- Вызов событий, колбэков или виртуальных методов внутри `lock`: чужой код может взять другую блокировку и замкнуть цикл.
- Синхронное ожидание асинхронного кода (`.Result`) под однопоточным `SynchronizationContext` — дедлок без единого `lock`.

**Правило**

Все берут блокировки в одном порядке. Где можно отступить — `Monitor.TryEnter` или `Lock.TryEnter` с таймаутом.

**Итог:** гонку убирает атомарность, дедлок — порядок захвата и короткие критические секции.

</A>

<A l="s">

**Под капотом**

- Data race — одновременный доступ к одной ячейке памяти без синхронизации, где хотя бы один доступ — запись.
- JIT может прочитать поле один раз и держать значение в регистре. Цикл `while (!_stop)` без `volatile` может так и не увидеть `_stop = true`.
- Дедлок требует четырёх условий Коффмана:
  1. взаимное исключение;
  2. удержание ресурса с ожиданием другого;
  3. отсутствие вытеснения;
  4. циклическое ожидание.

**Цена**

Дедлок — это зависание без загрузки CPU, которое часто проявляется только под нагрузкой. Процесс жив, но запросы, которым нужна блокировка, не завершаются.

**Компромиссы**

- Порядок блокировок (иерархия уровней) разрывает цикл, но требует дисциплины во всей кодовой базе.
- `TryEnter` с таймаутом убирает бесконечное ожидание, но добавляет ветку отказа, которую надо продумать.
- Livelock: потоки активны, но без прогресса — например, бесконечно повторяют `CompareExchange`. Лечится паузами между попытками (`SpinWait`).
- Лучшая синхронизация — её отсутствие: неизменяемые снимки, передача сообщений через очереди, разбиение данных по потокам.

**Как проверить в проде**

1. Снять дамп: `dotnet-dump collect -p PID`.
2. В `dotnet-dump analyze` выполнить `clrstack -all` или `parallelstacks` и найти потоки, стоящие в `Monitor.Enter`.
3. Команда `syncblk` покажет, какой поток владеет `Monitor` и сколько потоков его ждут.
4. Для async-цепочек — `dumpasync`.

**Итог:** дедлок — это цикл ожидания; его предотвращают порядком блокировок и находят по дампу.

</A>

<Ex>

```csharp
int unsafeCount = 0;
int safeCount = 0;

Parallel.For(0, 100_000, _ =>
{
    unsafeCount++;                        // гонка: чтение, сложение и запись не атомарны
    Interlocked.Increment(ref safeCount); // атомарно
});

Console.WriteLine(unsafeCount); // обычно меньше 100000
Console.WriteLine(safeCount);   // 100000

// Дедлок: два потока берут блокировки a и b в разном порядке
var a = new object();
var b = new object();
var t1 = Task.Run(() => { lock (a) { Thread.Sleep(50); lock (b) { } } });
var t2 = Task.Run(() => { lock (b) { Thread.Sleep(50); lock (a) { } } });
// await Task.WhenAll(t1, t2) не завершится никогда.
// Исправление: оба потока берут сначала a, потом b.
```

Первое число меняется от запуска к запуску — это и есть гонка.

</Ex>

<Next>

- Атомарна ли запись `long`? — На 64-битной платформе — да, если значение выровнено; на 32-битной — нет, нужны `Interlocked.Read` или `Volatile`.
- Почему `ContainsKey` и потом запись — ошибка даже для `ConcurrentDictionary`? — Между двумя вызовами вклинится другой поток; нужна одна операция `TryAdd` или `GetOrAdd`.
- Как найти дедлок в проде? — Снять дамп и посмотреть `clrstack -all` и `syncblk` в `dotnet-dump analyze` или Parallel Stacks в Visual Studio.
- Что такое livelock? — Потоки не заблокированы, но из-за постоянных повторов не делают полезной работы.
- Может ли поток устроить дедлок сам с собой? — С `lock` нет, он реентерабелен; с `SemaphoreSlim(1, 1)` да: повторный `Wait` ждёт сам себя.

</Next>

<Q id="dotnet.threading.lock" level="m">

## Как работает `lock` и что даёт тип `System.Threading.Lock` (.NET 9)?

<A short l="j">

`lock (obj) { ... }` пускает в блок только один поток за раз, а остальные ждут, пока он выйдет. Блокировка снимается даже при исключении, а с .NET 9 и C# 13 блокируются на отдельном поле типа `System.Threading.Lock`.

</A>

<A short l="m">

`lock` — синтаксический сахар: для обычного объекта он разворачивается в <T k="monitor">`Monitor.Enter`</T> и `Monitor.Exit` в `try/finally`, а для выражения типа <T k="lock-type">`System.Threading.Lock`</T> — в `using (x.EnterScope())`. Оба варианта <T k="reentrant-lock">реентерабельны</T> и привязаны к потоку: освободить блокировку должен тот же поток, что её взял. Поэтому внутри `lock` нельзя `await` (ошибка компиляции), а I/O и вызовы чужого кода там превращают блокировку в узкое место или в дедлок.

</A>

<A short l="s">

`Monitor` хранит состояние блокировки в заголовке объекта и при конкуренции переходит на <T k="sync-block">sync block</T>, поэтому заблокироваться можно на любом объекте — в том числе на чужом. `Lock` — выделенный тип со своим состоянием, и Microsoft рекомендует его ради производительности и ясности намерения. Цена — строгая типизация: если статический тип выражения не `Lock`, например после приведения к `object`, компилятор сгенерирует `Monitor` и выдаст предупреждение CS9216.

</A>

<A l="j">

**Что это**

`lock` гарантирует, что код внутри блока в каждый момент выполняет только один поток. Остальные потоки, дошедшие до `lock` с тем же объектом, ждут.

**Зачем**

Чтобы несколько потоков не меняли общие данные одновременно. Например, чтобы два списания с одного счёта не увели баланс в минус.

**Как пользоваться**

1. Завести приватное поле: `private readonly Lock _sync = new();` (до .NET 9 — `new object()`).
2. Обернуть работу с общими данными: `lock (_sync) { _balance -= amount; }`.
3. Держать внутри только эту работу — без I/O и долгих вычислений.

**Частая ошибка**

Блокироваться на `this`, `typeof(...)` или строке. Их может заблокировать и чужой код — получится лишняя конкуренция или дедлок.

**Итог:** `lock` — на приватном поле, коротко и только вокруг общих данных.

</A>

<A l="m">

**Как устроено**

- Для ссылочного типа `lock` компилируется в `Monitor.Enter(obj, ref lockTaken)` в `try` и `Monitor.Exit(obj)` в `finally`.
- Для `Lock` — в `using (x.EnterScope())`. `Lock.Scope` — это `ref struct` с методом `Dispose`.
- Поток, уже владеющий блокировкой, может войти повторно. Выйти нужно столько же раз.
- Освободить блокировку может только поток-владелец, иначе `SynchronizationLockException`.

**Когда что выбирать**

| Ситуация | Что взять |
|---|---|
| .NET 9+, синхронный код | поле `Lock` и `lock` |
| .NET 8 и раньше | поле `object` и `lock` |
| Нужен `await` внутри | семафор на один слот: `SemaphoreSlim(1, 1)` и `WaitAsync` |
| Нужен таймаут | `Lock.TryEnter` или `Monitor.TryEnter` |

**Ловушки**

- `await` внутри `lock` — ошибка CS1996: продолжение может выполниться на другом потоке, а выйти должен владелец.
- `object o = _sync; lock (o)` — это уже `Monitor`, а не `Lock` (предупреждение CS9216).
- Вызов событий, колбэков и виртуальных методов внутри `lock`: чужой код может взять другую блокировку и устроить дедлок.
- `lock` по значимому типу не компилируется: каждая упаковка давала бы новый объект.

**Правило**

Одна блокировка — на один ресурс, внутри — только работа с его данными.

**Итог:** `lock` — это `Monitor` или `Lock` в `try/finally`, привязанный к потоку, поэтому без `await` внутри.

</A>

<A l="s">

**Под капотом**

- Любой объект может служить монитором. Пока конкуренции нет, состояние блокировки лежит в заголовке объекта (thin lock).
- При конкуренции или ожидании рантайм «раздувает» блокировку до sync block — записи во внутренней таблице.
- `Lock` хранит состояние в собственном поле и не трогает заголовок объекта. Быстрый путь без конкуренции — атомарная операция над этим полем.
- Вход в блокировку не даёт последующим чтениям выполниться раньше него, а выход не даёт предыдущим записям задержаться после него. Поэтому полям, доступным только под `lock`, `volatile` не нужен.

**Цена**

- Неконкурентный `lock` дешёвый. Дорогой — конкурентный: потоки крутятся в спине, потом уходят в ожидание, и растёт задержка.
- Длинная очередь на одну блокировку (lock convoy) сводит параллельный код к последовательному.

**Компромиссы**

- `Lock` убирает лишний `object` и показывает намерение типом, но у него нет `Wait` и `Pulse`. Код на `Monitor.Wait` при миграции придётся переписать на другой примитив.
- Против конкуренции: сузить секцию, разбить данные на шарды с отдельными блокировками или перейти на структуры без блокировок.

**Как проверить в проде**

- В `dotnet-counters` — `dotnet.monitor.lock_contentions` (до .NET 9 — Monitor Lock Contention Count): сколько раз поток ждал занятый `Monitor`.
- В дампе команда `syncblk` показывает владельцев `Monitor` и число ждущих потоков.
- С .NET 9 `dotnet-trace` пишет событие WaitHandleWait со стеком, в том числе для ожиданий в `lock`.

**Итог:** `Lock` — выбор по умолчанию в .NET 9+, а узкое место ищут по счётчику конкуренции и стекам ожиданий.

</A>

<Ex>

```csharp
public sealed class Account
{
    private readonly Lock _sync = new(); // C# 13 / .NET 9+, раньше — new object()
    private decimal _balance;

    public bool TryDebit(decimal amount)
    {
        lock (_sync) // компилятор генерирует using (_sync.EnterScope())
        {
            if (_balance < amount) return false;
            _balance -= amount;
            return true;
        }
    }

    public void Credit(decimal amount)
    {
        lock (_sync) { _balance += amount; }
    }

    // object o = _sync; lock (o) { }       — предупреждение CS9216: это уже Monitor
    // lock (_sync) { await SaveAsync(); }  — ошибка CS1996: await внутри lock запрещён
}
```

</Ex>

<Next>

- Почему нельзя `lock (this)`? — Внешний код может заблокироваться на том же объекте: лишняя конкуренция или дедлок.
- Что будет, если внутри `lock` вылетит исключение? — Блокировка снимется в `finally`, но данные могут остаться в несогласованном состоянии.
- Как сделать взаимное исключение в async-коде? — `SemaphoreSlim(1, 1)`: `await WaitAsync()`, а `Release()` — в `finally`.
- Реентерабелен ли `lock`? — Да, и с `Monitor`, и с `Lock`: тот же поток может войти повторно.
- Что изменится, если поле с `new Lock()` объявить как `object`? — `lock` перейдёт на `Monitor`, а компилятор выдаст CS9216.

</Next>

<Q id="dotnet.threading.sync-primitives" level="m">

## Какие примитивы синхронизации есть в .NET и чем они отличаются?

<A short l="j">

Примитивы синхронизации — типы, которые координируют потоки: одни пускают в секцию один поток (`lock`, <T k="mutex">`Mutex`</T>), другие — до N потоков (<T k="semaphore-slim">`SemaphoreSlim`</T>), третьи передают сигнал «можно» (`ManualResetEventSlim`). Поэтому выбирают по задаче: исключить одновременный доступ, ограничить параллелизм или дождаться события.

</A>

<A short l="m">

Примитивы делятся на обёртки над объектами ядра ОС (`Mutex`, `Semaphore`, `EventWaitHandle`) и лёгкие управляемые типы (`SemaphoreSlim`, `ManualResetEventSlim`, <T k="reader-writer-lock">`ReaderWriterLockSlim`</T>, `Barrier`). Первые медленнее, зато умеют работать между процессами, вторые быстрее, но живут внутри одного процесса. Ещё одно отличие — <T k="thread-affinity">привязка к потоку</T>: `Mutex` и `ReaderWriterLockSlim` освобождает только владелец, поэтому с `await` из них работает только `SemaphoreSlim.WaitAsync`.

</A>

<A short l="s">

Выбор сводится к трём вопросам: нужна ли межпроцессная синхронизация, есть ли у примитива владелец и каково соотношение чтений и записей. Kernel-объекты платят системным вызовом даже без конкуренции, примитивы с владельцем запрещают `await`, а `ReaderWriterLockSlim` окупается лишь при длинных чтениях. Асинхронных RW-блокировок и событий в BCL нет, поэтому их строят на `SemaphoreSlim` и `TaskCompletionSource` или берут из Microsoft.VisualStudio.Threading.

</A>

<A l="j">

**Что это**

Примитив синхронизации — тип, который заставляет потоки ждать друг друга по определённому правилу.

**Зачем**

`lock` решает одну задачу: один поток в секции. Для ограничения параллелизма, разделения чтения и записи и сигналов нужны другие инструменты.

**Как пользоваться**

| Примитив | Что делает |
|---|---|
| `Mutex` | как `lock`, но может работать между процессами |
| `SemaphoreSlim` | пускает одновременно не больше N потоков |
| `ReaderWriterLockSlim` | читать могут многие сразу, писать — один |
| `ManualResetEventSlim` | потоки ждут в `Wait()`, пока кто-то не вызовет `Set()` |
| `Barrier` | потоки ждут друг друга в конце каждой фазы |

**Частая ошибка**

Не освободить примитив при исключении. `Release()`, `ExitReadLock()` и `ReleaseMutex()` всегда вызывают в `finally`.

**Итог:** `lock` — для взаимного исключения, семафор — для ограничения параллелизма, события — для сигналов.

</A>

<A l="m">

**Как устроено**

- `Mutex`, `Semaphore`, `AutoResetEvent` и `ManualResetEvent` наследуют `WaitHandle` и оборачивают объект ядра ОС.
- Именованный `Mutex` виден другим процессам на всех ОС, именованные `Semaphore` и `EventWaitHandle` — только на Windows.
- Типы с суффиксом `Slim` обходятся без объектов ядра, пока это возможно, и работают только внутри процесса.
- У семафоров нет владельца: `Wait` в одном потоке и `Release` в другом — нормальный сценарий.

**Когда что выбирать**

| Задача | Примитив |
|---|---|
| Один экземпляр приложения | именованный `Mutex` |
| Не больше N операций, есть `await` | `SemaphoreSlim` и `WaitAsync` |
| Читают часто и долго, пишут редко | `ReaderWriterLockSlim` |
| Один поток открывает «ворота» многим | `ManualResetEventSlim` |
| Дождаться N сигналов | `CountdownEvent` |
| Фазы вычислений в N потоках | `Barrier` |

**Ловушки**

- Поток завершился, не освободив `Mutex`, — следующий владелец получит `AbandonedMutexException`.
- Лишний `Release` у семафора проходит молча, а `SemaphoreFullException` получит позже другой поток со своим законным `Release`.
- `ReaderWriterLockSlim` по умолчанию без рекурсии. Из чтения в запись переходят только через upgradeable-режим, а в нём одновременно может быть один поток.

**Правило**

С `await` из этого списка работает только `SemaphoreSlim`; остальные — для синхронного кода.

**Итог:** примитив выбирают по задаче и по тому, есть ли в коде `await`.

</A>

<A l="s">

**Под капотом**

- `Monitor` и `Slim`-типы сначала крутятся в цикле (`SpinWait`), рассчитывая, что владелец скоро освободит ресурс. Только потом поток уходит в ожидание ядра.
- Kernel-объекты делают системный вызов на каждую операцию, даже без конкуренции.
- `SpinLock` — структура, которая только крутится. Копия `SpinLock` — независимая блокировка, поэтому его нельзя передавать по значению.

**Цена**

- Спин жжёт CPU и выгоден только для очень коротких ожиданий.
- У `ReaderWriterLockSlim` вход и выход дороже, чем у `lock`. На коротких секциях и частых записях обычный `lock` бывает быстрее.

**Компромиссы**

- Для данных, которые почти только читают, вместо RW-блокировки — неизменяемый снимок и атомарная замена ссылки. Читатели тогда не синхронизируются вовсе.
- Асинхронные RW-блокировку и события берут из Microsoft.VisualStudio.Threading (`AsyncReaderWriterLock`, `AsyncManualResetEvent`) или строят на `TaskCompletionSource`.
- `SemaphoreSlim` без владельца не реентерабелен: повторный `WaitAsync` в той же цепочке вызовов ждёт сам себя.
- Брошенный `Mutex` — сигнал, что защищаемое состояние может быть повреждено.

**Как проверить в проде**

- С .NET 9 `dotnet-trace` пишет событие WaitHandleWait, когда поток блокируется в `lock`, `ManualResetEventSlim.Wait` или `SemaphoreSlim.Wait`. Стеки этих событий показывают, кто и где ждёт.
- В дампе `parallelstacks` группирует потоки, стоящие в одном и том же ожидании.

**Итог:** самый дешёвый примитив — тот, без которого удалось обойтись; дальше выбирают по владельцу, межпроцессности и профилю нагрузки.

</A>

<Ex>

```csharp
// SemaphoreSlim: не больше 3 одновременных операций, работает с await
using var gate = new SemaphoreSlim(3);
await Task.WhenAll(Enumerable.Range(1, 10).Select(async i =>
{
    await gate.WaitAsync();
    try { await Task.Delay(100); }
    finally { gate.Release(); } // владельца нет: освободить может любой поток
}));

// Barrier: три потока синхронно проходят фазы вычислений
using var barrier = new Barrier(3, b => Console.WriteLine($"phase {b.CurrentPhaseNumber} done"));
var threads = Enumerable.Range(0, 3).Select(_ => new Thread(() =>
{
    for (int phase = 0; phase < 2; phase++)
    {
        Thread.Sleep(Random.Shared.Next(50)); // считаем свою часть
        barrier.SignalAndWait();             // ждём остальных
    }
})).ToList();
threads.ForEach(t => t.Start());
threads.ForEach(t => t.Join());
// phase 0 done
// phase 1 done
```

</Ex>

<Next>

- Чем `Mutex` отличается от `lock`? — Это объект ядра: медленнее, зато работает между процессами по имени; брошенный даёт `AbandonedMutexException`.
- Почему `SemaphoreSlim(1, 1)` — не полная замена `lock`? — У него нет владельца и реентерабельности: повторный вход в той же цепочке вызовов зависнет.
- Когда `ReaderWriterLockSlim` хуже обычного `lock`? — При коротких секциях и частых записях: вход и выход у него дороже.
- Чем `CountdownEvent` отличается от `Barrier`? — В `CountdownEvent` ждут N сигналов, в `Barrier` N участников ждут друг друга, фаза за фазой.
- Как асинхронно дождаться сигнала? — Через `TaskCompletionSource` вместо `ManualResetEvent`.

</Next>

<Q id="dotnet.threading.concurrent-collections" level="m">

## Как устроены конкурентные коллекции и когда они нужны?

<A short l="j">

<T k="concurrent-collections">Конкурентные коллекции</T> из `System.Collections.Concurrent` — `ConcurrentDictionary`, `ConcurrentQueue`, `ConcurrentStack`, `ConcurrentBag` — можно менять из нескольких потоков без своего `lock`. Обычные `List<T>` и `Dictionary<TKey,TValue>` при одновременной записи портятся, поэтому общую изменяемую коллекцию берут конкурентную.

</A>

<A short l="m">

Конкурентные коллекции синхронизируют себя сами: `ConcurrentDictionary` пишет под <T k="fine-grained-locking">мелкозернистыми блокировками</T> и читает без блокировок, а `ConcurrentQueue` и `ConcurrentStack` вообще <T k="lock-free">lock-free</T>. Главная тонкость — все методы потокобезопасны, но не все атомарны: фабрика в `GetOrAdd` выполняется вне блокировки и может отработать несколько раз. Поэтому дорогие фабрики или фабрики с побочными эффектами оборачивают в `Lazy<T>`, а составные операции делают одним вызовом.

</A>

<A short l="s">

Конкурентная коллекция защищает свою структуру, но не ваши инварианты: «проверить и изменить» двумя вызовами остаётся гонкой. Поэтому API построен на атомарных `TryAdd`, `TryRemove`, `TryUpdate` и `GetOrAdd`. Платят за это памятью и глобальными операциями: `Count`, `Keys`, `Values` и `ToArray` у `ConcurrentDictionary` берут все внутренние блокировки. Для данных, которые почти только читают, выгоднее неизменяемые коллекции или `FrozenDictionary` с атомарной заменой ссылки.

</A>

<A l="j">

**Что это**

Коллекции из `System.Collections.Concurrent`, которые безопасно менять из нескольких потоков одновременно.

**Зачем**

Обычный `Dictionary<TKey,TValue>` при одновременной записи может испортить свою внутреннюю структуру. Конкурентные коллекции синхронизируют себя сами.

**Как пользоваться**

| Коллекция | Порядок | Основные методы |
|---|---|---|
| `ConcurrentDictionary` | по ключу | `TryAdd`, `GetOrAdd`, `AddOrUpdate`, `TryRemove` |
| `ConcurrentQueue` | FIFO | `Enqueue`, `TryDequeue` |
| `ConcurrentStack` | LIFO | `Push`, `TryPop` |
| `ConcurrentBag` | без порядка | `Add`, `TryTake` |

Методы с `Try` возвращают `false`, если не получилось: другой поток мог успеть первым.

**Частая ошибка**

`if (!dict.ContainsKey(key)) dict[key] = value;` — два вызова, между которыми вклинится другой поток. Правильно — один вызов `dict.TryAdd(key, value)`.

**Итог:** общую коллекцию в многопоточном коде берут из `System.Collections.Concurrent` и меняют одним вызовом.

</A>

<A l="m">

**Как устроено**

- `ConcurrentDictionary` — таблица бакетов и массив блокировок, каждая из которых защищает часть бакетов. Запись берёт одну блокировку, чтение идёт без блокировок.
- Перечисление безопасно, но это не снимок: обход может увидеть изменения, сделанные после его начала.
- `ConcurrentQueue` и `ConcurrentStack` построены на `Interlocked`, без блокировок.
- `ConcurrentBag` хранит элементы в списках, привязанных к потокам. `TryTake` сначала смотрит свой список, потом забирает из чужих.

**Когда что выбирать**

| Задача | Коллекция |
|---|---|
| Общий кеш или индекс по ключу | `ConcurrentDictionary` |
| Работа в порядке поступления | `ConcurrentQueue` |
| Поток сам кладёт и сам забирает (пул объектов) | `ConcurrentBag` |

**Ловушки**

- **`GetOrAdd` с фабрикой.** Делегат вызывается вне блокировки. Два потока могут одновременно не найти ключ и оба вызвать фабрику, а сохранится одно значение.
- **`AddOrUpdate`** при конфликте может вызвать делегат обновления повторно. Поэтому он должен быть чистой функцией.
- **`ConcurrentQueue` не умеет ждать элемент.** Цикл `TryDequeue` без паузы жжёт CPU.

**Правило**

Составную операцию делайте одним атомарным методом, а фабрику с побочными эффектами — через `Lazy<T>`: `dict.GetOrAdd(key, k => new Lazy<T>(() => Create(k))).Value`. `Lazy<T>` по умолчанию потокобезопасен и вызовет `Create` один раз.

**Итог:** конкурентная коллекция потокобезопасна, но атомарен только каждый отдельный вызов.

</A>

<A l="s">

**Под капотом**

- `Count`, `Keys`, `Values`, `ToArray`, `Clear` и рост таблицы у `ConcurrentDictionary` захватывают все блокировки.
- Число блокировок по умолчанию зависит от числа процессоров; его задаёт параметр конструктора `concurrencyLevel`.
- `ConcurrentQueue` построена на сегментах — кольцевых буферах — и в установившемся режиме почти не аллоцирует.
- `ConcurrentStack` создаёт узел на каждый `Push`, `ConcurrentDictionary` — узел на каждую запись.

**Цена**

- Частый `Count` на горячем пути сериализует писателей. Нужен счётчик — ведите его отдельно через `Interlocked`.
- `ConcurrentBag` как очередь между разными производителями и потребителями проигрывает: потребители всё время забирают из чужих списков.

**Компромиссы**

- Справочники и конфигурацию, которые почти только читают, выгоднее держать в `FrozenDictionary` (.NET 8+) или `ImmutableDictionary` и атомарно заменять ссылку целиком. Чтения тогда идут вообще без синхронизации.
- Две связанные коллекции не станут согласованными сами: такой инвариант требует внешнего `lock`.
- Одновременное чтение обычного `Dictionary` без записей безопасно — конкурентная коллекция там не нужна.

**Как проверить в проде**

- В профиле CPU (dotnet-trace, PerfView) видно время во внутренних блокировках `ConcurrentDictionary`, например в `AcquireAllLocks`.
- В дампе `dotnet-dump analyze` показывает содержимое командами `dumpconcurrentdictionary` и `dumpconcurrentqueue`.

**Итог:** конкурентные коллекции хороши для частых записей из многих потоков; для редких записей и частых чтений дешевле неизменяемые снимки.

</A>

<Ex>

```csharp
using System.Collections.Concurrent;

var cache = new ConcurrentDictionary<string, Lazy<Client>>();
int created = 0;

Client Get(string key) =>
    cache.GetOrAdd(key, k => new Lazy<Client>(() =>
    {
        Interlocked.Increment(ref created); // внутри Lazy фабрика выполнится один раз
        return new Client(k);
    })).Value;

Parallel.For(0, 1000, _ => Get("billing"));
Console.WriteLine(created); // 1

var counts = new ConcurrentDictionary<string, int>();
Parallel.ForEach(new[] { "a", "b", "a" }, word =>
    counts.AddOrUpdate(word, 1, (_, old) => old + 1)); // чистая функция: может вызваться повторно
Console.WriteLine(counts["a"]); // 2

record Client(string Name);
```

Без `Lazy` при одновременных вызовах фабрика могла бы отработать несколько раз, хотя в словаре всё равно осталось бы одно значение.

</Ex>

<Next>

- Почему `GetOrAdd` может вызвать фабрику дважды? — Делегат выполняется вне блокировки, чтобы не держать её на чужом коде; сохраняется только одно значение.
- Дорого ли вызывать `Count` у `ConcurrentDictionary`? — Да: берутся все внутренние блокировки; на горячем пути лучше отдельный счётчик.
- Когда `ConcurrentBag` — плохой выбор? — Когда производители и потребители — разные потоки: потребители постоянно забирают из чужих списков.
- Даёт ли перечисление `ConcurrentDictionary` снимок? — Нет: обход безопасен, но видит изменения; снимок даёт `ToArray()`.
- Нужны ли конкурентные коллекции, если данные только читаются? — Нет: одновременное чтение обычных коллекций без записей безопасно.

</Next>

<Q id="dotnet.threading.interlocked-volatile" level="s">

## Что такое `Interlocked`, `volatile` и модель памяти .NET?

<A short l="j">

<T k="interlocked">`Interlocked`</T> выполняет простые операции над переменной атомарно, а <T k="volatile">`volatile`</T> только гарантирует, что чтение поля не закешируется и не переставится. Поэтому общий счётчик увеличивают через `Interlocked.Increment(ref count)`, а `volatile` годится разве что для флага остановки.

</A>

<A short l="m">

`Interlocked` — атомарные операции процессора (`Increment`, `Add`, `Exchange`, <T k="compare-and-swap">`CompareExchange`</T>), каждая из которых ещё и <T k="memory-barrier">полный барьер памяти</T>, а `volatile` даёт только порядок обращений без атомарности. Volatile-чтение не пускает последующие обращения раньше себя, volatile-запись не пускает предыдущие позже себя. Поэтому `volatile` подходит для флагов и публикации готового объекта, а для `x++` и «проверить и записать» нужен `Interlocked` или `lock`.

</A>

<A short l="s">

<T k="memory-model">Модель памяти .NET</T> разрешает JIT и процессору переставлять обычные обращения, если внутри потока это незаметно, а атомарны только выровненные значения до размера указателя. Volatile-операции дают порядок <T k="acquire-release">acquire/release</T>, а `Interlocked` и `Thread.MemoryBarrier` — полный барьер; acquire/release не запрещает перестановку записи с последующим чтением другой переменной. На x64 процессор переставляет только такие пары, поэтому многие ошибки всплывают лишь на ARM64. Отсюда правило: `lock` по умолчанию, `Interlocked` для одиночных переменных, `Volatile` — только когда точно понятно, что он гарантирует.

</A>

<A l="j">

**Что это**

- **`Interlocked`** — статический класс с атомарными операциями: `Increment`, `Decrement`, `Add`, `Exchange`, `CompareExchange`.
- **`volatile`** — модификатор поля, которое меняют другие потоки.

**Зачем**

- `count++` — это чтение, сложение и запись. Другой поток может вклиниться между ними, и увеличение потеряется.
- Без `volatile` JIT может прочитать поле один раз и держать значение в регистре. Цикл `while (!_stop)` тогда не увидит `_stop = true`.

**Как пользоваться**

- Счётчик: `Interlocked.Increment(ref _count);`.
- Флаг остановки: `private volatile bool _stop;`.

**Частая ошибка**

Думать, что `volatile` делает `x++` безопасным. Он не объединяет чтение и запись в одну операцию. К тому же его нельзя повесить на `long` и `double`.

**Итог:** `Interlocked` — для атомарных изменений, `volatile` — только для видимости флага.

</A>

<A l="m">

**Как устроено**

- Все методы `Interlocked` атомарны и работают как полный барьер: обращения к памяти не переносятся через них ни в одну сторону.
- Volatile-чтение (acquire) не даёт последующим обращениям выполниться раньше него.
- Volatile-запись (release) не даёт предыдущим обращениям задержаться после неё.
- Ключевое слово `volatile` делает такими все обращения к полю. Класс `Volatile` (`Volatile.Read`, `Volatile.Write`) — отдельные обращения, в том числе к `long`, `double` и элементам массивов.

**Когда что выбирать**

| Задача | Инструмент |
|---|---|
| Счётчик, сумма | `Interlocked.Increment`, `Interlocked.Add` |
| Флаг «остановиться» | `volatile` или `Volatile.Read` и `Volatile.Write` |
| Своя атомарная операция (максимум) | CAS-цикл на `CompareExchange` |
| Инвариант из нескольких полей | `lock` |

**Ловушки**

- Volatile не даёт «свежести»: чтение не обязано вернуть последнее значение, записанное другим процессором.
- Нет единого порядка volatile-записей, одинакового для всех потоков.
- `long` и `double` на 32-битной платформе читаются неатомарно. Используйте `Interlocked.Read` или `Volatile.Read`.

**Правило**

CAS-цикл строится так:

1. Прочитать текущее значение.
2. Вычислить новое.
3. Вызвать `CompareExchange`; если значение успели поменять — вернуться к шагу 1.

**Итог:** `Interlocked` даёт атомарность и полный барьер, `volatile` — только порядок.

</A>

<A l="s">

**Под капотом**

Модель памяти .NET описана в спецификации `Memory-model.md` в репозитории dotnet/runtime и строже ECMA-335:

- обычные обращения переставляются, только если это не видно внутри потока;
- JIT не добавляет новых чтений, но может склеить соседние чтения одного поля — отсюда зависший `while (!_flag)`;
- спекулятивные записи запрещены;
- запись ссылки на объект в общую память — release для его полей, поэтому опубликованный объект виден полностью сконструированным;
- чтения через ссылку не обгоняют чтение самой ссылки.

**Цена**

- На x64 volatile-чтение и запись — обычные инструкции: процессор (модель TSO) переставляет только запись с последующим чтением.
- На ARM64 модель слабее, и volatile-операциям нужны инструкции с барьерной семантикой.
- `Interlocked` на общей кеш-линии дорог: линия переходит между ядрами, и горячий общий счётчик плохо масштабируется.

**Компромиссы**

- Схемы «записал свой флаг — проверил чужой» требуют `Interlocked` или `Interlocked.MemoryBarrier`: acquire/release такую перестановку не запрещает.
- Горячий счётчик лучше шардировать: свой на поток или ядро, сумма — при чтении.
- False sharing: независимые горячие поля в одной кеш-линии мешают друг другу.
- Double-checked locking в .NET корректен, но `Lazy<T>` и `LazyInitializer` читаются проще.

**Как проверить в проде**

- Код, стабильный на x64, гоняют стресс-тестами на ARM64 (Graviton, Apple Silicon).
- Масштабируемость счётчиков меряют в BenchmarkDotNet с разным числом потоков.

**Итог:** корректный код опирается на гарантии модели памяти, а не на поведение x64.

</A>

<Ex>

```csharp
public sealed class Stats
{
    private long _requests;          // счётчик: только через Interlocked
    private int _maxLatencyMs;       // максимум: CAS-цикл
    private volatile bool _stopped;  // флаг: volatile достаточно

    public void Record(int latencyMs)
    {
        Interlocked.Increment(ref _requests);

        int current = Volatile.Read(ref _maxLatencyMs);
        while (latencyMs > current)
        {
            // записываем, только если с момента чтения никто не изменил значение
            int seen = Interlocked.CompareExchange(ref _maxLatencyMs, latencyMs, current);
            if (seen == current) break;
            current = seen; // нас опередили — пробуем снова
        }
    }

    public long Requests => Interlocked.Read(ref _requests); // атомарно и на 32-битной платформе
    public void Stop() => _stopped = true;
    public bool IsStopped => _stopped;
}
```

</Ex>

<Next>

- Почему `volatile` не делает `x++` безопасным? — Это три операции; volatile упорядочивает каждую, но не объединяет их в атомарную.
- Нужен ли `volatile` полю, к которому обращаются только под `lock`? — Нет: вход и выход из блокировки уже упорядочивают обращения.
- Что такое ABA-проблема? — CAS видит прежнее значение, хотя между чтением и записью его меняли и вернули; для счётчиков и индексов она реальна.
- Почему код, работавший на x64, ломается на ARM64? — У ARM слабее модель памяти: видны перестановки, которых x64 не делает.
- Что такое false sharing? — Независимые горячие поля в одной кеш-линии: ядра постоянно отбирают её друг у друга.

</Next>

<Q id="dotnet.threading.channels" level="s">

## Как построить producer-consumer: `BlockingCollection` или `System.Threading.Channels`?

<A short l="j">

<T k="producer-consumer">Producer-consumer</T> — схема, где одни потоки кладут работу в очередь, а другие забирают и обрабатывают. В .NET для неё есть <T k="blocking-collection">`BlockingCollection<T>`</T>, который блокирует поток при ожидании, и <T k="channels">каналы</T> `Channel<T>`, которые ждут асинхронно через `await`, поэтому в новом коде берут каналы.

</A>

<A short l="m">

`BlockingCollection<T>` — синхронная очередь с ограничением ёмкости, а `Channel<T>` — её асинхронный аналог. `Add` и `Take` блокируют поток, когда очередь полна или пуста, а `WriteAsync` и `ReadAllAsync` в тех же ситуациях отпускают поток до появления места или данных. Ограниченный канал (`CreateBounded`) даёт <T k="backpressure">backpressure</T>: быстрый производитель ждёт, а не раздувает память.

</A>

<A short l="s">

Producer-consumer — это прежде всего решение о границе очереди: неограниченная очередь при медленном потребителе превращает задержку в рост памяти. Ограниченный канал переносит давление на производителя — ждать (`Wait`) или сбрасывать элементы (`DropOldest`, `DropNewest`, `DropWrite`), а его async-методы возвращают `ValueTask` и не держат потоки. `BlockingCollection` держит заблокированными потоки пула и плохо сочетается с async-кодом, поэтому остаётся для выделенных потоков в синхронном коде.

</A>

<A l="j">

**Что это**

- **Producer** (производитель) создаёт работу.
- **Consumer** (потребитель) её обрабатывает.
- Между ними — потокобезопасная очередь.

**Зачем**

Чтобы разделить быстрый приём и медленную обработку. Например, принимать сообщения сразу, а записывать их в базу в своём темпе.

**Как пользоваться**

1. Создать канал: `var channel = Channel.CreateBounded<int>(100);` — не больше 100 элементов.
2. Производитель пишет `await channel.Writer.WriteAsync(item)`, а в конце вызывает `channel.Writer.Complete()`.
3. Потребитель читает `await foreach (var item in channel.Reader.ReadAllAsync())`.

**Частая ошибка**

Забыть `Complete()`. Потребитель тогда ждёт новых элементов вечно.

**Итог:** каналы — стандартная асинхронная очередь между производителями и потребителями.

</A>

<A l="m">

**Как устроено**

- `CreateUnbounded` — запись всегда завершается сразу, память не ограничена.
- `CreateBounded` — при заполнении срабатывает режим `FullMode` из `BoundedChannelOptions`.
- Каналы поддерживают несколько производителей и потребителей. Потребители с `ReadAllAsync` делят элементы между собой.
- `BlockingCollection<T>` — синхронная обёртка над `ConcurrentQueue<T>` (по умолчанию): `Add`, `Take`, `CompleteAdding`, `GetConsumingEnumerable`.

**Когда что выбирать**

| `FullMode` | Что происходит при заполнении |
|---|---|
| `Wait` (по умолчанию) | `WriteAsync` ждёт места, `TryWrite` возвращает `false` |
| `DropOldest` | из очереди выбрасывается самый старый элемент |
| `DropNewest` | из очереди выбрасывается самый новый элемент |
| `DropWrite` | выбрасывается элемент, который пытаются записать |

**Ловушки**

- При нескольких производителях `Complete()` вызывают, когда закончили все.
- `ReadAsync` на завершённом канале бросает `ChannelClosedException`, а `ReadAllAsync` просто заканчивает перечисление.
- Ошибку нельзя терять: `Writer.TryComplete(ex)` остановит запись и передаст исключение в `Reader.Completion`.

**Правило**

Канал по умолчанию — ограниченный; неограниченный — только если источник ограничен сам.

**Итог:** канал — это асинхронная очередь с явной границей и протоколом завершения.

</A>

<A l="s">

**Под капотом**

- Async-методы каналов возвращают `ValueTask`: если операция завершилась синхронно, аллокации нет.
- `SingleReader = true` и `SingleWriter = true` — обещание каналу, которое позволяет ему выбрать более быструю реализацию.
- `AllowSynchronousContinuations = true` позволяет продолжению читателя выполниться прямо внутри `WriteAsync` писателя.

**Цена**

- Ожидающий потребитель канала не занимает поток. Каждый ждущий `BlockingCollection.Take` держит поток, и на пуле это быстро съедает свободные потоки.
- Неограниченный канал при медленном потребителе превращает задержку в рост памяти, а затем в `OutOfMemoryException`.

**Компромиссы**

- `Wait` пробрасывает замедление назад по конвейеру — до источника, который перестаёт читать сокет или брокер.
- `DropOldest` подходит для телеметрии и «последнего значения». Для режимов со сбросом есть колбэк `itemDropped`.
- Синхронные продолжения уменьшают переключения, но писатель неожиданно выполняет код читателя и ждёт его.
- Для графов с ветвлением и встроенным ограничением параллелизма есть TPL Dataflow; каналы — более низкоуровневый строительный блок.

**Как проверить в проде**

- Длина очереди — главный сигнал: `Reader.Count`, если `Reader.CanCount` равно `true`.
- Растущее время `WriteAsync` означает, что система упирается в потребителя.
- Завершение `Reader.Completion` с исключением в логах показывает, что конвейер остановился с ошибкой.

**Итог:** главное решение в producer-consumer — граница очереди и поведение при её достижении.

</A>

<Ex>

```csharp
using System.Threading.Channels;

// Не больше 100 элементов; при заполнении производитель ждёт (backpressure)
var channel = Channel.CreateBounded<int>(
    new BoundedChannelOptions(100) { FullMode = BoundedChannelFullMode.Wait });

var producer = Task.Run(async () =>
{
    try
    {
        for (int i = 0; i < 1_000; i++)
            await channel.Writer.WriteAsync(i); // ждёт, если очередь полна
        channel.Writer.Complete();
    }
    catch (Exception ex) { channel.Writer.TryComplete(ex); } // ошибка дойдёт до потребителей
});

// Три потребителя делят элементы между собой
var consumers = Enumerable.Range(0, 3).Select(_ => Task.Run(async () =>
{
    await foreach (int item in channel.Reader.ReadAllAsync())
        await Task.Delay(1); // медленная обработка
})).ToArray();

await Task.WhenAll(consumers.Append(producer));
```

</Ex>

<Next>

- Что будет с неограниченным каналом, если потребитель медленнее производителя? — Очередь растёт без предела: память, задержка и в итоге OOM.
- Чем `DropOldest` отличается от `DropWrite`? — Первый выбрасывает самый старый элемент из очереди, второй — тот, который пытаются записать.
- Как остановить конвейер при ошибке? — `Writer.TryComplete(ex)`: запись прекратится, а `Reader.Completion` завершится с этим исключением.
- Когда `BlockingCollection` ещё уместна? — В синхронном коде с выделенными потоками-потребителями, где блокировка потока не мешает.
- Что даёт `SingleReader = true`? — Обещание, что читатель один: канал может выбрать более быструю реализацию.

</Next>

<Q id="dotnet.threading.thread-pool-starvation" level="s">

## Что такое голодание пула потоков и как его диагностировать?

<A short l="j">

<T k="thread-pool-starvation">Голодание пула потоков</T> — ситуация, когда все потоки пула заняты (обычно просто ждут), и новой работе не на чем выполняться. Приложение отвечает всё медленнее, хотя процессор почти свободен, и чаще всего виноват <T k="sync-over-async">sync-over-async</T> — `.Result` или `.Wait()` на асинхронной операции.

</A>

<A short l="m">

Голодание — это нехватка свободных потоков пула при растущей очереди работы. Пул сверх минимума (по умолчанию — число процессоров) добавляет потоки постепенно, поэтому под нагрузкой очередь растёт быстрее, чем он успевает. Признаки — медленный рост числа потоков, длинная очередь и низкая загрузка CPU, а лечится это переводом блокирующего кода на `await`, а не увеличением числа потоков.

</A>

<A short l="s">

Голодание пула — это когда работа стоит в очереди не из-за нехватки CPU, а из-за заблокированных потоков. Пул наращивает потоки медленно: <T k="hill-climbing">hill climbing</T> подбирает их число по пропускной способности, а с .NET 6 блокировка на `Task.Wait` компенсируется быстрее. Компенсация стоит сотен потоков, поэтому `SetMinThreads` — лишь заплатка, а лечат удалением sync-over-async. Диагностика: `dotnet-counters` даёт картину, `dotnet-stack` или дамп — постоянную причину, `dotnet-trace` с событием WaitHandleWait (.NET 9+) — плавающую.

</A>

<A l="j">

**Что это**

Все потоки пула заняты ожиданием, а новые запросы стоят в очереди.

**Как это выглядит**

Сервис под нагрузкой отвечает за секунды вместо миллисекунд. Процессор при этом загружен слабо.

**Почему возникает**

1. Запрос выполняется на потоке пула.
2. Код вызывает `httpClient.GetStringAsync(url).Result` — поток стоит и ждёт ответа.
3. Под нагрузкой так встают все потоки пула.
4. Новые запросы ждут в очереди, пока пул медленно добавляет потоки.

**Частая ошибка**

Лечить симптом: поднять минимум потоков вместо того, чтобы убрать блокировки.

**Итог:** в коде на пуле потоков — `await` до самого верха, без `.Result` и `.Wait()`.

</A>

<A l="m">

**Как устроено**

1. До минимума (`ThreadPool.GetMinThreads`, по умолчанию — число процессоров) пул создаёт потоки сразу.
2. Выше — с задержкой. В примере Microsoft число потоков быстро доходит до 2–3 на ядро, а дальше прибавляется по 1–2 в секунду.
3. Пока потоков не хватает, растёт очередь и задержка каждого запроса.

**Когда что выбирать**

| Причина | Решение |
|---|---|
| `.Result`, `.Wait()` на async-коде | `await` по всей цепочке |
| Синхронный I/O | асинхронные API (`ReadAsync`, `SaveChangesAsync`) |
| Сторонний блокирующий API | отдельный поток или `LongRunning` с ограничением параллелизма |
| Пережить всплеск до исправления | временно `SetMinThreads` |

**Ловушки**

- Число потоков стабилизировалось высоко — больше примерно трёх на ядро. Значит, код блокирует потоки, а пул компенсирует; при всплеске или рестарте голодание вернётся.
- `Thread.Sleep` и долгий `lock` в коде на пуле тоже съедают потоки.

**Правило**

Признаки голодания в `dotnet-counters`: число потоков пула медленно растёт, очередь длинная, завершённой работы мало, CPU заметно ниже 100%.

**Итог:** голодание лечат удалением блокировок, а не добавлением потоков.

</A>

<A l="s">

**Под капотом**

- Hill climbing периодически меняет число активных потоков и смотрит, выросла ли пропускная способность — число завершённых work items в секунду.
- Отдельный механизм добавляет поток, когда очередь есть, а прогресса нет. Оба видны в событиях `ThreadPoolWorkerThreadAdjustment` с причинами вроде Climbing move и Starvation.
- С .NET 6 пул сразу добавляет потоки, когда поток пула блокируется в ожидании задачи. Без задержки — до `ThreadsToAddWithoutDelay_ProcCountFactor`, умноженного на число процессоров, дальше с растущей задержкой.
- Этот механизм работает только для ожидания задач (`Task.Wait`, `.Result`), а не для `lock`, синхронного I/O или `Thread.Sleep`.

**Цена**

- Компенсация — это сотни потоков: память под стеки, переключения контекста, дольше обход стеков при сборке мусора.
- Большой `SetMinThreads` платит те же издержки постоянно, а не только во время всплеска.

**Компромиссы**

Настройки `System.Threading.ThreadPool.Blocking.*` и `MinThreads` покупают время до исправления кода. Настоящее решение — асинхронность по всему стеку и выделенные потоки для неизбежной блокировки.

**Как проверить в проде**

1. `dotnet-counters monitor -n MyApp`. В .NET 9+ это метрики `dotnet.thread_pool.thread.count`, `dotnet.thread_pool.queue.length` и `dotnet.thread_pool.work_item.count`; раньше — ThreadPool Thread Count, ThreadPool Queue Length и ThreadPool Completed Work Item Count.
2. Постоянная проблема: `dotnet-stack report -n MyApp` или дамп с `parallelstacks`. Ищите потоки с `WorkerThread` внизу стека и `Task.Wait` или `GetResult` наверху.
3. Плавающая проблема: `dotnet-trace collect -n MyApp --clrevents waithandle --clreventlevel verbose` (.NET 9+), затем стеки WaitHandleWait в PerfView.

**Итог:** голодание видно по счётчикам, а причину показывают стеки заблокированных потоков пула.

</A>

<Ex>

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddHttpClient();
var app = builder.Build();

// Плохо: sync-over-async — поток пула стоит всё время запроса
app.MapGet("/bad", (IHttpClientFactory f) =>
    f.CreateClient().GetStringAsync("https://example.com").Result.Length);

// Хорошо: на время ожидания поток возвращается в пул
app.MapGet("/good", async (IHttpClientFactory f) =>
    (await f.CreateClient().GetStringAsync("https://example.com")).Length);

app.Run();
```

Под нагрузкой `/bad` держит по потоку на каждый запрос, и число потоков пула растёт; `/good` обходится несколькими потоками.

</Ex>

<Next>

- Почему CPU загружен слабо, а запросы тормозят? — Потоки не считают, а ждут; работа стоит в очереди пула.
- Поможет ли `ThreadPool.SetMinThreads(500, 500)`? — Снимет симптом при всплесках, но добавит памяти и переключений; блокирующий код останется.
- Что изменилось в .NET 6? — Пул быстрее добавляет потоки, когда поток блокируется на `Task.Wait` или `.Result`; голодание короче, но не исчезает.
- Как отличить голодание от дедлока? — При голодании число потоков растёт и работа идёт медленно; при дедлоке потоки стоят на одних блокировках, и прогресса нет вовсе.
- Чем помогает `TaskCreationOptions.LongRunning`? — Долгая блокирующая работа получает отдельный поток и не занимает пул.
