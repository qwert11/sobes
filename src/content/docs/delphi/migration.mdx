## Что сломалось при переходе на Unicode в Delphi 2009 и как это чинить?

<A short l="j">

С Delphi 2009 `string` — это <T k="delphi-unicode-string">`UnicodeString`</T> в кодировке <T k="utf-16">UTF-16</T>, а `Char` занимает 2 байта, а не 1. Поэтому ломается код, который считал символ байтом: буферы, запись в файлы и потоки, вызовы старых DLL.

</A>

<A short l="m">

В Delphi 6 `string` был `AnsiString` — байтами в <T k="code-page">кодовой странице</T> Windows, а с Delphi 2009 это `UnicodeString`: `Char` = `WideChar`, `PChar` = `PWideChar`, функции WinAPI вызываются в W-версиях. Код, где строка служила буфером байтов или размер считался через `SizeOf`, компилируется, но портит данные. Лечение — явная граница: внутри программы всё `string`, на входе и выходе текст превращается в байты через <T k="delphi-tencoding">`TEncoding`</T>, а двоичные данные хранятся в <T k="delphi-tbytes">`TBytes`</T>.

</A>

<A short l="s">

Unicode опасен не ошибками компиляции, а тихой порчей данных: неявные преобразования между `AnsiString` и `string` компилятор вставляет сам и теряет символы вне кодовой страницы. Поэтому сначала включают предупреждения W1057–W1060 и разбирают каждое, затем находят все границы — файлы, потоки, DLL, сокеты, хеши, BLOB — и на каждой задают кодировку явно. Цена — ревизия всех мест, где строка была байтами, и совместимость с тем, что старая версия уже записала: файлы, хеши паролей, обмен с другими системами.

</A>

<A l="j">

**Что это**

В Delphi 6 `string` — это `AnsiString`: один байт на символ, текст в кодовой странице Windows, для кириллицы обычно 1251. С Delphi 2009 `string` — это `UnicodeString`: два байта на символ, кодировка UTF-16.

**Что поменялось**

| Тип | Delphi 6 | Delphi 2009+ |
|---|---|---|
| `string` | `AnsiString` | `UnicodeString` |
| `Char` | `AnsiChar`, 1 байт | `WideChar`, 2 байта |
| `PChar` | `PAnsiChar` | `PWideChar` |

**Как пользоваться**

- Обычная работа со строками — сложение, `Copy`, `Pos`, `Length` — не меняется.
- Ломается код, где строка — это байты: запись в поток, буферы для WinAPI, вызовы старых DLL.

**Частая ошибка**

Считать размер буфера символов через `SizeOf`. Он возвращает байты, а `Length` — число символов, и в Unicode это разные числа.

**Итог:** с Delphi 2009 символ занимает 2 байта, и всё, что считало его байтом, нужно проверить.

</A>

<A l="m">

**Как устроено**

- `AnsiString` теперь знает свою кодовую страницу: `type Cp1251String = type AnsiString(1251)`. При присваивании между `AnsiString` и `string` компилятор вставляет преобразование.
- Функции WinAPI без суффикса (`GetWindowText`) теперь указывают на W-версии. Они ждут `PWideChar`, а размер буфера — в символах.

**Было — стало — что делать**

| Было в Delphi 6 | Что ломается | Что делать |
|---|---|---|
| `Stream.Write(S[1], Length(S))` | пишется половина строки | байты из `TEncoding`, `TStreamWriter` |
| `SizeOf(Buf)` у массива `Char` | размер вдвое больше буфера | `Length(Buf)` |
| строка как буфер байтов | байты меняются при преобразовании | `TBytes` |
| `PChar` в объявлении чужой DLL | DLL получает UTF-16 вместо ANSI | `PAnsiChar` и `AnsiString` |
| `Ch in ['a'..'z']` | предупреждение W1050 | `CharInSet` |

**Ловушки**

- **Хеши и подписи.** MD5 от строки теперь считается по другим байтам, и старые хеши паролей не совпадут. Кодировку для хеша фиксируют явно — ту, что была.
- **Арифметика через `PChar`.** Шаг указателя стал 2 байта. Для арифметики над байтами — `PByte`.
- **Сторонние компоненты.** Версия для Delphi 6 либо не соберётся, либо соберётся с теми же ошибками внутри.

**Правило**

Внутри программы — `string`, на границе — явная кодировка, двоичные данные — `TBytes`.

**Итог:** найдите все места, где текст становится байтами, и задайте там кодировку явно.

</A>

<A l="s">

**Под капотом**

- У `UnicodeString` и `AnsiString` общий заголовок: кодовая страница, размер элемента, счётчик ссылок, длина. `UTF8String` — это `AnsiString(65001)`, а `RawByteString` принимает любую `AnsiString` без перекодирования.
- Неявное преобразование вставляет компилятор. В коде его не видно, оно стоит аллокации и копирования, а при сужении до ANSI заменяет непредставимые символы на `?`.
- `Length` считает элементы UTF-16. Символ вне базовой плоскости, например эмодзи, занимает два `Char` — суррогатную пару.

**Цена**

- Ревизия всех границ: файлы, потоки, сокеты, буферы WinAPI, DLL, BLOB-поля, хеши.
- Строки с кириллицей и латиницей занимают вдвое больше памяти; для настольного клиента это обычно незаметно.

**Компромиссы**

- **Быстрый путь** — объявить проблемные строки `AnsiString`. Работает, но ANSI расползается дальше, а каждый вызов VCL добавляет преобразование.
- **Правильный путь** — Unicode внутри и явная кодировка на границе. Дольше, зато долг не остаётся.
- **Внешние форматы не меняют молча.** Если партнёр ждёт файл в 1251, пишут 1251 через `TEncoding.GetEncoding(1251)`.

**Как проверить в проде**

1. Включить в проекте предупреждения W1057–W1060 и разобрать каждое.
2. Прогнать сценарии с текстом вне кодовой страницы 1251: иероглифы, эмодзи.
3. Сравнить побайтно файлы и выгрузки, которые записали старая и новая версии.

**Итог:** Unicode-миграция — это поиск всех границ, где текст становится байтами, и явная кодировка на каждой из них.

</A>

<Ex title="Delphi 6: строка как байты">

```pascal
// string = AnsiString: 1 символ = 1 байт
procedure SaveText(Stream: TStream; const S: string);
begin
  Stream.WriteBuffer(S[1], Length(S));  // в Unicode запишет половину строки
end;

function WinDir: string;
var
  Buf: array[0..MAX_PATH] of Char;
begin
  // в Unicode SizeOf(Buf) вдвое больше, чем символов в буфере
  SetString(Result, Buf, GetWindowsDirectory(Buf, SizeOf(Buf)));
end;

// старая DLL ждёт ANSI, а в Unicode PChar = PWideChar
function LegacyCheck(Code: PChar): Integer; stdcall; external 'legacy.dll';
```

</Ex>

<Ex title="Delphi 12: явная кодировка на границе">

```pascal
procedure SaveText(Stream: TStream; const S: string);
var
  Bytes: TBytes;
begin
  Bytes := TEncoding.UTF8.GetBytes(S);  // кодировка задана явно
  if Length(Bytes) > 0 then
    Stream.WriteBuffer(Bytes[0], Length(Bytes));
end;

function WinDir: string;
var
  Buf: array[0..MAX_PATH] of Char;
begin
  SetString(Result, Buf, GetWindowsDirectory(Buf, Length(Buf)));  // размер в символах
end;

function LegacyCheck(Code: PAnsiChar): Integer; stdcall; external 'legacy.dll';
// вызов: LegacyCheck(PAnsiChar(AnsiString(S)))
```

`AnsiString(S)` перекодирует строку в кодовую страницу системы. Если DLL ждёт конкретную кодировку, объявите тип `AnsiString(1251)`. Для старого формата файла вместо `TEncoding.UTF8` берут `TEncoding.GetEncoding(1251)`; этот экземпляр нужно освободить.

</Ex>

<Next>

- Чем `RawByteString` отличается от `AnsiString`? — Не перекодирует при присваивании; годится как параметр, принимающий строку в любой кодовой странице.
- Сколько `Char` занимает эмодзи? — Два: суррогатная пара UTF-16, поэтому `Length` не равен числу видимых символов.
- Как `TStringList.LoadFromFile` читает старые ANSI-файлы? — По BOM, если он есть; без BOM — в кодировке `DefaultEncoding`, по умолчанию это ANSI-страница системы.
- Как сохранить совместимость хешей паролей? — Считать хеш от байтов в старой кодировке: `TEncoding.GetEncoding(1251).GetBytes(...)`.
- Что делать со сторонним компонентом без Unicode-версии? — Обновить, заменить аналогом или портировать по исходникам; заброшенный компонент — постоянный риск.

</Next>

## Как перевести слой данных с ADO на FireDAC и что проверить?

<A short l="j">

<T k="firedac">FireDAC</T> — современная библиотека доступа к данным в Delphi, она заменяет компоненты ADO (<T k="ado-dbgo">dbGo</T>): `TADOQuery` → `TFDQuery`, `TADOStoredProc` → `TFDStoredProc`. Компоненты похожи, но типы полей, параметры и настройки по умолчанию отличаются, поэтому после замены каждую форму и вызов процедуры нужно проверить.

</A>

<A short l="m">

Механическую часть — переименование компонентов в .pas и <T k="dfm-file">.dfm</T> — делает утилита `reFind` со скриптом миграции dbGo, но ADO и FireDAC по-разному отображают типы MS SQL на поля и по-разному описывают параметры <T k="stored-procedure">хранимых процедур</T>. Расхождения закрывают <T k="delphi-map-rules">правилами отображения типов</T> (`FormatOptions.MapRules`) и общими опциями соединения, а не правкой каждой формы. Цена — тихие отличия вроде обрезанных пробелов или другого типа даты; их ловит только автоматическая сверка старой и новой версий.

</A>

<A short l="s">

Переход на FireDAC меняет семантику, а не только имена: типы полей, правила для строк и NULL, режим транзакций, способ получения параметров процедур. Поэтому его делают отдельным этапом после переезда на новую Delphi со старым ADO, чтобы не менять две вещи сразу, и настраивают централизованно на `TFDConnection`. Доказательство эквивалентности — автоматическая сверка: для каждой процедуры сравниваются имена, типы, направления и размеры параметров, а затем результаты вызовов на одних данных. Цена — инструмент сверки и прогоны на копии боевой базы, но без них расхождения находят пользователи.

</A>

<A l="j">

**Что это**

FireDAC — основная библиотека доступа к базам данных в современных Delphi. Компоненты ADO (dbGo) по-прежнему входят в поставку, но новые возможности получает FireDAC.

**Соответствие компонентов**

| ADO (dbGo) | FireDAC |
|---|---|
| `TADOConnection` | `TFDConnection` |
| `TADOQuery`, `TADODataSet` | `TFDQuery` |
| `TADOStoredProc` | `TFDStoredProc` |
| `TADOCommand` | `TFDCommand` |
| `TADOTable` | `TFDTable` |

**Как пользоваться**

1. Заменить компоненты в .pas и .dfm — вручную или утилитой `reFind`.
2. Настроить `TFDConnection` на MS SQL Server.
3. Открыть каждую форму и проверить поля и параметры.

**Частая ошибка**

Считать, что после замены имён всё работает. Если тип поля изменился, форма упадёт при открытии с ошибкой `Type mismatch for field`.

**Итог:** компоненты меняются один к одному, но поведение нужно проверять на каждой форме.

</A>

<A l="m">

**Как устроено**

| Что | ADO | FireDAC |
|---|---|---|
| Параметры процедуры | `Parameters`, `Direction` | `Params`, `ParamType` |
| Параметры из метаданных | `Parameters.Refresh` | `Prepare` при `fiMeta` в `FetchOptions.Items` |
| Транзакции | `BeginTrans`, `CommitTrans` | `StartTransaction`, `Commit` |

**Что проверить — по шагам**

1. **Типы полей.** `nvarchar` → `TWideStringField`, `nvarchar(max)` → `TWideMemoField`. <T k="persistent-fields">Persistent-поля</T> в .dfm должны совпасть с тем, что вернёт FireDAC; расхождения закрывают `MapRules`.
2. **Параметры процедур.** Имя, тип, направление, размер. Значения по умолчанию из объявления процедуры FireDAC не поддерживает — передавайте каждый параметр.
3. **Строки и NULL.** `StrsTrim` (по умолчанию `True`) обрезает хвостовые пробелы у `CHAR`/`NCHAR`, `StrsEmpty2Null` превращает пустую строку в NULL.
4. **Дата и время.** `datetime2`, `date` и `time` со старым ODBC-драйвером приходят строками — нужен современный драйвер.
5. **Автоинкремент.** `IDENTITY` распознаётся как `TFDAutoIncField`; проверьте, что новое значение видно после `Post`.
6. **Транзакции.** По умолчанию FireDAC работает в <T k="autocommit">автокоммите</T>; код с явными транзакциями переводится на `StartTransaction`/`Commit`/`Rollback`.

**Ловушки**

- `ResourceOptions.UnifyParams = True` убирает `@` из имён параметров, и `ParamByName('@Id')` перестанет находить параметр.
- Триггер без `SET NOCOUNT ON` даёт ошибку `Update command updated [N] instead of [1] record`.

**Правило**

Различия закрывайте настройками соединения, а не правками форм.

**Итог:** имена меняются механически, а типы, параметры и транзакции проверяют по списку и сверкой.

</A>

<A l="s">

**Под капотом**

- FireDAC работает с MS SQL Server через ODBC-драйвер Microsoft, ADO — через OLE DB-провайдер. Отсюда разные типы полей и параметров для одних и тех же колонок.
- Правила `MapRules` применяются при подготовке команды, срабатывает первое подходящее. Задав их на `TFDConnection`, вы меняете поведение всех наборов данных сразу.
- Параметры из метаданных стоят запроса к серверу при `Prepare`. Без `fiMeta` их описывают вручную — так делают, если метаданные врут, например у `VARCHAR` без размера.

**Почему нужна автоматическая сверка**

1. Снять с обеих версий описание каждого вызова: процедура, параметры с типом, направлением и размером.
2. Нормализовать различия: `pdInput` ↔ `ptInput`, `pdReturnValue` ↔ `ptResult`, `@` в именах.
3. Сравнить diff-ом и разобрать каждое расхождение.
4. Прогнать сценарии на копии боевой базы и сравнить результаты и данные после записи.

Ручная проверка тысячи форм выборочна, а сверка повторяется после каждого изменения.

**Цена**

- Инструмент сверки и копия базы для прогонов.
- ODBC Driver 18 по умолчанию шифрует соединение и проверяет сертификат сервера — это инфраструктурная работа до первого запуска.

**Компромиссы**

- Сначала Delphi 12 с ADO, потом FireDAC: дольше, но каждый этап проверяется отдельно.
- `MapRules` для совместимости со старыми типами быстрее, чем пересоздание persistent-полей, но закрепляет старые типы в новом коде.

**Как проверить в проде**

Трассировка SQL Server (Extended Events) на одном сценарии в старой и новой версиях показывает, какие вызовы и с какими параметрами пришли на сервер.

**Итог:** FireDAC меняет семантику доступа к данным, поэтому эквивалентность доказывают автоматической сверкой, а не ручной проверкой.

</A>

<Ex title="Delphi 6: ADO">

```pascal
ADOStoredProc1.ProcedureName := 'dbo.GetOrderTotal';
ADOStoredProc1.Parameters.Refresh;  // параметры из метаданных сервера
ADOStoredProc1.Parameters.ParamByName('@OrderId').Value := OrderId;
ADOStoredProc1.ExecProc;
Total := ADOStoredProc1.Parameters.ParamByName('@Total').Value;
```

</Ex>

<Ex title="Delphi 12: FireDAC">

```pascal
// Общая настройка соединения: datetime как TDateTimeField, пробелы CHAR не обрезать
FDConnection1.FormatOptions.OwnMapRules := True;
with FDConnection1.FormatOptions.MapRules.Add do
begin
  SourceDataType := dtDateTimeStamp;
  TargetDataType := dtDateTime;
end;
FDConnection1.FormatOptions.StrsTrim := False;

FDStoredProc1.StoredProcName := 'dbo.GetOrderTotal';
FDStoredProc1.Prepare;  // при fiMeta в FetchOptions.Items Params заполняются сами
FDStoredProc1.ParamByName('@OrderId').AsInteger := OrderId;
FDStoredProc1.ExecProc;
Total := FDStoredProc1.ParamByName('@Total').AsCurrency;
```

Правило `dtDateTimeStamp` → `dtDateTime` и `StrsTrim := False` взяты из официального примера миграции с BDE. Нужны ли они вам, решает сверка типов полей и данных старой и новой версий.

</Ex>

- Почему колонка `datetime2` пришла строкой? — Старый ODBC-драйвер SQL Server не знает типов SQL Server 2008; поставьте современный драйвер.
- Что будет с `ParamByName('@Id')` после `UnifyParams := True`? — Параметр не найдётся: префикс `@` убран из имён.
- Почему процедура падает с `Data too large for variable`? — Параметр объявлен как `VARCHAR` без размера; уберите `fiMeta` и задайте `Size` вручную.

<Q id="delphi.mig.64bit" level="m">

## Что нужно учесть при переходе на 64 бита?

<A short l="j">

В 64-битной программе указатель занимает 8 байт, а `Integer` остаётся 4 байта. Поэтому код, который хранил указатели или объекты в `Integer`, ломается; для таких значений есть <T k="delphi-native-int">`NativeInt`</T>, размер которого всегда равен размеру указателя.

</A>

<A short l="m">

Win64 увеличивает до 8 байт указатели, `NativeInt` и хэндлы, но оставляет 4 байта у `Integer`, `Cardinal` и `LongInt`, поэтому приведение указателя к `Integer` теперь его обрезает. Основные места поломок — `Tag := Integer(Obj)`, параметры Windows-сообщений (`WPARAM`, `LPARAM`), ассемблерные вставки внутри Pascal-кода и сторонние DLL и <T k="inproc-com">внутрипроцессные COM-серверы</T>, которые обязаны быть 64-битными. Цена — ревизия низкоуровневого кода и поиск 64-битных версий всех зависимостей.

</A>

<A short l="s">

Переход на Win64 — прежде всего вопрос зависимостей, а не кода: 32-битную DLL, OLE DB-провайдер или COM-компонент нельзя загрузить в 64-битный процесс. Код чинится по шаблонам — `NativeInt`, `LPARAM`, `SetWindowLongPtr`, — а у зависимости 64-битной версии может не быть вовсе. Поэтому сначала решают, нужен ли клиенту 64-битный режим: если 32-битному процессу хватает 4 ГБ с флагом <T k="large-address-aware">`LARGEADDRESSAWARE`</T>, выгоднее остаться в Win32 и вложить время в Unicode и FireDAC.

</A>

<A l="j">

**Что это**

64-битная программа может адресовать больше памяти, и каждый указатель в ней занимает 8 байт вместо 4.

**Что меняется**

| Тип | Win32 | Win64 |
|---|---|---|
| `Pointer`, ссылки на объекты | 4 байта | 8 байт |
| `NativeInt`, `NativeUInt` | 4 байта | 8 байт |
| `Integer`, `Cardinal`, `LongInt` | 4 байта | 4 байта |

**Как пользоваться**

- Указатель или объект в целом числе — только `NativeInt`: `Tag := NativeInt(Obj)`.
- Размер указателя — `SizeOf(Pointer)`, а не число 4.
- Платформа Windows 64-bit добавляется в Project Manager; Win32 и Win64 собираются в разные EXE.

**Частая ошибка**

`Integer(Obj)` компилируется и в Win64, но отрезает старшие 4 байта адреса. Ошибка проявится, только когда адрес окажется выше 4 ГБ, поэтому тесты её часто не ловят.

**Итог:** в Win64 указатель — 8 байт, а `Integer` — по-прежнему 4; всё, где одно хранилось в другом, нужно исправить.

</A>

<A l="m">

**Как устроено**

- Указатели, `NativeInt`, `THandle`, `HWND`, `WPARAM`, `LPARAM`, `LRESULT` — 8 байт; `Integer` и `LongInt` на Windows — 4 байта.
- `Extended` в Win64 — псевдоним `Double`: 8 байт вместо 10. Точные расчёты могут дать другой последний знак, а двоичные файлы с `Extended` станут несовместимы.
- Смешивать ассемблер и Pascal в одной функции нельзя: функция либо целиком на `asm`, либо на Pascal.

**Было — стало**

| Было | Стало |
|---|---|
| `Tag := Integer(Obj)` | `Tag := NativeInt(Obj)` |
| `SendMessage(..., Integer(@Buf))` | `LPARAM(@Buf)` |
| `SetWindowLong(..., GWL_WNDPROC, ...)` | `SetWindowLongPtr(..., GWLP_WNDPROC, ...)` |
| `Message.Result := Integer(Self)` | `LRESULT(Self)` |
| `Count * 4` для массива указателей | `Count * SizeOf(Pointer)` |

**Ловушки**

- **Зависимости.** DLL, `.obj`-файлы и внутрипроцессные COM-серверы нужны в 64-битной версии. Внепроцессный COM-сервер (EXE) работает с любой разрядностью.
- **Компоненты.** Пакеты для дизайнера нужны в версии под разрядность IDE, а для сборки — в 64-битной.
- **Драйвер БД.** Для FireDAC нужен 64-битный ODBC-драйвер SQL Server, для ADO — 64-битный OLE DB-провайдер.

**Правило**

Сначала инвентаризация зависимостей, потом правка кода.

**Итог:** код под Win64 чинится по шаблонам, а зависимость без 64-битной версии может заблокировать переход целиком.

</A>

<A l="s">

**Под капотом**

- 32-битный процесс на 64-битной Windows работает через <T k="wow64">WOW64</T> и получает 2 ГБ адресного пространства, а с флагом `IMAGE_FILE_LARGE_ADDRESS_AWARE` — до 4 ГБ. В Delphi флаг ставит директива `{$SetPEFlags IMAGE_FILE_LARGE_ADDRESS_AWARE}`.
- В процессе одна разрядность: 32-битную DLL нельзя загрузить в 64-битный процесс, и наоборот.
- Патчи функций во время выполнения и ассемблер под IA-32 переписываются под x64 вручную.

**Когда 64 бита не нужны**

- Клиенту хватает памяти: формы, гриды и отчёты укладываются в сотни мегабайт.
- У ключевой зависимости нет 64-битной версии: генератор отчётов, драйвер оборудования, COM-библиотека.

64 бита нужны, когда клиент упирается в память или когда зависимость выходит только в 64-битной версии.

**Компромиссы**

- Две платформы удваивают сборки и тестирование. Если переход нужен, его делают отдельным этапом после Unicode и FireDAC.
- 32-битную зависимость без замены выносят в отдельный процесс-посредник и вызывают через межпроцессное взаимодействие.

**Как проверить в проде**

- Тестовая машина с настройкой реестра `AllocationPreference` = `0x100000`: Windows выделяет память сверху вниз, и усечённые указатели падают сразу, а не после 4 ГБ.
- Сравнение результатов расчётов Win32 и Win64 на одних данных ловит расхождения из-за `Extended`.

**Итог:** решение о 64 битах принимают по зависимостям и памяти, а не по моде; если клиенту это ничего не даёт, переход откладывают.

</A>

<Ex title="Delphi 6, Win32: указатель в Integer">

```pascal
ListView1.Tag := Integer(Customer);           // в Win64 адрес обрежется
SendMessage(Edit1.Handle, WM_SETTEXT, 0, Integer(PChar(Title)));
OldProc := Pointer(SetWindowLong(Handle, GWL_WNDPROC, Integer(@NewWndProc)));
P := Pointer(Integer(P) + 10);                // арифметика через Integer
Move(Src^, Dst^, Count * 4);                  // 4 — «размер указателя»
```

</Ex>

<Ex title="Delphi 12: Win32 и Win64">

```pascal

SendMessage(Edit1.Handle, WM_SETTEXT, 0, LPARAM(PChar(Title)));
OldProc := Pointer(SetWindowLongPtr(Handle, GWLP_WNDPROC, LONG_PTR(@NewWndProc)));
P := PByte(P) + 10;                           // PByte поддерживает арифметику указателей
Move(Src^, Dst^, Count * SizeOf(Pointer));
```

</Ex>

- Почему результаты расчётов разошлись между Win32 и Win64? — `Extended` в Win64 — это `Double`, точность ниже.
- Можно ли из 64-битного клиента вызвать 32-битную DLL? — Не в своём процессе; только через отдельный 32-битный процесс-посредник.
- Что даёт `LARGEADDRESSAWARE`? — 32-битному процессу на 64-битной Windows доступно до 4 ГБ вместо 2.
- Работает ли ассемблер в Win64? — Только функции целиком на `asm`; смешивать с Pascal нельзя, код переписывают под x64.

<Q id="delphi.mig.strategy" level="s">

## Как спланировать миграцию большого Delphi-клиента без остановки бизнеса?

<A short l="j">

Большой клиент переводят по частям: сначала составляют список модулей, форм и сторонних компонентов, потом переносят и проверяют их по этапам. Старая версия продолжает работать, пока новая не пройдёт проверку на реальных пользователях.

</A>

<A short l="m">

План начинается с инвентаризации: модули и формы, сторонние компоненты и их замена, вызовы процедур, внешние зависимости. Дальше этапы, каждый из которых меняет одно — компилятор и Unicode, затем ADO на FireDAC, затем остальное, — и после каждого автоматическое сравнение со старой версией и <T k="regression-testing">регрессионное тестирование</T>. Цена — период, когда изменения приходится вносить в обе версии.

</A>

<A short l="s">

Миграция — проект с управляемым риском: её ведут этапами, каждый из которых можно выпустить и откатить. Основа — инвентаризация с оценкой каждого компонента, правило «один тип изменений на этап» и автоматическая сверка версий: .dfm, маппинг полей, вызовы процедур с параметрами. Выпуск — через <T k="parallel-run">параллельную эксплуатацию</T>: обе версии работают с одной базой, пилотная группа переходит первой, старая версия остаётся путём отката. Главные компромиссы — <T k="code-freeze">заморозка фич</T> против двух веток и граница улучшений: цель — та же функциональность на новой платформе, а не переписывание.

</A>

<A l="j">

**Что это**

Миграция клиента — перевод того же приложения на новую версию Delphi с сохранением поведения. Пользователь должен получить те же формы, расчёты и отчёты.

**Как пользоваться: этапы**

1. Составить список модулей, форм и сторонних компонентов.
2. Найти замену компонентам, которых нет для новой Delphi.
3. Собрать проект в новой версии и исправить ошибки компиляции.
4. Проверить формы и отчёты, сравнивая их со старой версией.
5. Отдать новую версию небольшой группе пользователей, старую оставить для отката.

**Частая ошибка**

Попутно улучшать код и интерфейс. Тогда при расхождении непонятно, что виновато — миграция или улучшение.

**Итог:** переносите по этапам, сравнивайте со старой версией и сохраняйте возможность откатиться.

</A>

<A l="m">

**Инвентаризация**

| Что | Что выяснить |
|---|---|
| Модули и формы | сколько, кто владелец, как часто используются |
| Сторонние компоненты | есть ли версия для Delphi 12/13 и исходники; чем заменить (RX Library — JVCL или стандартные VCL) |
| Доступ к данным | все запросы и вызовы процедур с параметрами |
| Внешние зависимости | DLL, COM, отчёты, оборудование |

**Когда что выбирать**

- **Заморозка фич.** Проще всего, но бизнес ждёт. Подходит, если перенос занимает недели.
- **Две ветки.** Новые фичи идут в старую ветку и регулярно переносятся в новую. Нужны частые слияния и автоматическая проверка расхождений.
- **Общий код для двух компиляторов.** Различия закрываются <T k="delphi-conditional-compilation">условной компиляцией</T> (`{$IFDEF UNICODE}`). Ветки не расходятся, но код обрастает условиями.

**Ловушки**

- Новая IDE при сохранении дописывает в .dfm свойства вроде `ExplicitWidth`, поэтому формы сравнивают после нормализации.
- Двоичные .dfm сначала переводят в текст утилитой `convert.exe` из поставки Delphi.
- Формы на мониторах с высоким DPI масштабируются иначе, чем в Delphi 6.

**Правило**

Один этап — один тип изменений, и у каждого этапа есть автоматическая проверка и откат.

**Итог:** инвентаризация задаёт объём, этапы ограничивают риск, а сверка со старой версией доказывает, что ничего не потеряли.

</A>

<A l="s">

**Этапы**

1. Инвентаризация и оценка: компоненты, процедуры, зависимости, критичные для бизнеса формы.
2. Сборка в Delphi 12/13 со старым ADO: Unicode, замена компонентов, без изменения поведения.
3. Переход с ADO на FireDAC под автоматической сверкой.
4. По необходимости — 64 бита, стили VCL, высокий DPI.

**Автоматизированные проверки**

- **Формы.** Сравнение .dfm: состав компонентов, свойства, обработчики событий.
- **Маппинг.** Persistent-поля и их типы, `DataField` и `DataSource` у контролов.
- **Вызовы процедур.** Имя и параметры с типом, направлением и размером, затем результаты на копии боевой базы.
- **Поведение.** <T k="characterization-test">Характеризующие тесты</T> для расчётов: входные данные из прода, эталон — результат старой версии.

**Цена**

- Две ветки или общий код с условиями на всё время миграции.
- Инструменты сверки, копия боевой базы и время пользователей на приёмку.

**Компромиссы**

- **Всё сразу против поэтапно.** Один большой релиз проще планировать, но откатывать приходится всю версию. Поэтапно дольше, зато каждый шаг маленький.
- **Параллельная эксплуатация.** Обе версии работают с одной базой, пилотная группа — на новой. Схема БД меняется только совместимо, иначе откат невозможен.

**Как проверить в проде: готовность и откат**

- Пилотная группа отработала полный бизнес-цикл, включая закрытие месяца.
- Новых ошибок в журнале нет, обращений в поддержку не стало больше.
- Откат — запуск старого EXE; он возможен, пока схема совместима с обеими версиями.

**Итог:** миграция без остановки бизнеса — это маленькие обратимые этапы, автоматическая сверка со старой версией и заранее заданные критерии готовности.

</A>

<Ex title="Снимок параметров: ADO (Delphi 6)">

```pascal
uses SysUtils, TypInfo, DB, ADODB;

// Описание параметров процедуры для сверки со снимком новой версии
function DescribeParams(Proc: TADOStoredProc): string;
var
  I: Integer;
  P: TParameter;
begin
  Result := Proc.ProcedureName;
  for I := 0 to Proc.Parameters.Count - 1 do
  begin
    P := Proc.Parameters[I];
    Result := Result + sLineBreak + Format('%s %s %s %d', [P.Name,
      GetEnumName(TypeInfo(TParameterDirection), Ord(P.Direction)),
      GetEnumName(TypeInfo(TFieldType), Ord(P.DataType)), P.Size]);
  end;
end;
```

</Ex>

<Ex title="Снимок параметров: FireDAC (Delphi 12)">


Снимки обеих версий нормализуют (`pdInput` ↔ `ptInput`, `pdReturnValue` ↔ `ptResult`) и сравнивают обычным diff. Каждая строка расхождения — повод разобраться до выпуска.

</Ex>

- Чем заменить RX Library? — Её компоненты вошли в JVCL; часть закрывается стандартными компонентами VCL.
- Как понять, что новая версия готова? — Пилот прошёл полный бизнес-цикл, сверка без расхождений, ошибок и обращений не больше, чем со старой.

<Q id="delphi.mig.to-dotnet" level="s">

## Как постепенно переносить функции из Delphi-клиента в .NET-сервисы?

<A short l="j">

Функции переносят по одной: в .NET-сервисе реализуют, например, расчёт или справочник, а Delphi-клиент вместо прямого SQL начинает вызывать сервис по HTTP. Старый код удаляют, только когда новый проверен, поэтому клиент работает всё время переноса.

</A>

<A short l="m">

Это <T k="strangler-fig">strangler fig</T> для толстого клиента: сервис забирает функции по одной, а клиент вызывает его по <T k="rest">REST</T> через <T k="delphi-thttpclient">`THTTPClient`</T> или `TRESTClient`. Переходное состояние — <T k="shared-database">общая база</T>: сервис и клиент работают с одними таблицами, но у каждой таблицы один пишущий владелец. Главный риск — двойная логика: одно правило в процедуре, клиенте и сервисе разъезжается при первой же правке.

</A>

<A short l="s">

Сначала решают, где граница: логика в хранимых процедурах может остаться в БД, и сервис её просто вызывает; логика из обработчиков форм переезжает в сервис; UI остаётся в Delphi. Переносят вертикальные срезы — функцию целиком — за <T k="anti-corruption-layer">anti-corruption layer</T> и <T k="feature-toggle">флагом</T>, а для расчётов параллельно сравнивают результаты. Цена — сеть в каждом вызове, аутентификация пользователей клиента в сервисе и период, когда правило живёт в двух местах. Поэтому у каждой функции один источник истины и срок удаления старого пути.

</A>

<A l="j">

**Что это**

Постепенный перенос: новая система растёт рядом со старой и забирает функции одну за другой. Подробнее о паттерне — в теме [Архитектурные стили](/sobes/arch/styles/).

**Как пользоваться**

1. Выбрать небольшую функцию: справочник, расчёт, отчёт.
2. Реализовать её в .NET-сервисе с HTTP API.
3. В Delphi-клиенте заменить SQL-запрос вызовом сервиса.
4. Сравнить результаты старого и нового пути.
5. Удалить старый код из клиента.

**Частая ошибка**

Скопировать правило в сервис и оставить его в клиенте «на всякий случай». Через месяц правку внесут только в одно место, и ответы разойдутся.

**Итог:** переносите по одной функции, и у каждого правила должен остаться один хозяин.

</A>

<A l="m">

**Где провести границу**

| Где сейчас логика | Что делать |
|---|---|
| Хранимые процедуры | оставить в БД, сервис их вызывает; переписывать позже |
| Обработчики форм в клиенте | переносить в сервис — главный выигрыш |
| UI и ввод данных | остаются в Delphi |

**Как устроено**

- Клиент обращается к сервису через `THTTPClient` (`System.Net.HttpClient`) или компоненты `TRESTClient`, `TRESTRequest`, `TRESTResponse` из REST Client Library.
- Общая база — переходное состояние: сервис и клиент работают с одними таблицами, но писать в таблицу может только один из них.
- Читающие функции переносить проще: они не меняют данные, а результат легко сравнить.

**Ловушки**

- **Двойная логика.** Правило живёт в двух местах; у старого пути должен быть срок удаления.
- **Синхронный вызов в UI-потоке.** Форма замирает, пока сервис отвечает. Нужны таймауты и вызов в фоне (`TTask.Run`) с возвратом в UI через `TThread.Queue`.
- **Недоступный сервис.** Клиент должен понятно сообщить об этом, а не упасть с исключением.

**Правило**

Одно правило — один владелец, одна таблица — один писатель.

**Итог:** сервис забирает функции по одной, клиент вызывает его по HTTP, а общая база живёт только до смены владельца данных.

</A>

<A l="s">

**Компромиссы границы**

- Логика в процедурах уже общая для всех клиентов. Переносить её в сервис стоит ради тестов, масштабирования или другого источника данных; иначе сервис её просто вызывает.
- Своя база сервиса появляется, когда в таблицы не пишет никто, кроме него. До этого — общая база через ACL, чтобы старая схема не протекала в новую модель.

**Под капотом вызова**

- Аутентификация пользователя клиента в сервисе — отдельная задача: доменная учётная запись Windows или токен.
- Старые версии клиента живут долго, поэтому контракт API меняется только совместимо или через версию.

**Цена**

- Сетевые задержки и отказы там, где раньше был локальный SQL.
- Две реализации и их сравнение в переходный период.

**Как проверить в проде**

- **Параллельный запуск для расчётов.** Клиент считает по-старому и вызывает сервис, расхождения пишутся в журнал, пользователь видит старый результат.
- **Метрики сервиса.** Задержка и ошибки по эндпоинтам, версия клиента в заголовке `User-Agent` — чтобы знать, когда старый путь можно удалить.
- **Откат.** Флаг по филиалу или группе пользователей возвращает старый путь без нового релиза.

**Итог:** перенос в .NET — это strangler fig с явной границей, одним владельцем каждого правила и таблицы и сравнением результатов до удаления старого пути.

</A>

<Ex title="До: клиент считает сам">

```pascal
// Остаток считает клиент прямым SQL к общей базе
function GetStock(const Sku: string): Integer;
begin
  StockQuery.SQL.Text := 'SELECT SUM(Qty) FROM StockMoves WHERE Sku = :Sku';
  StockQuery.Parameters.ParamByName('Sku').Value := Sku;
  StockQuery.Open;
  try
    Result := StockQuery.Fields[0].AsInteger;
  finally
    StockQuery.Close;
  end;
end;
```

</Ex>

<Ex title="После: клиент вызывает .NET-сервис">

```pascal
uses System.SysUtils, System.JSON, System.NetEncoding, System.Net.HttpClient;

function GetStock(const Sku: string): Integer;
var
  Client: THTTPClient;
  Resp: IHTTPResponse;
  Json: TJSONValue;
begin
  Client := THTTPClient.Create;
  try
    Client.ConnectionTimeout := 3000;  // мс; по умолчанию минута
    Client.ResponseTimeout := 5000;
    Resp := Client.Get('https://stock.internal/api/stock?sku=' + TNetEncoding.URL.Encode(Sku));
    if Resp.StatusCode <> 200 then
      raise Exception.CreateFmt('Stock service returned HTTP %d', [Resp.StatusCode]);
    Json := TJSONObject.ParseJSONValue(Resp.ContentAsString(TEncoding.UTF8));
    if Json = nil then
      raise Exception.Create('Stock service returned invalid JSON');
    try
      Result := Json.GetValue<Integer>('quantity');
    finally
      Json.Free;
    end;
  finally
    Client.Free;
  end;
end;
```

Сигнатура функции не изменилась, поэтому формы не трогают. Переключение между старой и новой реализацией удобно спрятать за флагом.

</Ex>

- Где должна жить бизнес-логика после миграции? — В сервисе; процедуры БД остаются там, где они дают общую точку для всех клиентов, пока их не перенесли.
- Можно ли сервису писать в таблицы, в которые пишет клиент? — Как переходное состояние — только с одним писателем на таблицу; иначе конфликты и двойная логика.
- Как не заморозить форму на время HTTP-вызова? — Вызов в `TTask.Run`, обновление UI через `TThread.Queue`, плюс таймауты.
- `THTTPClient` или `TRESTClient`? — `THTTPClient` — низкоуровневый и без компонентов на форме; `TRESTClient` удобнее для JSON и настраивается в дизайнере.
- Когда удалять старый путь в клиенте? — Когда старых версий клиента нет в метриках, а параллельный запуск не показывает расхождений полный бизнес-цикл.
